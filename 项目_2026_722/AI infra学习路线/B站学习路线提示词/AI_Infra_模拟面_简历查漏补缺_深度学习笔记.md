# 一、这节课一句话结论

这节课的核心不是泛泛讲 AI Infra 学习路线，而是通过两位同学的模拟面 / 简历查漏补缺，反复强调一个现实判断：

> **AI Infra 简历项目不能只写“我部署了模型”或“我看了源码”，必须用可验证的工程证据证明你真的做过性能分析、瓶颈定位、正确性对齐、算子实现或推理框架理解。**

具体来说，本节课反复强调五件事：

1. **部署项目必须有性能证据**：不能只写端到端延迟，要明确 batch size、输入规模、并发数、单路/多路吞吐、是否丢帧、单算子耗时、优化前后对比。
2. **算子能力要能落到代码和指标上**：面试中手撕 CUDA 很常见，Softmax、Reduce、MatMul/GEMM、NMS、FlashAttention 相关问题都可能出现。
3. **项目深度不是“让 AI 帮你想个优化点”**：nano-vLLM 或 vLLM 项目如果只是读过源码、让 Codex/AI 写一个不真实的 feature，面试时很容易被问穿。
4. **推理框架能力来自正确性 + 性能分析闭环**：精度对齐只是第一步，后续必须分析热点模块或热点算子，并证明优化有效。
5. **实习和真实工作记录很重要**：做实习时要记录每天的工作内容，后续才能从中挖掘简历点和面试表达。

# 二、课程宗旨与核心目标

这节课的本质是一次 **AI Infra 求职模拟面试 + 简历项目查漏补缺课**。它不是系统讲解某个单一技术，而是把真实求职中的问题拆开分析：

- 项目怎么写才像 AI Infra？
- 部署项目怎么体现推理工程能力？
- 算子项目怎么体现 CUDA 能力？
- vLLM / nano-vLLM 项目怎么避免同质化？
- 具身智能、端侧部署、VLA 加速这类项目如何靠近通用 AI Infra？
- 没有多段实习、没有大厂实习时，怎么补项目深度？
- 秋招前到底应该优先补 CUDA、vLLM、项目深度、八股还是 LeetCode？

这节课最适合以下人群：

- 已经开始学 vLLM / nano-vLLM，但不知道怎么做项目的人；
- 做过 TensorRT / ONNX Runtime / Paddle Inference 部署项目，但项目像“普通部署”而不是 AI Infra 的人；
- 想投 AI Infra 推理框架、算子开发、推理工具链、AI 芯片 Runtime 岗位的人；
- 有实验室项目，但不知道如何把项目转化成简历竞争力的人；
- 面试中担心被问 CUDA、vLLM、项目真实性、性能指标的人。

这节课给出的总方法是：

```text
真实项目场景
  → 正确性对齐
  → 建立 baseline
  → 做 benchmark
  → 找热点模块 / 热点算子
  → 选择一个可解释的优化点
  → 做 microbenchmark + end-to-end benchmark
  → 用指标证明优化有效
  → 简历中写清楚约束、方法、结果
  → 面试中能经得住追问
```

# 四、课程整体结构

整节课可以分成两大部分，对应两位同学的咨询。

## 4.1 第一位同学：部署 + CUDA 算子方向

第一位同学已有一个类似 **Paddle Inference + TensorRT** 的部署项目，原本更像安防 / 目标检测流水线项目。经过修改后加入了自定义前处理 / 后处理算子、pipeline 优化、端到端 benchmark 等内容，希望让项目更像 AI Infra。

老师主要指出：

- TensorRT 部署项目很常见，必须体现差异化；
- 如果写了自定义算子优化，就要给出单算子优化前后耗时；
- 端到端 31 ms 这种数字必须说明 batch size、输入数量、是否是单帧、是否是多路流；
- 多路摄像头场景要用每路 FPS、抽帧策略和队列堆积情况验证真实性；
- CUDA 手撕算子在面试中很常见；
- 深挖算子建议围绕 GEMM / Attention / MoE，不建议把 NMS 或 RMSNorm 当作长期主线；
- 量化模型中反量化操作值得学习；
- 接入第三方算子库不等于具备算子优化能力。

## 4.2 第二位同学：vLLM 学习 + 具身智能项目挖掘

第二位同学是研一，想做推理框架 / 推理加速，优先考虑互联网大厂，也考虑车企、芯片厂。困惑在于 AI Infra 知识面太大：CUDA、vLLM、项目深度、八股、LeetCode 都要准备，容易焦虑。

老师主要指出：

- AI Infra 准备可以拆成 CUDA、vLLM、项目深度、算法八股几块；
- CUDA 第一遍要真正调试和理解，面试前可以准备固定的手撕版本；
- vLLM 难点不是单点特别深，而是范围广：算子库、显存管理、请求分发、并行、量化等；
- 可以先看 nano-vLLM 过渡，但不能只“过一遍源码”；
- nano-vLLM 项目同质化严重，要规避“无工作量”和“不真实优化 idea”；
- 具身智能 / VLA 项目不是没有价值，但要从精度对齐走向热点分析和性能优化；
- 实验室实习或导师推荐实习可以去，但仍然要多面试、多积累反馈；
- 做实习期间要记录工作日志，后续才能挖简历点。

# 五、第一位同学：TensorRT / Paddle Inference 部署项目怎么改到像 AI Infra 项目

## 5.1 原项目的问题

该同学的项目原本类似目标检测 / 安防视频流部署项目，技术栈大致是：

```text
视频流 / 图像输入
  → 前处理
  → Paddle Inference / TensorRT 推理
  → 后处理，如 NMS
  → 输出检测结果
  → 多路流或端到端 pipeline 性能统计
```

这种项目在简历里非常常见，容易被面试官判断为：

- 只是调用框架部署模型；
- 主要做业务 pipeline；
- 没有真正的推理框架开发能力；
- 没有真实算子优化能力；
- 性能指标不完整，无法验证真实性。

因此老师建议，该项目必须从“我部署了模型”升级成“我分析并优化了推理 pipeline”。

## 5.2 正确改造方向

项目要往 AI Infra 靠，需要补三个层次的证据。

### 第一层：端到端 pipeline 性能证据

要说明：

- 输入是什么：图片、视频帧、几路流；
- batch size 是多少；
- 输入分辨率是多少；
- 是否包含解码、前处理、推理、后处理、可视化；
- 延迟统计方式是什么；
- 平均延迟、P95/P99 延迟是多少；
- 吞吐是多少；
- 多路流下每路 FPS 是多少；
- 队列是否堆积，是否丢帧。

错误写法：

> 端到端延迟 31 ms，性能提升明显。

更好的写法：

> 在 batch size = 4、输入分辨率 640×640、包含前处理 / TensorRT 推理 / NMS 后处理的端到端 pipeline 中，平均延迟由 X ms 降至 Y ms；12 路模拟视频流下，每路稳定处理 Z FPS，并通过队列长度监控验证无持续堆积。

### 第二层：单算子性能证据

如果简历中写了自定义算子、前处理算子、后处理算子或 CUDA 优化，就必须写清楚：

- 优化的是哪个算子；
- 原始实现是什么；
- 优化方式是什么；
- 用什么工具测试；
- 单算子耗时从多少降到多少；
- 是否影响端到端性能。

错误写法：

> 使用 CUDA 优化 NMS，提升推理速度。

更好的写法：

> 针对后处理 NMS 在高候选框数量下的耗时问题，实现 CUDA 并行版本；使用 CUDA Event 对单算子耗时进行 microbenchmark，对比 CPU / naive GPU / 优化 GPU 三个版本，并进一步统计其对端到端 pipeline 延迟的影响。

### 第三层：性能分析工具和瓶颈定位

老师提到，如果没有用 Nsight Systems / Nsight Compute，而只是用 CUDA Event 做 benchmark，也不是不行，但要知道二者区别。

| 工具 | 主要作用 | 适合回答的问题 |
|---|---|---|
| CUDA Event | 统计某段 GPU 代码耗时 | 某个 kernel 或某段流程耗时多少 |
| Nsight Systems | 系统级 timeline 分析 | CPU/GPU 是否同步阻塞？kernel launch 是否密集？pipeline 是否有空洞？ |
| Nsight Compute | 单 kernel 深度分析 | 访存效率如何？occupancy 如何？bank conflict 是否严重？瓶颈是计算还是访存？ |

面试中，如果你只说“我用 CUDA Event 测了时间”，面试官可能继续问：

- 为什么不用 Nsight？
- kernel 的瓶颈是什么？
- memory-bound 还是 compute-bound？
- 优化前后哪个指标变了？

因此，至少要能解释自己测量方法的边界。

# 六、第一段技术主线：项目真实性、Benchmark 与单算子性能证据

## 6.1 为什么“31 ms”这种数字容易被质疑

老师重点追问了端到端 31 ms 这个数字：

- 这是处理一张图的时间，还是一个 batch 的时间？
- batch size 是 1、2、4、8、16 中的哪个？
- 是单路摄像头，还是多路摄像头？
- 如果是 12 路流，每路实际 FPS 是多少？
- 视频流输入持续到达时，队列会不会越积越长？

这里的核心不是数字本身，而是 **指标语义必须清楚**。

对于视频流推理，单次延迟和系统吞吐不是同一个概念：

```text
单帧延迟低
  ≠ 多路流一定稳定
  ≠ 队列不会堆积
  ≠ 实时系统不会丢帧
```

如果 31 ms 是单帧端到端延迟，那么理论吞吐约为：

```text
1000 ms / 31 ms ≈ 32 FPS
```

如果有 12 路摄像头，简单平均下来每路只有约 2.7 FPS。实际系统还要考虑前处理、解码、后处理、同步、队列调度，所以这个数字可能不够支撑多路实时推理。

老师给出的业务经验是：摄像头常见 25 FPS，但系统不一定每帧都处理，常见策略是 3 抽 1，即每路约 8 FPS。也就是说，如果项目写 12 路流，至少要解释为什么每路处理能力能达到约 8 FPS，或者说明采用了怎样的抽帧 / 丢帧策略。

## 6.2 多路视频流推理应该怎么做 Benchmark

一个合格的多路流推理 benchmark 至少应该包含：

| 指标 | 说明 |
|---|---|
| 输入路数 | 例如 1 路、4 路、8 路、12 路 |
| 单路输入 FPS | 摄像头原始帧率，如 25 FPS |
| 抽帧策略 | 例如 3 抽 1、2 抽 1、关键帧触发 |
| 实际处理 FPS | 每路真正进入推理的帧数 |
| 端到端延迟 | 从帧进入 pipeline 到输出结果的时间 |
| 队列长度 | 判断是否出现持续堆积 |
| 丢帧数量 | 判断系统是否无法实时处理 |
| GPU 利用率 | 判断 GPU 是否满载或等待 |
| 显存占用 | 判断 batch / 并发能否继续扩大 |

推荐实验设计：

```text
实验 1：单路流
  - 统计单路输入 25 FPS 时，系统能处理多少 FPS
  - 判断是否能稳定无堆积

实验 2：多路流扩展
  - 1 路、4 路、8 路、12 路逐步增加
  - 每个配置统计平均延迟、P95 延迟、每路 FPS、队列长度

实验 3：不同 batch size
  - batch size = 1 / 2 / 4 / 8 / 16
  - 对比吞吐和延迟变化

实验 4：模块拆分耗时
  - 解码、前处理、推理、后处理、结果输出分别计时
```

## 6.3 这部分在 AI Infra 中的作用

这一段本质上在讲 **推理系统性能指标的可信表达**。

AI Infra 面试官并不只关心你有没有跑通模型，而是会看：

- 你是否知道自己测的是什么；
- 你的指标是否符合实际业务约束；
- 你的优化是否真的解决了瓶颈；
- 你的项目是否经得起真实流量或真实输入规模检验。

如果一个项目只有“提升 X%”但没有实验条件，这种提升在面试中可信度很低。

# 七、第二段技术主线：CUDA 算子面试与后续深挖方向

## 7.1 面试中 CUDA 手撕很常见

第一位同学反馈，他在面试中遇到过：

- 手撕 Softmax；
- 手撕 Reduce；
- 手撕 NMS；
- LeetCode 题，如前缀和 + 哈希、滑动窗口；
- 纯 C++ 问题，如多态。

老师据此判断：

> **AI Infra / 算子 / 推理工具链方向，一面中手撕 CUDA 或代码题是常见的，不能只准备八股。**

这里要注意：算子面试不是要求你临场发明一个极致优化版本，而是要求你至少有一个熟练版本，并能解释优化路径。

## 7.2 面试前算子应该怎么准备

老师认可的一种策略是：

```text
第一遍学习：不能投机，要自己调试、自己理解、自己写通。
面试前准备：可以准备一个专门用于面试的熟练版本，多写几遍。
```

也就是说，背代码不是完全不行，但前提是你理解它。

对于每个算子，建议准备四层：

1. **naive 版本**：最直观、最容易写对。
2. **并行版本**：利用 block / thread 做并行。
3. **优化版本**：shared memory、warp-level primitive、减少同步、合并访存等。
4. **性能解释**：为什么快，瓶颈在哪里，适合什么输入规模。

## 7.3 哪些算子最值得深挖

老师认为，如果后续从事算子开发，主线基本跑不出三类：

```text
GEMM / MatMul
Attention
MoE
```

### 7.3.1 GEMM / MatMul

GEMM 是大模型计算的核心。Attention、MLP、MoE 专家计算最终都会大量落到矩阵乘。

它复杂的原因包括：

- shape 多：M/N/K 不同；
- dtype 多：FP32、FP16、BF16、INT8、INT4、FP8；
- 硬件路径多：CUDA Core、Tensor Core；
- 优化层次多：thread/block/warp tiling、shared memory、register blocking、pipeline、双缓冲；
- 不同场景性能最优策略不同。

### 7.3.2 Attention

Attention 是 LLM 推理的核心模块，包含很多变体：

- MHA；
- MQA；
- GQA；
- MLA；
- FlashAttention；
- PagedAttention；
- 长上下文 attention。

Attention 的难点不只是算子本身，还包括 KV Cache、长序列、访存、softmax 数值稳定、prefill/decode 差异。

### 7.3.3 MoE

MoE 推理包含：

```text
Router / Gate
  → Top-k expert 选择
  → token dispatch
  → expert GEMM
  → expert output combine
  → load balance / expert parallel
```

老师提醒，MoE 的性能优化重点不只是 Top-k 选专家。Top-k 只是第一步，真正耗时的部分往往包括专家权重加载、专家 GEMM、token 重排和跨卡通信。

## 7.4 NMS 和 RMSNorm 是否值得作为主线

老师认为，NMS 和 RMSNorm 可以准备，但不建议作为长期主线的核心。

原因是：

- NMS 更偏目标检测后处理，和大模型推理核心链路距离较远；
- RMSNorm 是重要小算子，但深挖空间和岗位覆盖面不如 GEMM / Attention / MoE；
- 面试可能问 NMS 或 RMSNorm，但长期项目最好选更工业核心的算子。

## 7.5 量化模型中的反量化操作值得学习

老师特别提到，部署中常见 W8A16、W4A16、AWQ 等量化模型，这些模型往往涉及反量化操作。

以 W4A16 为例：

```text
权重以 INT4 存储
  → 推理时读取 INT4 权重
  → 使用 scale / zero point 反量化
  → 与 FP16 激活做矩阵乘
```

这里的优化点包括：

- 如何高效读取压缩权重；
- 如何减少反量化开销；
- 反量化和 GEMM 是否融合；
- scale 的粒度是 per-channel、per-group 还是 per-block；
- 访存节省是否抵消了反量化计算开销。

面试回答不能只说“量化省显存”，还要能说明推理 kernel 中反量化怎么发生。

# 八、第三段技术主线：算子接入框架和算子优化不是一回事

## 8.1 为什么“接入第三方算子库”不等于“会算子优化”

有同学提出：如果把第三方算子库接入推理框架，并完成 benchmark，是否能体现算子能力？

老师的判断是：

> 接入第三方算子库确实有工程工作量，但它主要体现框架对接能力，不一定体现算子优化能力。

原因是，接入工作通常包括：

- 参数格式转换；
- tensor shape 对齐；
- dtype 对齐；
- memory layout 对齐；
- 编译系统适配；
- runtime 调用接口适配；
- benchmark 脚本；
- 正确性测试。

这些工作有价值，但面试官如果想考察算子能力，会继续问：

- 这个算子是你写的吗？
- 你优化了哪一段？
- 原始瓶颈是什么？
- 和 cuBLAS / PyTorch / Triton / CUTLASS 相比达到多少性能？
- 你的优化改变了哪个指标？

如果你只是接入库，没有实现或优化算子，就不能把它包装成“算子优化能力”。

## 8.2 更好的项目表达方式

如果你确实做的是框架接入，可以这样写：

> 将第三方高性能算子库接入推理框架，完成 dtype / shape / memory layout 对齐，补充正确性测试和 benchmark，分析接入前后端到端性能变化。

如果你做的是算子优化，应该这样写：

> 针对推理链路中耗时占比较高的 X 算子，实现 CUDA / Triton 优化版本，通过 tiling、shared memory 复用、warp-level reduction 等方式降低单算子耗时，并与 PyTorch / cuBLAS / Triton baseline 对比。

二者的区别是：

| 类型 | 核心能力 | 简历关键词 |
|---|---|---|
| 框架接入 | 工程适配、接口设计、系统集成 | 接入、适配、正确性、benchmark、端到端 |
| 算子优化 | CUDA/Triton 实现、底层性能优化 | kernel、tiling、shared memory、Tensor Core、Nsight、microbenchmark |

# 九、第二位同学：AI Infra 学习焦虑、vLLM 项目深度与具身智能项目挖掘

## 9.1 第二位同学的主要困惑

第二位同学是研一，已经学习 AI Infra 大约半年，希望未来去互联网大厂、车企或芯片厂，偏向推理框架 / 推理加速方向。

他的困惑可以总结为四点：

1. **入门资料少**：除开源项目外，系统讲解资料不多。
2. **知识面太杂**：CUDA、推理框架、训练框架、国产芯片、量化、算法题都要学。
3. **岗位要求不清楚**：推理框架岗位到底要会 vLLM 到什么程度？要不要手撕 CUDA？要不要刷 LeetCode？
4. **项目深挖困难**：不知道怎么从 nano-vLLM 或实验室项目中找到真实优化点。

老师把准备方向拆成：

```text
CUDA
vLLM / 推理框架
项目深度
算法八股 / LeetCode
```

这是一种很实用的拆分方法，因为 AI Infra 不是单点技术，而是多个能力块的组合。

## 9.2 vLLM 的难点是“广”而不是每个点都极深

老师指出，vLLM 不是说每个点都特别难，而是覆盖面太广。

它涉及：

- 算子库；
- 显存资源管理；
- 请求分发；
- 调度；
- 并行，如 tensor parallel；
- 量化；
- worker / model runner；
- KV Cache；
- prefix cache；
- prefill / decode。

CUDA 算子是深度难，vLLM 是广度难。

```text
CUDA 难在：需要结合 GPU 体系结构做深度优化。
vLLM 难在：模块多、概念多、版本变化快、系统链路长。
```

## 9.3 先学 nano-vLLM 是否可行

老师认为，直接看 vLLM 可能强度较大，可以先用 nano-vLLM 过渡。

nano-vLLM 的价值在于：

- 代码量更小；
- 可以理解请求调度；
- 可以理解 sequence / scheduler / block manager；
- 可以理解 KV Cache block；
- 可以理解 prefill / decode；
- 可以理解简化版推理引擎怎么跑起来。

但老师也强调，nano-vLLM 项目不能停留在“我看过源码”。

# 十、第四段技术主线：vLLM / nano-vLLM 怎么学才不空

## 10.1 nano-vLLM 项目的两类常见问题

老师总结了两类同质化问题。

### 问题一：只是过了一遍源码，没有自己的工作量

这种同学可能会说：

> 我学习了 nano-vLLM，理解了调度、KV Cache、PagedAttention 思想。

但面试官会追问：

- 你改了什么？
- 你发现了什么问题？
- 你有什么优化思路？
- 你做过 benchmark 吗？
- 你能证明你的改动有效吗？

如果都答不上来，项目就像“上过一门课”，不是工程项目。

### 问题二：让 AI 想一个不真实的 feature 或优化点

有些同学会让 Codex / ChatGPT 给 nano-vLLM 想优化点，然后直接让 AI 实现。

风险在于：

- 优化 idea 不符合真实推理场景；
- 代码能跑但没有工程意义；
- 没有 benchmark 证明；
- 自己不理解实现细节；
- 面试官一问设计动机和边界条件就暴露。

因此，AI 可以辅助学习，但不能替代你理解问题。

## 10.2 nano-vLLM 项目应该怎么做才有深度

一个更合理的 nano-vLLM 项目应该包含：

```text
源码理解
  → 找一个真实问题
  → 提出可验证修改
  → 实现改动
  → 正确性测试
  → benchmark
  → 解释适用场景和局限
```

可选方向：

| 方向 | 说明 | 面试价值 |
|---|---|---|
| Benchmark 增强 | 统计 TTFT、TPOT、吞吐、显存、prefill/decode 时间 | 体现推理服务性能意识 |
| 日志可观测性 | 打印每轮调度的 waiting/running/finished、batch tokens、KV block 使用 | 体现调度理解 |
| 调度策略实验 | 对比不同 max_num_batched_tokens、max_num_seqs、prefill/decode 混排策略 | 体现 scheduler 理解 |
| KV Cache 统计 | 记录 block 分配、释放、复用、碎片情况 | 体现显存管理理解 |
| Prefix Cache 简化实验 | 对相同前缀请求复用 KV block | 体现 vLLM 核心机制迁移 |
| 流式输出接口 | 实现简单 streaming 输出 | 体现服务化理解 |

关键是：不要只写“优化了调度”，要写清楚优化目标、实验条件和指标。

## 10.3 学 vLLM 的正确资料顺序

老师强调，框架更新很快，网上很多八股可能过期。

推荐顺序是：

```text
官方文档
  → 当前版本源码
  → 课程 / 文章辅助理解
  → 自己跑 demo 和 benchmark
  → 对照旧文章识别版本差异
```

不要只看网上旧八股，因为 vLLM 社区更新很快，模块名、架构、入口、调度实现都可能发生变化。

# 十一、第五段技术主线：具身智能 / VLA 项目如何靠近通用 AI Infra

## 11.1 具身智能项目的原始情况

第二位同学的实验室项目大致是：

```text
采集具身智能任务数据
  → 微调 VLA / 视觉-语言-动作模型
  → 将模型部署到具身智能设备
  → 使用某个加速框架后，输出和原始微调模型不匹配
  → 定位精度差异原因
```

他已经发现一些问题：

- 加速框架使用的模型结构和自己微调后的模型结构不一致；
- 输出动作维度不同，例如原始任务输出 16 维，但加速框架可能输出 50 维；
- 图像 token 数不同，例如一个处理 64 个图像 token，另一个处理 32 个图像 token；
- 因此输出无法对齐，精度下降很大。

## 11.2 精度对齐是第一步，不是最终能力体现

老师明确指出：

> 精度对齐只是做推理框架、推理加速、算子开发时的最基本要求。

也就是说，你写的算子或框架必须先算对。如果精度不对，再谈性能优化没有意义。

正确顺序是：

```text
确认模型结构一致
  → 确认输入预处理一致
  → 确认 tokenizer / image token 处理一致
  → 确认输出维度一致
  → 确认 dtype / 量化配置一致
  → 对齐中间层输出
  → 对齐最终输出
  → 再做性能分析和优化
```

## 11.3 怎么从“部署项目”升级成“AI Infra 项目”

老师认为，该项目有挖掘价值，但目前分析太粗。

现在的分析是模块级：

```text
VLM / Vision Encoder
DiT / Action Diffusion 或核心动作模块
Backbone
```

发现最大耗时在 DiT 模块。但这还不够，需要继续向下挖：

```text
DiT 模块
  → 哪些 layer 最耗时？
  → 哪些算子最耗时？
  → attention 还是 MLP / GEMM？
  → 是否有 LayerNorm / RMSNorm 小算子频繁 launch？
  → 是否有数据搬运或格式转换开销？
  → 是否有 CPU/GPU 同步？
```

一个更像 AI Infra 的项目应该回答：

- 模型推理瓶颈在哪里？
- 如何定位到该瓶颈？
- 使用了什么 profiling 工具？
- 选择优化哪个算子 / 哪个模块？
- 优化是否保持精度？
- 优化后单算子和端到端分别提升多少？

## 11.4 具身智能方向是否会偏离通用 AI Infra

老师认为不一定。

虽然具身智能不是最典型的云端 LLM serving，但它仍然涉及通用 AI Infra 能力：

- 模型结构适配；
- 推理部署；
- 性能 profiling；
- 算子热点定位；
- 加速框架适配；
- 正确性对齐；
- 端侧或机器人设备推理；
- VLM / DiT / Attention / GEMM 等通用模块。

因此，实验室项目不是必须放弃，而是要往“通用推理加速方法”上靠。

可以这样包装：

> 面向具身智能 VLA 模型部署，完成微调模型与加速框架的结构、输入 token、输出维度和 dtype 对齐；进一步基于 profiling 定位推理热点模块，分析核心算子耗时，并探索将 vLLM / 通用推理框架中的调度或缓存思想迁移到具身智能推理链路中。

# 十三、整节课从输入到输出的完整流程

这节课可以抽象成一个 AI Infra 项目从输入到输出的完整流程。

## 13.1 输入：真实场景、模型、硬件和业务约束

一个项目的输入不只是模型文件，还包括：

- 业务场景：视频流、LLM 服务、具身智能、端侧推理；
- 模型结构：检测模型、VLM、VLA、LLM、DiT；
- 硬件平台：GPU、NPU、端侧设备、机器人平台；
- 输入规模：分辨率、token 数、batch size、并发数；
- 正确性要求：精度、输出维度、动作空间、检测结果；
- 性能要求：延迟、吞吐、FPS、显存、队列稳定性。

## 13.2 第一步：正确性对齐

优化前必须确认输出正确：

```text
PyTorch / 原始模型输出
  ↕ 对齐
TensorRT / Paddle Inference / 加速框架输出
```

对齐内容包括：

- 模型结构；
- 权重加载；
- 输入预处理；
- token 数；
- 输出维度；
- dtype；
- 量化 scale；
- 后处理逻辑。

## 13.3 第二步：建立 baseline

需要建立多个 baseline：

- PyTorch baseline；
- 原始推理框架 baseline；
- TensorRT / vLLM / ONNX Runtime baseline；
- CPU 后处理 baseline；
- naive CUDA baseline；
- 优化 CUDA baseline。

没有 baseline，就无法证明优化有效。

## 13.4 第三步：做端到端 benchmark

端到端 benchmark 要回答：

- 用户看到的延迟是多少？
- 系统吞吐是多少？
- 并发数上来后是否稳定？
- 视频流是否堆积？
- LLM 服务 TTFT / TPOT 是否改善？
- 显存是否下降？

## 13.5 第四步：做模块级 / 算子级 profiling

端到端变慢后，要继续拆：

```text
端到端耗时
  → 模块耗时
  → 算子耗时
  → kernel 内部瓶颈
```

对应工具：

- Python time / logging；
- CUDA Event；
- Nsight Systems；
- Nsight Compute；
- 框架自带 profiler。

## 13.6 第五步：选择优化点

优化点必须来自 profiling，而不是凭空想象。

典型优化点包括：

- 前处理数据搬运；
- NMS 后处理；
- Softmax / Reduce；
- GEMM shape 特化；
- Attention；
- MoE expert GEMM；
- 量化反量化融合；
- batch 调度；
- KV Cache 管理；
- CPU/GPU 同步减少。

## 13.7 第六步：实现优化并验证

必须同时验证：

```text
正确性：输出是否一致 / 精度是否保持
性能：单算子是否变快 / 端到端是否变快
稳定性：多路流或并发请求下是否稳定
边界条件：不同 batch、shape、输入长度是否仍然有效
```

## 13.8 第七步：输出为简历和面试表达

最终输出不是代码本身，而是可解释的工程故事：

> 在什么业务约束下，发现什么性能瓶颈，用什么工具定位，采用什么优化方法，优化前后指标如何变化，为什么这个方法有效，有什么限制。

这就是本节课的核心闭环。

# 十四、面向 AI Infra 面试的高频问题与参考答案

## 14.1 项目真实性与 Benchmark

### Q1：你简历上写端到端延迟 31 ms，这个数字具体是什么意思？

**参考答案：**  
需要说明这是单帧还是一个 batch 的耗时，是否包含前处理、推理、后处理，batch size 是多少，输入分辨率是多少，测量方法是 CUDA Event、Nsight 还是框架日志。如果是视频流场景，还要说明单路和多路下的实际 FPS、队列是否堆积、是否丢帧。否则单独一个 31 ms 没有可解释性。

### Q2：为什么只写端到端性能还不够？

**参考答案：**  
端到端性能能反映用户侧效果，但不能证明我优化了哪个部分。如果简历写了自定义算子或 CUDA 优化，就必须拆出单算子耗时、模块耗时和优化前后对比。否则面试官无法判断性能提升来自算子、框架配置、batch size 变化，还是测试条件变化。

### Q3：多路摄像头推理中如何判断系统是否真的实时？

**参考答案：**  
要看每路实际处理 FPS、输入 FPS、抽帧策略、队列长度和丢帧情况。例如 25 FPS 摄像头如果采用 3 抽 1，系统每路至少要稳定处理约 8 FPS。只看单帧延迟不够，因为多路输入持续到达时，如果处理能力不足，队列会持续堆积，最终必须丢帧。

### Q4：CUDA Event、Nsight Systems、Nsight Compute 的区别是什么？

**参考答案：**  
CUDA Event 主要用于统计 GPU 代码段耗时，适合做简单 microbenchmark。Nsight Systems 是系统级 timeline 工具，可以看 CPU/GPU 同步、kernel launch、数据拷贝和 pipeline 空洞。Nsight Compute 是 kernel 级性能分析工具，可以看 occupancy、访存效率、warp stall、shared memory bank conflict、memory throughput 等指标。

## 14.2 CUDA 算子与性能优化

### Q5：面试中手撕 Softmax，应该怎么讲优化思路？

**参考答案：**  
先写 naive 版本，每个 row 做 max、exp、sum、normalize。优化时可以用 block 处理一行，使用 shared memory 或 warp-level reduction 求 max 和 sum，减少 global memory 访问，保证数值稳定。对于长向量，可以分块处理；对于短向量，可以考虑一个 warp 处理一行，减少同步开销。

### Q6：Reduce 算子常见优化点有哪些？

**参考答案：**  
常见优化包括连续访存、shared memory block 内归约、减少 bank conflict、循环展开、warp-level primitive、避免分支发散、减少同步次数。进一步可以根据输入规模选择 block-level reduce 或 warp-level reduce。

### Q7：为什么 GEMM 是算子开发最重要的方向？

**参考答案：**  
LLM 中 Attention 的 QKV projection、output projection、MLP 的 up/down/gate projection、MoE expert computation 本质上都大量依赖 GEMM。GEMM 覆盖 shape、dtype 和硬件路径非常多，优化空间大，也是 cuBLAS、CUTLASS、Tensor Core 的核心场景。

### Q8：Attention 算子为什么值得深挖？

**参考答案：**  
Attention 同时涉及矩阵乘、softmax、mask、KV Cache、长上下文和访存优化。Prefill 阶段 attention 计算量大，decode 阶段更受 KV Cache 读写和显存带宽影响。FlashAttention、PagedAttention、MQA/GQA/MLA 都围绕 attention 的计算和显存问题展开。

### Q9：MoE 优化是不是只优化 Top-k 选专家？

**参考答案：**  
不是。Top-k routing 只是 MoE 流程第一步。工程瓶颈往往还包括 token dispatch、expert GEMM、专家权重加载、token combine、跨卡 All-to-All、负载均衡和 expert placement。优化 MoE 需要看整个 router → dispatch → expert computation → combine 链路。

### Q10：W4A16 / W8A16 量化推理中反量化为什么重要？

**参考答案：**  
权重量化后虽然减少显存和带宽，但推理时通常需要把压缩权重结合 scale 反量化后参与计算。反量化如果单独做，会引入额外开销；更好的方式是把反量化与 GEMM 融合，边加载边反量化边计算，从而让访存节省真正转化为端到端性能提升。

## 14.3 算子接入与框架工程

### Q11：把第三方算子库接入推理框架，能不能体现算子优化能力？

**参考答案：**  
能体现工程适配能力，但不一定体现算子优化能力。接入工作包括参数对齐、shape/dtype/layout 适配、编译和 runtime 调用、正确性测试和 benchmark。如果要体现算子优化能力，需要说明自己实现或修改了 kernel，定位了什么瓶颈，优化后相对 baseline 提升多少。

### Q12：一个算子优化项目应该怎么写简历？

**参考答案：**  
应该写清楚 baseline、瓶颈、优化方法、测试工具和结果。例如“针对 X 算子耗时占比高的问题，用 Nsight Compute 分析发现访存效率低；通过 shared memory tiling 和 warp-level reduction 优化，单算子耗时从 A 降到 B，端到端延迟下降 C%”。

## 14.4 vLLM / nano-vLLM

### Q13：vLLM 学习为什么难？

**参考答案：**  
vLLM 的难点不在于每个模块都极深，而在于范围广。它包含 API server、Engine、Scheduler、KV Cache 管理、Worker、ModelRunner、算子后端、并行、量化、prefill/decode、streaming output 等多个模块，需要用系统视角理解。

### Q14：为什么可以先学 nano-vLLM？

**参考答案：**  
nano-vLLM 代码量更小，适合先理解 LLM 推理引擎的核心链路，例如请求状态、scheduler、prefill/decode、KV block 分配、model runner 调用。学完 nano-vLLM 后再看 vLLM，能降低理解成本。

### Q15：nano-vLLM 项目为什么容易同质化？

**参考答案：**  
很多人只是读过源码，没有自己的修改和实验；或者让 AI 生成一个不真实的优化点，自己并不理解。面试官会追问优化动机、适用场景、benchmark 和边界条件，如果答不上来，就会暴露项目没有真实工作量。

### Q16：nano-vLLM 项目怎么做才有深度？

**参考答案：**  
可以做真实可验证的小改动，例如增加 benchmark 统计 TTFT/TPOT、打印调度状态、统计 KV block 使用率、实现简单 prefix cache、对比不同 max_num_batched_tokens 配置。关键是有正确性测试和性能对比，而不是只改代码。

### Q17：网上 vLLM 八股为什么不能完全依赖？

**参考答案：**  
vLLM 社区更新很快，版本变化可能导致模块结构、类名、执行路径和实现细节变化。学习时应该以官方文档和当前版本源码为准，再用网上文章辅助理解，并主动识别版本差异。

## 14.5 具身智能 / VLA 项目

### Q18：为什么模型加速前必须先做精度对齐？

**参考答案：**  
正确性是推理优化的前提。如果模型结构、输入 token、输出维度、dtype 或预处理不一致，输出就无法对齐。此时即使推理速度变快也没有意义，因为优化的是错误计算。

### Q19：具身智能部署项目怎么体现 AI Infra 能力？

**参考答案：**  
不能只说“我把模型部署到设备上”。要进一步做结构对齐、输入输出对齐、profiling、热点模块定位、热点算子分析、优化实现和端到端 benchmark。这样才能体现推理系统分析能力，而不是普通部署能力。

### Q20：只定位到 DiT 模块耗时最高够不够？

**参考答案：**  
不够。模块级耗时只能说明大概方向，还要继续拆到 layer 和 operator，例如 attention、MLP/GEMM、norm、数据搬运、格式转换、CPU/GPU 同步等。真正的优化点通常来自更细粒度的 profiling。

## 14.6 实习与秋招

### Q21：AI Infra 秋招没有实习是不是没机会？

**参考答案：**  
不是没机会，但竞争力会下降。AI Infra 很看真实工程经验和项目可信度。有相关实习能提供真实业务问题、真实代码库和真实性能优化经验。只有一段实习也有价值，但最好做深，能讲出具体问题和指标。

### Q22：实习期间为什么要记工作日志？

**参考答案：**  
因为实习做的工作很碎，过几个月很容易忘。记录每天修改的模块、定位的问题、实验数据、profiling 结果和可写进简历的点，后续才能整理出高质量简历和面试故事。

### Q23：导师推荐实习要不要去？

**参考答案：**  
可以去，但不要停止其他面试和学习。导师推荐实习可以积累真实项目，但面试本身也能帮助发现短板、获得行业反馈、优化项目表达。

## 14.7 LeetCode / C++ / 综合能力

### Q24：AI Infra 岗位还要刷 LeetCode 吗？

**参考答案：**  
要。算子岗可能更高频手撕 CUDA，但 LeetCode 仍可能出现，尤其是推理框架、工具链、C++ 工程岗位。数组、哈希、滑动窗口、前缀和、链表、二叉树、图、动态规划基础都要准备。

### Q25：为什么面试还会问 C++ 多态？

**参考答案：**  
很多 AI Infra 岗位虽然使用 Python 和 CUDA，但底层 runtime、推理框架、算子库、插件系统大量使用 C++。C++ 面向对象、虚函数、多态、RAII、内存管理、多线程都是基础工程能力。

# 十六、最终总结

这节课最核心的价值是把“AI Infra 求职项目到底怎么才算有深度”讲清楚了。

对于部署项目，重点不是“我会用 TensorRT / Paddle Inference / ONNX Runtime”，而是：

> 我能在真实业务约束下建立 baseline，测清楚端到端性能，拆出瓶颈模块和热点算子，并用 microbenchmark 和系统 benchmark 证明优化有效。

对于 CUDA 算子，重点不是“我学过 CUDA”，而是：

> 我能手写高频算子，讲清楚 naive 到优化版本的路径，知道如何用 profiling 工具判断瓶颈，并能围绕 GEMM / Attention / MoE 中至少一个方向深入。

对于 vLLM / nano-vLLM，重点不是“我看过源码”，而是：

> 我能解释请求调度、KV Cache、prefill/decode、batching、worker/model runner 的执行链路，并能做一个真实、可验证、可 benchmark 的小改动。

对于具身智能 / 实验室项目，重点不是“它是不是标准 AI Infra 项目”，而是：

> 它能否体现通用推理系统能力：正确性对齐、模型结构适配、性能 profiling、热点定位、算子或框架优化。

最后，本节课给你的求职策略可以压缩成一句话：

> **不要把简历写成“工具使用记录”，要把项目做成“问题定位—系统分析—工程优化—指标验证”的闭环。**
