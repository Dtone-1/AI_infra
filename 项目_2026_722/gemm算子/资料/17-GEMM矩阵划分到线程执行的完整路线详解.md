# 当前 GEMM 项目中“完整矩阵 → Thread Block Tile → Warp Tile → Thread Tile → 线程寄存器输出元素”的完整划分与执行路线

> 目标：**结合你当前 GEMM 项目源码**，沿着下面这条主线，详细解释一个矩阵是如何被不断切分、分配、最后由线程执行完成的。
>
> ```text
> 完整矩阵
>   ↓
> Thread Block Tile
>   ↓
> Warp Tile
>   ↓
> Thread Tile
>   ↓
> 线程寄存器中的多个输出元素
> ```
>
> 重点源码文件：
>
> - `include/gemm/kernels/gemm_warp_tile_config.h`
> - `src/launcher.cu`
> - `src/kernels/gemm_warp_tile.cu`

---

# 1. 先说结论：这个项目到底在做什么切分

这个项目实现的是：

```text
C = A × B
```

更准确地说是：

```text
C = alpha × A × B + beta × C
```

它对**输出矩阵 C**的计算采用了多层切分：

```text
完整矩阵 C
    ↓
按 Block 切成一个个大的 C Tile
    ↓
每个 Block 内再按 Warp 切成更小的 Warp Tile
    ↓
每个 Warp 再按 Thread 切成更小的 Thread Tile
    ↓
每个线程把自己负责的若干输出元素放在寄存器 res[] 中累加
```

所以你在源码里看到的 `BM / BN / BK / WM / WN / TM / TN`，本质上都在回答一个问题：

> **这个大矩阵，最后是怎样分给 block / warp / thread 的？**

---

# 2. 这个项目里有哪些配置

项目在 `gemm_warp_tile_config.h` 中定义了 3 套配置：

## 2.1 Default 配置（大多数大矩阵使用）

```cpp
using WarpTileDefaultConfig = WarpTileConfig<
    128, 256, 8,
    64, 64,
    4,
    8, 4,
    256
>;
```

也就是：

| 参数 | 数值 | 含义 |
|---|---:|---|
| BM | 128 | 一个 Block 负责的 C Tile 行数 |
| BN | 256 | 一个 Block 负责的 C Tile 列数 |
| BK | 8 | K 方向每次处理的深度 |
| WM | 64 | 一个 Warp 负责的 C Tile 行数 |
| WN | 64 | 一个 Warp 负责的 C Tile 列数 |
| WNITER | 4 | Warp 在 N 方向分几段处理 |
| TM | 8 | 线程在 M 方向的微块大小 |
| TN | 4 | 线程在 N 方向的微块大小 |
| NUM_THREADS | 256 | 一个 Block 的线程数 |

---

## 2.2 Small 配置（小矩阵使用）

```cpp
using WarpTileSmallConfig = WarpTileConfig<
    64, 64, 8,
    32, 32,
    2,
    4, 4,
    128
>;
```

---

## 2.3 Irregular 配置（非规则中小矩阵使用）

```cpp
using WarpTileIrregularConfig = WarpTileConfig<
    64, 128, 8,
    32, 64,
    2,
    4, 4,
    128
>;
```

---

## 2.4 当前分析重点

为了帮助你真正理解切分逻辑，下面我会：

1. **先以 Default 配置为主讲**，因为它最有代表性；
2. 然后再补充 Small / Irregular 配置有什么区别。

因为这三套配置的思想是一模一样的，只是 tile 大小不同。

---

# 3. 第 0 层：完整矩阵层面

假设我们要计算：

```text
C[M × N] = A[M × K] × B[K × N]
```

例如：

```text
M = 4096
N = 4096
K = 4096
```

那么从最外层看：

- A 是 `4096 × 4096`
- B 是 `4096 × 4096`
- C 是 `4096 × 4096`

此时整个 C 矩阵非常大，不可能由一个 block 或一个 warp 一次算完，所以必须切分。

---

# 4. 第 1 层：完整矩阵 C → Thread Block Tile

在 `launch_gemm_warp_tile_cfg<Cfg>()` 中：

```cpp
dim3 blockDim(Cfg::NUM_THREADS);
dim3 gridDim(CEIL_DIV(N, Cfg::BN), CEIL_DIV(M, Cfg::BM));
```

这意味着：

```text
grid.x = ceil(N / BN)
grid.y = ceil(M / BM)
```

也就是：

- `blockIdx.x` 负责 **N 方向（列）**
- `blockIdx.y` 负责 **M 方向（行）**

---

## 4.1 Default 配置下，一个 Block 负责多大

Default 配置下：

```text
BM = 128
BN = 256
```

所以：

> **一个 Thread Block 负责计算 C 中的一个 `128 × 256` 大块。**

---

## 4.2 整个 C 如何被切成 Block Tile

如果 C 是 `4096 × 4096`：

```text
M 方向：4096 / 128 = 32 个 Block Tile
N 方向：4096 / 256 = 16 个 Block Tile
```

所以总共：

```text
32 × 16 = 512 个 Thread Block
```

---

## 4.3 示意图：完整矩阵如何切成 Block Tile

下面这个图只是示意，不代表真实比例：

```text
完整矩阵 C（4096 × 4096）
+----------------+----------------+----------------+-----+
| Block Tile 0,0 | Block Tile 0,1 | Block Tile 0,2 | ... |
|   128 × 256    |   128 × 256    |   128 × 256    |     |
+----------------+----------------+----------------+-----+
| Block Tile 1,0 | Block Tile 1,1 | Block Tile 1,2 | ... |
|   128 × 256    |   128 × 256    |   128 × 256    |     |
+----------------+----------------+----------------+-----+
| Block Tile 2,0 | Block Tile 2,1 | Block Tile 2,2 | ... |
|   128 × 256    |   128 × 256    |   128 × 256    |     |
+----------------+----------------+----------------+-----+
|      ...       |      ...       |      ...       | ... |
+----------------+----------------+----------------+-----+
```

每一个大框，就是**一个 block 最终要算出来的 C 子矩阵**。

---

## 4.4 一个 Block 负责哪个区域

在 kernel 中：

```cpp
const uint c_row = blockIdx.y;
const uint c_col = blockIdx.x;
const uint c_row_start = c_row * BM + warp_row * WM;
const uint c_col_start = c_col * BN + warp_col * WN;
```

对于 Block 来说，最基本的块起点是：

```text
block 的 C 起始行 = blockIdx.y × BM
block 的 C 起始列 = blockIdx.x × BN
```

例如：

```text
blockIdx.y = 3
blockIdx.x = 2
```

则它负责：

```text
行范围：3×128  ~  3×128+127   = 384 ~ 511
列范围：2×256  ~  2×256+255   = 512 ~ 767
```

也就是 C 中一个 `128 × 256` 的子块。

---

# 5. 第 2 层：Thread Block Tile → Warp Tile

Block 还太大，不能直接给单个 warp 来做，所以 Block 内部还要继续切。

---

## 5.1 Default 配置下，一个 Warp 负责多大

Default 配置：

```text
WM = 64
WN = 64
```

所以：

> **一个 Warp 负责计算一个 `64 × 64` 的 Warp Tile。**

---

## 5.2 一个 Block 里有几个 Warp

Default 配置：

```text
NUM_THREADS = 256
```

一个 warp 有 32 个线程，所以：

```text
256 / 32 = 8 个 Warp
```

所以一个 block 内有 8 个 warp。

---

## 5.3 一个 Block Tile 如何切成 8 个 Warp Tile

Block Tile 大小是：

```text
128 × 256
```

Warp Tile 大小是：

```text
64 × 64
```

因此：

- M 方向：`128 / 64 = 2`
- N 方向：`256 / 64 = 4`

总共：

```text
2 × 4 = 8 个 Warp Tile
```

正好对应：

```text
8 个 Warp
```

---

## 5.4 这 8 个 Warp Tile 的示意图

这就是你想要的那种图：

```text
Block Tile（128 × 256）
+---------+---------+---------+---------+
| Warp 0  | Warp 1  | Warp 2  | Warp 3  |
| 64×64   | 64×64   | 64×64   | 64×64   |
+---------+---------+---------+---------+
| Warp 4  | Warp 5  | Warp 6  | Warp 7  |
| 64×64   | 64×64   | 64×64   | 64×64   |
+---------+---------+---------+---------+
```

这个图非常关键，它告诉你：

> 一个 block 不是“256 个线程一起乱算”，而是先分成 8 个 warp，每个 warp 先拿到自己负责的 `64 × 64` 输出区域。

---

## 5.5 源码中 Warp 的二维定位

源码里：

```cpp
const uint warp_idx = threadIdx.x / WARP_SIZE;
const uint warp_row = warp_idx / (BN / WN);
const uint warp_col = warp_idx % (BN / WN);
```

Default 配置下：

```text
BN / WN = 256 / 64 = 4
```

因此：

```text
warp_row = warp_idx / 4
warp_col = warp_idx % 4
```

所以：

| warp_idx | warp_row | warp_col |
|---:|---:|---:|
| 0 | 0 | 0 |
| 1 | 0 | 1 |
| 2 | 0 | 2 |
| 3 | 0 | 3 |
| 4 | 1 | 0 |
| 5 | 1 | 1 |
| 6 | 1 | 2 |
| 7 | 1 | 3 |

正好对应上面的二维布局图。

---

# 6. 第 3 层：Warp Tile → Thread Tile

现在我们已经把 C 的一个 Block Tile 分给了某个 warp。

但是一个 warp 还是有 32 个线程，`64 × 64 = 4096` 个输出元素也不可能由一个线程算完，所以 warp 还要继续切。

---

## 6.1 先解释几个中间量

在 kernel 中：

```cpp
constexpr int WSUBN = WN / WNITER;
constexpr int WSUBM = (WARP_SIZE / (WSUBN / TN)) * TM;
constexpr int WMITER = WM / WSUBM;
```

Default 配置：

```text
WN = 64
WNITER = 4
TN = 4
TM = 8
WARP_SIZE = 32
```

所以：

### 1）WSUBN

```text
WSUBN = 64 / 4 = 16
```

### 2）WSUBM

```text
WSUBM = (32 / (16 / 4)) × 8
      = (32 / 4) × 8
      = 8 × 8
      = 64
```

### 3）WMITER

```text
WMITER = 64 / 64 = 1
```

---

## 6.2 它意味着什么

对于 Default 配置，一个 warp 虽然最终负责：

```text
64 × 64
```

但它是分 **WNITER=4 个列子块**来做的。

每一轮一个 warp 中 32 个线程一起负责一个：

```text
WSUBM × WSUBN = 64 × 16
```

的小区域。

因为：

```text
64 × 16 × 4 = 64 × 64
```

所以 4 轮就能把整个 warp 的 `64 × 64` 区域做完。

---

## 6.3 Warp Tile 的进一步切分示意图

```text
一个 Warp 负责的 64×64 区域
+----------------+----------------+----------------+----------------+
|   子块 0       |    子块 1      |    子块 2      |    子块 3      |
|    64×16       |    64×16       |    64×16       |    64×16       |
+----------------+----------------+----------------+----------------+
```

这 4 个 `64×16` 子块，就是该 warp 沿 N 方向分 4 次算完的。

---

# 7. 第 4 层：Warp 内 32 个线程如何分工

现在再进一步看，一个 `64 × 16` 的子区域，又是怎么分给 32 个线程的。

---

## 7.1 Thread 在 Warp 内的二维坐标

源码中：

```cpp
const uint tiwarp = threadIdx.x % WARP_SIZE;
const uint tcol   = tiwarp % (WSUBN / TN);
const uint trow   = tiwarp / (WSUBN / TN);
```

Default 配置下：

```text
WSUBN / TN = 16 / 4 = 4
```

所以：

```text
tcol = lane_id % 4
trow = lane_id / 4
```

其中 `lane_id = 0~31`。

于是 32 个线程可以看成一个：

```text
8 行 × 4 列
```

的小线程网格。

---

## 7.2 32 个线程的布局示意图

```text
一个 Warp 的 32 个线程（按 trow × tcol 组织）
+--------+--------+--------+--------+
| lane 0 | lane 1 | lane 2 | lane 3 |
+--------+--------+--------+--------+
| lane 4 | lane 5 | lane 6 | lane 7 |
+--------+--------+--------+--------+
| lane 8 | lane 9 | lane10 | lane11 |
+--------+--------+--------+--------+
| lane12 | lane13 | lane14 | lane15 |
+--------+--------+--------+--------+
| lane16 | lane17 | lane18 | lane19 |
+--------+--------+--------+--------+
| lane20 | lane21 | lane22 | lane23 |
+--------+--------+--------+--------+
| lane24 | lane25 | lane26 | lane27 |
+--------+--------+--------+--------+
| lane28 | lane29 | lane30 | lane31 |
+--------+--------+--------+--------+
```

即：

- `trow` 有 8 个取值：0~7
- `tcol` 有 4 个取值：0~3

---

## 7.3 每个线程负责多大的 Thread Tile

Default 配置中：

```text
TM = 8
TN = 4
WMITER = 1
WNITER = 4
```

一个线程最终的输出数量是：

```text
M 方向：WMITER × TM = 1 × 8 = 8
N 方向：WNITER × TN = 4 × 4 = 16
```

所以：

> **一个线程最终负责一个 `8 × 16` 的 Thread Tile。**

也就是：

```text
8 × 16 = 128 个输出元素
```

---

## 7.4 Thread Tile 的示意图

一个线程最终负责的输出区域可看成：

```text
Thread Tile（单线程）
+----+----+----+----+----+----+----+----+----+----+----+----+----+----+----+----+
|    |    |    |    |    |    |    |    |    |    |    |    |    |    |    |    |
+----+----+----+----+----+----+----+----+----+----+----+----+----+----+----+----+
|    |    |    |    |    |    |    |    |    |    |    |    |    |    |    |    |
+----+----+----+----+----+----+----+----+----+----+----+----+----+----+----+----+
|                                                                                  |
|                           共 8 行 × 16 列                                         |
|                                                                                  |
+----------------------------------------------------------------------------------+
```

---

# 8. 第 5 层：Thread Tile → 线程寄存器里的多个输出元素

这是最细的一层，也就是你最终在 kernel 里看到的 `res[]`。

---

## 8.1 结果寄存器 `res[]`

在 kernel 中：

```cpp
float res[WMITER * TM * WNITER * TN] = {};
```

Default 配置下：

```text
WMITER = 1
TM = 8
WNITER = 4
TN = 4
```

所以：

```text
res 大小 = 1 × 8 × 4 × 4 = 128
```

也就是说：

> **一个线程会在寄存器里维护 128 个累加器。**

这些寄存器元素，正好对应这个线程负责的 `8 × 16` 输出区域。

---

## 8.2 `res[]` 对应的二维布局

虽然代码里它是一维数组，但逻辑上可以看成一个 `8 × 16` 小矩阵。

```text
单线程寄存器 res[] 逻辑视图
+------+------+------+------+------+------+------+------+------+------+------+------+------+------+------+------+
|r00   |r01   |r02   |r03   |r04   |r05   |r06   |r07   |r08   |r09   |r10   |r11   |r12   |r13   |r14   |r15   |
+------+------+------+------+------+------+------+------+------+------+------+------+------+------+------+------+
|r10   |r11   |r12   |r13   |r14   |r15   |r16   |r17   |r18   |r19   |r1,10 |r1,11 |r1,12 |r1,13 |r1,14 |r1,15 |
+------+------+------+------+------+------+------+------+------+------+------+------+------+------+------+------+
|                                                                                                               |
|                                              共 8 行 × 16 列                                                 |
|                                                                                                               |
+---------------------------------------------------------------------------------------------------------------+
```

更准确地说，代码中的索引方式是：

```cpp
res[(wr*TM + rm) * (WNITER*TN) + wc*TN + rn]
```

它本质是在表示：

```text
res[逻辑行][逻辑列]
```

其中：

- 行索引来自 `wr` 和 `rm`
- 列索引来自 `wc` 和 `rn`

---

# 9. 这些寄存器值是怎么被算出来的

上面只讲了“怎么切分输出矩阵 C”，但要真正理解执行，你还要知道：

> **这些 `res[]` 中的值，是怎么一步步累加出来的？**

---

## 9.1 A / B 不是一次性用完整矩阵，而是沿 K 方向切块

虽然输出 C 是按 `BM × BN` 分块的，但矩阵乘法还涉及 K 维。

项目使用：

```text
BK = 8
```

表示：

> Block 每次只处理 K 方向上的 8 列/行。

---

## 9.2 对应的数据块

对于一个 `C` 的 Block Tile（`BM × BN`），它需要：

- A 的一个 `BM × BK` Tile
- B 的一个 `BK × BN` Tile

例如 Default 配置：

```text
A Tile: 128 × 8
B Tile: 8 × 256
```

这两块数据会先进入 shared memory。

---

## 9.3 数据流路线

这个项目的数据流路线是：

```text
Global Memory 中的大矩阵 A/B
    ↓
当前 Block 所需的 A Tile / B Tile
    ↓
搬到 Shared Memory（AS / BS）
    ↓
每个线程从 Shared Memory 读出自己需要的 A/B 小片段
    ↓
放到寄存器 reg_m / reg_n
    ↓
做乘加，累加到寄存器 res[]
```

可以记成：

```text
A/B: Global → Shared → Registers
C: Registers → Global
```

---

## 9.4 与输出切分的关系

输出矩阵的切分是：

```text
C
完整矩阵 → Block Tile → Warp Tile → Thread Tile → res[]
```

而输入矩阵的使用则是：

```text
A / B
完整矩阵 → 当前 Block 所需 Tile → Shared Memory Tile → 当前线程需要的片段
```

所以你可以把 GEMM 理解为：

> **输出 C 是按空间区域分工的，输入 A/B 是按 K 维逐块喂给这些负责输出的线程去消费。**

---

# 10. 把 Default 配置完整串起来看一遍

下面我们把整个路线完整串起来。

---

## 10.1 第一步：完整矩阵

假设：

```text
C 是 4096 × 4096
```

---

## 10.2 第二步：切成 Block Tile

Default 配置：

```text
一个 Block = 一个 128 × 256 的 C Tile
```

---

## 10.3 第三步：一个 Block 再切成 8 个 Warp Tile

```text
Block Tile（128 × 256）
+---------+---------+---------+---------+
| Warp 0  | Warp 1  | Warp 2  | Warp 3  |
| 64×64   | 64×64   | 64×64   | 64×64   |
+---------+---------+---------+---------+
| Warp 4  | Warp 5  | Warp 6  | Warp 7  |
| 64×64   | 64×64   | 64×64   | 64×64   |
+---------+---------+---------+---------+
```

---

## 10.4 第四步：一个 Warp Tile 再拆给 32 个线程

一个 warp 最终负责：

```text
64 × 64
```

但它分 4 次处理，每次处理一个：

```text
64 × 16
```

的小子块。

每次的 `64 × 16` 子块，再分给 32 个线程：

- 8 行线程
- 4 列线程
- 每个线程负责 `8 × 4`

而因为总共要做 4 次列方向迭代，最终每个线程累计得到：

```text
8 × 16
```

的输出区域。

---

## 10.5 第五步：一个线程的输出落在寄存器里

每个线程最后拥有：

```text
res[128]
```

逻辑上就是一个：

```text
8 × 16
```

的小矩阵。

这些值会随着 K 方向的推进不断累加。

---

## 10.6 第六步：K 方向循环累加

因为：

```text
BK = 8
```

所以每次取：

- A 的 `128 × 8`
- B 的 `8 × 256`

放到 shared memory。

然后一个线程会从 shared 中读出：

- 自己需要的若干个 A 值，放进 `reg_m[]`
- 自己需要的若干个 B 值，放进 `reg_n[]`

接着执行类似：

```cpp
res[...] += reg_m[...] * reg_n[...];
```

不断累加，直到整个 K 维度全部处理完。

---

## 10.7 第七步：写回 C

当 K 的所有分块都处理完成后，线程把自己寄存器里的 `res[]` 写回到全局内存中的 C 对应位置。

于是：

- 32 个线程拼出一个 warp 的结果
- 8 个 warp 拼出一个 block 的结果
- 所有 block 拼出整个矩阵 C 的结果

---

```text
             沿 N 方向分成 4 次，每次处理一个 64 × 16 的子块
                                     ↓
                    32 个线程以 8×4 的方式分工处理这块区域
                                     ↓
                    每个线程最终负责一个 8 × 16 的 Thread Tile
                                     ↓
                     该 Thread Tile 对应线程寄存器中的 res[128]
```

# 12. Small 配置也按同样思路理解

下面我们顺手把另外两套配置的“层次关系”也算出来，方便你建立完整认知。

## 12.1 Small 配置

参数：

```text
BM=64, BN=64, BK=8
WM=32, WN=32
WNITER=2
TM=4, TN=4
NUM_THREADS=128
```

---

### 12.1.1 Block Tile

一个 Block 负责：

```text
64 × 64
```

---

### 12.1.2 Warp 数量

```text
128 / 32 = 4 个 Warp
```

---

### 12.1.3 一个 Block 被切成几个 Warp Tile

Warp Tile 是：

```text
32 × 32
```

所以：

- M 方向：`64 / 32 = 2`
- N 方向：`64 / 32 = 2`

总共：

```text
2 × 2 = 4 个 Warp Tile
```

正好对应 4 个 warp。

---

### 12.1.4 示意图

```text
Block Tile（64 × 64）
+---------+---------+
| Warp 0  | Warp 1  |
| 32×32   | 32×32   |
+---------+---------+
| Warp 2  | Warp 3  |
| 32×32   | 32×32   |
+---------+---------+
```

---

### 12.1.5 单线程负责多大

计算：

```text
WSUBN = 32 / 2 = 16
WSUBM = (32 / (16 / 4)) × 4 = (32 / 4) × 4 = 32
WMITER = 32 / 32 = 1
```

所以：

```text
单线程 M 方向 = 1 × 4 = 4
单线程 N 方向 = 2 × 4 = 8
```

即：

> **每个线程负责 `4 × 8 = 32` 个输出元素。**

# 14. 你看源码时，应该把哪些变量和这套图对应起来

这一节非常重要。你重新去看 `gemm_warp_tile.cu` 时，可以这样对照。

---

## 14.1 对应完整矩阵 / Block Tile

这些变量对应：

```cpp
blockIdx.x
blockIdx.y
c_row
c_col
```

它们表示：

> 当前 block 正在算完整矩阵 C 的哪一个大块。

---

## 14.2 对应 Warp Tile

这些变量对应：

```cpp
warp_idx
warp_row
warp_col
```

它们表示：

> 当前线程所在的 warp，在 block 内对应的是哪一个 warp tile。

---

## 14.3 对应 Thread Tile

这些变量对应：

```cpp
tiwarp
trow
tcol
```

它们表示：

> 当前线程在 warp 内的位置，以及它负责 Thread Tile 的哪一块。

---

## 14.4 对应线程寄存器输出元素

这些变量对应：

```cpp
res[]
reg_m[]
reg_n[]
```

其中：

- `res[]`：线程最终负责的输出累加器
- `reg_m[]`：当前线程从 shared memory 取出的 A 方向数据
- `reg_n[]`：当前线程从 shared memory 取出的 B 方向数据

---

# 15. 最后，把这条路线压缩成一句话

这个项目中，一个矩阵数据最终是这样被执行的：

> **完整矩阵 C 先按 `BM × BN` 切成很多个 Thread Block Tile，每个 Block 再按 `WM × WN` 切成多个 Warp Tile，每个 Warp 再把自己的区域分给 32 个线程，每个线程最终负责一个更小的 Thread Tile，并把这些输出元素放在寄存器 `res[]` 中，随着 K 方向分块不断累加，最后写回到 C。**

# 17. 你接下来最应该继续补的东西

如果你已经理解了这份文档，下一步最应该补的是：

1. **A/B 数据是怎么从 Global Memory 搬到 Shared Memory 的**
2. **Shared Memory 里的 A/B 又是怎么映射到每个线程的 `reg_m` / `reg_n` 的**
3. **`compute()` 里面为什么是外积式累加**
4. **为什么这个项目要用 `BK=8`、双缓冲、`cp.async`**

因为现在你已经理解了：

```text
输出矩阵 C 是怎么被切给 block / warp / thread 的
```

下一步就是理解：

```text
输入矩阵 A/B 是怎么被喂给这些线程的
```

这两部分合起来，你就能真正看懂这个 GEMM kernel。

# 18. 一个最简洁的脑内模型

最后给你一个最简洁、最实用的脑内模型：

```text
C 的空间切分：
完整矩阵
    ↓
Block Tile
    ↓
Warp Tile
    ↓
Thread Tile
    ↓
寄存器输出元素

A/B 的供数路线：
Global Memory
    ↓
Shared Memory
    ↓
reg_m / reg_n
    ↓
res 累加
```

只要你把这两条线同时记住，这个项目就不再“绕”，而会变得非常清晰。
