# 当前 GEMM 项目：按真实执行顺序理解完整优化流程

> 本文基于当前仓库实际源码，按一次 GEMM 从 CPU 入口到 GPU 结果写回的**真实时间顺序**梳理整个过程。重点不是逐行解释 CUDA 语法，而是理解每一阶段在做什么、为什么这样设计，以及它相对于最简单 Naive GEMM 优化了哪里。
>
> 核心文件：
>
> - `tests/test_perf_gemm.cpp`：测试入口、显存申请、cuBLAS 对比、计时
> - `src/launcher.cu`：统一 GEMM 调用入口
> - `include/gemm/kernels/gemm_warp_tile_config.h`：不同矩阵规模对应的 Tile 参数
> - `src/kernels/gemm_warp_tile.cu`：真正执行计算的 CUDA Kernel
>
> 当前算子实现：
>
> ```text
> C = alpha × A × B + beta × C
> ```
>
> 它是一个 **FP32 CUDA Core Warp-Tiled GEMM**，没有使用 Tensor Core。优化主线可以概括为：
>
> ```text
> 输出怎么分：Matrix → Block Tile → Warp Tile → Thread Tile
> 数据怎么走：Global Memory → Shared Memory → Registers → Global Memory
> 流水怎么做：cp.async + Shared Memory 双缓冲
> ```

---

# 1. 先建立整条执行时间线

一次自定义 GEMM 的核心执行链是：

```text
test_perf_gemm.cpp
        ↓
准备 A / B / C，并复制到 GPU
        ↓
launch_gemm()
        ↓
选择 WarpTile 算法
        ↓
launch_gemm_warp_tile()
        ↓
根据 M/N/K 选择 Default / Small / Irregular 配置
        ↓
计算 gridDim / blockDim
        ↓
启动 gemm_warp_tile_kernel<Cfg>()
        ↓
Block 找到自己负责的 C Tile
        ↓
Warp 找到自己的 Warp Tile
        ↓
Thread 找到自己的 Thread Tile
        ↓
沿 K 方向不断取 A/B Tile
        ↓
Global → Shared
        ↓
Shared → reg_m / reg_n
        ↓
寄存器外积累加到 res
        ↓
下一 K Tile 重复上述过程
        ↓
res 写回 C
        ↓
测试程序把 C 拷回 CPU，与 cuBLAS 比较
```

理解这个项目最重要的是始终区分两件事：

```text
① 谁负责算哪些 C？
② A/B 数据怎样送到这些线程手里？
```

前者由 Block/Warp/Thread Tiling 解决，后者由 Shared Memory、寄存器、`cp.async` 和双缓冲解决。

---

# 2. 测试入口：数据先进入 GPU Global Memory

程序从：

```cpp
tests/test_perf_gemm.cpp::main()
```

开始。

测试会生成从 256 到 8192 的规则尺寸，以及 100、257、511、1000、1234、2047 等非规则尺寸。当前主测试统一设置：

```cpp
M = N = K = sz;
```

然后按照 GEMM 的矩阵关系申请：

```text
A：M × K
B：K × N
C：M × N
```

CPU 上先分配 A/B/C，GPU 上再：

```cpp
cudaMalloc(&d_A, ...);
cudaMalloc(&d_B, ...);
cudaMalloc(&d_C, ...);
```

随后：

```cpp
cudaMemcpy(d_A, A, ...);
cudaMemcpy(d_B, B, ...);
```

所以自定义 Kernel 启动前，完整 A/B 已经位于 GPU **Global Memory**。

这一阶段没有 GEMM 优化，只是在为 Kernel 准备输入。后面的所有优化，本质都围绕一个问题：

> Global Memory 容量大，但访问代价高，怎样让一份 A/B 数据进入 GPU 片上后被尽可能多次利用？

---

# 3. `launch_gemm()`：统一入口只负责“选算法”

测试程序调用：

```cpp
launch_gemm(M, N, K, alpha, d_A, d_B, beta, d_C);
```

进入 `src/launcher.cu`。

接口默认使用：

```cpp
GemmAlgo::Auto
```

但当前：

```cpp
select_gemm_algo()
```

固定返回：

```cpp
GemmAlgo::WarpTile
```

因此真实调用链实际上是：

```text
launch_gemm()
    ↓
launch_gemm_warp_tile()
```

这里的意义主要是工程解耦：测试程序只认识统一 `launch_gemm()`，以后即使增加 Naive、Tensor Core 或其他专用 Kernel，也不需要修改上层测试接口。

---

# 4. 先选 Tile 配置：不同矩阵不能都用同一套参数

`launch_gemm_warp_tile()` 根据 M/N/K 选择三套配置。

| 配置 | Block Tile `BM×BN` | `BK` | Warp Tile `WM×WN` | 线程数 |
|---|---|---:|---|---:|
| Default | 128×256 | 8 | 64×64 | 256 |
| Small | 64×64 | 8 | 32×32 | 128 |
| Irregular | 64×128 | 8 | 32×64 | 128 |

大致逻辑：

```text
中小规模且存在不规则尺寸 → Irregular
较小且规则             → Small
其他情况                 → Default
```

为什么要 Dispatch？

因为 Tile 太大时，小矩阵可能只产生少量 Block，GPU 并行度不够；Tile 太小时，大矩阵的数据复用又下降。因此这个项目并不是只追求“Tile 越大越好”，而是根据问题规模在并行度和数据复用之间取平衡。

---

# 5. Kernel Launch：先把完整 C 分给各个 Block

选定配置后进入：

```cpp
launch_gemm_warp_tile_cfg<Cfg>()
```

其中：

```cpp
dim3 blockDim(Cfg::NUM_THREADS);

dim3 gridDim(
    CEIL_DIV(N, Cfg::BN),
    CEIL_DIV(M, Cfg::BM)
);
```

也就是说：

```text
grid.x：沿 C 的 N 方向切
grid.y：沿 C 的 M 方向切
```

一个 Block 负责一个：

```text
BM × BN
```

的输出 C Tile。

以 Default 为例：

```text
BM = 128
BN = 256
```

所以：

```text
一个 Block → C 中 128 行 × 256 列
```

如果 C 是 `4096×4096`：

```text
N 方向：4096 / 256 = 16 个 Block
M 方向：4096 / 128 = 32 个 Block
总计：512 个 Block
```

至此完成第一层分工：

```text
完整 C
    ↓
许多 Block Tile
```

---

# 6. Block 内继续切成 Warp Tile

Kernel：

```cpp
gemm_warp_tile_kernel<Cfg>()
```

启动后，每个线程首先根据：

```cpp
warp_idx
warp_row
warp_col
```

确定自己属于哪个 Warp，以及这个 Warp 负责 Block Tile 中哪块区域。

Default 配置：

```text
Block Tile = 128×256
Warp Tile  = 64×64
256 Threads = 8 Warp
```

所以：

```text
+---------+---------+---------+---------+
| Warp 0  | Warp 1  | Warp 2  | Warp 3  |
| 64×64   | 64×64   | 64×64   | 64×64   |
+---------+---------+---------+---------+
| Warp 4  | Warp 5  | Warp 6  | Warp 7  |
| 64×64   | 64×64   | 64×64   | 64×64   |
+---------+---------+---------+---------+
```

之所以显式做 Warp Tile，是因为 GPU 实际以 32 个线程组成的 Warp 为调度单位。先规定每个 Warp 的输出责任，后面的 Shared Memory 读取和寄存器计算就可以围绕这个区域组织。

---

# 7. Warp 再切给线程：一个线程不再只算一个 C

接下来通过：

```cpp
trow
tcol
TM
TN
WNITER
WMITER
```

确定线程在 Warp Tile 中负责哪些输出。

Default 配置下，每个线程最终维护：

```text
8 × 16 = 128 个 C 输出元素
```

这些元素全部保存在：

```cpp
float res[...] = {};
```

中。

这一步与最简单 Naive GEMM 差别很大。

Naive：

```text
一个线程 → 一个 sum → 一个 C
```

当前项目：

```text
一个线程 → 一组 res → 多个 C
```

为什么这样更快？

因为线程从 Shared Memory 取来一组 A 和一组 B 后，可以用它们组合出很多次乘加，而不是只得到一个结果，从而提高寄存器级数据复用率。这就是 **Thread Tile / Register Blocking**。

---

# 8. 输出区域分完后，开始解决“输入数据怎么来”

到这里已经决定：

```text
Block 算哪块 C
Warp 算哪块 C
Thread 算哪几个 C
```

但 A/B 还在 Global Memory。

矩阵乘法：

```text
C[m,n] = Σ A[m,k] × B[k,n]
```

所以每个输出还要遍历完整 K。

项目设置：

```text
BK = 8
```

表示不会一次把整个 K 维数据送进来，而是每次处理一个 K Tile。

Default 下，每轮 Block 需要：

```text
A Tile：128 × 8
B Tile：8 × 256
```

然后：

```text
K=0~7
K=8~15
K=16~23
...
```

逐块推进。

这样做是因为完整 A/B 太大，不可能都放进 Shared Memory；而一个小 `BK` 工作集可以放在片上高速存储中反复使用。

---

# 9. Global Memory → Shared Memory：第一次真正的数据复用

Kernel 声明：

```cpp
__shared__ float AS[2][A_STRIDE * BK];
__shared__ float BS[2][BK * BN];
```

可以把它理解为：

```text
AS：当前 Block 正在使用的 A Tile
BS：当前 Block 正在使用的 B Tile
```

Block 内所有线程协作，把当前 A/B Tile 从 Global Memory 搬进 Shared Memory：

```text
Global A/B
    ↓
Block 中线程共同搬运
    ↓
AS / BS
```

为什么要多绕一层 Shared Memory，而不是直接计算？

因为同一个 A/B 元素会被 Block 内多个输出反复需要。如果每个线程都直接访问 Global Memory，就会重复读取大量相同数据。

Shared Memory Tiling 的核心就是：

> Global Memory 只付一次较昂贵的加载成本，进入 Shared 后让整个 Block 多次复用。

---

# 10. Fast Path 使用 `cp.async`：把“搬数据”也优化

规则、完整且满足对齐条件的 Block 会进入 Fast Path。

数据搬运由：

```cpp
load_tile_async()
```

完成，内部使用：

```cpp
cp_async16()
```

一次搬：

```text
16 Bytes = 4 个 float
```

路径可以理解为：

```text
Global Memory
    ↓ cp.async
Shared Memory
```

相关：

```text
cp_async_commit()
cp_async_wait_group()
```

用于组织和等待异步搬运。

这一层优化的重点不是增加乘法数量，而是优化**数据到达 Shared Memory 的方式**，同时为后面的“边搬下一块、边算当前块”创造条件。

---

# 11. Shared Memory 双缓冲：当前项目的主要流水优化

注意源码不是：

```text
AS
BS
```

各一份，而是：

```text
AS[2]
BS[2]
```

也就是两套 Buffer。

主循环中：

```cpp
cur = t & 1;
nxt = 1 - cur;
```

让两份缓冲交替使用：

```text
开始：加载 Tile 0 → Buffer 0

第 0 轮：
计算 Buffer 0
同时预取 Tile 1 → Buffer 1

第 1 轮：
计算 Buffer 1
同时预取 Tile 2 → Buffer 0

第 2 轮：
计算 Buffer 0
同时预取 Tile 3 → Buffer 1
```

没有双缓冲时：

```text
搬运 → 等待 → 计算 → 搬运 → 等待 → 计算
```

双缓冲的目标则是：

```text
当前 Tile 正在计算
          +
下一 Tile 正在 Global → Shared
```

让计算尽量覆盖访存等待时间。

这就是项目中所谓的**流水化**：不是改变 GEMM 数学，而是重新安排“搬数据”和“算数据”的时间顺序。

---

# 12. Shared Memory → `reg_m/reg_n`：数据最后进入线程私有寄存器

Shared Memory 是一个 Block 共享的，但真正执行乘加时，每个线程只需要自己对应的部分。

`compute()` 中，每个 K Tile 又沿：

```text
d = 0 ... BK-1
```

依次处理。

线程从：

```text
AS → reg_m[]
BS → reg_n[]
```

取数据。

以 Default 为例，可以把当前线程想成每个 d 取得：

```text
reg_m：8 个 A 数据
reg_n：16 个 B 数据
```

Shared Memory 的作用是 Block 级复用，而 `reg_m/reg_n` 的作用是让当前线程即将执行的操作数进入最快的线程私有存储。

所以完整层次是：

```text
Global：完整大矩阵
    ↓
Shared：Block 当前 Tile
    ↓
Register：Thread 当前要计算的数据
```

---

# 13. 寄存器外积：一次取数更新一整个 Thread Tile

`compute()` 最核心的逻辑是：

```cpp
res[...] += reg_m[...] * reg_n[...];
```

Default 下可以理解为：

```text
reg_m：8×1
reg_n：1×16

        ↓ 外积

产生 8×16 个乘加
        ↓
累积到 res[128]
```

也就是说，一组 A 寄存器和一组 B 寄存器不是只算一个 C，而是组合起来更新整个线程负责的输出微块。

这就是当前 GEMM 提高算术强度的关键：

```text
一次 Shared → Register 读取
        ↓
产生大量 FMA
```

`res[]` 会从 Kernel 开始一直留在线程寄存器里：

```text
第 0 个 K Tile → 累加
第 1 个 K Tile → 累加
第 2 个 K Tile → 累加
...
```

直到完整 K 维结束才写回 Global C。

如果每处理一个 BK 都把中间 C 写回显存，再下一轮重新读回来，会产生大量没有必要的 Global Memory 流量。

---

# 14. `__syncthreads()`：保证共享数据真的准备好了

A/B Tile 是整个 Block 的线程一起搬入 Shared Memory 的，而计算阶段又可能读取其他线程搬进来的数据。

因此必须保证：

```text
所有需要的数据都准备完成
    ↓
所有线程到达同一阶段
    ↓
才能开始使用 Shared Memory
```

源码中因此出现：

```cpp
cp_async_wait_group<0>();
__syncthreads();
```

前者等待异步搬运，后者让整个 Block 同步。

所以同步不是“为了让代码整齐”，而是 Shared Memory 协作加载能够正确工作的必要条件。

---

# 15. Fast Path 与 Edge Path：性能和通用性分开处理

Kernel 通过：

```cpp
fast
```

判断当前 Block 是否完整、是否满足相关对齐条件。

如果满足：

```text
Fast Path
```

走：

```text
cp.async
双缓冲
完整 Tile 计算
float4 写回
```

如果是矩阵最右侧、最下侧，或者尺寸不满足条件，则走：

```text
Edge / Unaligned Path
```

它会：

```text
先清零 Shared
    ↓
只加载合法 A/B
    ↓
compute_edge()
    ↓
只写合法 C
```

为什么不让所有 Block 都走一种通用代码？

因为内部绝大多数 Block 都是完整 Tile。如果主循环每次都检查边界，就会让最常见路径承担额外分支和访存开销。

所以当前设计原则是：

```text
大量内部区域 → 专门优化
少量边界区域 → 单独保证正确
```

---

# 16. K 方向有余数时怎么收尾

即使 Fast Path 成立：

```text
K
```

也不一定能被：

```text
BK = 8
```

整除。

例如：

```text
K = 100
```

可以处理 12 个完整 Tile：

```text
12×8 = 96
```

最后还剩 4。

源码通过：

```cpp
compute_k(..., k_rem)
```

处理尾部。

整体数据流不变：

```text
剩余 A/B
    ↓
Shared
    ↓
reg_m / reg_n
    ↓
res
```

只是只计算真正有效的 `k_rem` 个位置。

---

# 17. K 全部结束后，结果才写回 Global Memory

此时每个线程的：

```cpp
res[]
```

已经包含完整 K 维上的累加结果。

写回遵循：

```text
C = alpha × res + beta × C_old
```

Fast Path 使用：

```cpp
float4
```

一次读写连续 4 个 `float`，减少 Load/Store 指令并利用连续地址。

所以最后的数据流是：

```text
res Registers
    ↓
alpha × res + beta × C
    ↓
float4
    ↓
Global Memory C
```

Edge Path 因为可能只剩 1、2、3 个合法元素，所以改用逐元素边界检查写回。

---

# 18. 所有 Block 完成后，测试程序做什么

各 Block 负责不同的 C Tile，所以彼此不需要共享最终结果：

```text
Block 0 → C 的一块
Block 1 → C 的另一块
Block 2 → C 的另一块
...
```

所有 Block 完成后，完整 C 已经位于 GPU Global Memory。

测试代码再：

```cpp
cudaMemcpy(C, d_C, ..., cudaMemcpyDeviceToHost);
```

拷回 CPU，与 cuBLAS 结果比较，并根据 CUDA Event 时间计算 GFLOPS。

仓库 README 中保存的稳定 `dispatch_A` 基线，5 次运行的 `my_gflops / cublas_gflops` 均值约为 `0.7456`。仓库说明选择这一版本，是因为它在总体吞吐、稳定性和不规则尺寸表现之间更均衡。

# 19. 把整个优化路线和 Naive GEMM 对照起来

最简单 Naive GEMM：

```text
一个 Thread → 一个 C
A/B 每次直接从 Global Memory 读取
```

当前项目逐层变成：

```text
① Block Tiling
完整 C → BM×BN
确定 Block 级复用区域

        ↓

② Warp Tiling
Block Tile → WM×WN
明确 Warp 的输出责任

        ↓

③ Thread Tiling / Register Blocking
一个 Thread → 多个 C
用 reg_m/reg_n 的一次取数更新多个 res

        ↓

④ K Tiling
完整 K → 多个 BK
让当前工作集能够放入片上存储

        ↓

⑤ Shared Memory Tiling
Global A/B → AS/BS
让 Block 内线程重复利用同一份数据

        ↓

⑥ cp.async
优化 Global → Shared 的搬运过程

        ↓

⑦ 双缓冲
当前 Tile 计算，同时预取下一 Tile

        ↓

⑧ res 长期驻留寄存器
中间结果不反复写回显存

        ↓

⑨ float4 写回
连续输出向量化写回

        ↓

⑩ Fast / Edge 分离
主区域专门追求性能，边界单独保证正确
```

# 20. 最终应该形成的脑内模型

这个项目真正的核心并不是某一条 `cp.async` 或某一个下标，而是三层优化思想。

### 第一层：先解决“谁来算”

```text
Matrix
  ↓
Block Tile
  ↓
Warp Tile
  ↓
Thread Tile
  ↓
res[]
```

### 第二层：再解决“数据放哪”

```text
完整 A/B
Global Memory
  ↓
当前 Block 的 A/B Tile
Shared Memory
  ↓
当前线程马上需要的数据
reg_m / reg_n
```

### 第三层：最后解决“什么时候搬”

```text
计算当前 Tile
        +
异步预取下一 Tile
```

因此整个项目可以压缩成一句话：

> **先用 Block/Warp/Thread Tiling 把输出 C 的计算责任划分清楚，再让 A/B 沿 K 方向分块从 Global Memory 进入 Shared Memory，并进一步进入线程寄存器做外积累加；中间结果始终保留在 `res` 中，同时利用 `cp.async + 双缓冲` 让下一块数据搬运与当前计算尽量重叠，最后再一次性把结果写回 C。**

如果能真正理解这句话，就已经抓住了当前仓库 GEMM 优化的主干。


---

# 21. 用一次 `4096×4096×4096` GEMM 把全过程串起来

前面讲的是各阶段的作用，现在用 Default 配置把一次真实的大矩阵 GEMM 走一遍。

假设：

```text
M = N = K = 4096
```

因为尺寸较大而且规则，所以进入：

```text
WarpTileDefaultConfig
```

参数：

```text
BM=128
BN=256
BK=8
WM=64
WN=64
TM=8
TN=4
Threads=256
```

首先 Kernel Launch 会得到：

```text
grid.x = 4096 / 256 = 16
grid.y = 4096 / 128 = 32
```

因此整个 C 被切成：

```text
16 × 32 = 512 个 Block Tile
```

每个 Block 负责：

```text
128 × 256 = 32768 个 C 元素
```

一个 Block 内有 256 个线程，也就是 8 个 Warp。每个 Warp 负责 `64×64`，8 个 Warp 正好拼出完整 `128×256` Block Tile。

继续往下，一个线程最终维护 `8×16=128` 个输出，因此：

```text
256 个线程 × 128 个输出
=
32768 个输出
```

恰好就是整个 Block Tile 的元素数量。这个等式非常重要，它说明线程映射最终完整覆盖了 Block 的输出区域，没有遗漏。

接着进入 K 维。因为：

```text
K = 4096
BK = 8
```

所以一个 Block 要执行：

```text
4096 / 8 = 512 个 K Tile
```

每个 K Tile 需要：

```text
A：128×8
B：8×256
```

的数据。

当前 Block 并不是把 4096 长度的 K 一次全部装进 Shared Memory，而是不断执行：

```text
取第 0 个 K Tile → 计算
取第 1 个 K Tile → 计算
...
取第 511 个 K Tile → 计算
```

每完成一个 K Tile，只更新 `res[]`，不写 C。直到 512 个 K Tile 全部完成，线程才把最终结果写回 Global Memory。

所以从时间上看，一个 Block 的生命周期可以想象为：

```text
确定自己负责的 128×256 输出
        ↓
预取 K=0~7
        ↓
计算 K=0~7，同时预取 K=8~15
        ↓
计算 K=8~15，同时预取下一块
        ↓
持续 512 轮
        ↓
res 中形成最终结果
        ↓
写回 128×256 的 C Tile
```

这就是整个 Kernel 最直观的时间模型。

# 22. 为什么 Shared Memory 能明显减少显存访问

以 Default 配置中的一个 K Tile 为例。

A Tile：

```text
128 × 8 = 1024 个 float
```

B Tile：

```text
8 × 256 = 2048 个 float
```

也就是说，一个 Block 每轮只需把这一小块 A/B 从 Global Memory 搬入 Shared Memory。

但这批数据随后会参与整个：

```text
128 × 256
```

输出区域的计算。

例如 A 中某个固定的 `A[m,k]`，会与 B 当前 K 位置上很多不同列的数据相乘；B 中一个 `B[k,n]` 也会被很多不同输出行使用。

如果没有 Shared Memory，每个线程各自从 Global Memory 读取，会让相同数据被反复请求。现在先搬到：

```text
AS / BS
```

后，Block 内线程都能复用。

因此 Shared Memory 的价值不是“它本身做计算”，而是：

> **把高复用的数据临时放在离计算核心更近的位置，降低对 Global Memory 带宽和延迟的依赖。**

这也是为什么 GEMM 特别适合 Tiling：矩阵乘法本身就有很强的数据复用结构。

# 23. 为什么寄存器里要放这么多 `res`

在 Naive GEMM 中：

```text
一个线程只有一个 sum
```

每取得一个 A 和一个 B，只能更新一个输出。

当前项目让一个线程维护很多 `res`。Default 下逻辑上是 `8×16` 个输出。

这样，当线程已经把：

```text
一组 A → reg_m
一组 B → reg_n
```

放入寄存器后，就不只做一次：

```text
A × B
```

而是做整个小外积。

也就是说，同一份寄存器数据被多次使用。

这相当于继续向计算核心靠近：

```text
Global Memory 级复用
    ↓
Shared Memory 级复用
    ↓
Register 级复用
```

越靠近寄存器，访问越快，但容量越小。因此 GEMM 优化实际上一直在做一个平衡：

```text
Tile 太小 → 数据复用不足
Tile 太大 → Shared Memory / Register 压力过高
```

当前仓库中的 Default、Small、Irregular 三套配置，本质就是在这个平衡上选择不同点。

---

# 24. 为什么 `cp.async + 双缓冲` 是在优化“等待时间”

即使已经使用 Shared Memory，数据还是必须先从 Global Memory 搬进来。如果执行顺序永远是：

```text
先搬完
再计算
再搬下一块
再计算
```

那么 GPU 在搬数据期间，部分计算资源会等待。

当前项目的双缓冲把 Shared Memory 分成两套：

```text
Buffer 0
Buffer 1
```

于是可以安排：

```text
计算 Buffer 0
同时让 Buffer 1 接收下一批数据
```

随后交换。

这里需要特别理解：

> 双缓冲并没有减少 GEMM 总共需要的乘加次数，也没有让 Global Memory 的数据凭空消失，它主要是在改变时间安排，让“搬数据”和“做计算”出现重叠。

所以 GEMM 优化可以分成两类：

```text
数据复用优化：
Shared Memory、Register Blocking
→ 尽量少搬

流水优化：
cp.async、Double Buffer
→ 必须搬的时候尽量不要干等
```

这两类手段组合起来，才形成当前 Kernel 的主要性能路径。

---

# 25. 为什么最终只在最后写一次 C

在整个 K 循环中：

```text
res
```

一直存在寄存器里。

如果每处理一个 BK Tile 就执行：

```text
res → Global C
```

下一轮又需要：

```text
Global C → Register
```

继续累加，那么一个输出会在 K 循环中反复访问 Global Memory。

当前实现选择：

```text
K 方向所有贡献
全部先在 res 中累完
```

最后才：

```text
res → C
```

所以对每个最终输出而言，理想主流程只需要一次最终写回。

这正体现了高性能 GEMM 的一个重要原则：

> **中间结果尽量留在最快的存储层中，不要过早落回显存。**

# 26. 面试时应该怎样概括这个项目的优化逻辑

如果面试官问“你的 GEMM 是怎么优化的”，可以按照下面的逻辑回答，而不是直接堆技术名词：

> 最开始 Naive GEMM 是一个线程算一个元素，而且 A/B 基本直接访问 Global Memory，数据复用很差。我的实现首先把输出按 Block、Warp、Thread 三级 Tile 划分，让每个线程一次维护多个输出；然后把 K 维也按 BK 分块，每个 Block 协作把当前 A/B Tile 放到 Shared Memory，使同一份数据可以被整个 Block 重复使用。计算阶段再把 Shared Memory 数据放到 `reg_m/reg_n`，通过外积一次更新多个 `res`，让中间结果一直留在寄存器。访存方面又使用 `cp.async` 和 Shared Memory 双缓冲，在计算当前 K Tile 时提前加载下一 Tile，尽量隐藏显存延迟。最后 K 全部算完后再用 `float4` 把结果写回。对于边界和不规则尺寸，则单独走带检查的 Edge Path，避免拖慢主要的规则路径。

如果这段逻辑能够自然讲出来，就说明你理解的已经不只是“这份代码怎么写”，而是：

```text
为什么 GEMM 要这样优化
```
