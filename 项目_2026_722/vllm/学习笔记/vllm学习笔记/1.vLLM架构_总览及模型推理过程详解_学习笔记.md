## 0. 本节课的核心目标

这节课的主线不是单独讲某一个优化点，而是讲清楚：

> **一个用户请求进入 vLLM 之后，如何经过 API Server、EngineCore、Scheduler、Executor、Worker、ModelRunner、Model，最终完成一次大模型推理并把 token 流式返回。**

如果前面课程重点是 **KV Cache / PagedAttention / Block 管理 / 请求与显存块映射**，那么这一节课就是把这些局部知识放进 vLLM v1 的完整架构中，回答下面几个关键问题：

1. vLLM 为什么要拆成多个进程？
2. API Server、EngineCore、GPU Worker 分别负责什么？
3. Scheduler、KVCacheManager、Executor、Worker、ModelRunner 之间是什么关系？
4. 一个请求从文本输入到 token 输出，中间到底经历了哪些对象和数据结构？
5. ModelRunner 在真正执行模型推理前，需要准备哪些输入？
6. vLLM 为什么能支持 continuous batching、PagedAttention、多卡并行、流式输出？

学习完这一节，面试时应该能够完整说出：

> **用户请求进入 vLLM 后，先由入口层接收和预处理，再交给 EngineCore 调度；Scheduler 决定本轮哪些请求、多少 token 被执行；KVCacheManager 分配或复用 KV cache block；Executor 将调度结果分发给 Worker；每个 Worker 内的 ModelRunner 构建模型输入、调用模型 forward、采样新 token；最后输出结果回到 API Server，经过 detokenize 后流式返回给用户。**

## 1. vLLM v1 架构总览

### 1.1 为什么需要 vLLM v1 架构

vLLM 最早出名的核心技术是 **PagedAttention**，它解决的是大模型推理中 KV Cache 显存管理的问题：传统做法容易为每个请求预留过多连续显存，导致显存碎片和浪费；PagedAttention 则把 KV Cache 拆成固定大小的 block，按需分配，让逻辑上连续的上下文可以存放在物理上不连续的显存块中。

但是，随着 vLLM 支持的模型、硬件后端、量化方式、调度策略、并行方式越来越多，架构本身也会变复杂。vLLM v1 的目标是把核心执行链路重新整理为更清晰的模块化架构，包括：

- API Server
- EngineCore
- Scheduler
- KV Cache Manager
- Executor
- Worker
- ModelRunner
- Model
- Sampler
- OutputProcessor

vLLM 官方博客中提到，v1 的目标包括：更简单、模块化、易修改；降低 CPU overhead；把关键优化统一到一个架构中；尽量默认启用合理优化。官方文档也说明，v1 采用多进程架构来分离职责并提升吞吐。

---

### 1.2 vLLM v1 的高层分层

可以把 vLLM v1 理解为 5 层：

```text
用户 / 客户端
    ↓
入口层：LLM / OpenAI-compatible API Server
    ↓
引擎层：EngineCore / AsyncLLM / LLMEngine
    ↓
调度与执行层：Scheduler / KVCacheManager / Executor
    ↓
GPU 执行层：Worker / ModelRunner / Model / CUDA Kernel
```

每一层的职责不同：

| 层级 | 代表组件 | 主要作用 |
|---|---|---|
| 用户入口层 | `LLM`、`vllm serve`、OpenAI API Server | 接收离线或在线请求 |
| 引擎层 | `EngineCore`、`LLMEngine`、`AsyncLLMEngine` | 管理请求生命周期，驱动推理循环 |
| 调度层 | `Scheduler`、`KVCacheManager` | 决定本轮执行哪些 token，并分配 KV Cache |
| 执行分发层 | `Executor` | 把调度结果分发给 Worker |
| GPU 执行层 | `Worker`、`ModelRunner`、`Model` | 构建输入、执行 forward、采样输出 |

## 2. vLLM v1 架构核心类介绍

### 2.1 `LLM`：离线推理入口

`LLM` 是 vLLM 的 Python 离线推理接口，适合批量推理，例如：

```python
from vllm import LLM, SamplingParams

llm = LLM(model="Qwen/Qwen2.5-0.5B-Instruct")
sampling_params = SamplingParams(temperature=0.7, max_tokens=128)

outputs = llm.generate(
    ["请用一句话介绍 vLLM"],
    sampling_params,
)
```

它适合：

- 本地批量 benchmark
- 数据集离线生成
- 简单验证模型推理效果
- 学习 vLLM 内部执行链路

在源码学习中，可以从 `LLM.generate()` 入手，看请求如何被包装成内部请求，然后交给 engine 执行。

---

### 2.2 `vllm serve` / API Server：在线服务入口

在线服务通常通过：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct
```

启动。

这会启动一个 OpenAI-compatible API Server，对外暴露类似：

```text
POST /v1/chat/completions
POST /v1/completions
```

的接口。

API Server 主要负责：

1. 接收 HTTP 请求；
2. 解析 OpenAI 格式参数；
3. 进行 chat template 渲染；
4. tokenizer 编码；
5. 多模态输入预处理；
6. 把请求发送给 EngineCore；
7. 接收输出 token；
8. detokenize；
9. 以 SSE / streaming 方式返回给客户端。

这里要注意：

> **API Server 不直接执行模型 forward。它更像请求入口、预处理器和结果出口。**

---

### 2.3 `EngineCore`：vLLM v1 的核心循环

`EngineCore` 是 vLLM v1 的核心执行进程。它的核心职责是：

- 保存请求状态；
- 运行 scheduler；
- 管理 KV Cache；
- 调用 executor；
- 接收模型执行结果；
- 更新请求状态；
- 判断请求是否结束；
- 把结果返回给上层。

可以把它理解为：

> **EngineCore 是 vLLM 推理服务的“大脑”，负责决定每一步让哪些请求继续生成。**

一个 EngineCore 中通常包含：

```text
EngineCore
 ├── Scheduler
 ├── KVCacheManager
 ├── Executor
 ├── Request state
 └── Output processing logic
```

在数据并行场景下，通常每个 DP rank 对应一个 EngineCore 进程。

---

### 2.4 `Scheduler`：决定本轮执行哪些 token

Scheduler 是 vLLM 的调度器。它要解决的问题是：

> 当前系统中可能有很多请求，有些刚进来需要 prefill，有些已经生成了一半需要 decode，那么这一轮 GPU forward 应该处理哪些请求、每个请求处理多少 token？

在 vLLM v1 中，一个重要变化是：

> **Scheduler 不再把 prefill 和 decode 看成完全割裂的两类任务，而是把 prompt token 和 output token 统一视为“本轮要处理的 token 数”。**

例如本轮调度结果可以抽象为：

```python
{
    request_id_1: 1,
    request_id_2: 8,
    request_id_3: 32,
}
```

含义是：

- 请求 1 本轮处理 1 个 token，可能是 decode；
- 请求 2 本轮处理 8 个 token，可能是 chunked prefill；
- 请求 3 本轮处理 32 个 token，可能是较长 prompt 的一部分。

这使得 vLLM 可以更自然地支持：

- continuous batching；
- chunked prefill；
- prefix caching；
- speculative decoding；
- 不同请求混合调度。

---

### 2.5 `KVCacheManager`：管理 KV Cache Block

KVCacheManager 负责 KV Cache 的逻辑和物理管理。

它要解决的问题是：

1. 一个请求需要多少 KV Cache block？
2. 当前还有哪些 free blocks？
3. 某个请求的逻辑 block 映射到哪个物理 block？
4. 哪些 block 可以被 prefix caching 复用？
5. 请求结束后如何释放 block？
6. 显存不足时如何换出或淘汰？

关键概念：

| 概念 | 含义 |
|---|---|
| block | 固定数量 token 对应的 KV Cache 存储单元 |
| block size | 一个 block 能容纳的 token 数量，例如 16 或 32 |
| physical block | 实际显存中的 KV Cache block |
| logical block | 某个请求视角下的第几个 block |
| block table | 逻辑 block 到物理 block 的映射表 |
| slot mapping | token 级别映射，表示某个 token 的 KV 应该写入哪个具体 slot |

可以这样理解：

```text
请求 A 的逻辑 KV 序列：
logical block 0 → physical block 7
logical block 1 → physical block 2
logical block 2 → physical block 9

虽然逻辑上是连续上下文，
但物理显存中可以不连续。
```

这就是 PagedAttention / 分页 KV Cache 的核心思想。

---

### 2.6 `Executor`：EngineCore 和 Worker 之间的执行分发层

Executor 不是模型本体，它主要负责：

- 管理一个或多个 Worker；
- 把 Scheduler 产生的调度结果广播给 Worker；
- 在 TP / PP / DP 场景下协调多进程执行；
- 收集 Worker 返回的模型输出；
- 把结果交回 EngineCore。

如果只看单卡推理，Executor 的存在感可能不强；但一旦进入多卡推理，它就非常重要。

例如 `tensor_parallel_size=4` 时，通常会有 4 个 GPU Worker。Executor 要保证这 4 个 Worker 在同一轮 forward 中处理同一批调度任务，并完成必要的通信。

---

### 2.7 `Worker`：每个 GPU 的执行进程

Worker 可以理解为：

> **一个 GPU 对应的模型执行进程。**

Worker 主要负责：

- 初始化分布式环境；
- 加载本 rank 对应的模型权重；
- 初始化 KV Cache；
- 持有 ModelRunner；
- 接收 Executor 下发的执行命令；
- 调用 ModelRunner 执行模型；
- 返回采样结果。

在 TP 场景下，每个 Worker 只持有模型的一部分权重。例如：

```text
tensor_parallel_size = 2

Worker rank 0：持有一部分 attention / MLP 权重
Worker rank 1：持有另一部分 attention / MLP 权重
```

它们通过 collective communication 共同完成一次模型 forward。

---

### 2.8 `ModelRunner`：真正组织模型执行的组件

ModelRunner 是本节课最重要的组件之一。

它不只是简单调用：

```python
model(input_ids)
```

而是要做大量执行前准备工作，包括：

1. 根据调度结果构建本轮模型输入；
2. 准备 `input_ids`；
3. 准备 `positions`；
4. 准备 attention metadata；
5. 准备 block table；
6. 准备 slot mapping；
7. 准备 KV Cache 写入位置；
8. 处理 CUDA Graph / torch.compile 相关逻辑；
9. 调用模型 forward；
10. 调用 sampler 得到下一个 token。

可以把 ModelRunner 理解为：

> **Worker 内部真正把“调度结果”转换成“模型可执行张量”的组件。**

---

### 2.9 `Model`：实际的 `torch.nn.Module`

ModelRunner 内部持有实际模型对象，也就是类似：

```python
QwenForCausalLM
LlamaForCausalLM
DeepseekForCausalLM
```

这样的模型实现。

它是真正执行 Transformer 层的地方：

```text
input_ids
  ↓
embedding
  ↓
Transformer blocks
  ├── attention
  ├── MLP
  └── residual / norm
  ↓
lm_head
  ↓
logits
```

但是在 vLLM 中，attention 不再是普通 PyTorch attention，而会使用适配 KV Cache block 布局的高性能 attention kernel。

## 4. vLLM 整体运行流程图

下面用“从输入到输出”的方式梳理完整流程。

---

### 4.1 第一步：用户发起请求

在线服务中，用户可能发送：

```json
{
  "model": "Qwen/Qwen2.5-7B-Instruct",
  "messages": [
    {"role": "user", "content": "请介绍一下 vLLM"}
  ],
  "temperature": 0.7,
  "max_tokens": 128,
  "stream": true
}
```

API Server 接收到请求后，会做：

1. 参数解析；
2. 校验模型名；
3. 应用 chat template；
4. 把 messages 转成 prompt；
5. tokenizer 编码成 token ids；
6. 生成 request id；
7. 封装 sampling parameters。

---

### 4.2 第二步：请求进入 EngineCore

EngineCore 接收到请求后，会创建内部请求对象，大致包含：

```text
request_id
prompt_token_ids
sampling_params
arrival_time
num_computed_tokens
output_token_ids
status
```

其中最重要的是：

| 字段 | 作用 |
|---|---|
| `request_id` | 唯一标识一个请求 |
| `prompt_token_ids` | prompt 编码后的 token id |
| `num_computed_tokens` | 已经完成 forward 的 token 数 |
| `output_token_ids` | 已生成 token |
| `sampling_params` | temperature、top_p、max_tokens 等参数 |
| `status` | waiting / running / finished 等状态 |

---

### 4.3 第三步：Scheduler 选择本轮执行内容

系统中可能同时有很多请求：

```text
Request A：刚进入，prompt 有 200 token，还没 prefill
Request B：已经 prefill 完，正在 decode
Request C：prompt 很长，只完成了一部分 chunked prefill
Request D：等待 KV Cache 空间
```

Scheduler 要在每个 step 做决策：

```text
本轮 token budget = 8192

Request B：执行 1 个 decode token
Request C：继续执行 512 个 prefill token
Request A：执行 1024 个 prefill token
...
```

它会综合考虑：

- `max_num_batched_tokens`
- `max_num_seqs`
- 当前 KV Cache 可用空间
- 请求优先级
- decode 优先策略
- chunked prefill
- prefix cache 命中情况
- 是否存在抢占或等待

---

### 4.4 第四步：KVCacheManager 分配显存块

假设某个请求 prompt 有 33 个 token，`block_size=16`：

```text
token 0  - 15  → logical block 0
token 16 - 31  → logical block 1
token 32       → logical block 2
```

它需要 3 个逻辑 block。

KVCacheManager 会从 free block pool 中分配物理 block：

```text
logical block 0 → physical block 12
logical block 1 → physical block 3
logical block 2 → physical block 21
```

然后构造：

```text
block_table = [12, 3, 21]
```

如果本轮只处理 token 32，那么还要知道：

```text
token 32 应该写入 physical block 21 的 offset 0
```

这类 token 级映射就是 `slot_mapping` 的作用。

---

### 4.5 第五步：Executor 分发执行任务

Scheduler 输出本轮调度结果后，EngineCore 会调用 Executor。

Executor 会把调度结果发送给 Worker：

```text
schedule_output
    ↓
Executor
    ↓
Worker 0
Worker 1
Worker 2
Worker 3
```

在单卡场景中，Executor 只需要调用一个 Worker。

在 TP 多卡场景中，Executor 要广播同一个调度任务给多个 Worker，并确保它们协同完成同一次 forward。

---

### 4.6 第六步：Worker 调用 ModelRunner

Worker 接收到任务后，不直接手写模型 forward，而是调用自己的 ModelRunner。

```text
Worker.execute_model(schedule_output)
    ↓
ModelRunner.execute_model(...)
```

ModelRunner 接下来会构建模型真正需要的输入。

---

## 5. ModelRunner 执行模型推理

### 5.1 ModelRunner 的核心职责

ModelRunner 的作用可以总结为一句话：

> **把 Scheduler 的调度结果转换为模型 forward 所需的张量与元数据，然后调用模型执行并采样输出。**

它通常需要处理：

1. 哪些 token 要参与本轮 forward；
2. 每个 token 的 position id；
3. 每个请求对应的上下文长度；
4. 每个请求的 block table；
5. 每个 token 的 slot mapping；
6. attention backend 需要的 metadata；
7. CUDA Graph 或 torch.compile 的执行路径；
8. logits 与 sampler 的调用；
9. 返回 sampled token。

---

### 5.2 模型输入主要包括哪些内容

一次模型 forward 并不只是传入 `input_ids`。

在 vLLM 中，模型输入通常包括：

| 输入 | 作用 |
|---|---|
| `input_ids` | 本轮要计算的 token id |
| `positions` | 每个 token 在序列中的位置 |
| `kv_caches` | 每层 attention 的 KV Cache 存储 |
| `attn_metadata` | attention 后端所需的元信息 |
| `block_tables` | 每个请求的逻辑 block 到物理 block 映射 |
| `slot_mapping` | 每个 token 写入 KV Cache 的具体 slot |
| `seq_lens` / `context_lens` | 每个请求当前上下文长度 |
| `sampling_metadata` | 采样参数和请求映射关系 |

为什么需要这些？

因为在普通 Transformer 里，输入可能只是：

```python
model(input_ids, attention_mask)
```

但在高性能推理服务里，batch 中每个请求的长度不同、状态不同、KV Cache 位置不同。vLLM 必须把这些动态状态整理成 attention kernel 能高效使用的数据结构。

---

### 5.3 Prefill 与 Decode 在输入构建上的区别

#### Prefill

Prefill 处理的是 prompt token。

特点：

- 一次可能处理多个 token；
- 主要是计算密集型；
- 会为 prompt 中每个 token 写入 KV Cache；
- 会得到最后一个位置的 logits，用于生成第一个输出 token。

示例：

```text
prompt: "Hello world, I am"
tokens: [101, 202, 303, 404]

prefill forward:
input_ids = [101, 202, 303, 404]
positions = [0, 1, 2, 3]
```

---

#### Decode

Decode 处理的是模型刚生成的新 token。

特点：

- 通常每个请求每轮只处理 1 个 token；
- 主要是 memory bandwidth bound；
- 需要读取历史 KV Cache；
- 生成下一个 token 后继续循环。

示例：

```text
已有上下文 token 数 = 4
上轮生成 token = 505

decode forward:
input_ids = [505]
positions = [4]
```

---

#### vLLM v1 的统一调度视角

vLLM v1 更倾向于从“本轮处理多少 token”的角度统一 prefill 和 decode。

也就是说：

```text
prefill: 本轮处理多个 prompt token
decode: 本轮处理一个 generated token
```

它们都可以被抽象成：

```text
request_id → num_tokens_to_compute
```

这样 Scheduler 更容易把两类任务混合在一个 step 中处理。

---

### 5.4 Attention Metadata 的作用

Attention metadata 是 ModelRunner 构造给 attention backend 的“说明书”。

它告诉 attention kernel：

1. 当前 batch 有几个请求；
2. 每个请求当前处理哪些 token；
3. 每个请求历史 KV Cache 在哪些 block；
4. 每个 token 的 KV 要写到哪里；
5. 每个请求的 query 起始位置；
6. 哪些 token 属于 prefill，哪些属于 decode；
7. 使用哪个 attention backend。

常见字段包括：

```text
query_start_loc
seq_lens
block_tables
slot_mapping
context_lens
max_query_len
max_seq_len
```

这里的关键理解是：

> **attention kernel 不知道“请求”这个业务概念，它只认识张量、地址、长度和映射关系。ModelRunner 的工作就是把请求状态翻译成这些底层张量。**

---

### 5.5 `block_tables` 和 `slot_mapping` 的区别

这是面试高频点。

#### `block_tables`

`block_tables` 是 block 级别映射。

它回答：

> 某个请求的第 i 个逻辑 KV block 存在哪个物理 block？

例如：

```text
Request A:
logical block 0 → physical block 5
logical block 1 → physical block 9

block_table[A] = [5, 9]
```

---

#### `slot_mapping`

`slot_mapping` 是 token 级别映射。

它回答：

> 当前这个 token 的 KV 应该写入物理 KV Cache 中哪个具体 slot？

假设：

```text
block_size = 16
physical block id = 9
token offset in block = 3
```

那么这个 token 的 KV 会写入：

```text
physical block 9 的第 3 个 token slot
```

一句话总结：

```text
block_table：请求级 / block 级，描述历史 KV 在哪些物理 block。
slot_mapping：token 级，描述当前 token 的 KV 写到哪个具体位置。
```

---

## 6. 模型的执行、更新请求与模型输入构建

### 6.1 模型 forward 的执行链路

ModelRunner 构建好输入后，会调用模型 forward：

```text
input_ids + positions + kv_caches + attn_metadata
        ↓
model.forward(...)
        ↓
hidden_states
        ↓
lm_head
        ↓
logits
        ↓
sampler
        ↓
next_token_ids
```

对于 Transformer decoder-only 模型，内部大致是：

```text
Embedding
  ↓
Layer 0
  ├── RMSNorm / LayerNorm
  ├── Self-Attention
  │     ├── QKV projection
  │     ├── RoPE
  │     ├── 写入当前 token 的 K/V 到 KV Cache
  │     ├── 读取历史 K/V
  │     └── attention output
  ├── Residual
  ├── MLP
  └── Residual
  ↓
...
  ↓
Final norm
  ↓
LM Head
  ↓
Logits
```

---

### 6.2 Attention 执行时 KV Cache 如何参与

以 decode 为例，当前请求已经有 100 个历史 token，本轮输入 1 个 token。

普通 Transformer 如果没有 KV Cache，可能需要重新计算前 100 个 token 的 K/V。

有 KV Cache 后：

```text
当前 token:
  计算 Q, K, V

历史 token:
  直接从 KV Cache 读取 K, V

Attention:
  当前 Q 和 历史 K/V + 当前 K/V 做注意力计算
```

这样就避免了重复计算历史 token 的 K/V。

在 vLLM 中，这些历史 K/V 可能存放在多个不连续的 physical block 里，所以 attention kernel 必须通过 block table 找到它们。

---

### 6.3 Sampler 如何生成新 token

模型 forward 输出 logits：

```text
logits shape ≈ [num_tokens, vocab_size]
```

Sampler 会根据 sampling parameters 选择下一个 token：

- greedy decoding
- temperature
- top-k
- top-p
- repetition penalty
- stop token / EOS 判断

对于每个请求，Sampler 生成一个 token：

```text
Request A → token 501
Request B → token 1024
Request C → token 2(EOS)
```

---

### 6.4 EngineCore 如何更新请求状态

采样得到新 token 后，EngineCore 会更新请求状态：

```text
output_token_ids.append(new_token)
num_computed_tokens += 本轮处理的 token 数
```

同时判断：

1. 是否生成 EOS；
2. 是否达到 `max_tokens`；
3. 是否命中 stop string；
4. 是否被取消；
5. 是否发生错误；
6. 是否需要继续下一轮 decode。

如果请求结束：

```text
释放 KV Cache block
从 running 队列移除
构造最终 RequestOutput
```

如果请求未结束：

```text
保留请求状态
下一轮继续参与调度
```

---

### 6.5 流式输出如何发生

在线服务中，用户看到的效果是：

```text
v
vL
vLL
vLLM
...
```

或者一个 token 一个 token 地返回。

内部流程是：

```text
Sampler 生成 token id
    ↓
EngineCore 返回增量输出
    ↓
API Server detokenize
    ↓
SSE / HTTP chunk 推送给客户端
```

这里要注意：

> **流式输出不是模型一次生成完整答案后再返回，而是每次 decode step 产生新 token 后，就可以把增量 token 返回给用户。**

---

## 7. 完整技术主线：从输入到输出

下面用一条完整链路串起来。

### 7.1 在线服务完整链路

```text
1. 用户通过 OpenAI API 发送 messages
2. API Server 接收 HTTP 请求
3. API Server 渲染 chat template
4. tokenizer 把文本转成 token ids
5. API Server 创建 request_id 和 sampling_params
6. 请求通过 IPC/ZMQ 发送到 EngineCore
7. EngineCore 把请求加入 waiting/running 状态管理
8. Scheduler 在每个 step 决定本轮执行哪些请求、多少 token
9. KVCacheManager 为请求分配或复用 KV Cache block
10. Scheduler 产出 schedule_output
11. Executor 把 schedule_output 分发给 Worker
12. Worker 调用 ModelRunner
13. ModelRunner 构建 input_ids、positions、block_tables、slot_mapping、attention metadata
14. ModelRunner 调用 model.forward
15. Attention kernel 根据 block table 读取历史 KV Cache，并把当前 K/V 写入 slot
16. 模型输出 logits
17. Sampler 根据采样参数生成 next token
18. Worker 返回 token 给 Executor
19. Executor 汇总结果给 EngineCore
20. EngineCore 更新请求状态
21. 如果请求未结束，下一轮继续调度
22. 如果开启 streaming，API Server detokenize 增量 token 并返回客户端
23. 如果请求结束，释放 KV Cache block 并返回最终结果
```

---

## 8. 本节课必须掌握的核心结论

### 8.1 vLLM 架构不是单层模型调用

很多初学者会以为：

```python
prompt → model.generate() → output
```

但 vLLM 的真实推理服务是：

```text
请求接收
  → 请求调度
  → KV Cache 管理
  → 多 Worker 分发
  → 模型输入构建
  → GPU forward
  → 采样
  → 请求状态更新
  → 流式返回
```

---

### 8.2 EngineCore 不直接做模型计算

EngineCore 负责调度和状态管理，但真正的 GPU forward 在 Worker / ModelRunner / Model 中完成。

```text
EngineCore：决定做什么
Executor：把任务发下去
Worker：在某张 GPU 上执行
ModelRunner：准备输入并调用模型
Model：实际 forward
```

---

### 8.3 ModelRunner 是源码学习重点

如果你想真正看懂 vLLM 推理过程，ModelRunner 是核心入口之一。

你需要重点关注：

- 它如何维护 persistent batch；
- 它如何根据 schedule_output 更新输入；
- 它如何构造 attention metadata；
- 它如何处理 prefill/decode；
- 它如何调用模型；
- 它如何调用 sampler；
- 它如何返回结果。

---

### 8.4 KV Cache 管理贯穿整个执行链路

KV Cache 不是一个孤立优化，它影响：

- Scheduler 能否接收新请求；
- 请求是否能继续 decode；
- block table 如何构建；
- slot mapping 如何构建；
- attention kernel 如何读取历史 K/V；
- 请求结束后显存如何释放；
- 系统最大并发和吞吐。

---

## 9. 面试题与参考答案

### Q1：请你从整体上讲一下 vLLM v1 的架构。

**参考答案：**

vLLM v1 可以从入口层、引擎层、调度层、执行层和模型层来理解。入口层包括离线推理的 `LLM` 和在线服务的 OpenAI-compatible API Server；API Server 负责接收 HTTP 请求、tokenization、多模态预处理和流式返回。请求进入 EngineCore 后，EngineCore 负责维护请求状态、运行 Scheduler、管理 KV Cache，并通过 Executor 调用 GPU Worker。每个 GPU Worker 内部有一个 ModelRunner，ModelRunner 构建模型输入和 attention metadata，然后调用模型 forward 和 sampler 生成新 token。最后结果回到 EngineCore，再返回 API Server，detokenize 后流式输出给用户。

---

### Q2：API Server 和 EngineCore 的区别是什么？

**参考答案：**

API Server 是服务入口，负责 HTTP 协议、OpenAI API 兼容、tokenization、chat template、多模态预处理和响应返回。EngineCore 是推理核心，负责请求状态管理、调度、KV Cache 管理和驱动模型执行。API Server 不直接做模型 forward，EngineCore 也不直接处理 HTTP，它们通过 IPC/ZMQ 通信解耦。

---

### Q3：Scheduler 在 vLLM 中负责什么？

**参考答案：**

Scheduler 负责决定每一轮推理 step 中哪些请求被执行，以及每个请求执行多少 token。它会综合 token budget、sequence budget、KV Cache 空间、prefill/decode 状态、chunked prefill、prefix cache 命中等因素。vLLM v1 中，Scheduler 倾向于把 prompt token 和 output token 统一成“本轮要计算的 token 数”，这使得 prefill、decode、chunked prefill 等任务可以统一调度。

---

### Q4：Executor、Worker、ModelRunner 的关系是什么？

**参考答案：**

Executor 是 EngineCore 和 Worker 之间的执行分发层，负责把调度结果发送给 Worker，并收集执行结果。Worker 通常对应一个 GPU 进程，负责加载权重、管理 GPU 资源、持有 ModelRunner。ModelRunner 是 Worker 内真正组织模型执行的组件，负责构建输入张量、attention metadata、调用模型 forward 和 sampler。简单说：Executor 负责分发，Worker 负责承载 GPU 执行，ModelRunner 负责具体组织模型推理。

---

### Q5：为什么 vLLM 需要 Worker？不能 EngineCore 直接调用模型吗？

**参考答案：**

单卡简单场景下看起来可以直接调用模型，但生产级推理需要支持多 GPU、tensor parallel、pipeline parallel、data parallel、异步通信、独立 GPU 进程和资源隔离。Worker 把每张 GPU 的执行逻辑封装起来，EngineCore 只需要做调度和状态管理，Executor 负责分发给不同 Worker。这样架构更清晰，也更容易支持多卡和多进程。

---

### Q6：ModelRunner 为什么重要？

**参考答案：**

因为模型 forward 前需要把动态请求状态转换成模型可执行的张量。vLLM 的 batch 中每个请求长度不同、KV Cache block 不同、position 不同、采样参数不同。ModelRunner 负责构建 `input_ids`、`positions`、`block_tables`、`slot_mapping`、attention metadata 等输入，并调用模型和 sampler。因此它是从调度层到模型层的关键桥梁。

---

### Q7：`block_table` 和 `slot_mapping` 有什么区别？

**参考答案：**

`block_table` 是 block 级别映射，表示某个请求的逻辑 block 对应哪个物理 KV Cache block。`slot_mapping` 是 token 级别映射，表示当前 token 的 K/V 应该写入物理 KV Cache 中哪个具体 slot。前者主要用于读取历史 KV Cache，后者主要用于写入当前 token 的 KV Cache。

---

### Q8：vLLM 中 prefill 和 decode 有什么区别？

**参考答案：**

Prefill 处理用户 prompt，通常一次处理多个 token，是计算密集型，会把 prompt token 的 K/V 写入 KV Cache，并产生第一个输出 token 的 logits。Decode 处理模型生成阶段，通常每个请求每轮只处理一个 token，是 memory bandwidth bound，需要读取历史 KV Cache，并生成下一个 token。vLLM v1 在调度上弱化两者边界，把它们统一成每个请求本轮需要计算多少 token。

---

### Q9：为什么 decode 阶段通常更容易成为 memory-bound？

**参考答案：**

Decode 每轮通常只输入一个新 token，计算量相对小，但需要读取该请求历史上下文的 KV Cache。随着上下文变长，读取 K/V 的显存带宽开销很大，而矩阵计算规模较小，所以更容易受显存带宽限制。Prefill 一次处理很多 token，矩阵乘法规模大，GPU 计算单元利用率更高，通常更偏 compute-bound。

---

### Q10：为什么 vLLM 使用多进程架构？

**参考答案：**

多进程架构可以把 HTTP 服务、tokenization、调度、GPU 执行等任务拆开，减少互相阻塞，并提高 CPU 和 GPU 的重叠执行效率。API Server 可以专注处理请求和流式返回，EngineCore 专注调度和 KV Cache 管理，Worker 专注 GPU forward。这样既提升吞吐，也让架构职责更清晰。

---

### Q11：vLLM v1 相比 v0 的架构变化重点是什么？

**参考答案：**

vLLM v1 重新设计了 scheduler、KV cache manager、worker、sampler 和 API server 等核心组件。它强调更模块化、更低 CPU overhead、更统一的调度表示，并通过 EngineCore 独立执行循环、worker 侧缓存请求状态、persistent batch、prefix caching 优化、torch.compile 和 piecewise CUDA graph 等方式提升整体性能和可维护性。

---

### Q12：一次请求什么时候释放 KV Cache？

**参考答案：**

当请求完成时释放 KV Cache。完成条件可能包括生成 EOS token、达到 `max_tokens`、命中 stop string、客户端取消请求或出现错误。释放后，对应物理 block 回到 free block pool，可以被其他请求复用。

---

### Q13：vLLM 为什么适合高并发服务？

**参考答案：**

核心原因包括：PagedAttention 提高 KV Cache 显存利用率；continuous batching 让不同请求可以动态加入 batch；Scheduler 能在每个 step 重新选择请求；多进程架构让请求处理和模型执行解耦；多 GPU worker 支持张量并行和数据并行；流式输出降低用户感知延迟。

---

### Q14：如果面试官问“vLLM 的推理流程”，你应该怎么答？

**参考答案：**

我会从请求入口开始讲：用户请求先进入 API Server，经过 chat template、tokenization 和参数解析后发送给 EngineCore。EngineCore 将请求加入内部队列，并在每个 step 调用 Scheduler 决定哪些请求执行多少 token。Scheduler 同时通过 KVCacheManager 分配或复用 KV Cache block，形成调度输出。Executor 把调度输出分发给 GPU Worker，Worker 内部的 ModelRunner 构建 `input_ids`、`positions`、`block_tables`、`slot_mapping` 和 attention metadata，然后调用模型 forward。模型输出 logits 后由 sampler 生成新 token，结果返回 EngineCore 更新请求状态。如果请求未结束继续下一轮调度；如果结束则释放 KV Cache。在线服务场景下，新 token 会被 detokenize 并流式返回给客户端。

---
