## 1. Attention 算子成为性能瓶颈的原因

### 1.1 Transformer 推理中的主要计算

一个 Decoder-only LLM 的每层大致包含：

```text
输入 hidden states
    ↓
RMSNorm / LayerNorm
    ↓
QKV projection
    ↓
Attention
    ↓
O projection
    ↓
MLP / FFN / MoE
    ↓
输出 hidden states
```

其中 Attention 相关计算包括：

```text
Q = XWq
K = XWk
V = XWv

scores = QK^T / sqrt(d)
probs = softmax(scores)
out = probs V
```

在 **prefill 阶段**，输入 prompt 通常较长，`QK^T` 的复杂度随序列长度平方增长。  
在 **decode 阶段**，每次通常只生成一个 token，当前 query 很少，但要读取历史所有 token 的 KV Cache，因此经常是 **memory bandwidth bound**。

---

### 1.2 为什么 Attention 容易成为瓶颈

#### 第一，计算复杂度高

标准 self-attention 的核心 `QK^T` 在 prefill 阶段接近：

```text
O(seq_len^2 * head_dim)
```

例如：

```text
seq_len = 4096
attention score shape = [4096, 4096]
```

如果直接 materialize 出整个 score 矩阵，会产生巨大的中间张量。

#### 第二，中间张量读写开销大

朴素 PyTorch 写法：

```python
scores = q @ k.transpose(-2, -1)
scores = scores / math.sqrt(head_dim)
probs = torch.softmax(scores, dim=-1)
out = probs @ v
```

这会隐含多个中间张量：

```text
scores
scaled_scores
probs
out
```

每一步都可能触发 global memory 的读写。GPU 算力很强，但 global memory 访问相对昂贵。很多推理算子真正慢的地方不是“算不动”，而是“数据搬运太多”。

#### 第三，decode 阶段 KV Cache 访问复杂

vLLM 使用 PagedAttention 管理 KV Cache。KV Cache 会被切成 block：

```text
logical block 0 → physical block 7
logical block 1 → physical block 2
logical block 2 → physical block 15
```

这种管理方式可以提高显存利用率，但 attention kernel 需要通过 `block_table` 找到物理块位置。

因此 vLLM 的 attention 不只是普通 `QK^T`，还要处理：

```text
block_table
slot_mapping
query_start_loc
seq_lens
KV cache layout
prefill/decode 不同路径
```

---

### 1.3 为什么不能只依赖 PyTorch

PyTorch 适合表达模型结构，但推理框架需要极致性能时，PyTorch 原生算子有三个局限：

| 问题 | 解释 |
|---|---|
| 算子粒度偏粗 | PyTorch 更像在调用一个个现成算子，不容易把多个步骤深度融合 |
| 中间张量多 | Softmax、mask、scale、matmul 分开执行时会产生大量内存读写 |
| 难处理特殊 layout | vLLM 的 paged KV cache、block table、ragged batch 等结构不是普通 dense tensor |

所以高性能推理框架通常会写自定义 kernel，例如：

```text
FlashAttention kernel
PagedAttention kernel
RMSNorm kernel
RoPE kernel
Sampling kernel
MoE routing kernel
Quantized GEMM kernel
```

## 2. OpenAI Triton 定义与核心特性

### 2.1 Triton 是什么

Triton 是一种用于编写高性能 GPU kernel 的 Python-like DSL 和编译器。它的目标是：

> 用比 CUDA 更高的开发效率，写出接近 CUDA 手写 kernel 性能的深度学习算子。

可以这样理解：

```text
PyTorch：调用已有 GPU 算子
Triton：自己写 GPU 算子，但仍然用 Python-like 语法
CUDA：用 C++/CUDA 直接写底层 GPU kernel
```

Triton 的核心价值：

1. **比 PyTorch 更底层**：可以控制每个 program 处理哪些数据块；
2. **比 CUDA 更高层**：不需要手写过多 thread、block、shared memory 细节；
3. **支持 JIT 编译**：首次运行时根据 shape、dtype、meta 参数编译 kernel；
4. **适合深度学习算子**：尤其适合 matmul、softmax、attention、normalization、elementwise fusion；
5. **便于快速实验**：适合推理框架中开发新 kernel 或做算法验证。

---

### 2.2 Triton 的基本编程模型

一个 Triton kernel 通常长这样：

```python
import triton
import triton.language as tl

@triton.jit
def kernel(x_ptr, y_ptr, out_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)

    offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
    mask = offsets < n_elements

    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)

    out = x + y

    tl.store(out_ptr + offsets, out, mask=mask)
```

核心概念如下：

| 概念 | 作用 |
|---|---|
| `@triton.jit` | 把 Python-like 函数 JIT 编译成 GPU kernel |
| `tl.program_id(axis=0)` | 当前 program/block 的编号 |
| `tl.arange` | 在一个 program 内生成向量化 offsets |
| `tl.load` | 从 global memory 读取数据 |
| `tl.store` | 向 global memory 写回数据 |
| `mask` | 防止越界访问 |
| `tl.constexpr` | 编译期常量，用于 kernel specialization |
| grid | 指定启动多少个 Triton program |

Triton 的一个 `program` 可以粗略类比 CUDA 里的一个 thread block，但 Triton 直接以“向量/块”的方式写程序，而不是逐个 thread 写。

## 3. Triton 与 CUDA 的差异

### 3.1 CUDA 的特点

CUDA 是 NVIDIA GPU 编程的底层主流方案，特点是：

```text
性能上限高
控制粒度细
开发难度高
调试复杂
对 GPU 架构理解要求高
```

写 CUDA kernel 时通常要直接考虑：

```text
threadIdx / blockIdx
warp
shared memory
bank conflict
register pressure
occupancy
memory coalescing
synchronization
```

### 3.2 Triton 的特点

Triton 仍然写 GPU kernel，但抽象层级更高。你通常不直接写：

```text
threadIdx
warp 内具体线程编号
shared memory 分配细节
```

而是写：

```text
当前 program 处理一个 block 的数据
这个 block 内用向量化方式加载、计算、存储
```

### 3.3 PyTorch / Triton / CUDA 对比

| 维度 | PyTorch | Triton | CUDA |
|---|---|---|---|
| 抽象层级 | 高 | 中 | 低 |
| 开发语言 | Python | Python-like DSL | C++/CUDA |
| 是否能写自定义 GPU kernel | 间接 | 是 | 是 |
| 开发难度 | 低 | 中 | 高 |
| 性能上限 | 依赖已有算子 | 高 | 最高 |
| 算子融合能力 | 有限 | 强 | 最强 |
| 调试难度 | 低 | 中 | 高 |
| 适合场景 | 模型搭建、训练、常规推理 | 自定义深度学习 kernel | 极致优化、底层平台开发 |

一句话总结：

> **PyTorch 负责表达模型，CUDA 负责极致底层性能，Triton 是二者之间的高性能开发折中点。**

## 4. Triton 编译过程

### 4.1 从 Python 函数到 GPU 执行

Triton kernel 不是普通 Python 函数。它的执行过程大致是：

```text
Python 代码定义 kernel
        ↓
@triton.jit 捕获 kernel 函数
        ↓
根据输入 shape、dtype、constexpr 参数做 specialization
        ↓
生成 Triton IR / MLIR 相关中间表示
        ↓
经过编译优化和 lowering
        ↓
生成目标 GPU 后端代码，例如 PTX / AMD GPU 目标代码
        ↓
launch kernel 到 GPU
```

这就是为什么 Triton 第一次运行某个 kernel 时可能会慢一些，因为要编译；后续如果 shape 和 meta 参数相同，通常可以复用编译缓存。

### 4.2 `tl.constexpr` 为什么重要

```python
BLOCK_SIZE: tl.constexpr
```

表示 `BLOCK_SIZE` 是编译期常量。编译器可以在编译时知道：

```text
每个 program 处理多少元素
tl.arange 的长度
mask 的 shape
向量化长度
```

这样编译器可以做更多优化。

### 4.3 编译过程和推理系统的关系

在 vLLM 这类推理服务中，编译开销很重要。如果一个 Triton kernel 因为 shape 多变而频繁重新编译，会影响线上请求延迟。

生产系统通常关注：

```text
kernel cache
shape specialization
autotuning
warmup
benchmark
不同 batch / seq_len / block_size 下的 kernel 选择
```

## 5. 第一个 Triton 算子：一维向量相加

### 5.1 任务定义

输入：

```text
x: [N]
y: [N]
```

输出：

```text
out[i] = x[i] + y[i]
```

这是最简单的 Triton kernel，核心是理解：

```text
每个 program 负责一段连续元素
用 offsets 计算当前 program 要处理的数据位置
用 mask 处理边界
```

### 5.2 PyTorch 实现

```python
import torch

def torch_add(x, y):
    return x + y
```

### 5.3 Triton 实现

```python
import torch
import triton
import triton.language as tl

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n_elements, BLOCK_SIZE: tl.constexpr):
    pid = tl.program_id(axis=0)

    block_start = pid * BLOCK_SIZE
    offsets = block_start + tl.arange(0, BLOCK_SIZE)

    mask = offsets < n_elements

    x = tl.load(x_ptr + offsets, mask=mask)
    y = tl.load(y_ptr + offsets, mask=mask)

    out = x + y

    tl.store(out_ptr + offsets, out, mask=mask)


def add(x: torch.Tensor, y: torch.Tensor):
    assert x.is_cuda and y.is_cuda
    assert x.shape == y.shape

    out = torch.empty_like(x)
    n_elements = x.numel()

    BLOCK_SIZE = 1024
    grid = (triton.cdiv(n_elements, BLOCK_SIZE),)

    add_kernel[grid](x, y, out, n_elements, BLOCK_SIZE=BLOCK_SIZE)

    return out
```

### 5.4 关键解释

#### `grid`

```python
grid = (triton.cdiv(n_elements, BLOCK_SIZE),)
```

表示启动多少个 Triton program。

如果：

```text
n_elements = 10000
BLOCK_SIZE = 1024
```

则：

```text
grid = ceil(10000 / 1024) = 10
```

也就是启动 10 个 program。

#### `pid`

```python
pid = tl.program_id(axis=0)
```

表示当前 program 的编号。

```text
pid = 0 → 处理 [0, 1024)
pid = 1 → 处理 [1024, 2048)
pid = 2 → 处理 [2048, 3072)
```

#### `offsets`

```python
offsets = pid * BLOCK_SIZE + tl.arange(0, BLOCK_SIZE)
```

如果 `pid = 2`，`BLOCK_SIZE = 1024`：

```text
offsets = [2048, 2049, ..., 3071]
```

#### `mask`

```python
mask = offsets < n_elements
```

最后一个 block 可能不满，mask 用来避免越界读写。

## 6. 更复杂的 Softmax 算子：PyTorch vs Triton

### 6.1 Softmax 公式

对一行向量 `x`：

```text
softmax(x_i) = exp(x_i - max(x)) / sum_j exp(x_j - max(x))
```

减去 `max(x)` 是为了数值稳定，避免指数爆炸。

### 6.2 PyTorch 实现

```python
import torch

def torch_softmax(x):
    return torch.softmax(x, dim=-1)
```

### 6.3 Triton 实现思路

假设输入：

```text
x: [M, N]
```

我们让每个 Triton program 处理一行：

```text
program 0 → 第 0 行
program 1 → 第 1 行
```

Triton kernel：

```python
@triton.jit
def softmax_kernel(x_ptr, out_ptr, n_cols: tl.constexpr, BLOCK_SIZE: tl.constexpr):
    row_id = tl.program_id(axis=0)

    offsets = tl.arange(0, BLOCK_SIZE)
    row_start = row_id * n_cols

    mask = offsets < n_cols

    x = tl.load(x_ptr + row_start + offsets, mask=mask, other=-float("inf"))

    x = x - tl.max(x, axis=0)
    numerator = tl.exp(x)
    denominator = tl.sum(numerator, axis=0)
    y = numerator / denominator

    tl.store(out_ptr + row_start + offsets, y, mask=mask)
```

### 6.4 为什么 Triton Softmax 可能更快

Softmax 包含多个步骤：

```text
max
subtract
exp
sum
divide
store
```

Triton 可以把这些操作融合到一个 kernel 中：

```text
从 global memory 读一行
在寄存器/片上存储中完成 max、exp、sum、divide
最后写回一次
```

减少中间张量读写，就是性能提升的关键。

### 6.5 Softmax 和 Attention 的关系

Attention 中最关键的归一化就是：

```text
softmax(QK^T / sqrt(d))
```

在 FlashAttention / PagedAttention 中，真正高效的地方不是简单调用 softmax，而是：

```text
边算 QK^T
边做 online softmax
边乘 V
避免完整 materialize attention score 矩阵
```

## 7. 实现 Matmul 算子

### 7.1 Matmul 任务

输入：

```text
A: [M, K]
B: [K, N]
```

输出：

```text
C: [M, N]
C[i, j] = sum_k A[i, k] * B[k, j]
```

Matmul 是 LLM 中最重要的算子之一：

```text
QKV projection
O projection
FFN up projection
FFN down projection
lm_head
quantized GEMM
```

### 7.2 Triton Matmul 的核心思想：tiling

不要一个 program 只算一个元素，而是让一个 program 计算 C 的一个小块：

```text
BLOCK_M × BLOCK_N
```

然后沿 K 维度分块累加：

```text
for k in range(0, K, BLOCK_K):
    A_tile = A[m_offsets, k_offsets]
    B_tile = B[k_offsets, n_offsets]
    acc += dot(A_tile, B_tile)
```

### 7.3 Triton Matmul 核心骨架

```python
@triton.jit
def matmul_kernel(
    a_ptr, b_ptr, c_ptr,
    M: tl.constexpr, N: tl.constexpr, K: tl.constexpr,
    stride_am: tl.constexpr, stride_ak: tl.constexpr,
    stride_bk: tl.constexpr, stride_bn: tl.constexpr,
    stride_cm: tl.constexpr, stride_cn: tl.constexpr,
    BLOCK_M: tl.constexpr,
    BLOCK_N: tl.constexpr,
    BLOCK_K: tl.constexpr,
):
    pid = tl.program_id(axis=0)
    num_pid_n = tl.cdiv(N, BLOCK_N)

    pid_m = pid // num_pid_n
    pid_n = pid % num_pid_n

    offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)
    offs_n = pid_n * BLOCK_N + tl.arange(0, BLOCK_N)
    offs_k = tl.arange(0, BLOCK_K)

    acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)

    for k_start in range(0, K, BLOCK_K):
        a = tl.load(
            a_ptr + offs_m[:, None] * stride_am + (k_start + offs_k[None, :]) * stride_ak,
            mask=(offs_m[:, None] < M) & ((k_start + offs_k[None, :]) < K),
            other=0.0,
        )
        b = tl.load(
            b_ptr + (k_start + offs_k[:, None]) * stride_bk + offs_n[None, :] * stride_bn,
            mask=((k_start + offs_k[:, None]) < K) & (offs_n[None, :] < N),
            other=0.0,
        )
        acc += tl.dot(a, b)

    tl.store(
        c_ptr + offs_m[:, None] * stride_cm + offs_n[None, :] * stride_cn,
        acc,
        mask=(offs_m[:, None] < M) & (offs_n[None, :] < N),
    )
```

### 7.4 Matmul 的性能关键点

Matmul 优化通常关注：

```text
BLOCK_M / BLOCK_N / BLOCK_K
num_warps
num_stages
memory coalescing
shared memory / SRAM reuse
register pressure
occupancy
tensor core 使用
```

Triton 中 `tl.dot` 会映射到底层矩阵乘指令或对应后端实现。

## 8. 实现 Attention 算子

### 8.1 朴素 Attention 的问题

朴素实现：

```python
scores = q @ k.transpose(-2, -1)
scores = scores / math.sqrt(head_dim)
probs = torch.softmax(scores, dim=-1)
out = probs @ v
```

问题是：

```text
scores 矩阵太大
softmax 需要额外中间张量
global memory 读写太多
causal mask / padding mask 增加复杂度
decode 阶段需要访问 KV Cache
```

### 8.2 FlashAttention 思想

FlashAttention 的核心思想不是改变数学公式，而是改变计算方式：

```text
不完整存储 attention score 矩阵
按 tile 分块处理 Q/K/V
用 online softmax 维护局部 max 和 sum
把 QK^T、softmax、乘 V 融合进一个 kernel
```

公式上仍然是：

```text
softmax(QK^T / sqrt(d))V
```

但执行上变成：

```text
分块读 K/V
计算局部 score
更新 online softmax 统计量
累积输出
最后写回 out
```

### 8.3 Attention kernel 需要处理哪些输入

一个推理框架中的 Attention kernel 往往不只是 `q, k, v` 三个张量。

它还可能需要：

```text
q
k
v
kv_cache
block_tables
slot_mapping
seq_lens
query_start_loc
context_lens
alibi_slopes
scaling
causal mask
sliding window
softcap
```

在 vLLM 中尤其重要的是：

```text
block_tables: 逻辑 block 到物理 block 的映射
slot_mapping: token 到 KV cache slot 的映射
query_start_loc: 拼接 batch 中每个请求 query 的起止位置
```

这些元数据让 kernel 能在 paged KV cache 上正确访问每个请求的历史 K/V。

### 8.4 Triton Attention 的高层伪代码

```text
for each query block:
    初始化 m_i = -inf
    初始化 l_i = 0
    初始化 acc = 0

    for each key/value block:
        根据 block_table 找到物理 KV cache block
        加载 K tile 和 V tile
        score = Q tile @ K tile^T * scale
        应用 causal mask / padding mask

        m_new = max(m_i, max(score))
        p = exp(score - m_new)

        alpha = exp(m_i - m_new)
        acc = acc * alpha + p @ V
        l_i = l_i * alpha + sum(p)
        m_i = m_new

    out = acc / l_i
    store out
```

这就是 online softmax 的核心逻辑。

### 8.5 Prefill Attention 和 Decode Attention 的差异

| 阶段 | Q 数量 | K/V 来源 | 主要瓶颈 | kernel 特点 |
|---|---:|---|---|---|
| Prefill | prompt 中多个 token | 当前 prompt 的 K/V | 计算量大 | 更像长序列 attention，计算密集 |
| Decode | 通常每请求 1 个新 token | 历史 KV Cache + 当前 token | 显存带宽大 | 访问 KV Cache，memory bound |
| Mixed | 部分请求 prefill，部分请求 decode | 两者都有 | 调度复杂 | kernel 需要处理 ragged batch |

## 9. vLLM 中的 Triton Attention 后端

### 9.1 vLLM 为什么需要 Attention backend

vLLM 支持多种模型、多种硬件、多种 attention 实现，因此它需要把 attention 实现抽象成 backend。

不同 backend 可以对应：

```text
FlashAttention
FlashInfer
Triton Attention
ROCm backend
CPU fallback
自定义硬件插件 backend
```

Attention backend 负责根据当前模型、平台、dtype、KV cache layout、prefill/decode 场景选择合适的 kernel。

### 9.2 Triton Attention 后端的定位

Triton Attention 后端的意义是：

1. **降低自定义 attention kernel 的开发门槛**；
2. **提高跨硬件平台可移植性**；
3. **便于快速实验不同 attention 算法**；
4. **为 vLLM platform plugin / attention backend 提供更灵活的实现路径**；
5. **对非 NVIDIA 硬件尤其有价值**，因为 CUDA kernel 不天然跨 AMD/Intel 等平台。

工程上，Triton backend 通常会处理：

```text
kernel 选择
meta 参数生成
autotuning
prefill/decode 区分
block table / kv cache layout 适配
和 vLLM ModelRunner / Attention metadata 对接
```

### 9.3 vLLM Attention 执行链路

结合前面课程，可以把 vLLM 的 Attention 执行链路理解为：

```text
用户请求
    ↓
API Server / LLM 接口
    ↓
Engine
    ↓
Scheduler
    ↓
KV Cache Manager 分配 block
    ↓
构造 attention metadata
    - query_start_loc
    - block_tables
    - slot_mapping
    - seq_lens
    ↓
Executor
    ↓
Worker
    ↓
ModelRunner
    ↓
模型 forward
    ↓
Attention layer
    ↓
Attention backend 选择具体 kernel
    ↓
Triton / CUDA / FlashAttention kernel 执行
    ↓
输出 hidden states
    ↓
Sampler 采样下一个 token
```

其中 Triton kernel 位于最底层的算子执行部分，但它必须理解上层传下来的 metadata。

### 9.4 Triton Attention 和 PagedAttention 的关系

PagedAttention 不是单纯的 “attention 算子”，它包括两层含义：

```text
1. KV Cache 分页管理机制
2. 能够基于 block table 访问非连续 KV Cache 的 attention kernel
```

普通 Attention：

```text
K/V 是连续矩阵
```

PagedAttention：

```text
K/V 存在 KV cache block 中
每个请求的逻辑 block 映射到不同物理 block
kernel 需要通过 block_table 间接寻址
```

这也是 vLLM Attention backend 比普通 PyTorch attention 更复杂的核心原因。

## 10. 从输入到输出串联整节课

### 10.1 用户输入进入 vLLM

用户发出 prompt：

```text
"介绍一下 vLLM"
```

Tokenizer 把文本变成 token ids：

```text
[123, 456, 789, ...]
```

请求进入 Engine，由 Scheduler 决定本轮哪些 token 参与计算。

### 10.2 Scheduler 分配 KV Cache

如果是 prefill，Scheduler 要为 prompt token 分配 KV Cache block。

```text
token ids
    ↓
按 block_size 切分逻辑 block
    ↓
KV Cache Manager 分配物理 block
    ↓
生成 block_table / slot_mapping
```

### 10.3 ModelRunner 构建模型输入

ModelRunner 把调度结果转换成模型可执行输入：

```text
input_ids
positions
attention metadata
kv cache pointers
block_tables
slot_mapping
query_start_loc
```

这一步是上层调度和底层算子之间的桥梁。

### 10.4 Attention backend 执行

模型进入 attention layer。

如果选择 Triton backend，那么会调用 Triton kernel：

```text
加载 Q
根据 block_table 访问 K/V cache
执行 QK^T
执行 mask
执行 online softmax
执行 weighted sum with V
写回输出 hidden states
```

在 decode 阶段，它通常只对新 token 的 Q 做计算，但要读取历史所有 K/V。

### 10.5 后续层和采样

Attention 输出继续进入：

```text
O projection
MLP / MoE
下一层 Transformer
最终 lm_head
Sampler
```

Sampler 根据 logits 和采样参数选择下一个 token：

```text
greedy / temperature / top-p / top-k / repetition penalty
```

如果流式输出开启，生成一个 token 后就可以返回增量结果。

## 11. 面试高频问题与参考答案

### Q1：为什么大模型推理框架需要自定义算子？

**答：**  
因为 PyTorch 原生算子虽然易用，但在推理服务中经常存在算子粒度过粗、中间张量读写多、无法适配特殊 KV Cache layout 等问题。LLM 推理需要处理 FlashAttention、PagedAttention、RMSNorm、RoPE、Sampling、量化 GEMM 等高频热点算子，这些算子如果不融合、不针对内存访问优化，性能会受到显存带宽和 kernel launch overhead 限制。因此 vLLM 这类框架需要 CUDA、Triton 或其他 backend 实现自定义高性能 kernel。

### Q2：Triton 和 CUDA 的区别是什么？

**答：**  
CUDA 是更底层的 GPU 编程模型，需要显式管理 thread/block、shared memory、warp、同步等细节，性能上限高但开发成本也高。Triton 是 Python-like DSL，开发者以 program/tile 的方式表达计算，用 `tl.load`、`tl.store`、`tl.dot` 等高层原语写 kernel，由 Triton 编译器 lowering 到目标 GPU 代码。Triton 的性能通常可以接近手写 CUDA，同时开发效率更高，适合深度学习算子快速开发和跨硬件适配。

### Q3：Triton 中 `program_id` 是什么？

**答：**  
`tl.program_id(axis=0)` 表示当前 Triton program 在 grid 中的编号。一个 program 通常负责处理一个数据块，比如向量加法中的一段连续元素、softmax 中的一行、matmul 输出矩阵中的一个 tile。通过 `program_id` 可以计算当前 program 处理的 offsets。

### Q4：为什么 Triton kernel 常常需要 mask？

**答：**  
因为输入长度不一定刚好是 `BLOCK_SIZE` 的整数倍。最后一个 block 可能越界。mask 用来告诉 `tl.load` 和 `tl.store` 哪些位置合法，防止访问非法地址。

### Q5：`tl.constexpr` 的作用是什么？

**答：**  
`tl.constexpr` 表示编译期常量。Triton 编译器可以根据这些常量生成专门优化的 kernel，比如根据 `BLOCK_SIZE` 展开向量长度、推导 shape、优化循环。但不同 constexpr 取值可能触发不同版本的编译。

### Q6：Softmax 为什么适合用 Triton 写？

**答：**  
Softmax 包含 max、subtract、exp、sum、divide 等多个步骤。朴素 PyTorch 实现可能产生多个中间张量并多次读写 global memory。Triton 可以把这些步骤融合在一个 kernel 中，让一行数据在片上完成归一化，减少 global memory 流量，从而提高性能。

### Q7：Matmul 在大模型推理中为什么重要？

**答：**  
LLM 中大量计算都是矩阵乘法，包括 QKV projection、O projection、FFN up/down projection、gate projection、lm_head 等。Prefill 阶段尤其依赖 GEMM 吞吐。Matmul 性能决定了模型在高 batch 或长 prompt 场景下的主要计算效率。

### Q8：Attention 为什么比普通 Matmul 更复杂？

**答：**  
Attention 不只是一个矩阵乘法，它包含 QK^T、scale、mask、softmax、再乘 V，并且还要考虑 causal mask、padding、不同序列长度、prefill/decode 两种执行模式。在 vLLM 中还要处理 paged KV cache，通过 block table 间接访问 K/V，因此比普通 dense matmul 更复杂。

### Q9：FlashAttention 的核心思想是什么？

**答：**  
FlashAttention 的核心是避免完整 materialize attention score 矩阵。它通过 tiling 分块加载 Q/K/V，用 online softmax 维护局部最大值和归一化因子，把 QK^T、softmax、乘 V 融合在一个 kernel 中，减少 global memory 读写。

### Q10：PagedAttention 和普通 Attention 的区别是什么？

**答：**  
普通 Attention 假设 K/V 是连续存储的 dense tensor。PagedAttention 中，KV Cache 被切成固定大小的 block，一个请求的逻辑 block 可以映射到不连续的物理 block。Attention kernel 需要通过 `block_table` 找到每个逻辑块对应的物理 KV cache 位置。因此 PagedAttention 同时包含 KV Cache 分页管理和支持分页寻址的 attention kernel。

### Q11：vLLM 中 `block_table` 和 `slot_mapping` 有什么区别？

**答：**  
`block_table` 是 block 级别映射，表示每个请求的逻辑 block 对应哪个物理 KV cache block。`slot_mapping` 是 token 级别映射，表示每个 token 的 KV 应该写入或读取 KV cache 中的哪个具体 slot。前者用于 attention 读取历史 K/V，后者常用于把当前 token 的 K/V 写入正确位置。

### Q12：Triton Attention backend 在 vLLM 中处于什么位置？

**答：**  
它位于模型 forward 的 Attention layer 内部，是 attention backend 的一种实现。上层的 Scheduler 和 ModelRunner 负责生成 input_ids、positions、KV cache、attention metadata 等信息；Attention backend 根据这些 metadata 调用具体的 Triton kernel 完成 attention 计算。

### Q13：为什么 decode 阶段经常是 memory bound？

**答：**  
Decode 阶段每个请求通常只生成一个新 token，因此当前 Q 的计算量很小，但它需要读取该请求历史上所有 token 的 K/V cache。长上下文下，读取 KV Cache 的显存带宽开销很大，所以 decode 阶段经常受 memory bandwidth 限制。

### Q14：Triton kernel 第一次运行为什么可能慢？

**答：**  
因为 Triton 使用 JIT 编译。第一次遇到某个 kernel 的特定 shape、dtype、constexpr 参数组合时，需要生成和编译 GPU 代码。后续相同配置通常可以复用缓存。线上服务通常会通过 warmup 和固定常见 shape 来减少编译带来的延迟波动。

### Q15：面试中如何一句话总结 Triton 在 vLLM 中的价值？

**答：**  
Triton 让 vLLM 可以用较高开发效率实现接近手写 CUDA 性能的自定义 GPU kernel，尤其适合 Attention、PagedAttention、Softmax、Matmul、RMSNorm、Sampling 等推理热点算子，并且有利于跨硬件后端适配。

## 12. 学习路径建议

如果你是为了 AI Infra 面试，可以按下面顺序学习：

```text
1. 先理解 PyTorch 中 attention / softmax / matmul 的普通实现
2. 学 Triton vector add，掌握 program_id、offsets、mask、load/store
3. 学 Triton softmax，理解 reduction 和 kernel fusion
4. 学 Triton matmul，理解 tiling、BLOCK_M/N/K、tl.dot
5. 学 FlashAttention，理解 online softmax
6. 学 vLLM PagedAttention，理解 block_table 和 KV Cache 分页
7. 看 vLLM Attention backend，理解 Triton kernel 如何接入推理框架
```

学习时不要只背代码，而要始终追问：

```text
这个 kernel 减少了什么内存访问？
这个 kernel 融合了哪些操作？
这个 kernel 的输入 layout 是什么？
这个 kernel 在 prefill 和 decode 中表现有什么区别？
这个 kernel 为什么比 PyTorch 写法更适合推理服务？
```
