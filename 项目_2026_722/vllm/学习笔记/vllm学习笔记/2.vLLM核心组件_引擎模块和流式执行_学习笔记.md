# vLLM 核心组件：引擎模块和流式执行学习笔记

> 课时 02：vLLM 核心组件：引擎模块和流式执行  
> 课程关键词：REQ/REP、DEALER/ROUTER、PULL/PUSH、ZeroMQ、IPC/socket、AsyncLLM、EngineCore、Engine 接收数据、Engine 发送数据、流式输出、请求生命周期、RequestOutput、AsyncStream

---

## 0. 本节课核心目标

本节课讲的是 vLLM 在线推理服务中最靠近“请求入口和结果出口”的部分：**引擎模块与流式执行链路**。

前面理解 Transformer、KV Cache、Scheduler、ModelRunner 时，更多关注的是：

```text
模型怎么计算？
KV Cache 怎么管理？
哪些请求进入本轮 prefill / decode？
GPU Worker 怎么执行 forward？
```

但真实在线推理系统还需要解决一个非常重要的问题：

```text
用户请求从哪里进入？
请求如何跨进程送到 EngineCore？
模型每生成一个 token 后，结果怎么及时返回给用户？
为什么 vLLM 需要 socket / IPC / ZeroMQ？
REQ/REP、DEALER/ROUTER、PULL/PUSH 这些通信模式分别解决什么问题？
```

本节课主线可以概括为：

```text
用户调用 AsyncLLM.generate / OpenAI API
        ↓
AsyncLLM 创建请求流 AsyncStream
        ↓
请求通过 ZMQ socket 发给 EngineCore 进程
        ↓
EngineCore 接收请求并加入调度队列
        ↓
Scheduler / ModelExecutor / Worker / ModelRunner 执行推理
        ↓
每轮生成的 token 被封装成输出对象
        ↓
EngineCore 通过输出 socket 把结果发回 AsyncLLM
        ↓
AsyncLLM 的 output_handler 把结果放入每个请求对应的 AsyncStream
        ↓
API Server / 调用方异步迭代 AsyncGenerator
        ↓
实现流式返回
```

一句话理解本节课：

> **vLLM 的 Engine 不只是“跑模型”的地方，更是请求进入、跨进程通信、调度执行、结果流式返回的中枢。ZeroMQ 的不同 socket pattern 则用于解耦 API Server、AsyncLLM、EngineCore 和输出处理之间的并发通信。**

# 第一部分：为什么 vLLM 需要通信模块？

## 1. 单进程推理和在线推理的区别

最简单的大模型推理代码可能是：

```python
from vllm import LLM, SamplingParams

llm = LLM(model="Qwen/Qwen2.5-7B-Instruct")
outputs = llm.generate(["hello"], SamplingParams(max_tokens=32))
```

这种离线推理看起来像一个普通函数调用：

```text
输入 prompt
  ↓
同步执行推理
  ↓
返回完整结果
```

但在线服务不同。

在线服务要同时处理大量请求：

```text
用户 A 正在流式生成第 10 个 token
用户 B 刚提交一个长 prompt
用户 C 请求取消
用户 D 请求还在排队
用户 E 的请求已经完成
```

此时系统必须支持：

- 多请求并发接入；
- 请求进入后异步执行；
- 每个请求不断产生部分输出；
- 某个请求完成后释放资源；
- 请求取消、超时、异常处理；
- API Server 和 EngineCore 解耦；
- 多进程 / 多 GPU / 多 DP rank 扩展。

因此 vLLM 不能只是一个简单的同步函数，而需要一套异步通信架构。

---

## 2. 为什么要把 API Server 和 EngineCore 分开？

在线 vLLM 通常有不同的进程 / 组件：

```text
API Server Process
  - HTTP 请求处理
  - OpenAI-compatible API
  - tokenizer / input processing
  - 多模态数据加载
  - 流式响应返回

EngineCore Process
  - Scheduler
  - KV Cache 管理
  - 模型执行协调
  - GPU Worker 调用
  - 输出对象生成
```

这样分开的原因是：

1. **隔离 CPU 网络服务和 GPU 推理执行**
   - API Server 处理 HTTP、JSON、tokenizer、streaming；
   - EngineCore 专注调度和模型执行。

2. **避免 API Server 阻塞 GPU 执行**
   - HTTP 请求慢、客户端断开、网络波动不应直接阻塞模型推理核心。

3. **方便多进程扩展**
   - DP 场景下可以有多个 EngineCore；
   - API Server 可以把请求路由给不同 EngineCore。

4. **提高容错和模块边界清晰度**
   - 请求入口、调度核心、GPU worker 分层后，更适合工程维护。

---

## 3. IPC / socket 是什么？

### 3.1 IPC

IPC 是：

```text
Inter-Process Communication
进程间通信
```

因为 API Server 和 EngineCore 可能运行在不同进程中，所以它们不能直接访问彼此的 Python 对象，需要通过某种通信机制交换消息。

常见 IPC 方式包括：

- pipe；
- queue；
- shared memory；
- Unix domain socket；
- TCP socket；
- ZeroMQ；
- gRPC；
- Ray actor；
- multiprocessing queue。

### 3.2 socket

socket 可以理解为进程之间发送消息的“通信端口”。

两个进程通过 socket 连接：

```text
Process A socket  <---- message ---->  Process B socket
```

可以是：

```text
同机器进程间：ipc://...
不同机器之间：tcp://ip:port
进程内线程间：inproc://...
```

vLLM 中常用 ZeroMQ 把这些通信方式封装成更高级的消息模式。

---

## 4. ZeroMQ 是什么？

ZeroMQ，也写作 ZMQ / ØMQ，是一个高性能消息通信库。

它不是传统意义上的消息队列服务器，而是一个可以嵌入应用程序的通信框架。它提供了多种 socket pattern，例如：

```text
REQ/REP      请求-响应
DEALER/ROUTER 异步请求-路由
PUSH/PULL    任务推送-结果拉取
PUB/SUB      发布-订阅
PAIR         点对点
```

在 vLLM 这种推理系统里，ZMQ 的价值是：

- 支持进程间消息传递；
- 支持异步通信；
- 支持多对多连接；
- 比手写 socket 更容易管理消息边界；
- 适合 API Server 和 EngineCore 解耦；
- 支持 request routing 和 streaming output。

---

# 第二部分：REQ/REP 通信模式

## 5. REQ/REP 是什么？

REQ/REP 是最基础的请求-响应模式：

```text
Client REQ  ---- request ---->  Server REP
Client REQ  <---- reply ------  Server REP
```

特点是：

```text
REQ 发送一个请求后，必须等待一个回复；
REP 接收一个请求后，必须发送一个回复。
```

它非常像普通 HTTP 的思路：

```text
请求一次
等待一次响应
```

---

## 6. REQ/REP 的优点

REQ/REP 的优点是简单：

- 语义清晰；
- 容易理解；
- 适合同步 RPC；
- 适合“一问一答”的控制命令。

例如：

```text
Client: 现在服务健康吗？
Server: healthy
```

或者：

```text
Client: 请返回当前 KV Cache 使用率
Server: 70%
```

---

## 7. REQ/REP 的缺点

REQ/REP 不适合高并发流式推理，原因是它严格交替：

```text
send request
receive reply
send next request
receive next reply
```

这会带来问题：

1. **不能自然支持一个请求多次返回**
   - LLM 流式输出是一个请求对应很多 token 输出；
   - REQ/REP 更像一个请求对应一个完整结果。

2. **并发能力弱**
   - 如果一个请求很慢，会阻塞后续请求；
   - 不适合大量请求同时进行。

3. **不适合复杂路由**
   - 多 API Server、多 EngineCore、多 DP rank 场景下，需要更灵活的身份和路由机制。

所以 REQ/REP 是理解通信模式的起点，但不是 vLLM 流式推理最核心的模式。

---

# 第三部分：DEALER/ROUTER 通信模式

## 8. 为什么需要 DEALER/ROUTER？

LLM 在线服务需要：

```text
多个客户端并发发请求
多个 EngineCore 并发处理请求
请求和输出可以异步返回
某个请求可以多次返回 token
```

这比 REQ/REP 复杂得多。

DEALER/ROUTER 就是 ZeroMQ 中更灵活的异步 request-reply 模式。

可以粗略理解为：

```text
DEALER：异步客户端，可以连续发送多个请求，不必严格等回复
ROUTER：带身份识别的路由端，可以知道消息来自哪个 peer，并把回复路由回去
```

---

## 9. DEALER 是什么？

DEALER socket 可以理解成“异步 REQ”。

REQ 的限制是：

```text
send -> recv -> send -> recv
```

DEALER 更自由：

```text
send request A
send request B
send request C
recv response B
recv response A
recv response C
```

它适合：

- 高并发请求；
- 请求执行时间不同；
- 响应乱序返回；
- 异步 RPC；
- 后台 EngineCore 处理。

---

## 10. ROUTER 是什么？

ROUTER socket 可以理解成“带地址识别的异步 REP”。

ROUTER 收到消息时，会知道消息来自哪个连接方。它可以把消息转发给特定连接方。

消息结构可以抽象为：

```text
[client_identity][empty delimiter][payload]
```

其中 `client_identity` 就像返回地址。

这对 vLLM 很重要，因为系统要知道：

```text
这个请求来自哪个 API Server / AsyncLLM？
这个输出结果应该发回哪个连接？
```

---

## 11. DEALER/ROUTER 在 vLLM 中解决什么问题？

### 11.1 请求入口侧并发

多个请求可能同时进入：

```text
request A
request B
request C
```

DEALER 可以连续发送请求，不必等待 A 完成才能发 B。

### 11.2 请求路由

如果有多个 EngineCore：

```text
EngineCore 0
EngineCore 1
EngineCore 2
EngineCore 3
```

API Server 可以把请求发给不同 EngineCore。ROUTER 能处理身份和路由。

### 11.3 流式输出

一个请求可能产生很多部分输出：

```text
request_id=abc, token 1
request_id=abc, token 2
request_id=abc, token 3
...
request_id=abc, finished=True
```

异步通信模式可以让输出不断返回，而不是必须等完整文本生成完。

---

## 12. DEALER/ROUTER 和 request_id 的关系

ZeroMQ 的 socket identity 解决的是：

```text
这条消息应该发回哪个连接？
```

但 vLLM 还需要区分：

```text
这个连接上的哪一个请求？
```

所以 vLLM 请求还要有 `request_id`。

两者层次不同：

| 概念 | 解决的问题 |
|---|---|
| socket identity | 消息发回哪个进程 / socket 连接 |
| request_id | 消息属于哪个用户请求 |

例如：

```text
API Server 连接 identity = api_server_0
request_id = chatcmpl-abc123
```

EngineCore 返回输出时，既要通过 socket 发回正确 API Server，也要让 AsyncLLM 知道这个输出属于哪个 request stream。

# 第四部分：PULL/PUSH 通信模式

## 13. PUSH/PULL 是什么？

PUSH/PULL 是 ZeroMQ 的 pipeline 模式：

```text
PUSH ---- task ----> PULL
```

多个 PUSH 可以把任务推给一个或多个 PULL；多个 PULL 也可以从 PUSH 端接收任务。

它适合：

- 单向传输；
- 任务分发；
- 结果收集；
- pipeline 流水线；
- 不需要每个消息立即回复的场景。

---

## 14. PUSH/PULL 和 REQ/REP 的区别

| 模式 | 方向 | 是否要求回复 | 适合场景 |
|---|---|---|---|
| REQ/REP | 双向 | 是，一问一答 | 简单同步请求 |
| DEALER/ROUTER | 双向 | 异步、多请求、多响应 | 高并发异步 RPC |
| PUSH/PULL | 单向 | 否 | pipeline、任务分发、结果推送 |

PUSH/PULL 没有“请求必须对应回复”的语义。

例如输出侧可以看成：

```text
EngineCore PUSH 输出
AsyncLLM / output_handler PULL 输出
```

当然，具体实现可能因 vLLM 版本而变化，但从架构理解上，PUSH/PULL 很适合解释“单向结果流”。

---

## 15. 为什么输出侧适合单向 pipeline？

因为模型生成输出具有流式特点：

```text
step 1 -> 输出 token A
step 2 -> 输出 token B
step 3 -> 输出 token C
...
```

EngineCore 不需要每输出一个 token 都等待 API Server 回一个确认，否则会严重拖慢推理。

更合理的是：

```text
EngineCore 不断 push outputs
AsyncLLM output_handler 不断 pull outputs
再按 request_id 分发到 AsyncStream
```

这就是流式执行的核心。

# 第五部分：vLLM Engine 接收数据

## 16. Engine 接收哪些数据？

EngineCore 接收的不是原始 HTTP 请求，而是经过上层处理后的内部请求对象。

一个生成请求通常包含：

```text
request_id
prompt token ids
sampling params
arrival time
priority
LoRA request
multi-modal inputs
trace headers
cache info
```

其中最核心的是：

```text
request_id
input token ids
sampling params
```

---

## 17. Engine 接收数据的流程

从用户请求到 EngineCore 接收：

```text
用户 HTTP 请求 / Python generate 调用
  ↓
API Server / AsyncLLM
  ↓
tokenizer / input processor
  ↓
创建 request_id
  ↓
创建 AsyncStream / RequestOutputCollector
  ↓
封装 EngineCoreRequest
  ↓
通过 ZMQ socket 发送给 EngineCore
  ↓
EngineCore input socket 接收请求
  ↓
add_request 加入 Scheduler waiting 队列
```

---

## 18. EngineCore 为什么要有 input socket 线程？

EngineCore 主循环要持续做：

```text
schedule
execute model
process output
```

如果接收 socket 消息和执行主循环耦合太紧，可能导致：

```text
等待 socket 消息阻塞 GPU 调度
或者模型执行太久导致新请求接收不及时
```

因此实际工程中常见设计是：

```text
单独 input socket IO 逻辑
把收到的请求放入内部队列
EngineCore 主循环从内部队列取请求
```

这样可以把：

```text
网络 / IPC I/O
```

和：

```text
调度 / GPU 执行
```

解耦。

---

## 19. add_request 做什么？

EngineCore 收到请求后，通常会进入 `add_request` 类似逻辑。

它要完成：

1. 校验请求；
2. 创建 Request / Sequence 状态；
3. 记录 prompt token ids；
4. 保存 sampling params；
5. 初始化输出状态；
6. 加入 Scheduler waiting 队列；
7. 等待后续调度进入 prefill。

此时请求还没有真正跑模型。

可以理解为：

```text
add_request = 把请求登记进 vLLM 内部调度系统
```

---

# 第六部分：vLLM Engine 发送数据

## 20. Engine 发送哪些数据？

EngineCore 执行模型后，会产生输出。

输出通常包括：

```text
request_id
new token ids
new text delta
logprobs
finish reason
stop reason
finished flag
usage stats
metrics
```

对于流式输出，每一轮可能只包含一小段：

```text
request_id = abc
new_text = "你"
finished = False
```

下一轮：

```text
request_id = abc
new_text = "好"
finished = False
```

最后：

```text
request_id = abc
new_text = "。"
finished = True
finish_reason = "stop"
```

---

## 21. Engine 发送数据的流程

完整输出链路：

```text
ModelRunner forward
  ↓
Sampler 采样 next token
  ↓
更新 request 状态
  ↓
构造 EngineCoreOutputs
  ↓
EngineCore output socket 发送输出消息
  ↓
AsyncLLM output_handler 接收输出
  ↓
根据 request_id 找到对应 AsyncStream
  ↓
把 RequestOutput 放入 AsyncStream
  ↓
API Server 异步迭代并流式返回给客户端
```

---

## 22. 为什么输出必须带 request_id？

因为 EngineCore 可能同时处理很多请求：

```text
request A -> token 10
request B -> token 2
request C -> token 99
```

输出顺序不一定等于请求进入顺序。

例如：

```text
A 先提交，但 B 的 prompt 短，B 先输出；
C 中途结束；
A 还在继续生成。
```

所以每个输出都必须带 `request_id`，让 AsyncLLM 知道它属于哪个 stream。

---

## 23. Engine 输出为什么适合异步？

因为流式生成天然是异步事件流：

```text
每次 decode step 可能有输出
有些请求本轮没有输出
有些请求本轮完成
有些请求本轮被取消
```

如果输出同步阻塞，会拖慢整个引擎。

异步输出可以做到：

```text
EngineCore 继续下一轮调度和推理
output_handler 后台分发结果
API Server 按客户端速度流式发送
```

---

# 第七部分：AsyncLLM 发送请求

## 24. AsyncLLM 是什么？

`AsyncLLM` 可以理解为 vLLM V1 中面向异步在线推理的上层接口。

它负责：

- 接收 API Server 或用户的异步生成调用；
- 处理输入；
- 创建请求流；
- 发送请求到 EngineCore；
- 后台接收结果；
- 将结果以 AsyncGenerator 形式返回。

它不是模型计算本体，而是异步请求管理层。

---

## 25. AsyncLLM.generate 的概念流程

一个 `generate()` 调用可以抽象为：

```text
async def generate(prompt, sampling_params, request_id):
    1. 创建 RequestOutputCollector / AsyncStream
    2. 处理 prompt 输入
    3. 添加请求到 Detokenizer
    4. 通过 EngineCoreClient 把请求发给 EngineCore
    5. 不断从 AsyncStream 中取 RequestOutput
    6. yield 给调用方
```

这就是为什么用户可以：

```python
async for output in engine.generate(...):
    print(output)
```

边生成边拿结果。

---

## 26. AsyncLLM 发送请求的关键状态

AsyncLLM 需要维护：

```text
request_id -> AsyncStream / output queue
```

当请求发给 EngineCore 后，它不会同步等待完整结果，而是立即返回一个异步生成器。

后台 output_handler 会不断把 EngineCore 输出塞到对应队列里。

---

## 27. 为什么 AsyncLLM 不能同步等待？

如果同步等待完整结果：

```text
调用 generate
等待模型生成完整文本
一次性返回
```

就不能实现：

- token streaming；
- 并发请求；
- 客户端边收边显示；
- 请求取消；
- 长文本生成时的低延迟体验。

AsyncLLM 的价值就是把请求生命周期变成异步流：

```text
request submitted
  ↓
partial output 1
  ↓
partial output 2
  ↓
...
  ↓
finished
```

---

# 第八部分：AsyncLLM 接收结果

## 28. output_handler 是什么？

`output_handler` 是 AsyncLLM 中的后台异步任务。

它持续做：

```text
从 EngineCore 拉取输出
  ↓
解析输出消息
  ↓
根据 request_id 找到对应 stream
  ↓
把输出放进 stream
  ↓
如果请求完成，关闭 stream
```

它的作用是把 EngineCore 的全局输出流拆成每个请求自己的输出流。

---

## 29. 为什么需要 per-request AsyncStream？

EngineCore 输出是混合的：

```text
output for request A
output for request C
output for request B
output for request A
output for request B
```

但用户只关心自己的请求：

```text
request A stream:
  A output 1
  A output 2
  A output 3
```

所以需要：

```text
request_id -> AsyncStream
```

把全局输出分发到各自的 stream 中。

---

## 30. 流式输出是怎么形成的？

流式输出的本质是：

```text
每一轮 decode 产生部分 token
每个部分 token 都尽快返回给用户
```

流程：

```text
Decode step 1
  ↓
输出 token 1
  ↓
AsyncStream yield token 1

Decode step 2
  ↓
输出 token 2
  ↓
AsyncStream yield token 2

Decode step 3
  ↓
输出 token 3
  ↓
AsyncStream yield token 3
```

API Server 再把这些输出转换成 OpenAI streaming chunk：

```text
data: {"choices": [{"delta": {"content": "你"}}]}

data: {"choices": [{"delta": {"content": "好"}}]}

data: [DONE]
```

# 第九部分：完整端到端流程

## 31. 从用户请求到流式输出

完整流程如下：

```text
1. 用户发送 HTTP 请求或 Python async generate 调用

2. API Server / AsyncLLM 接收请求
   - 生成 request_id
   - tokenizer 编码 prompt
   - 解析 sampling params
   - 创建 AsyncStream

3. AsyncLLM 通过 EngineCoreClient 发送请求
   - 通过 ZMQ socket
   - 请求进入 EngineCore input socket

4. EngineCore 接收请求
   - process_input_sockets
   - add_request
   - 加入 Scheduler waiting 队列

5. Scheduler 调度请求
   - prefill 新请求
   - decode running 请求
   - 分配 KV blocks

6. ModelExecutor / Worker / ModelRunner 执行
   - 构造 input_ids / positions / block_table / slot_mapping
   - 调用 model.forward
   - 调用 sampler

7. EngineCore 生成输出
   - RequestOutput / EngineCoreOutput
   - 带 request_id
   - 通过 output socket 发回 AsyncLLM

8. AsyncLLM output_handler 接收输出
   - 根据 request_id 找到 AsyncStream
   - 把结果放入 stream

9. generate() 异步迭代输出
   - API Server 转成 SSE chunk
   - 客户端边收边显示

10. 请求完成
   - EOS / stop / max_tokens
   - EngineCore 标记 finished
   - AsyncStream 关闭
   - KV Cache 释放
```

# 第十部分：为什么这些通信模式对 AI Infra 面试重要？

## 33. 面试官为什么会问 Engine 通信？

因为推理框架不是只会写模型 forward。

真实 AI Infra 岗位关注的是：

```text
请求怎么进来？
怎么并发？
怎么流式返回？
怎么跨进程？
怎么避免阻塞 GPU？
怎么管理 request_id？
怎么取消请求？
怎么扩展到多 DP rank？
```

如果你只懂 Transformer，不懂 Engine 通信，会很难回答“推理服务系统设计”。

---

## 34. 一句话区分几个组件

| 组件 | 一句话理解 |
|---|---|
| API Server | 接 HTTP 请求，做 OpenAI API 兼容和流式响应 |
| AsyncLLM | 异步请求管理层，创建 stream，发送请求，接收输出 |
| EngineCore | 调度和模型执行核心，管理 KV Cache 和 GPU worker |
| Scheduler | 决定本轮哪些请求执行 prefill/decode |
| Worker | 绑定 GPU rank，执行模型任务 |
| ModelRunner | 构建模型输入并调用 forward/sampler |
| AsyncStream | 每个请求自己的输出队列 / 异步流 |
| ZeroMQ | API Server / AsyncLLM / EngineCore 之间的消息通道 |

# 第十一部分：常见面试问题与答案

## 35. 面试题 1：vLLM 的 Engine 在系统中负责什么？

答：

vLLM 的 Engine / EngineCore 是推理服务的调度执行核心。它接收来自 AsyncLLM 或 API Server 的请求，将请求加入 Scheduler 队列，管理 KV Cache，调度 prefill 和 decode，协调 Worker / ModelRunner 执行模型 forward，并把每轮生成的输出通过输出通道发回上层。Engine 不是单纯的模型对象，而是请求生命周期管理、调度、执行和流式输出的中枢。

---

## 36. 面试题 2：为什么 vLLM 要用 ZMQ / socket？

答：

因为 vLLM 在线服务中 API Server、EngineCore、Worker 等组件可能运行在不同进程中，需要进程间通信。ZMQ 提供高性能消息传递和多种通信模式，可以支持 API Server 与 EngineCore 解耦、异步请求发送、多 EngineCore 路由和流式结果返回。这样网络服务和 GPU 推理核心不会互相阻塞，也方便多进程和数据并行扩展。

---

## 37. 面试题 3：REQ/REP、DEALER/ROUTER、PUSH/PULL 有什么区别？

答：

REQ/REP 是最简单的一问一答模式，发送请求后必须等待回复，适合同步控制命令。DEALER/ROUTER 是更灵活的异步 request-reply 模式，DEALER 可以连续发送多个请求，ROUTER 能识别连接身份并路由消息，适合高并发请求和异步输出。PUSH/PULL 是单向 pipeline 模式，适合任务分发或结果流，不要求每条消息都有回复。

---

## 38. 面试题 4：为什么 REQ/REP 不适合 LLM 流式输出？

答：

REQ/REP 强制一问一答，一个请求通常对应一个回复。而 LLM 流式输出中，一个请求会持续产生多个部分结果，每生成一个 token 或一段文本都可能返回一次。同时在线服务中多个请求并发执行，输出顺序可能乱序。REQ/REP 的同步交替语义太严格，容易阻塞，所以更适合使用 DEALER/ROUTER 或 pipeline 形式的异步通信。

---

## 39. 面试题 5：DEALER/ROUTER 为什么适合 vLLM 请求入口？

答：

因为 DEALER/ROUTER 支持异步、多请求、多响应和路由。AsyncLLM 或 API Server 可以连续发送多个请求，不必等待前一个请求完成。EngineCore 可以根据连接身份和 request_id 把结果发回正确请求。多 API Server、多 EngineCore、数据并行场景下，ROUTER 的身份路由能力能帮助系统建立多对多请求路由。

---

## 40. 面试题 6：request_id 在流式推理中有什么作用？

答：

request_id 用于标识某个用户请求。EngineCore 同时处理很多请求，输出可能交错返回，所以每条输出都必须带 request_id。AsyncLLM 的 output_handler 根据 request_id 找到对应 AsyncStream，把输出放入正确的请求队列。没有 request_id，就无法把混合输出流拆回每个用户自己的流式结果。

---

## 41. 面试题 7：AsyncLLM.generate 大致做什么？

答：

AsyncLLM.generate 是异步生成入口。它会创建当前请求对应的 AsyncStream 或 RequestOutputCollector，处理 prompt 输入和采样参数，将请求添加到 detokenizer 和 EngineCore，然后返回一个 AsyncGenerator。后台 output_handler 会持续从 EngineCore 拉取输出并放入对应 stream，generate 的调用方异步迭代这个 stream，从而实现流式输出。

---

## 42. 面试题 8：Engine 接收请求后是否立刻执行模型？

答：

不一定。Engine 接收请求后通常先执行 add_request，把请求状态加入 Scheduler 的 waiting 队列。真正什么时候执行模型由 Scheduler 决定。Scheduler 会根据 KV Cache、max_num_batched_tokens、max_num_seqs、prefill/decode 状态等约束，决定本轮哪些请求进入模型 forward。

---

## 43. 面试题 9：Engine 如何发送输出？

答：

ModelRunner forward 和 sampler 生成新 token 后，EngineCore 会把输出封装成包含 request_id、token delta、finish flag、logprobs 等信息的输出对象，然后通过输出 socket 发送给 AsyncLLM。AsyncLLM 的 output_handler 接收这些输出，根据 request_id 分发到对应 AsyncStream，API Server 再把 stream 中的内容转换成 OpenAI-compatible streaming chunk 返回给客户端。

---

## 44. 面试题 10：为什么 output_handler 要作为后台任务？

答：

因为 EngineCore 的输出是全局异步事件流。如果 generate 调用同步等待输出，会阻塞请求处理。output_handler 作为后台任务，可以持续从 EngineCore 拉取输出并分发到各个 AsyncStream，使 EngineCore 可以继续调度和执行下一轮模型推理，同时用户侧可以异步迭代自己的请求结果。

---

## 45. 面试题 11：vLLM 流式输出和普通一次性输出的区别是什么？

答：

普通一次性输出需要等模型生成完整文本后再返回。流式输出则是在每轮 decode 生成 token 后立即将部分结果返回给用户。这样可以显著降低用户感知延迟，尤其是长文本生成时，用户不必等完整回答完成。vLLM 通过 EngineCore 输出流、AsyncLLM output_handler 和 per-request AsyncStream 实现流式返回。

---

## 46. 面试题 12：EngineCore 和 ModelRunner 有什么区别？

答：

EngineCore 是更高层的调度执行核心，负责接收请求、调用 Scheduler、管理 KV Cache、协调模型执行和发送输出。ModelRunner 是 Worker 内部更靠近模型的一层，负责把 Scheduler 输出转换成模型输入，例如 input_ids、positions、block_table、slot_mapping、attention metadata，并调用 model.forward 和 sampler。EngineCore 管“什么时候跑谁”，ModelRunner 管“这一轮模型具体怎么跑”。

# 第十二部分：本节课总结

本节课主线：

```text
vLLM 在线推理需要支持高并发和流式输出
        ↓
API Server / AsyncLLM 和 EngineCore 通常通过 ZMQ 解耦
        ↓
REQ/REP 是基础同步一问一答模式
        ↓
DEALER/ROUTER 支持异步请求和路由，更适合高并发入口
        ↓
PUSH/PULL 支持单向 pipeline，更适合理解结果流推送
        ↓
AsyncLLM 发送请求时创建 request_id 和 AsyncStream
        ↓
EngineCore input socket 接收请求并 add_request
        ↓
Scheduler 决定请求何时 prefill / decode
        ↓
Worker / ModelRunner 执行模型 forward 和 sampler
        ↓
EngineCore output socket 发回每轮输出
        ↓
AsyncLLM output_handler 按 request_id 分发到 AsyncStream
        ↓
调用方 async for 迭代结果，实现流式返回
```

最重要的理解：

> **vLLM 的流式推理不是一个同步函数调用，而是一条异步消息链路：请求进入和结果返回通过 socket 解耦，EngineCore 在后台持续调度 GPU 工作，AsyncLLM 用 per-request stream 把混合输出拆回每个用户自己的流式响应。**
