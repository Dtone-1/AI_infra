# vLLM 分布式推理：数据并行详解 学习笔记

> 课程主题：课时 12 —— **vLLM 分布式推理：数据并行详解**  
> 目录关键词：DP 概述、DP 逻辑框架和流程图、DP 如何部署模型、混合张量并行和数据并行  
> 学习目标：理解 vLLM 中 Data Parallelism（数据并行，DP）为什么存在、它在推理服务中如何组织进程、请求如何路由到不同 DP rank、如何与 Tensor Parallelism（张量并行，TP）组合，以及面试中如何解释 DP/TP/PP/EP 的区别。

---

## 0. 本节课的核心主线

这节课不是单纯讲“多卡怎么启动 vLLM”，而是讲 **vLLM 在在线推理服务中如何把多个 GPU/多个模型副本组织成高吞吐推理系统**。

一句话概括：

> **数据并行 DP 是把“完整模型副本”复制到多个 GPU 或多个 GPU 组上，每个副本独立处理一部分请求，从而提升系统整体吞吐量；而张量并行 TP 是把“同一个模型的一层计算”切到多个 GPU 上，用来解决单卡放不下模型或单卡算力不足的问题。**

所以本节课要理顺四件事：

1. **DP 是什么**：模型副本复制，请求维度切分。
2. **DP 在 vLLM 中怎么落地**：每个 DP rank 是一个独立的 core engine / engine core，拥有独立调度器和 KV Cache。
3. **请求怎么流转**：API Server 接收请求，然后把请求路由到某个 DP rank；该请求后续 decode 阶段一般需要留在同一个 rank，因为 KV Cache 在这个 rank 上。
4. **DP 如何和 TP 混合**：一个 DP rank 内部可以再用 TP 把模型切到多个 GPU 上；总 GPU 数通常近似为 `DP size × TP size`。

---

## 1. DP 概述：数据并行到底解决什么问题？

### 1.1 从单卡推理开始理解

假设我们有一个模型 Qwen-7B，单张 GPU 能完整放下模型权重和 KV Cache。最简单的部署方式是：

```text
Client 请求
   ↓
vLLM API Server
   ↓
Engine Core / Scheduler
   ↓
GPU Worker / ModelRunner
   ↓
模型 forward
   ↓
返回 token
```

这个结构的问题是：

- 只有一个模型副本；
- 所有请求都排队进入同一个调度器；
- 高并发时，单个 GPU 的算力、显存和 KV Cache 容量会成为瓶颈；
- 即使 vLLM 有 continuous batching，也只能在一个模型副本内部提升 batch 利用率。

如果有 4 张 GPU，并且每张 GPU 都能独立放下模型，那么最直接的扩容方式不是把模型切开，而是：

```text
GPU0：完整模型副本，处理请求 A/B/C
GPU1：完整模型副本，处理请求 D/E/F
GPU2：完整模型副本，处理请求 G/H/I
GPU3：完整模型副本，处理请求 J/K/L
```

这就是推理服务中的 **数据并行 DP**。

---

### 1.2 DP 的本质

DP 的本质是：

> **模型不切分，请求切分。**

更准确地说：

- 每个 DP rank 持有一份完整模型副本；
- 每个 DP rank 拥有自己的 Scheduler、KV Cache、running queue、waiting queue；
- 不同 DP rank 处理不同请求；
- 大多数 dense model 的 DP rank 之间不需要在每一步 forward 中通信；
- 系统吞吐量随 DP 副本数增加而提升，但单个请求的 latency 不一定下降。

可以把 DP 类比为开多个餐厅窗口：

```text
窗口 0：完整厨师团队，处理一批顾客
窗口 1：完整厨师团队，处理另一批顾客
窗口 2：完整厨师团队，处理另一批顾客
窗口 3：完整厨师团队，处理另一批顾客
```

每个窗口都能独立完成一份菜，不需要互相协作。这样总出餐量变大，但某一个顾客的单份菜制作速度不一定变快。

---

### 1.3 DP 解决的是吞吐量问题，不是单请求模型放不下问题

很多初学者会混淆 DP 和 TP。

| 问题 | 应该优先考虑 |
|---|---|
| 模型一张 GPU 放不下 | TP / PP / 量化 |
| 模型一张 GPU 放得下，但请求很多 | DP |
| 单请求 latency 太高 | kernel 优化、CUDA Graph、speculative decoding、TP 可能有帮助 |
| 整体 QPS/TPS 不够 | DP、continuous batching、负载均衡 |
| MoE 专家层过大或专家计算分布不均 | EP / DP+EP / TP+EP |

判断标准：

- **DP 扩吞吐**：多份模型副本并行处理不同请求。
- **TP 扩单模型容量/算力**：一个模型副本被切到多个 GPU 上共同完成一次 forward。
- **PP 跨层切模型**：不同层放到不同 GPU 或不同节点上。
- **EP 切专家**：MoE 模型中不同专家放在不同 GPU 上。

## 2. DP 和训练里的 Data Parallel 有什么区别？

训练中的数据并行通常是：

```text
每张 GPU 有完整模型副本
每张 GPU 处理不同 mini-batch
反向传播后 AllReduce 梯度
更新参数保持一致
```

训练 DP 的核心通信是 **梯度同步**。

推理中的数据并行是：

```text
每个 GPU / GPU 组有完整模型副本
每个模型副本处理不同请求
没有反向传播
通常不需要同步梯度
```

推理 DP 的核心问题不是梯度同步，而是：

1. **请求路由**：新请求应该分给哪个 DP rank？
2. **负载均衡**：如何避免某个 rank 排队很长，其他 rank 很空？
3. **KV Cache 局部性**：已经 prefill 的请求，decode 阶段是否还留在同一个 rank？
4. **prefix caching 命中率**：相同前缀的请求是否应该路由到同一个 rank？
5. **MoE 场景同步**：如果 DP 和 EP 混合，部分层可能需要跨 rank 协同。

因此：

> 训练 DP 的重点是参数一致性；推理 DP 的重点是请求调度、KV Cache 管理和负载均衡。

## 3. vLLM 中 DP 的核心对象和逻辑架构

### 3.1 vLLM 在线服务的抽象层次

在 vLLM V1 架构中，可以把在线服务理解成几层：

```text
用户 / Client
   ↓ HTTP / OpenAI-compatible API
API Server
   ↓ ZMQ / IPC
Engine Core / Core Engine  ← 每个 DP rank 通常对应一个 Engine Core
   ↓
Scheduler + KV Cache Manager
   ↓
Executor
   ↓
GPU Worker(s)
   ↓
ModelRunner
   ↓
Model forward
```

这些组件的职责是：

| 组件 | 职责 |
|---|---|
| API Server | 接收 HTTP 请求、OpenAI API 兼容、tokenization、streaming 返回 |
| Engine Core | 推理引擎核心；维护请求状态、调度、KV Cache 管理 |
| Scheduler | 决定本轮调度哪些请求、哪些 token 进入 batch |
| KV Cache Manager | 分配、释放、复用 KV Cache block |
| Executor | 把调度结果下发给 Worker，协调多 GPU 执行 |
| Worker | 通常对应具体 GPU 进程 |
| ModelRunner | 构造模型输入、attention metadata、调用模型 forward |
| Model | 具体 Decoder-only Transformer 模型对象 |

---

### 3.2 DP rank 是什么？

在分布式推理里，`rank` 可以理解为一个并行组中的编号。

对于 DP 来说：

```text
DP rank 0：第 0 个模型副本
DP rank 1：第 1 个模型副本
DP rank 2：第 2 个模型副本
DP rank 3：第 3 个模型副本
```

每个 DP rank 通常有：

- 自己的 Engine Core；
- 自己的 Scheduler；
- 自己的 KV Cache；
- 自己的 waiting/running 请求队列；
- 自己负责的一部分请求。

如果没有 TP，那么一个 DP rank 可以对应一个 GPU。

如果使用 TP，那么一个 DP rank 可以对应一组 GPU。

例如：

```text
DP=2, TP=4
总 GPU 数 = 2 × 4 = 8

DP rank 0:
  GPU0, GPU1, GPU2, GPU3 共同组成一个 TP group
  这 4 张 GPU 合作承载一份模型副本

DP rank 1:
  GPU4, GPU5, GPU6, GPU7 共同组成另一个 TP group
  这 4 张 GPU 合作承载另一份模型副本
```

也就是说，DP rank 不一定等于单张 GPU；它可以是一个 GPU 组。

---

### 3.3 单纯 DP 架构图

假设 `DP=4, TP=1`，模型每张 GPU 都能完整放下：

```text
                    ┌──────────────────┐
Client Requests ───▶│    API Server     │
                    └────────┬─────────┘
                             │ 负载均衡 / 路由
          ┌──────────────────┼──────────────────┐
          │                  │                  │
          ▼                  ▼                  ▼
┌────────────────┐ ┌────────────────┐ ┌────────────────┐ ┌────────────────┐
│ DP rank 0      │ │ DP rank 1      │ │ DP rank 2      │ │ DP rank 3      │
│ Engine Core 0  │ │ Engine Core 1  │ │ Engine Core 2  │ │ Engine Core 3  │
│ Scheduler 0    │ │ Scheduler 1    │ │ Scheduler 2    │ │ Scheduler 3    │
│ KV Cache 0     │ │ KV Cache 1     │ │ KV Cache 2     │ │ KV Cache 3     │
│ GPU0 Model     │ │ GPU1 Model     │ │ GPU2 Model     │ │ GPU3 Model     │
└────────────────┘ └────────────────┘ └────────────────┘ └────────────────┘
```

这个结构中：

- 每个 DP rank 独立处理请求；
- 每个 rank 上都有完整模型权重；
- 每个 rank 的 KV Cache 互不共享；
- 请求一旦被分配给某个 rank，后续 decode 通常也要在这个 rank 上继续执行。

---

### 3.4 DP + TP 混合架构图

假设 `DP=2, TP=4`：

```text
                          ┌──────────────────┐
Client Requests ─────────▶│    API Server     │
                          └────────┬─────────┘
                                   │
                    ┌──────────────┴──────────────┐
                    ▼                             ▼
          ┌──────────────────┐          ┌──────────────────┐
          │   DP rank 0      │          │   DP rank 1      │
          │   Engine Core 0  │          │   Engine Core 1  │
          └────────┬─────────┘          └────────┬─────────┘
                   │ Scheduler Output             │ Scheduler Output
       ┌───────────┼───────────┐       ┌───────────┼───────────┐
       ▼           ▼           ▼       ▼           ▼           ▼
    GPU0        GPU1        GPU2... GPU4        GPU5        GPU6...
  Worker0     Worker1     Worker2  Worker0     Worker1     Worker2
       \________ TP group 0 ______/      \________ TP group 1 ______/

```

这里有两个模型副本：

- 副本 0 被 TP 切到 GPU0~GPU3；
- 副本 1 被 TP 切到 GPU4~GPU7。

在一个 DP rank 内部，TP workers 需要协同完成一次模型 forward。比如：

- QKV projection 按 head 或 hidden dimension 切分；
- MLP 的上投影/下投影切分；
- 层内需要 AllReduce 或 ReduceScatter 等通信；
- 每个 worker 持有部分权重。

所以：

> DP rank 之间处理不同请求；TP rank 之间共同处理同一请求。

## 4. DP 请求从输入到输出的完整流程

下面按照一次在线请求的生命周期，把 DP 流程串起来。

---

### 4.1 第一步：用户请求进入 API Server

用户通过 OpenAI-compatible API 请求模型：

```bash
curl http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "Qwen/Qwen2.5-7B-Instruct",
    "prompt": "请解释 vLLM 的数据并行",
    "max_tokens": 128,
    "stream": true
  }'
```

API Server 负责：

1. 接收 HTTP 请求；
2. 解析 sampling parameters；
3. tokenizer 编码 prompt；
4. 生成 request_id；
5. 把请求送入后端 Engine Core。

在 DP 场景中，API Server 还要决定：

> 这个新请求应该交给哪个 DP rank？

这一步就是负载均衡。

---

### 4.2 第二步：负载均衡选择 DP rank

最简单的策略是 round-robin：

```text
请求 1 → DP rank 0
请求 2 → DP rank 1
请求 3 → DP rank 2
请求 4 → DP rank 3
请求 5 → DP rank 0
```

但真实推理服务中，round-robin 往往不够好，因为不同请求的负载差异很大：

| 请求 | 输入长度 | 输出长度 | 负载 |
|---|---:|---:|---:|
| A | 32 tokens | 32 tokens | 很轻 |
| B | 4000 tokens | 2048 tokens | 很重 |
| C | 1024 tokens | 16 tokens | prefill 重、decode 轻 |
| D | 16 tokens | 4096 tokens | prefill 轻、decode 重 |

更合理的策略应该考虑：

- 每个 rank 当前 running 请求数；
- 每个 rank waiting queue 长度；
- 每个 rank KV Cache 剩余容量；
- 每个 rank 当前 prefill/decode 压力；
- 是否存在相同 prefix，可以利用 prefix caching；
- 请求的 expected output length；
- 请求是否是长上下文请求。

vLLM 官方文档也强调，在线 DP 部署中的负载均衡可以结合每个 DP engine 的运行队列、等待队列和 KV Cache 状态进行优化。

---

### 4.3 第三步：请求被送入某个 Engine Core

假设请求被路由到 `DP rank 2`：

```text
API Server
   ↓ ZMQ / IPC
DP rank 2 Engine Core
   ↓
waiting queue
```

Engine Core 内部会维护请求状态：

```text
WAITING → RUNNING → FINISHED
```

它会把请求放入 waiting queue，等待 Scheduler 调度。

此时还没有真正执行模型 forward，也还没有生成新 token。

---

### 4.4 第四步：Scheduler 决定本轮执行哪些 token

vLLM 的 Scheduler 每轮会决定：

- 哪些 waiting 请求进入 running；
- 哪些 running 请求继续 decode；
- 每个请求本轮执行多少 token；
- 是否做 chunked prefill；
- 是否因为 KV Cache 不够而延迟某些请求；
- 是否抢占、换出或重排请求。

调度输出可以抽象为：

```text
ScheduleOutput:
  - selected_requests
  - num_scheduled_tokens
  - block_tables
  - slot_mapping
  - sampling_metadata
```

在 DP 场景里，每个 DP rank 有自己的 Scheduler，所以调度决策是局部的：

```text
DP rank 0 Scheduler：只调度 rank 0 的请求
DP rank 1 Scheduler：只调度 rank 1 的请求
DP rank 2 Scheduler：只调度 rank 2 的请求
DP rank 3 Scheduler：只调度 rank 3 的请求
```

这也是 DP 的优势：

> 不同 DP rank 的调度器可以独立工作，不需要每一步都和其他 rank 同步。

但对 MoE + EP 场景，情况会复杂一些，后文单独讲。

---

### 4.5 第五步：KV Cache 在该 DP rank 内部分配

每个请求进入模型 forward 前，需要为它的 token 分配 KV Cache。

注意：

> **每个 DP rank 的 KV Cache 是独立的。**

例如请求 A 被放到 DP rank 2，则它的 KV Cache 存在 rank 2 的 GPU 显存里：

```text
Request A:
  prompt KV Cache → DP rank 2 的 KV Cache blocks
  decode KV Cache → 继续写入 DP rank 2 的 KV Cache blocks
```

这带来一个非常重要的结论：

> 请求一旦在某个 rank 完成 prefill，它后续 decode 阶段通常不能随便迁移到另一个 rank，除非把 KV Cache 也迁移过去。

为什么？

因为 decode 每生成一个新 token，都要读取历史 token 的 K/V：

```text
新 token 的 Q
   ↓ attend to
历史所有 token 的 K/V
```

历史 K/V 在 rank 2，如果把请求迁到 rank 0，rank 0 没有这些 K/V，就无法正确继续 decode。

这就是 **KV Cache locality**。

---

### 4.6 第六步：Executor / Worker / ModelRunner 执行 forward

如果 `TP=1`，某个 DP rank 内部只有一个 GPU Worker：

```text
DP rank 2 Engine Core
   ↓
Worker on GPU2
   ↓
ModelRunner
   ↓
Model forward
```

如果 `TP=4`，一个 DP rank 内部有 4 个 Worker：

```text
DP rank 0 Engine Core
   ↓
Executor
   ↓ broadcast ScheduleOutput
GPU0 Worker + GPU1 Worker + GPU2 Worker + GPU3 Worker
   ↓
各自 ModelRunner 构造本地输入
   ↓
TP 协同执行模型 forward
```

ModelRunner 负责的事情包括：

1. 根据调度结果构造 input_ids；
2. 构造 positions；
3. 构造 attention metadata；
4. 准备 block table、slot mapping；
5. 调用模型 forward；
6. 得到 logits；
7. 交给 sampler 得到下一个 token。

---

### 4.7 第七步：输出 token 返回 API Server

模型 forward 之后得到 logits：

```text
hidden_states → LM Head → logits → sampler → next_token_id
```

然后：

```text
DP rank Engine Core
   ↓
output queue
   ↓ ZMQ / IPC
API Server
   ↓
Tokenizer decode
   ↓
streaming 返回给用户
```

如果是流式输出，用户会看到 token 一个个返回：

```text
v
vL
vLL
vLLM
vLLM 是
vLLM 是一个
...
```

## 5. DP 如何部署模型？

### 5.1 单机内部负载均衡部署

如果一台机器有 4 张 GPU，每张 GPU 都能放下模型，可以使用：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --data-parallel-size 4
```

含义：

```text
DP=4, TP=1
总 GPU 数 = 4
每张 GPU 一个完整模型副本
API Server 对外暴露一个 endpoint
内部把请求分发给 4 个 DP rank
```

---

### 5.2 DP + TP 单机部署

如果一台机器有 8 张 GPU，希望每 2 张 GPU 组成一个 TP group，然后复制 4 份模型副本：

```bash
vllm serve Qwen/Qwen2.5-72B-Instruct \
  --data-parallel-size 4 \
  --tensor-parallel-size 2
```

含义：

```text
DP=4, TP=2
总 GPU 数 = 4 × 2 = 8
每个模型副本切到 2 张 GPU 上
一共有 4 个模型副本
```

架构：

```text
DP rank 0: GPU0 + GPU1
DP rank 1: GPU2 + GPU3
DP rank 2: GPU4 + GPU5
DP rank 3: GPU6 + GPU7
```

注意：

- `--max-num-seqs` 等调度参数通常按 DP rank 生效；
- 如果 DP=4，则整体并发能力不是简单等于 `max_num_seqs`，而是近似 `4 × 每 rank 能承载的有效请求数`；
- 但实际吞吐还受模型大小、KV Cache、输出长度、负载均衡和通信开销影响。

---

### 5.3 多节点 DP 部署

假设有两台机器，每台 2 张 GPU，共 4 张 GPU，要部署 `DP=4`。

可以让第 0 台机器作为 head node，持有 rank 0/1；第 1 台机器持有 rank 2/3。

抽象结构：

```text
Node 0:
  API Server
  DP rank 0
  DP rank 1

Node 1:
  DP rank 2
  DP rank 3
```

示意命令：

```bash
# Node 0
vllm serve $MODEL \
  --data-parallel-size 4 \
  --data-parallel-size-local 2 \
  --data-parallel-address <HEAD_NODE_IP> \
  --data-parallel-rpc-port 13345

# Node 1
vllm serve $MODEL \
  --headless \
  --data-parallel-size 4 \
  --data-parallel-size-local 2 \
  --data-parallel-start-rank 2 \
  --data-parallel-address <HEAD_NODE_IP> \
  --data-parallel-rpc-port 13345
```

关键参数解释：

| 参数 | 含义 |
|---|---|
| `--data-parallel-size` | 全局 DP rank 总数 |
| `--data-parallel-size-local` | 当前节点上启动多少个 DP rank |
| `--data-parallel-start-rank` | 当前节点第一个 DP rank 的编号 |
| `--data-parallel-address` | DP 通信使用的地址，通常是 head node IP |
| `--data-parallel-rpc-port` | DP rank 之间或控制面的 RPC 端口 |
| `--headless` | 当前节点不暴露 API Server，只运行后端 engine |

---

### 5.4 内部负载均衡、混合负载均衡、外部负载均衡

vLLM 在线 DP 部署可以理解为三种负载均衡形态。

---

#### 5.4.1 内部负载均衡 Internal Load Balancing

```text
用户请求
   ↓
单个 API endpoint
   ↓
vLLM API Server 内部路由
   ↓
多个 DP rank
```

优点：

- 部署简单；
- 对用户只暴露一个 endpoint；
- 适合单机或规模不大的多机部署。

缺点：

- API Server 所在节点可能成为瓶颈；
- 跨节点路由可能带来额外通信；
- 大规模场景下，需要更强的外部流量调度系统。

---

#### 5.4.2 混合负载均衡 Hybrid Load Balancing

```text
上游 LB / Ingress
   ↓
Node 0 API Server → Node 0 本地 DP ranks
Node 1 API Server → Node 1 本地 DP ranks
Node 2 API Server → Node 2 本地 DP ranks
```

特点：

- 每个节点都有自己的 API endpoint；
- 每个节点只调度本地 DP ranks；
- 上游负载均衡器负责把请求分发到不同节点；
- 减少跨节点流量；
- 适合多节点中等规模部署。

典型启动参数会包含：

```bash
--data-parallel-hybrid-lb
```

并且每个节点需要正确设置：

```bash
--data-parallel-size-local
--data-parallel-start-rank
```

---

#### 5.4.3 外部负载均衡 External Load Balancing

```text
用户请求
   ↓
外部 Router / Gateway / K8s Ingress / 自研调度系统
   ↓
Rank 0 vLLM endpoint
Rank 1 vLLM endpoint
Rank 2 vLLM endpoint
Rank 3 vLLM endpoint
```

特点：

- 每个 DP rank 可以看作一个独立 vLLM 服务；
- 外部系统根据 telemetry 进行路由；
- 可以结合业务侧限流、租户隔离、优先级、SLO；
- 适合大规模生产系统。

外部路由可以考虑：

- 当前请求数；
- waiting queue 长度；
- running queue 长度；
- GPU 利用率；
- KV Cache 使用率；
- prefix caching 命中；
- 平均 TTFT / TPOT；
- 业务优先级。

---

## 6. 混合张量并行和数据并行

### 6.1 为什么要混合 DP 和 TP？

单纯 DP 的前提是：

> 每个 GPU 能放下一份完整模型。

但大模型经常不满足这个条件。

例如：

- 7B 模型可能单卡能放下；
- 32B 模型可能需要 2~4 张 GPU；
- 70B 模型可能需要 4~8 张 GPU；
- 671B MoE 模型需要更复杂的 TP/EP/PP/DP 混合。

如果一个模型副本需要 4 张 GPU 才能放下，那么在 8 张 GPU 上就不能做 `DP=8`，只能做：

```text
DP=2, TP=4
```

也就是：

```text
两个模型副本，每个副本用四张 GPU 承载。
```

---

### 6.2 总 GPU 数如何计算？

在常见 dense model 场景下，可以近似理解为：

```text
总 GPU 数 = DP size × TP size × PP size
```

如果没有 PP：

```text
总 GPU 数 = DP size × TP size
```

例子：

| 配置 | 总 GPU 数 | 含义 |
|---|---:|---|
| DP=4, TP=1 | 4 | 4 个完整副本，每副本 1 GPU |
| DP=2, TP=4 | 8 | 2 个副本，每副本 4 GPU |
| DP=4, TP=2 | 8 | 4 个副本，每副本 2 GPU |
| DP=1, TP=8 | 8 | 1 个副本，被切到 8 GPU |

---

### 6.3 DP 和 TP 的核心区别

| 维度 | DP | TP |
|---|---|---|
| 切分对象 | 请求 / batch | 模型权重和中间计算 |
| 每个 rank 是否有完整模型 | 是，或每个 DP group 有完整模型副本 | 否，TP rank 只持有部分权重 |
| 是否提升吞吐 | 是，通常明显提升整体吞吐 | 可能提升，也可能被通信抵消 |
| 是否降低单卡显存压力 | 不降低，每个副本仍需模型权重 | 降低，把权重切到多卡 |
| 是否需要频繁通信 | dense DP 通常不需要每步通信 | 需要 AllReduce / ReduceScatter 等 |
| 适合场景 | 模型能放下，请求多 | 模型单卡放不下或层计算太大 |

---

### 6.4 DP + TP 的工作流程

以 `DP=2, TP=4` 为例：

```text
1. API Server 接收请求 A/B/C/D
2. 负载均衡器把 A/B 分给 DP rank 0，把 C/D 分给 DP rank 1
3. DP rank 0 的 Scheduler 只调度 A/B
4. DP rank 1 的 Scheduler 只调度 C/D
5. DP rank 0 内部的 4 个 TP workers 共同执行 A/B 的 forward
6. DP rank 1 内部的 4 个 TP workers 共同执行 C/D 的 forward
7. 两个 DP rank 的输出分别返回 API Server
8. API Server 根据 request_id 流式返回给对应客户端
```

图示：

```text
Request A/B ──▶ DP rank 0 ──▶ TP workers 0,1,2,3 ──▶ Output A/B
Request C/D ──▶ DP rank 1 ──▶ TP workers 4,5,6,7 ──▶ Output C/D
```

---

### 6.5 如何选择 DP 和 TP 的比例？

假设你有 8 张 GPU。

#### 情况 A：模型单卡能放下

推荐：

```text
DP=8, TP=1
```

原因：

- 每张卡一个副本；
- 无 TP 通信；
- 吞吐扩展简单直接；
- 适合高 QPS 服务。

#### 情况 B：模型至少需要 2 张 GPU 才能放下

推荐：

```text
DP=4, TP=2
```

原因：

- 每个副本由 2 张 GPU 承载；
- 一共 4 个副本；
- 在模型容量和吞吐之间折中。

#### 情况 C：模型至少需要 8 张 GPU 才能放下

只能：

```text
DP=1, TP=8
```

原因：

- 8 张 GPU 只能组成一个模型副本；
- 没有多副本并行能力；
- 高并发吞吐依赖 continuous batching 和调度能力。

#### 情况 D：模型是 MoE

可能需要考虑：

```text
DP + TP + EP
```

例如：

```text
Attention 层使用 DP 或 TP
Expert 层使用 EP
部分 dense 层使用 TP
```

---

## 7. MoE 场景中的 DP：为什么会更复杂？

对于 dense model，DP rank 之间通常可以完全独立。

但对于 MoE 模型，情况不一定。

MoE 模型里有专家层：

```text
Token hidden states
   ↓
Router / Gate
   ↓
选择 top-k experts
   ↓
专家计算
   ↓
合并输出
```

如果专家被切分到不同 GPU 或不同 rank 上，就会发生 All-to-All 通信。

在 vLLM 的一些 DP+EP 场景中：

- attention 层可能按 DP 复制；
- expert 层可能按 EP 切分；
- 某个 DP rank 没有请求，也可能需要参与 dummy forward；
- 因为 expert 层通信需要多个 rank 对齐；
- 需要 DP Coordinator 协调哪些 rank 处于 active / idle 状态。

这说明：

> Dense model 的 DP 更像“完全独立的多个副本”；MoE model 的 DP+EP 可能不是完全独立，因为专家层存在跨 rank 通信和同步。

---

## 8. DP 中最重要的系统问题：负载均衡

### 8.1 为什么 DP 负载均衡很难？

LLM 请求不是普通 HTTP 请求，它有状态。

一次请求分为：

```text
Prefill 阶段：处理 prompt，计算历史 KV Cache
Decode 阶段：逐 token 生成，持续读取和追加 KV Cache
```

一旦 prefill 在某个 DP rank 上完成，这个请求的 KV Cache 就在这个 rank 上。

所以 decode 阶段通常要继续留在同一个 rank。

这带来两个难点：

1. **请求粘性 sticky assignment**  
   请求不能随便迁移，否则要迁移 KV Cache。

2. **负载会动态变化**  
   请求的输出长度一开始不知道。一个看起来很轻的请求，可能最后生成 4096 tokens。

因此，DP 负载均衡比普通无状态服务更难。

---

### 8.2 负载均衡应该看哪些指标？

生产系统中，路由一个新请求时可以考虑：

| 指标 | 含义 |
|---|---|
| waiting queue length | 等待队列长度 |
| running queue length | 正在运行的请求数 |
| num scheduled tokens | 当前调度 token 数 |
| KV Cache free blocks | 剩余 KV Cache block 数 |
| prefix cache hit potential | 前缀缓存潜在命中率 |
| average TTFT | 平均首 token 延迟 |
| average TPOT | 平均每 token 延迟 |
| GPU utilization | GPU 利用率 |
| prefill/decode ratio | 当前 rank 是 prefill 压力大还是 decode 压力大 |

简单策略：

```text
选 waiting + running 最少的 rank
```

更高级策略：

```text
估算请求未来 decode 长度 + 当前 rank KV Cache 压力 + prefix cache 命中率
```

---

## 9. DP 与 KV Cache / Prefix Caching 的关系

### 9.1 每个 DP rank 有独立 KV Cache

假设有 4 个 DP rank：

```text
DP rank 0: KV Cache Pool 0
DP rank 1: KV Cache Pool 1
DP rank 2: KV Cache Pool 2
DP rank 3: KV Cache Pool 3
```

这些 KV Cache 彼此独立，不会自动共享。

所以：

- rank 0 命中过的 prefix，不代表 rank 1 也命中；
- 相同系统 prompt 的请求如果被随机分散到不同 rank，会降低 prefix caching 的总体收益；
- 如果业务中存在大量相同前缀，路由器最好具备 prefix-aware 能力。

---

### 9.2 prefix-aware routing 的意义

假设很多请求都有相同系统提示词：

```text
你是一个专业客服助手，请严格按照以下规则回答……
```

如果请求都路由到同一个 rank，这个 rank 的 prefix cache 可能命中：

```text
相同 prefix → 复用已有 KV blocks → 减少 prefill 计算
```

如果请求被随机分散到 4 个 rank：

```text
rank 0 需要算一次 prefix
rank 1 需要算一次 prefix
rank 2 需要算一次 prefix
rank 3 需要算一次 prefix
```

就会重复计算。

因此，大规模服务里，DP 负载均衡不是简单“平均分请求”，还要考虑缓存局部性。

## 10. DP 部署调参建议

### 10.1 `--data-parallel-size`

控制 DP rank 总数。

```bash
--data-parallel-size 4
```

表示启动 4 个数据并行副本。

---

### 10.2 `--tensor-parallel-size`

控制每个模型副本内部使用多少张 GPU 切分模型。

```bash
--tensor-parallel-size 2
```

和 DP 组合：

```bash
--data-parallel-size 4 --tensor-parallel-size 2
```

表示：

```text
4 个副本 × 每副本 2 GPU = 8 GPU
```

---

### 10.3 `--max-num-seqs`

表示单个 engine / 单个 rank 中可并发调度的最大序列数。

注意：

> DP 场景中，`max_num_seqs` 通常是 per DP rank 的概念，不是全局总数。

例如：

```bash
--data-parallel-size 4 --max-num-seqs 64
```

粗略理解：

```text
每个 DP rank 最多 64 条序列
全局理论上最多约 4 × 64 条序列
```

但实际能否达到还取决于 KV Cache、prompt 长度、输出长度、显存容量和调度策略。

---

### 10.4 `--gpu-memory-utilization`

控制 vLLM 可以使用多少 GPU 显存。

例如：

```bash
--gpu-memory-utilization 0.9
```

表示 vLLM 尽量使用 90% GPU 显存，剩余显存留给系统、CUDA runtime、临时 tensor 等。

DP 场景中每个 rank 都要独立分配权重和 KV Cache，所以该参数会影响每个副本的并发能力。

---

### 10.5 `--api-server-count`

在较大 DP size 时，单个 API Server 可能成为瓶颈。可以增加 API Server 数量：

```bash
--api-server-count 4
```

作用：

- 增加 HTTP 接入处理能力；
- 降低 tokenization / detokenization / streaming 的 CPU 瓶颈；
- 配合 DP 多 engine 提升服务端吞吐。

---

## 11. 一个具体例子：8 卡机器怎么部署？

假设一台 8 卡 H100，模型是 Qwen2.5-32B。

### 11.1 方案一：DP=8, TP=1

```bash
vllm serve Qwen/Qwen2.5-32B-Instruct \
  --data-parallel-size 8 \
  --tensor-parallel-size 1
```

只有当每张 GPU 都能独立放下模型时才可行。

优点：

- 8 个副本；
- 吞吐高；
- 无 TP 通信。

缺点：

- 每张卡都要完整模型权重；
- 如果模型太大，单卡放不下。

---

### 11.2 方案二：DP=4, TP=2

```bash
vllm serve Qwen/Qwen2.5-32B-Instruct \
  --data-parallel-size 4 \
  --tensor-parallel-size 2
```

适合模型需要 2 张 GPU 才能稳定放下的情况。

优点：

- 有 4 个副本；
- 每副本显存压力下降；
- 吞吐和容量折中。

缺点：

- 每个副本内部有 TP 通信；
- 单请求 latency 可能受通信影响。

---

### 11.3 方案三：DP=2, TP=4

```bash
vllm serve Qwen/Qwen2.5-72B-Instruct \
  --data-parallel-size 2 \
  --tensor-parallel-size 4
```

适合更大的模型。

优点：

- 能部署更大模型；
- 仍有 2 个副本做请求级并行。

缺点：

- 副本数量少于方案二；
- TP 通信更重；
- 负载均衡空间变小。

---

### 11.4 方案四：DP=1, TP=8

```bash
vllm serve Qwen/Qwen2.5-72B-Instruct \
  --tensor-parallel-size 8
```

适合模型非常大，8 张卡只能放下一份副本。

优点：

- 能最大化单模型容量；
- 适合大 dense model。

缺点：

- 只有一个副本；
- 高并发主要依赖 continuous batching；
- DP 扩吞吐能力为 0。

## 12. 面试中如何讲 DP？

### 12.1 30 秒版本

> vLLM 中的数据并行是把模型副本复制到多个 DP rank 上，每个 rank 独立处理一部分请求。它主要解决高并发吞吐问题，而不是解决单卡放不下模型的问题。每个 DP rank 通常有独立的 Engine Core、Scheduler 和 KV Cache。在线服务中 API Server 会把请求路由到某个 DP rank；由于 KV Cache 存在该 rank 上，请求后续 decode 通常要保持在同一个 rank。DP 也可以和 TP 混合，比如 DP=4、TP=2 表示 4 个模型副本，每个副本由 2 张 GPU 组成。

---

### 12.2 2 分钟版本

> 在推理服务中，DP 是请求级并行。相比 TP 切模型权重，DP 是复制模型副本，把不同请求分发到不同副本上执行。vLLM 里每个 DP rank 可以看作一个独立的 core engine process，内部有自己的 scheduler、KV cache manager 和运行队列。API Server 接收请求之后，通过内部或者外部负载均衡把请求发给某个 DP rank。这个 rank 会完成 prefill、分配 KV Cache，并在 decode 阶段不断生成 token。由于 KV Cache 是 rank-local 的，所以请求通常是 sticky 的，不能每轮 decode 随便换 rank，否则就要迁移 KV Cache。DP 的优势是 dense model 场景下 rank 之间几乎不需要每步同步，吞吐扩展直接；缺点是模型权重会被复制多份，单卡显存压力不会降低。如果模型单卡放不下，就需要在每个 DP group 内部再用 TP，也就是 DP×TP 混合部署。

---

## 13. 常见面试题与参考答案

### Q1：vLLM 中的数据并行和张量并行有什么区别？

**答案：**

数据并行是请求维度并行。每个 DP rank 持有完整模型副本或完整模型副本对应的 GPU group，不同 rank 处理不同请求，主要提升系统吞吐。

张量并行是模型维度并行。它把模型层内的权重矩阵或 attention heads 切到多张 GPU 上，一个请求的同一次 forward 需要多个 TP rank 协同完成，主要解决单卡放不下模型或单卡算力不足的问题。

---

### Q2：为什么 DP 能提升吞吐，但不一定降低单请求延迟？

**答案：**

DP 增加的是模型副本数量，让多个请求可以分散到不同副本并行执行，所以整体 QPS/TPS 会提高。但某一个请求进入某个 DP rank 后，它的 prefill、decode、sampling 仍然在该 rank 内部完成，单请求计算路径没有本质缩短。因此 DP 对吞吐提升明显，对单请求 latency 的改善取决于是否减少了排队时间，而不是减少了模型 forward 本身的计算量。

---

### Q3：为什么一个请求被分到某个 DP rank 后，decode 阶段通常不能换到另一个 rank？

**答案：**

因为 prefill 阶段生成的 KV Cache 存在该 DP rank 的 GPU 显存中。decode 每生成一个 token，都需要读取历史 token 的 K/V。如果把请求迁移到另一个 rank，而另一个 rank 没有这些 KV Cache，就无法正确计算 attention。除非系统实现 KV Cache 迁移或共享，否则请求需要 sticky 到同一个 rank。

---

### Q4：`DP=4, TP=2` 表示什么？需要几张 GPU？

**答案：**

`DP=4, TP=2` 表示有 4 个数据并行模型副本，每个副本内部用 2 张 GPU 做张量并行。因此总 GPU 数是：

```text
4 × 2 = 8
```

每个 DP rank 是一个 TP group，例如 rank0 使用 GPU0/1，rank1 使用 GPU2/3，rank2 使用 GPU4/5，rank3 使用 GPU6/7。

---

### Q5：如果模型单卡能放下，有 8 张 GPU，应该优先 DP=8 还是 TP=8？

**答案：**

通常优先 DP=8。因为模型单卡能放下时，TP 会引入额外通信，而 DP 可以让每张卡独立处理不同请求，更直接提升吞吐。TP=8 更适合模型单卡放不下或者单卡计算能力不足的情况。

---

### Q6：DP 的负载均衡为什么比普通 Web 服务难？

**答案：**

普通 Web 请求通常无状态，路由到任意后端都可以。但 LLM 推理请求有 KV Cache 状态。一个请求 prefill 后，它的 KV Cache 保存在某个 rank 上，decode 阶段需要继续访问这些历史 K/V。因此请求具有 sticky 属性，不能随便迁移。另外输出长度未知，不同请求负载差异大，导致负载均衡更难。

---

### Q7：DP 场景下 prefix caching 和路由有什么关系？

**答案：**

每个 DP rank 的 prefix cache / KV Cache 是独立的。如果相同前缀的请求被分散到不同 rank，每个 rank 都要重复计算该 prefix。若路由器能把相同或相似 prefix 的请求路由到已有缓存的 rank，可以提高 prefix cache 命中率，减少 prefill 计算，提高吞吐并降低 TTFT。

---

### Q8：vLLM 的内部负载均衡和外部负载均衡有什么区别？

**答案：**

内部负载均衡是 vLLM 自己暴露一个 API endpoint，在 API Server 内部把请求路由到多个 DP rank。部署简单，但大规模时 API Server 可能成为瓶颈。

外部负载均衡是把每个 DP rank 或每组 vLLM 实例看作独立服务，由外部 router、gateway、Kubernetes ingress 或自研调度系统根据指标分发请求。它更适合大规模生产系统，也更容易结合业务优先级、SLO 和监控指标。

---

### Q9：MoE 模型中的 DP 为什么比 dense model 更复杂？

**答案：**

Dense model 的 DP rank 通常完全独立，不同副本之间不用每步通信。但 MoE 模型中专家层可能使用 EP 或 TP 切分，token 需要根据 gate 路由到不同专家，专家计算可能涉及 All-to-All 通信。如果 DP 和 EP 混合，不同 DP rank 在专家层可能需要同步或对齐 forward，因此不是完全独立。某些没有请求的 rank 也可能需要 dummy forward 来保证通信一致性。

---

### Q10：`max_num_seqs` 在 DP 场景中怎么理解？

**答案：**

它通常是每个 DP rank 的限制，而不是全局限制。比如 `DP=4, max_num_seqs=64`，可以粗略理解为每个 rank 最多调度 64 条序列，理论全局上限约为 256 条。但实际并发还受 KV Cache 容量、prompt 长度、输出长度和调度策略影响。

---

### Q11：什么时候选择 DP？什么时候选择 TP？

**答案：**

如果模型能单卡放下，但请求量很大，优先选择 DP；如果模型单卡放不下，或单卡计算太慢，需要把模型切到多卡上，则选择 TP 或 PP。如果模型既很大又请求量很大，就混合使用 DP 和 TP，例如 `DP=4, TP=2`。

---

### Q12：DP rank 内部有什么关键状态？

**答案：**

一个 DP rank 内部通常包括 Scheduler、KV Cache Manager、Block Tables、running queue、waiting queue、模型权重、Worker/ModelRunner，以及该 rank 正在处理的请求状态。它们共同决定该 rank 当前还能接多少请求、能否分配 KV Cache，以及本轮能调度哪些 token。

---

| 知识点 | 一句话理解 |
|---|---|
| DP | 复制模型副本，切请求，提高吞吐 |
| DP rank | 一个数据并行副本，通常对应一个 engine core |
| TP | 切模型权重和计算，一个请求由多卡协同完成 |
| DP+TP | 多个模型副本，每个副本内部再多卡切分 |
| KV Cache locality | 请求的 KV Cache 在哪个 rank，decode 就要在哪个 rank |
| 负载均衡 | 根据队列、KV Cache、GPU 状态、prefix cache 等选择 rank |
| 内部 LB | vLLM 内部 API Server 负责路由 |
| 外部 LB | 由外部网关或自研调度系统路由 |
| MoE DP | attention 可 DP，expert 层可能 EP/TP，需要额外同步 |
| 面试重点 | DP vs TP、请求流转、KV Cache 粘性、部署参数、DP+TP 计算 |

最终要记住：

> **DP 是推理服务横向扩展的核心手段；TP 是单模型跨卡承载的核心手段。vLLM 的分布式推理通常不是二选一，而是根据模型大小、GPU 数量、请求压力和通信成本组合使用 DP、TP、PP、EP。**
