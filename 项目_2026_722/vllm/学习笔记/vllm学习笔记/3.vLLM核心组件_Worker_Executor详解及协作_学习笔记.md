# vLLM 核心组件：Worker / Executor 详解及协作学习笔记

> 课时 03：vLLM 核心组件：Worker / Executor 详解及协作  
> 课程关键词：Executor、Worker、ModelRunner、GPU Worker、rank、Tensor Parallel、Pipeline Parallel、RPC、multiprocessing、Ray、driver worker、remote worker、ExecuteModelRequest、Scheduler Output、SamplerOutput、WorkerResponseMQ

---

## 0. 本节课核心目标

本节课要解决的问题是：

> **vLLM 中 Engine 已经负责接收请求和调度，为什么还需要 Executor 和 Worker？Executor 和 Worker 之间如何通信？Worker 最终又是怎么调用 ModelRunner 和模型 forward 的？**

你可以先记住一句话：

> **Engine / EngineCore 负责“决定做什么”，Executor 负责“把执行命令发给哪些 Worker”，Worker 负责“在具体 GPU 上真正跑模型”。**

在 nano-vLLM 这类教学项目中，链路可能被简化成：

```text
Engine / Scheduler
  ↓
ModelRunner
  ↓
model.forward
```

但真正的 vLLM 要支持：

- 单机单卡；
- 单机多卡 Tensor Parallel；
- 多机多卡；
- Ray worker；
- multiprocessing worker；
- driver worker + remote worker；
- TP / PP / DP / EP 等并行形式；
- 多进程隔离；
- GPU 资源绑定；
- worker 故障处理；
- 异步模型执行；
- 输出聚合和流式返回。

所以 vLLM 必须在 Engine 和 ModelRunner 中间增加一层执行抽象：

```text
EngineCore / Scheduler
  ↓
Executor
  ↓
Worker
  ↓
ModelRunner
  ↓
Model forward
```

本节课的主线就是把这条链路讲清楚。

# 1. 从整体架构看 Worker / Executor 的位置

## 1.1 vLLM 推理链路总览

一个用户请求进入 vLLM 后，大致经过：

```text
Client / OpenAI API
  ↓
API Server / AsyncLLM
  ↓
Engine / EngineCore
  ↓
Scheduler
  ↓
Executor
  ↓
Worker(s)
  ↓
ModelRunner
  ↓
Model.forward
  ↓
Sampler
  ↓
Output Processor
  ↓
Streaming response
```

其中：

| 层级 | 核心职责 |
|---|---|
| API Server / AsyncLLM | 接收用户请求，处理异步流式输出 |
| Engine / EngineCore | 管理请求生命周期，驱动调度和执行循环 |
| Scheduler | 决定本轮哪些请求执行，分配 KV Cache block |
| Executor | 根据调度结果调用一个或多个 Worker 执行模型 |
| Worker | 绑定具体 GPU / rank，持有模型、KV Cache、ModelRunner |
| ModelRunner | 构建模型输入，调用模型 forward，执行 sampler |
| Model | Transformer 权重和具体算子 |

---

## 1.2 为什么 Engine 不直接跑模型？

在最小教学实现中，Engine 直接调用 ModelRunner 是可以的。

但 vLLM 是生产级推理系统，Engine 不直接跑模型有几个原因：

### 原因 1：多 GPU 需要多 Worker

如果开启 Tensor Parallel：

```bash
--tensor-parallel-size 4
```

一个模型 forward 需要 4 个 GPU 进程共同完成。Engine 不能只调用一个 Python 对象，而要协调 4 个 Worker。

```text
Worker rank 0 -> GPU 0 -> 持有一部分权重
Worker rank 1 -> GPU 1 -> 持有一部分权重
Worker rank 2 -> GPU 2 -> 持有一部分权重
Worker rank 3 -> GPU 3 -> 持有一部分权重
```

Executor 就是用来统一管理这些 Worker 的执行入口。

---

### 原因 2：分布式执行后端不同

vLLM 支持不同 distributed executor backend：

```text
multiprocessing / mp
Ray
external launcher
single process
```

不同后端的进程创建、通信方式、资源管理方式都不一样。Engine 不应该关心这些细节。

因此需要一个抽象：

```text
Executor 接口固定
底层实现可以是 MultiprocExecutor / RayExecutor / UniProcExecutor
```

---

### 原因 3：Engine 应该专注调度和请求生命周期

Engine / Scheduler 关心的是：

```text
哪些请求 running？
哪些请求 waiting？
哪些请求 prefill？
哪些请求 decode？
哪些请求 finished？
KV Cache block 是否够？
本轮最多跑多少 token？
```

Worker 关心的是：

```text
本 GPU 上模型权重在哪？
KV Cache tensor 在哪？
input_ids / positions / attention metadata 怎么构建？
怎么执行 model.forward？
怎么通信 all-reduce？
```

这两类职责完全不同，拆开更清晰。

---

## 1.3 Executor / Worker / ModelRunner 的关系

可以这样理解：

```text
Executor：任务分发者 / 多 Worker 管理者
Worker：GPU 进程 / rank 持有者
ModelRunner：Worker 内部真正执行模型输入构建和 forward 的对象
```

关系图：

```text
EngineCore
  |
  | ExecuteModelRequest
  v
Executor
  |
  | broadcast / RPC / multiprocessing queue / Ray remote call
  v
Worker rank 0 ── ModelRunner ── model shard on GPU0
Worker rank 1 ── ModelRunner ── model shard on GPU1
Worker rank 2 ── ModelRunner ── model shard on GPU2
Worker rank 3 ── ModelRunner ── model shard on GPU3
  |
  | outputs / hidden states / sampler output
  v
Executor
  |
  v
EngineCore
```

# 2. 前言：先理解 rank、driver worker、remote worker

## 2.1 rank 是什么？

在分布式计算中，`rank` 表示当前进程在某个通信组里的编号。

例如 TP=4：

```text
rank 0 -> 第 0 个 GPU worker
rank 1 -> 第 1 个 GPU worker
rank 2 -> 第 2 个 GPU worker
rank 3 -> 第 3 个 GPU worker
```

它不是“等级高低”，只是编号。

rank 的作用：

- 决定当前 Worker 使用哪张 GPU；
- 决定当前 Worker 持有哪部分模型权重；
- 决定通信时当前进程的身份；
- 决定 tensor parallel 中矩阵切片位置；
- 决定哪个 rank 负责返回最终结果。

---

## 2.2 local rank、global rank、world size

常见几个概念：

| 概念 | 含义 |
|---|---|
| `world_size` | 通信组中总共有多少个进程 / rank |
| `rank` / `global_rank` | 当前进程在全局通信组中的编号 |
| `local_rank` | 当前节点内部的 GPU 编号 |
| `driver_worker` | 通常是负责发起执行、聚合结果的主 Worker |
| `remote_worker` | 被 driver 调用的其他 Worker |

单机 4 卡：

```text
world_size = 4

global rank 0, local rank 0 -> GPU0
global rank 1, local rank 1 -> GPU1
global rank 2, local rank 2 -> GPU2
global rank 3, local rank 3 -> GPU3
```

多机时：

```text
node 0:
  global rank 0, local rank 0
  global rank 1, local rank 1

node 1:
  global rank 2, local rank 0
  global rank 3, local rank 1
```

---

## 2.3 driver worker 是什么？

driver worker 可以理解为：

> **Executor 直接驱动的主 Worker，通常负责发起本轮模型执行，并接收或聚合输出。**

在某些实现中，driver worker 也是 rank 0 worker。

典型职责：

- 接收 Executor 的执行请求；
- 与其他 worker 同步执行；
- 在需要时聚合结果；
- 返回 `SamplerOutput` 或模型执行结果给 Executor。

但注意：

> 不同 vLLM 版本和不同 backend 中 driver worker 细节可能不完全一样，理解时抓住“主控执行入口”即可。

---

# 3. Worker 组件介绍

## 3.1 Worker 是什么？

Worker 是 vLLM 中的 GPU 执行单元。

一个 Worker 通常对应：

```text
一个进程
一个 rank
一张 GPU 或一个设备上下文
一个 ModelRunner
一份模型权重 shard 或完整权重
一份本地 KV Cache
```

如果是单卡推理：

```text
1 个 Worker 持有完整模型
```

如果是 TP=4：

```text
4 个 Worker 各持有 1/4 权重 shard
```

---

## 3.2 Worker 内部通常有哪些状态？

Worker 内部可能包含：

| 状态 | 作用 |
|---|---|
| `model_runner` | 构建输入并执行模型 |
| `device` | 当前 Worker 绑定的 GPU |
| `rank` | 当前 Worker 的分布式编号 |
| `local_rank` | 当前节点上的 GPU 编号 |
| `distributed_environment` | 通信组、NCCL、TP/PP 信息 |
| `kv_cache` | 当前 rank 持有的 KV Cache |
| `model_config` | 模型结构配置 |
| `parallel_config` | TP / PP / DP 等并行配置 |
| `cache_config` | KV Cache block size、显存比例等 |
| `scheduler_config` | 调度相关配置 |
| `lora_config` | LoRA 相关配置 |
| `device_config` | CUDA / CPU / XPU 等设备配置 |

不同版本字段名会变化，但职责基本稳定。

---

## 3.3 Worker 初始化流程

Worker 初始化大致包括：

```text
创建 Worker 进程
  ↓
设置 rank / local_rank / device
  ↓
初始化分布式通信环境
  ↓
设置随机种子
  ↓
加载模型权重
  ↓
初始化 ModelRunner
  ↓
profile 可用显存
  ↓
分配 KV Cache blocks
  ↓
warmup / CUDA Graph capture
  ↓
等待 Executor 发来执行请求
```

---

## 3.4 Worker 为什么要初始化分布式通信？

因为多 GPU 模型并行时，Worker 之间必须通信。

例如 Tensor Parallel 中：

- Column Parallel Linear 后可能需要 AllGather；
- Row Parallel Linear 后可能需要 AllReduce；
- attention / MLP 分片需要同步；
- Pipeline Parallel 需要发送 hidden states；
- Expert Parallel 需要 AllToAll dispatch/combine。

通信后端常见是：

```text
NCCL
Gloo
Ray communication
Custom all-reduce
```

Worker 必须知道：

```text
我是谁？
总共有多少人？
我要和谁通信？
用什么 backend？
```

---

## 3.5 Worker 执行模型的基本流程

当 Worker 收到执行请求：

```text
ExecuteModelRequest
```

它会调用类似：

```text
worker.execute_model(request)
```

内部再调用：

```text
model_runner.execute_model(request)
```

ModelRunner 会：

```text
根据 scheduler output 准备 input_ids / positions
准备 attention metadata
准备 block_tables / slot_mapping
调用 model.forward
调用 sampler
返回输出
```

对于 TP 多卡：

```text
每个 Worker 都会参与 forward
但通常只有 driver / rank 0 返回最终 sampler output
```

其他 rank 可能只返回中间结果或空输出，具体取决于实现。

# 4. Executor 组件介绍

## 4.1 Executor 是什么？

Executor 是 Engine 和 Worker 之间的执行抽象。

它负责：

```text
接收 EngineCore 的 ExecuteModelRequest
  ↓
把请求分发给一个或多个 Worker
  ↓
协调多 Worker 同步执行
  ↓
收集 Worker 输出
  ↓
返回给 EngineCore
```

可以把 Executor 理解为：

> **vLLM 的“模型执行控制器”。**

---

## 4.2 Executor 为什么存在？

如果没有 Executor，Engine 就要直接处理：

- 单卡执行；
- 多进程 Worker；
- Ray Worker；
- TP rank 广播；
- PP stage 执行；
- Worker 失败处理；
- 结果聚合；
- worker 生命周期；
- 多后端差异。

这样 Engine 会变得非常复杂。

Executor 把这些细节封装掉：

```text
Engine 只需要调用 executor.execute_model(...)
Executor 内部决定怎么跑
```

---

## 4.3 常见 Executor 类型

不同版本中类名和路径可能有差异，但概念上有几类：

| Executor 类型 | 使用场景 |
|---|---|
| UniProc / Uniproc Executor | 单进程、单 GPU 或调试场景 |
| Multiproc Executor | 单机多 GPU，多进程 worker |
| Ray Executor | 多机或 Ray 集群 worker |
| External Launcher Executor | torchrun / 外部进程管理场景 |
| Distributed Executor | 泛指多 Worker 执行器 |

vLLM 官方文档中对 Executor 的抽象描述是：Executor 负责在一个设备或多个分布式设备上执行模型。

---

## 4.4 Executor 的核心方法

一个 Executor 通常需要提供以下能力：

```text
initialize workers
load model
determine available memory
initialize KV cache
execute model
check health
shutdown
```

其中最核心的是：

```text
execute_model
```

伪代码：

```python
class Executor:
    def execute_model(self, execute_model_req):
        self.broadcast_to_workers(execute_model_req)
        outputs = self.collect_worker_outputs()
        return outputs
```

当然真实实现更复杂，涉及异步执行、多进程队列、异常处理、worker response queue 等。

---

## 4.5 Executor 与 Scheduler 的关系

Scheduler 输出的是“本轮应该执行什么”。

例如：

```text
scheduled_requests = [req1, req2, req3]
num_scheduled_tokens = [12, 1, 1]
new_blocks = {...}
blocks_to_swap_in = ...
blocks_to_swap_out = ...
blocks_to_copy = ...
```

Executor 不负责决定这些请求是否该执行。

Executor 只负责：

```text
把 Scheduler 已经决定好的本轮执行请求交给 Worker 跑
```

所以职责边界是：

```text
Scheduler：调度决策
Executor：执行分发
Worker：实际执行
```

# 5. Executor 和 Worker 通信 Demo：RPC 过程

## 5.1 RPC 是什么？

RPC 全称是 Remote Procedure Call，远程过程调用。

普通本地调用：

```python
worker.execute_model(req)
```

RPC 调用像是：

```python
remote_worker.execute_model(req)
```

虽然代码看起来像调用函数，但实际发生的是：

```text
序列化请求
  ↓
通过进程间通信 / 网络发送
  ↓
远端 Worker 反序列化
  ↓
执行函数
  ↓
序列化结果
  ↓
返回调用方
```

---

## 5.2 vLLM 中为什么需要 RPC？

因为 Worker 可能不在当前进程中。

例如 multiprocessing：

```text
EngineCore process
  ↓
Worker process 0
Worker process 1
Worker process 2
Worker process 3
```

或者 Ray：

```text
Head node process
  ↓
Ray worker actor on node A
Ray worker actor on node B
```

Executor 需要像调用本地方法一样调用远端 Worker 方法，所以需要 RPC 抽象。

---

## 5.3 一个极简 RPC Demo

假设有一个 Worker：

```python
class Worker:
    def init_device(self):
        print("init cuda")

    def load_model(self):
        print("load model")

    def execute_model(self, request):
        return f"output for {request}"
```

Executor 想调用：

```python
worker.execute_model(req)
```

如果 Worker 是远端进程，就需要变成：

```text
Executor
  ↓ send RPC message:
    {
      "method": "execute_model",
      "args": [req]
    }
  ↓
Worker process
  ↓ call real method
  ↓ return result
```

Worker 侧伪代码：

```python
while True:
    msg = recv()
    method_name = msg["method"]
    args = msg["args"]

    result = getattr(worker, method_name)(*args)

    send(result)
```

Executor 侧伪代码：

```python
def call_worker(method, *args):
    send({"method": method, "args": args})
    return recv()
```

这就是 RPC 的核心思想。

---

## 5.4 vLLM 中的 RPC 广播

多 Worker 场景下，Executor 经常需要把同一个命令发给所有 Worker。

例如初始化设备：

```text
init_device -> all workers
```

加载模型：

```text
load_model -> all workers
```

执行模型：

```text
execute_model -> all workers
```

广播示意：

```text
Executor
  ├── RPC to Worker rank 0: execute_model(req)
  ├── RPC to Worker rank 1: execute_model(req)
  ├── RPC to Worker rank 2: execute_model(req)
  └── RPC to Worker rank 3: execute_model(req)
```

但注意，实际多卡执行时，不一定每个 Worker 都拿到完全一样的张量内容。有些输入元数据一致，有些 tensor 根据 rank 不同而不同。

---

## 5.5 Multiproc Executor 的典型通信思路

在 multiprocessing 后端中，通常会有：

```text
Engine / Executor process
  ↓
request queue / broadcast queue
  ↓
Worker process
  ↓
response queue
  ↓
Engine / Executor process
```

可以抽象为：

```text
RPCBroadcastMQ:
  Executor -> Workers

WorkerResponseMQ:
  Workers -> Executor
```

执行流程：

```text
1. Executor 把 execute_model 命令放入 broadcast queue
2. Worker 进程从 queue 中取命令
3. Worker 执行对应方法
4. Worker 把结果放入 response queue
5. Executor 收集结果
6. Executor 返回给 EngineCore
```

---

## 5.6 Ray Executor 的典型通信思路

Ray 后端中，Worker 可能是 Ray Actor。

调用形式类似：

```python
worker.execute_model.remote(req)
```

Ray 负责：

- 远端 actor 调度；
- 序列化；
- 网络传输；
- 资源分配；
- 返回 future；
- 错误传播。

Executor 的职责是管理这些 Ray actor，并等待结果。

# 6. Worker 组件介绍及初始化、执行

## 6.1 Worker 初始化步骤详解

### Step 1：创建进程 / Actor

Executor 启动时创建 Worker：

```text
MultiprocExecutor -> Python multiprocessing.Process
RayExecutor -> Ray Actor
UniProcExecutor -> 本进程对象
```

---

### Step 2：绑定设备

每个 Worker 需要绑定自己的 GPU：

```python
torch.cuda.set_device(local_rank)
```

例如：

```text
rank 0 -> cuda:0
rank 1 -> cuda:1
rank 2 -> cuda:2
rank 3 -> cuda:3
```

---

### Step 3：初始化分布式环境

如果 world size > 1：

```text
init process group
initialize model parallel group
initialize tensor parallel group
initialize pipeline parallel group
```

TP=4 时，4 个 rank 形成 tensor parallel group。

---

### Step 4：加载模型

每个 Worker 加载自己需要的权重：

- 单卡：完整权重；
- TP：权重 shard；
- PP：部分层；
- EP：部分 experts；
- DP：每个副本一份完整或组合权重。

例如 TP 中一层 Linear：

```text
完整 weight: [out_features, in_features]

rank 0 持有一部分
rank 1 持有一部分
rank 2 持有一部分
rank 3 持有一部分
```

---

### Step 5：profile 显存并分配 KV Cache

Worker 会统计：

```text
总显存
- 模型权重
- runtime buffer
- profiling peak memory
= 可用于 KV Cache 的显存
```

然后计算可分配 block 数：

```text
num_blocks = available_kv_memory / block_size_bytes
```

之后创建 KV Cache tensor。

---

### Step 6：warmup / CUDA Graph capture

如果启用 CUDA Graph，Worker / ModelRunner 会进行 warmup 和 capture。

目的：

- 预热 kernel；
- 触发编译；
- capture 常见 batch size；
- 后续 decode replay，提高性能。

---

## 6.2 Worker execute_model 流程

Worker 执行模型大致如下：

```text
Worker.execute_model(execute_model_req)
  ↓
处理 KV cache swap/copy 等操作
  ↓
调用 ModelRunner.execute_model(...)
  ↓
ModelRunner 构建输入
  ↓
模型 forward
  ↓
Sampler
  ↓
返回 SamplerOutput / ModelRunnerOutput
```

---

## 6.3 ExecuteModelRequest 是什么？

`ExecuteModelRequest` 可以理解为：

> **Engine / Scheduler 生成的本轮模型执行请求。**

它可能包含：

- 本轮调度请求；
- KV Cache block 操作；
- running request 状态；
- finished request ids；
- intermediate tensors；
- previous hidden states；
- virtual engine id；
- lookahead slots；
- async callback 等。

不同 vLLM 版本字段不同，但本质是：

```text
告诉 Worker：本轮该怎么执行模型
```

---

## 6.4 SamplerOutput 是什么？

`SamplerOutput` 是模型执行后的采样结果。

它通常包含：

- 每个请求新生成的 token id；
- logprobs；
- finish reason；
- prompt logprobs；
- speculative decoding 中接受 token 信息；
- 每个 sequence 的输出状态。

Engine 收到它后，会更新请求状态并流式返回给用户。

---

# 7. Executor 和 Worker 组件的协作

## 7.1 一次 step 的完整协作流程

一次 Engine step 可以拆成：

```text
1. EngineCore 调用 Scheduler
2. Scheduler 选择本轮请求
3. Scheduler 分配 / 更新 KV Cache block
4. EngineCore 构造 ExecuteModelRequest
5. EngineCore 调用 Executor.execute_model(req)
6. Executor 向 Worker 广播执行请求
7. Worker 调用 ModelRunner.execute_model
8. Worker 执行 model.forward
9. 多 Worker 之间进行必要通信
10. Sampler 生成 token
11. Worker 返回输出
12. Executor 收集输出
13. Executor 返回 EngineCore
14. EngineCore 更新请求状态
15. AsyncLLM / API Server 流式返回 token
```

---

## 7.2 单卡场景

单卡最简单：

```text
EngineCore
  ↓
UniProcExecutor
  ↓
Worker rank 0
  ↓
ModelRunner
  ↓
完整模型 forward
```

这时 Executor 只是薄薄的一层封装。

---

## 7.3 多卡 TP 场景

TP=4：

```text
EngineCore
  ↓
MultiprocExecutor / RayExecutor
  ↓
Worker rank 0,1,2,3
  ↓
每个 Worker 持有一部分模型
  ↓
所有 Worker 同步执行 forward
  ↓
中间使用 AllReduce / AllGather 等通信
  ↓
rank 0 或 driver 返回最终输出
```

例如 Row Parallel Linear：

```text
rank 0 计算部分输出
rank 1 计算部分输出
rank 2 计算部分输出
rank 3 计算部分输出
  ↓
AllReduce
  ↓
每个 rank 得到完整结果
```

---

## 7.4 多卡 PP 场景

Pipeline Parallel 把模型层切到不同 GPU：

```text
rank 0: layer 0-9
rank 1: layer 10-19
rank 2: layer 20-29
rank 3: layer 30-39
```

执行时：

```text
rank 0 计算前几层
  ↓ send hidden states
rank 1 继续计算
  ↓ send hidden states
rank 2 继续计算
  ↓ send hidden states
rank 3 得到最后 logits
```

Executor 要协调不同 pipeline stage 的执行。

---

## 7.5 多卡 EP 场景

Expert Parallel 中，不同 Worker 持有不同专家：

```text
rank 0: expert 0,1,2
rank 1: expert 3,4,5
rank 2: expert 6,7,8
rank 3: expert 9,10,11
```

MoE 层执行：

```text
Router 计算 token -> expert
  ↓
AllToAll dispatch token 到 expert 所在 rank
  ↓
本地 expert compute
  ↓
AllToAll combine 结果
```

Executor 管理 Worker，Worker 内部的分布式通信完成专家计算。

---

## 7.6 Executor 并不替代 NCCL 通信

一个常见误解是：

> “Executor 负责 Worker 之间所有通信。”

更准确地说：

```text
Executor 负责控制面通信：发命令、收结果、管理 Worker
NCCL / distributed backend 负责数据面通信：tensor allreduce/alltoall/send/recv
```

也就是说：

```text
Executor -> Worker：告诉你本轮执行
Worker <-> Worker：在 forward 内通过 NCCL 交换 tensor
```

---

# 8. 为什么要用 Executor 抽象不同后端？

## 8.1 单进程后端

适合：

- 单卡；
- 调试；
- 简化部署。

特点：

```text
没有复杂进程通信
调用链短
但不适合大规模分布式
```

---

## 8.2 Multiprocessing 后端

适合：

- 单机多 GPU；
- TP/PP 多进程；
- 无需 Ray 集群。

特点：

```text
每个 Worker 是本机进程
通过 multiprocessing queue / shared memory / socket 通信
性能较好
部署较简单
```

---

## 8.3 Ray 后端

适合：

- 多机；
- 集群资源调度；
- 弹性 worker；
- 与 Ray Serve 生态结合。

特点：

```text
Worker 是 Ray actor
Ray 负责资源和通信
部署灵活
但引入 Ray 运行时开销和复杂度
```

---

## 8.4 Engine 为什么不关心具体后端？

因为有 Executor：

```text
EngineCore:
  executor.execute_model(req)

MultiprocExecutor:
  用进程队列发给本机 Worker

RayExecutor:
  用 Ray remote call 发给远端 Actor

UniProcExecutor:
  直接本地调用 Worker
```

Engine 代码不用关心底层执行方式。

这就是抽象的价值。

---

# 9. 和 nano-vLLM 的对比

## 9.1 nano-vLLM 为什么看不到复杂 Executor / Worker？

nano-vLLM 是教学项目，通常只保留核心概念：

- Scheduler；
- BlockManager；
- KV Cache；
- ModelRunner；
- 简单 Engine；
- 单机单卡或简化多卡。

它重点是让你理解：

```text
请求调度
prefill/decode
KV Cache block 管理
模型输入构建
```

所以可以省略复杂的 Executor / Worker。

---

## 9.2 vLLM 为什么必须有？

真实 vLLM 要面对：

```text
多进程
多 GPU
多机
Ray / mp 后端
TP / PP / DP / EP
CUDA Graph
异步执行
worker 错误处理
性能优化
```

因此必须拆成：

```text
EngineCore：调度和请求生命周期
Executor：执行后端抽象和 Worker 管理
Worker：具体设备执行
ModelRunner：模型输入构建和 forward
```

---

## 9.3 面试表达

如果面试官问：

> nano-vLLM 中好像 Engine 直接调用 ModelRunner，vLLM 为什么要多出 Executor 和 Worker？

可以答：

> nano-vLLM 是单机简化教学实现，直接调用 ModelRunner 可以表达核心推理流程。但 vLLM 是生产级推理框架，要支持 TP/PP/DP/EP、多进程、多机、Ray、mp 等不同执行后端。Engine 如果直接调用 ModelRunner，会把调度、进程管理、GPU rank、分布式通信和模型执行耦合在一起。vLLM 用 Executor 抽象执行后端，用 Worker 绑定具体 GPU/rank，用 ModelRunner 执行模型输入构建和 forward，从而让 Engine 专注请求调度和生命周期管理。

# 11. 本节课完整技术主线

可以把本节内容串成一条完整链路：

```text
用户请求进入 API Server
        ↓
AsyncLLM 把请求发送到 Engine
        ↓
EngineCore 管理请求状态
        ↓
Scheduler 决定本轮哪些请求执行
        ↓
Scheduler 输出本轮调度结果和 KV block 操作
        ↓
EngineCore 构造 ExecuteModelRequest
        ↓
Executor 接收执行请求
        ↓
Executor 通过 RPC / Queue / Ray 调用 Worker
        ↓
每个 Worker 绑定一个 GPU / rank
        ↓
Worker 调用自己的 ModelRunner
        ↓
ModelRunner 根据调度结果构建模型输入
        ↓
多个 Worker 通过 NCCL 完成 TP/PP/EP 数据通信
        ↓
模型 forward 得到 hidden states / logits
        ↓
Sampler 采样得到 next token
        ↓
Worker 返回输出给 Executor
        ↓
Executor 聚合输出并返回 EngineCore
        ↓
EngineCore 更新请求状态
        ↓
AsyncLLM 接收结果
        ↓
API Server 流式返回给用户
```

最重要的是这条边界：

```text
Engine / Scheduler：决定“哪些请求跑”
Executor：决定“让哪些 Worker 跑”
Worker / ModelRunner：决定“在 GPU 上怎么跑”
```

---

# 12. 常见易混点

## 12.1 Worker 是模型吗？

不是。

Worker 是执行进程 / 执行单元，它内部持有模型或模型 shard。

```text
Worker ≠ Model
Worker 持有 ModelRunner
ModelRunner 持有或调用 Model
```

---

## 12.2 Executor 是调度器吗？

不是。

Scheduler 决定请求调度。

Executor 负责执行分发。

```text
Scheduler：该跑谁？
Executor：让哪些 Worker 执行？
Worker：怎么在 GPU 上执行？
```

---

## 12.3 rank 0 是不是完整模型？

不一定。

在 TP 场景下，rank 0 也只持有模型的一部分权重。它可能是 driver worker，但不是完整模型。

---

## 12.4 所有 Worker 都返回完整输出吗？

通常不是。

多卡模型并行中，所有 Worker 都参与 forward，但最终输出可能只由 driver worker / rank 0 返回，或者由特定 pipeline last stage 返回。其他 Worker 主要参与计算和通信。

---

## 12.5 Executor 负责 AllReduce 吗？

不负责具体 tensor AllReduce。

AllReduce 在 Worker 内部模型 forward 过程中由分布式通信库执行。Executor 只负责控制 Worker 执行。

---

# 13. 面试问答

## 13.1 面试题 1：vLLM 中 Executor 的作用是什么？

答：

Executor 是 Engine 和 Worker 之间的执行抽象。Engine / Scheduler 决定本轮哪些请求要执行后，会构造 ExecuteModelRequest 交给 Executor。Executor 根据当前后端，比如 uniproc、multiprocessing 或 Ray，把执行请求分发给一个或多个 Worker，并收集 Worker 的模型输出返回给 Engine。它屏蔽了单卡、多卡、多进程、多机等执行差异。

---

## 13.2 面试题 2：Worker 的作用是什么？

答：

Worker 是 vLLM 中绑定具体 GPU/rank 的执行单元。每个 Worker 通常运行在独立进程中，持有当前 rank 的模型权重 shard、KV Cache、分布式通信上下文和 ModelRunner。Worker 接收 Executor 发来的执行请求，调用 ModelRunner 构建输入并执行 model.forward，再把输出返回给 Executor。

---

## 13.3 面试题 3：Executor 和 Scheduler 的区别是什么？

答：

Scheduler 做调度决策，决定本轮哪些请求执行、每个请求执行多少 token、KV Cache blocks 如何分配。Executor 不做请求调度，它负责把 Scheduler 的执行结果分发给 Worker 去运行，并收集结果。简单说，Scheduler 负责“选谁跑”，Executor 负责“让 Worker 跑”。

---

## 13.4 面试题 4：Executor 和 Worker 为什么不能合成一个？

答：

单卡场景中二者可以很薄，但生产级 vLLM 要支持多种执行后端和多 GPU/多机。Executor 是后端无关的控制抽象，负责 worker 生命周期、RPC、广播、结果收集；Worker 是具体设备上的执行实体。拆开后，Engine 不需要关心底层是 Ray 还是 multiprocessing，也不需要直接管理多个 GPU rank。

---

## 13.5 面试题 5：Worker 和 ModelRunner 的区别是什么？

答：

Worker 是进程级或设备级执行单元，负责设备初始化、分布式通信、模型加载、KV Cache 初始化和接收执行命令。ModelRunner 是 Worker 内部的模型执行对象，负责根据调度结果构建 input_ids、positions、attention metadata、block table、slot mapping，调用模型 forward 和 sampler。Worker 偏资源和进程管理，ModelRunner 偏模型执行逻辑。

---

## 13.6 面试题 6：什么是 rank？

答：

rank 是分布式通信组中每个进程的编号。例如 tensor_parallel_size=4 时，会有 rank 0 到 rank 3 四个 Worker。每个 rank 绑定一张 GPU，持有模型的一部分权重，并在 forward 中通过 NCCL 等通信库协同计算。rank 不是级别高低，只是分布式进程编号。

---

## 13.7 面试题 7：driver worker 和 remote worker 有什么区别？

答：

driver worker 通常是主控 worker，负责发起执行、与 Executor 直接交互并返回最终输出；remote worker 是其他参与模型并行计算的 worker。多卡执行时所有 worker 都参与 forward，但通常由 driver worker 聚合或返回结果。具体细节会随 vLLM 版本和 executor backend 变化。

---

## 13.8 面试题 8：Executor 和 Worker 之间怎么通信？

答：

如果是 multiprocessing 后端，通常通过进程间队列、socket 或 message queue 进行控制消息广播和结果返回；如果是 Ray 后端，则通过 Ray actor remote call；如果是单进程，则可能直接函数调用。本质都是 RPC：Executor 发送“调用某个 worker 方法”的命令，Worker 执行后把结果返回。

---

## 13.9 面试题 9：控制面通信和数据面通信有什么区别？

答：

控制面通信是 Executor 和 Worker 之间传递执行命令、初始化命令、结果状态等，通常通过 RPC、queue、Ray 等完成。数据面通信是 Worker 在模型 forward 中交换 tensor，例如 TP 的 AllReduce、EP 的 AllToAll，通常由 NCCL 等高性能通信库完成。Executor 主要管控制面，NCCL 主要管数据面。

---

## 13.10 面试题 10：单卡时还需要 Executor 吗？

答：

单卡时 Executor 可能只是很薄的一层，甚至接近直接调用 Worker。但保留 Executor 抽象可以让上层 Engine 使用统一接口，不需要区分单卡、多卡、Ray、mp 等情况，也方便后续扩展和调试。

---

## 13.11 面试题 11：TP=4 时，Executor 会做什么？

答：

TP=4 时，通常会启动 4 个 Worker，每个 Worker 对应一个 rank/GPU，持有模型权重的一部分。EngineCore 构造本轮执行请求后交给 Executor，Executor 将请求广播或分发给 4 个 Worker。4 个 Worker 同步执行模型 forward，并在 forward 内部通过 NCCL 做 AllReduce/AllGather 等通信。执行完成后，driver worker 或特定 rank 的输出返回给 Executor，再返回 EngineCore。

---

## 13.12 面试题 12：为什么 nano-vLLM 中可以没有复杂 Executor / Worker？

答：

nano-vLLM 是教学项目，重点展示 KV Cache、调度、prefill/decode 和模型输入构建，通常只考虑单机简化场景，所以可以直接 Engine 调 ModelRunner。vLLM 是生产框架，需要支持多 GPU、多进程、多机、Ray、TP/PP/EP、异步执行和故障处理，所以必须用 Executor / Worker 把执行后端和具体 GPU 计算封装起来。

---

## 13.13 面试题 13：Worker 初始化主要做哪些事？

答：

Worker 初始化包括绑定 GPU device，设置 rank/local_rank，初始化分布式通信组，加载模型权重，创建 ModelRunner，profile 显存，计算可用于 KV Cache 的 block 数，初始化 KV Cache，执行 warmup 或 CUDA Graph capture，最后等待 Executor 发来执行请求。

---

## 13.14 面试题 14：ExecuteModelRequest 里大概包含什么？

答：

它是本轮模型执行请求，通常包含 Scheduler 输出的本轮请求信息、每个请求要执行的 token 数、KV Cache block 操作、running request 状态、finished request ids、可能的中间 tensor 或异步回调等。字段会随版本变化，但本质是告诉 Worker 本轮模型 forward 应该怎么跑。

---

## 13.15 面试题 15：如何一句话讲清楚 Executor / Worker / ModelRunner？

答：

Executor 是 Engine 到模型执行层的控制器，负责把执行请求分发给一个或多个 Worker；Worker 是绑定具体 GPU/rank 的执行进程，负责模型权重、KV Cache 和分布式通信；ModelRunner 是 Worker 内部真正构建模型输入并调用 forward/sampler 的对象。

---

# 14. 本节课总结

本节课可以总结成三句话：

1. **Executor 是执行后端抽象**：它屏蔽单进程、多进程、Ray、多机多卡等差异，让 Engine 用统一方式发起模型执行。
2. **Worker 是具体 GPU 执行单元**：每个 Worker 绑定 rank/GPU，持有模型权重 shard、KV Cache、通信上下文和 ModelRunner。
3. **ModelRunner 是模型执行核心**：它把 Scheduler 的调度结果转成模型输入，调用 forward 和 sampler，返回 token 输出。

最终链路是：

```text
EngineCore / Scheduler
  ↓ ExecuteModelRequest
Executor
  ↓ RPC / Queue / Ray
Worker(s)
  ↓
ModelRunner
  ↓
Model.forward + distributed communication
  ↓
SamplerOutput
  ↓
Executor
  ↓
EngineCore
  ↓
Streaming output
```

最重要的理解是：

> **vLLM 中多出来的 Executor 和 Worker 不是“为了复杂而复杂”，而是为了把生产级推理系统中的调度、进程管理、GPU rank、分布式通信和模型执行分层解耦。**
