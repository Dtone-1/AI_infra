## 0. 本节课的核心目标

这一节课讲的是 **Tensor Parallelism，张量并行，简称 TP**。它是大模型推理系统里最重要的分布式并行方式之一。

如果说上一节的数据并行 DP 是：

> 多张 GPU 各自持有一份完整模型，每张 GPU 处理不同请求。

那么张量并行 TP 是：

> 一个模型的一层太大，单张 GPU 放不下或算不过来，于是把同一层的权重矩阵切到多张 GPU 上，每张 GPU 只负责一部分矩阵计算，然后通过通信把结果拼接或求和，得到和单卡执行等价的输出。

这一节课的主线是：

```text
为什么需要 TP
  ↓
什么是 AllReduce
  ↓
Transformer 中哪些线性层可以切
  ↓
Column Parallel / Row Parallel 怎么工作
  ↓
Attention 和 MLP 如何做张量并行
  ↓
vLLM 如何通过 tensor_parallel_size 启动多个 GPU Worker
  ↓
TP 对显存、吞吐、通信、部署策略有什么影响
```

## 1. 为什么大模型推理需要张量并行？

### 1.1 单卡推理的瓶颈

一个 Decoder-only LLM 主要由很多层 Transformer Block 组成，每一层内部有：

1. Attention 相关线性层：`q_proj`、`k_proj`、`v_proj`、`o_proj`；
2. MLP/FFN 相关线性层：`gate_proj`、`up_proj`、`down_proj`；
3. LayerNorm / RMSNorm；
4. 残差连接；
5. 最后的 `lm_head`。

模型参数量越大，权重矩阵越大。比如一个线性层：

```text
Y = XW
```

其中：

```text
X: [num_tokens, hidden_size]
W: [hidden_size, output_size]
Y: [num_tokens, output_size]
```

当 `hidden_size`、`intermediate_size`、`num_layers` 很大时，单张 GPU 可能会遇到三个问题：

| 问题 | 说明 |
|---|---|
| 权重显存不足 | 模型权重本身太大，单卡放不下 |
| KV Cache 显存不足 | 长上下文、多并发时 KV Cache 很大 |
| 单卡算力不足 | 大矩阵乘法都在单卡上执行，吞吐受限 |

DP 只能复制模型、分摊请求，不能解决“单个模型副本放不下”的问题。TP 则可以把同一个模型副本切到多张 GPU 上。

## 2. 张量并行 TP 的基本概念

### 2.1 TP 到底“并行”的是什么？

张量并行不是把请求切开，也不是把 Transformer 层切开，而是把 **某一层内部的大张量计算切开**。

最典型的是切线性层权重矩阵：

```text
单卡：
Y = XW

TP 多卡：
W 被切成 W0, W1, W2, ...
每张 GPU 只算一部分：Y0 = XW0, Y1 = XW1, ...
然后通过 concat 或 all-reduce 得到完整 Y
```

所以 TP 的核心对象是：

```text
Linear / MatMul / Attention / MLP 中的大矩阵
```

### 2.2 TP size 是什么？

`tensor_parallel_size = N` 表示一个模型副本被切到 N 张 GPU 上。

例如：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct --tensor-parallel-size 4
```

含义是：

```text
一个模型副本由 4 张 GPU 共同持有和执行。
每张 GPU 是一个 TP rank。
rank 0 持有一部分权重。
rank 1 持有一部分权重。
rank 2 持有一部分权重。
rank 3 持有一部分权重。
```

### 2.3 rank 是什么？

在分布式计算中，每个参与并行计算的进程都有一个编号，这个编号叫 **rank**。

在 TP 中：

```text
TP rank 0 → GPU 0 → 持有每层权重的一部分
TP rank 1 → GPU 1 → 持有每层权重的一部分
...
```

rank 不是模型层数，也不是请求编号，而是分布式进程/GPU 的编号。

## 3. AllReduce 原理

### 3.1 什么是 collective communication？

在多 GPU 推理中，多个 GPU 经常需要一起完成某个通信操作。例如：

| 通信操作 | 含义 | 常见用途 |
|---|---|---|
| Broadcast | 一个 rank 发给所有 rank | 同步参数、同步配置 |
| Reduce | 多个 rank 结果汇总到一个 rank | 汇总统计量 |
| AllReduce | 多个 rank 结果求和后，每个 rank 都拿到完整结果 | TP 中汇总部分输出 |
| AllGather | 每个 rank 拿一部分，最后所有 rank 拿到拼接后的完整结果 | 拼接分片结果 |
| ReduceScatter | 先 reduce，再 scatter | 大规模并行优化 |
| AllToAll | 每个 rank 给其他所有 rank 发送不同数据 | MoE Expert Parallel 中常见 |

这些操作叫 collective，因为每个 rank 都要参与。只要有一个 rank 没调用，程序就可能卡死。

### 3.2 AllReduce 的数学含义

假设有 4 张 GPU：

```text
rank0 有 A0
rank1 有 A1
rank2 有 A2
rank3 有 A3
```

执行 sum AllReduce 后，每张 GPU 都得到：

```text
A = A0 + A1 + A2 + A3
```

也就是：

```text
rank0 得到 A
rank1 得到 A
rank2 得到 A
rank3 得到 A
```

它和 Reduce 的区别是：

```text
Reduce：只把结果给某一个 root rank
AllReduce：每个 rank 都得到完整结果
```

### 3.3 为什么 TP 经常需要 AllReduce？

因为有些线性层是按输入维度切分的。每个 GPU 只能算出输出的一部分贡献，最终输出需要把所有 GPU 的贡献相加。

例如：

```text
Y = XW
```

如果按 W 的行方向切：

```text
X = [X0, X1]
W = [W0; W1]
```

那么：

```text
Y = X0W0 + X1W1
```

每个 GPU 算一项：

```text
rank0: Y0 = X0W0
rank1: Y1 = X1W1
```

最终：

```text
Y = Y0 + Y1
```

这个求和过程就需要 AllReduce。

## 4. 张量并行中的两种核心线性层切法

Transformer 里大部分耗时来自矩阵乘法。TP 的关键就是怎么切 Linear。

常见有两类：

1. Column Parallel Linear，列并行线性层；
2. Row Parallel Linear，行并行线性层。

---

## 5. Column Parallel Linear：列并行

### 5.1 单卡线性层

普通线性层：

```text
Y = XW + b
```

形状：

```text
X: [B, H]
W: [H, O]
Y: [B, O]
```

其中：

```text
B = token 数，可以理解为 batch 内所有 token 数
H = hidden_size
O = output_size
```

### 5.2 按列切 W

Column Parallel 是把 `W` 的输出维度切开：

```text
W = [W0, W1, W2, W3]
```

如果 TP=4：

```text
W0: [H, O/4]
W1: [H, O/4]
W2: [H, O/4]
W3: [H, O/4]
```

每个 rank 做：

```text
rank0: Y0 = XW0  → [B, O/4]
rank1: Y1 = XW1  → [B, O/4]
rank2: Y2 = XW2  → [B, O/4]
rank3: Y3 = XW3  → [B, O/4]
```

完整输出是：

```text
Y = concat([Y0, Y1, Y2, Y3], dim=-1)
```

### 5.3 Column Parallel 的特点

| 特点 | 说明 |
|---|---|
| 每张 GPU 持有部分输出通道 | 权重显存减少为原来的 1/TP |
| 每张 GPU 算出部分输出 | 计算量减少为原来的 1/TP |
| 一般不需要立即 AllReduce | 因为输出本来就是被切开的 |
| 后续层如果能接受分片输出，就可以继续并行 | 避免不必要通信 |

### 5.4 在 Transformer 中的典型使用位置

Column Parallel 常用于：

```text
q_proj / k_proj / v_proj
gate_proj / up_proj
```

因为这些层的输出维度可以自然切分。

---

## 6. Row Parallel Linear：行并行

### 6.1 按行切 W

Row Parallel 是把 `W` 的输入维度切开：

```text
W = [W0; W1; W2; W3]
```

如果 TP=4：

```text
W0: [H/4, O]
W1: [H/4, O]
W2: [H/4, O]
W3: [H/4, O]
```

同时输入 `X` 也按 hidden 维度切开：

```text
X = [X0, X1, X2, X3]
```

每个 rank 做：

```text
rank0: P0 = X0W0
rank1: P1 = X1W1
rank2: P2 = X2W2
rank3: P3 = X3W3
```

最终输出：

```text
Y = P0 + P1 + P2 + P3
```

这个求和就需要 AllReduce。

### 6.2 Row Parallel 的特点

| 特点 | 说明 |
|---|---|
| 输入是分片的 | 每张 GPU 只拿 hidden 的一部分 |
| 权重按输入维度切 | 每张 GPU 存 `H/TP × O` |
| 输出需要求和 | 因为每张 GPU 只算了一部分贡献 |
| 常伴随 AllReduce | 把各 rank 的 partial output 加起来 |

### 6.3 在 Transformer 中的典型使用位置

Row Parallel 常用于：

```text
o_proj
down_proj
```

因为前面的 Column Parallel 已经产生了分片输出，而 `o_proj` / `down_proj` 正好可以把分片输入映射回 hidden_size。

## 7. Transformer 模型中的张量并行

```text
  ↓

  ↓
Residual Add
  ↓

```

## 8. Attention 层如何做张量并行？

### 8.1 单卡 Attention 计算

Attention 的核心计算：

```text
Q = XWq
K = XWk
V = XWv
Attention(Q, K, V) = softmax(QK^T / sqrt(d)) V
O = Attention(Q, K, V) Wo
```

形状大致为：

```text
X: [num_tokens, hidden_size]
Q/K/V: [num_tokens, num_heads, head_dim]
O: [num_tokens, hidden_size]
```

其中：

```text
hidden_size = num_heads × head_dim
```

### 8.2 QKV Projection 的 TP 切法

QKV 投影一般做 Column Parallel：

```text
Wq, Wk, Wv 按输出头维度切分
```

如果有 32 个 attention heads，TP=4，则每张 GPU 大致负责：

```text
32 / 4 = 8 个 heads
```

每张 GPU 算自己负责的 Q/K/V heads：

```text
rank0: heads 0~7
rank1: heads 8~15
rank2: heads 16~23
rank3: heads 24~31
```

这样做的好处是：

```text
每个 attention head 原本就是相对独立计算的。
把 head 切到不同 GPU 上，天然适合并行。
```

### 8.3 Attention 计算本身是否需要 AllReduce？

通常每个 rank 只计算自己负责的 heads：

```text
rank0 只算 heads 0~7 的 attention
rank1 只算 heads 8~15 的 attention
...
```

每个 rank 得到一部分 attention output：

```text
A0: [num_tokens, hidden_size/TP]
A1: [num_tokens, hidden_size/TP]
...
```

这一步通常不需要 AllReduce，因为每个 head 的 Attention 可以独立完成。

### 8.4 Output Projection 的 TP 切法

Attention output projection：

```text
O = A Wo
```

其中 `A` 是所有 heads 拼接后的结果。由于 TP 下每个 rank 只持有一部分 heads，对应输入是分片的，所以 `o_proj` 一般做 Row Parallel：

```text
rank0: P0 = A0 Wo0
rank1: P1 = A1 Wo1
rank2: P2 = A2 Wo2
rank3: P3 = A3 Wo3
```

最终：

```text
O = P0 + P1 + P2 + P3
```

所以 `o_proj` 后面需要一次 AllReduce。

### 8.5 Attention TP 小结

```text
q_proj/k_proj/v_proj：Column Parallel，按 head 切
attention kernel：每个 rank 算自己的 heads
output projection：Row Parallel，需要 AllReduce
```

完整路径：

```text
X
 ↓
ColumnParallel QKV
 ↓
每个 GPU 只算部分 heads 的 Attention
 ↓
RowParallel O Projection
 ↓
AllReduce 得到完整 hidden_states
```

## 9. MLP 层如何做张量并行？

### 9.1 单卡 MLP 结构

现代 LLM 常用 SwiGLU / Gate MLP：

```text
up = X W_up
gate = X W_gate
hidden = silu(gate) * up
out = hidden W_down
```

形状：

```text
X: [num_tokens, hidden_size]
W_up: [hidden_size, intermediate_size]
W_gate: [hidden_size, intermediate_size]
W_down: [intermediate_size, hidden_size]
```

其中 `intermediate_size` 往往比 `hidden_size` 大很多，所以 MLP 是 Transformer 中非常大的计算模块。

### 9.2 gate_proj / up_proj：Column Parallel

`gate_proj` 和 `up_proj` 通常按输出维度切：

```text
W_gate = [W_gate0, W_gate1, W_gate2, W_gate3]
W_up   = [W_up0,   W_up1,   W_up2,   W_up3]
```

每个 rank 算一部分中间维度：

```text
rank0: gate0 = X W_gate0, up0 = X W_up0
rank1: gate1 = X W_gate1, up1 = X W_up1
...
```

然后每个 rank 本地做：

```text
hidden_i = silu(gate_i) * up_i
```

这一步不需要通信，因为激活函数和逐元素乘法都在本地分片上完成。

### 9.3 down_proj：Row Parallel

`down_proj` 把 `intermediate_size` 映射回 `hidden_size`：

```text
out = hidden W_down
```

由于 `hidden` 已经按 intermediate 维度分片，所以 `W_down` 做 Row Parallel：

```text
rank0: P0 = hidden0 W_down0
rank1: P1 = hidden1 W_down1
...
```

最终：

```text
out = P0 + P1 + ...
```

所以 `down_proj` 后面需要 AllReduce。

### 9.4 MLP TP 小结

```text
gate_proj / up_proj：Column Parallel
SwiGLU 激活：各 rank 本地计算
down_proj：Row Parallel
最后 AllReduce 得到完整输出
```

完整路径：

```text
X
 ↓
ColumnParallel gate/up
 ↓
local SwiGLU
 ↓
RowParallel down
 ↓
AllReduce
 ↓
MLP output
```

## 10. LM Head / Vocabulary Parallel

最后一层通常是：

```text
logits = hidden_states W_vocab^T
```

其中：

```text
hidden_states: [num_tokens, hidden_size]
W_vocab: [vocab_size, hidden_size]
logits: [num_tokens, vocab_size]
```

`vocab_size` 很大，所以 `lm_head` 也可以按词表维度切分：

```text
rank0: vocab 0 ~ V/TP
rank1: vocab V/TP ~ 2V/TP
...
```

每个 rank 只计算一部分 logits：

```text
logits_i: [num_tokens, vocab_size/TP]
```

采样时需要注意：

1. 如果要得到完整 logits，需要 AllGather；
2. 如果做分布式 top-k/top-p，可以先在本地求局部候选，再跨 rank 合并；
3. vLLM 内部会根据模型执行和采样路径处理这些分片输出。

## 11. vLLM 中的张量并行架构

### 11.1 vLLM 的分布式执行层次

结合前面课程中的 Engine / Executor / Worker / ModelRunner，可以把 TP 流程理解为：

```text
用户请求
  ↓
API Server / LLM / AsyncLLM
  ↓
EngineCore
  ↓
Scheduler 决定本轮执行哪些 token
  ↓
Executor 接收调度结果
  ↓
多个 Worker 并行执行
  ↓
每个 Worker 绑定一个 GPU / 一个 TP rank
  ↓
每个 Worker 内部的 ModelRunner 执行模型 forward
  ↓
TP 通信：AllReduce / AllGather 等
  ↓
返回 logits / sampled token
```

### 11.2 一个 TP rank 对应什么？

当：

```text
tensor_parallel_size = 4
```

vLLM 通常会启动 4 个参与同一模型副本计算的 Worker：

```text
Worker 0 / TP rank 0 / GPU 0
Worker 1 / TP rank 1 / GPU 1
Worker 2 / TP rank 2 / GPU 2
Worker 3 / TP rank 3 / GPU 3
```

每个 Worker 的 ModelRunner：

1. 加载模型权重的一部分；
2. 维护本 rank 的 KV Cache；
3. 执行本 rank 的模型 forward；
4. 在需要时参与 collective 通信。

### 11.3 vLLM 中 TP 主要切哪些权重？

典型包括：

| 模块 | TP 切法 | 是否需要通信 |
|---|---|---|
| QKV projection | Column Parallel | 通常不立即通信 |
| Attention heads | 按 head 分给不同 rank | 通常本地计算 |
| O projection | Row Parallel | 需要 AllReduce |
| MLP gate/up | Column Parallel | 通常不立即通信 |
| MLP down | Row Parallel | 需要 AllReduce |
| LM Head | vocab parallel | 采样时可能需要跨 rank 合并 |

### 11.4 vLLM 为什么采用 Megatron-LM 风格 TP？

Megatron-LM 的核心思想就是：

```text
把 Transformer 中的大矩阵乘法拆成列并行和行并行，尽量减少通信次数。
```

也就是说，不是每个 Linear 后都通信，而是让多个局部计算连续执行，直到必须恢复完整 hidden_states 时再通信。

典型模式：

```text
Column Parallel Linear
  ↓
本地激活 / 本地 attention head 计算
  ↓
Row Parallel Linear
  ↓
AllReduce
```

这样可以把通信集中在少数必要位置。

## 12. TP 和 KV Cache 的关系

### 12.1 KV Cache 也会被切分吗？

会。因为 Attention heads 被分到不同 TP rank 上，每个 rank 只负责一部分 K/V heads。

例如：

```text
num_heads = 32
tensor_parallel_size = 4
```

则每个 rank 负责约 8 个 heads 的 K/V Cache：

```text
rank0 KV Cache: heads 0~7
rank1 KV Cache: heads 8~15
rank2 KV Cache: heads 16~23
rank3 KV Cache: heads 24~31
```

所以每个 rank 的 KV Cache 不是完整模型所有 heads 的 KV Cache，而是本 rank 负责的 heads 的 KV Cache。

### 12.2 TP 会降低 KV Cache 显存吗？

对于单个 TP rank 来说，会降低本卡 KV Cache 压力，因为每张卡只保存部分 heads 的 KV Cache。

但是从整个 TP group 总量看，所有 rank 加起来仍然保存完整模型所需的 KV Cache。

因此：

```text
单卡视角：KV Cache 显存下降
整个模型副本视角：KV Cache 总量基本不变
```

### 12.3 对 PagedAttention 有什么影响？

PagedAttention 管理的是 KV Cache block。TP 下每个 rank 都有自己的 KV Cache block pool，只不过这些 block 存的是本 rank 对应 heads 的 K/V。

逻辑上：

```text
请求 sequence 的 block table 是一致的
但每个 rank 中物理 block 存储的是本 rank 负责的 KV heads
```

也就是说：

```text
同一个 token 在不同 rank 上都有对应的 KV Cache slot，
但每个 rank 存的是不同 head 分片的 K/V。
```

## 13. TP 推理流程：从输入到输出

下面用一次请求推理串起来。

### 13.1 请求进入 vLLM

```text
prompt = "你好，请介绍一下 vLLM"
```

请求进入 API Server 后：

```text
Tokenizer 编码
  ↓
得到 input_ids
  ↓
EngineCore 接收请求
  ↓
Scheduler 决定本轮执行哪些 token
```

### 13.2 调度结果广播给 TP Workers

Scheduler 产生 `scheduler_output` 后，Executor 会把本轮模型执行任务发给所有 TP ranks：

```text
rank0 收到本轮 token ids / positions / block tables
rank1 收到本轮 token ids / positions / block tables
rank2 收到本轮 token ids / positions / block tables
rank3 收到本轮 token ids / positions / block tables
```

注意：

```text
所有 rank 都处理同一批 token，
但每个 rank 使用不同的权重分片、KV head 分片。
```

### 13.3 Embedding 阶段

输入 token id 被映射成 hidden states。

如果 embedding 做 vocab parallel，每个 rank 可能只持有一部分 embedding table。系统需要保证最终得到等价的 hidden states。

简化理解：

```text
input_ids → hidden_states
```

### 13.4 进入每一层 Transformer Block

每一层执行：

```text
RMSNorm
  ↓
QKV Column Parallel
  ↓
每个 rank 计算自己的 attention heads
  ↓
O Projection Row Parallel
  ↓
AllReduce
  ↓
Residual
  ↓
RMSNorm
  ↓
MLP gate/up Column Parallel
  ↓
本地 SwiGLU
  ↓
MLP down Row Parallel
  ↓
AllReduce
  ↓
Residual
```

### 13.5 最后得到 logits

最后：

```text
hidden_states → lm_head → logits
```

如果 lm_head 也被切分，则每个 rank 只得到部分 vocab logits。采样时需要跨 rank 合并或进行分布式采样。

### 13.6 采样并返回 token

vLLM 根据 sampling params 执行：

```text
temperature / top-k / top-p / greedy
```

选出下一个 token：

```text
next_token_id
```

然后：

1. 更新请求状态；
2. 更新 KV Cache；
3. 如果还没结束，下一轮 decode 继续；
4. 如果生成 EOS 或达到最大长度，释放资源并返回结果。

## 14. TP 在 Prefill 和 Decode 阶段的差异

### 14.1 Prefill 阶段

Prefill 输入是一整段 prompt：

```text
prompt length = L
```

每层 Attention 会处理多个 token：

```text
Q/K/V: [L, heads, head_dim]
```

特点：

| 特点 | 说明 |
|---|---|
| GEMM 较大 | 矩阵乘法规模大，GPU 利用率较高 |
| 计算密集 | 通常算力压力大 |
| TP 有较好加速效果 | 大 GEMM 被切到多卡上 |
| 通信开销相对容易被计算掩盖 | 计算量大时通信占比下降 |

### 14.2 Decode 阶段

Decode 每轮通常只生成一个 token：

```text
query token 数通常是 1
```

特点：

| 特点 | 说明 |
|---|---|
| 小 batch / 小 GEMM | 单步计算规模小 |
| 更容易 memory-bound | 读权重、读 KV Cache 成为瓶颈 |
| TP 通信开销更敏感 | 每层 AllReduce 对 latency 影响明显 |
| batch 足够大时 TP 才更有效 | continuous batching 可以缓解小 GEMM 问题 |

所以面试中经常会问：

> 为什么 TP 不一定线性加速？

答案就是：

```text
TP 减少了每张 GPU 的计算和显存，但引入了跨 GPU 通信。Prefill 计算量大，通信更容易被摊薄；Decode 单步计算小，通信开销更容易成为瓶颈。
```

## 15. TP、DP、PP 的区别

| 并行方式 | 切分对象 | 每张 GPU 是否有完整模型 | 主要目的 | 通信特点 |
|---|---|---|---|---|
| DP 数据并行 | 请求 / batch | 是 | 提高吞吐 | 推理时 DP ranks 间基本独立 |
| TP 张量并行 | 层内矩阵 / heads | 否 | 让大模型放下、加速层内计算 | 每层有 AllReduce / AllGather |
| PP 流水线并行 | Transformer layers | 否 | 跨节点/不均匀切模型 | stage 间传 hidden states |
| EP 专家并行 | MoE experts | 否 | 分散专家权重和专家计算 | 常用 AllToAll |

简单理解：

```text
DP：复制模型，切请求。
TP：切每一层的大矩阵。
PP：切模型层。
EP：切 MoE 专家。
```

## 16. TP 部署策略

### 16.1 什么时候用 TP？

适合使用 TP 的情况：

1. 模型单卡放不下；
2. 单卡吞吐不足；
3. GPU 之间通信很快，例如 NVLink；
4. 模型层内大矩阵较多，切分后能获得明显计算收益。

不适合盲目增大 TP 的情况：

1. 模型本来单卡就能高效运行；
2. GPU 之间通信慢，例如跨节点但没有高速网络；
3. decode batch 很小，通信开销大于计算收益；
4. TP size 不能很好整除模型 head 数、hidden size 或 intermediate size。

### 16.2 单机多卡部署

常见命令：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --tensor-parallel-size 4
```

含义：

```text
用 4 张 GPU 共同跑一个模型副本。
```

### 16.3 多机多卡部署

常见做法是：

```text
每个节点内部用 TP
节点之间用 PP
```

例如 2 台机器，每台 8 张 GPU：

```bash
vllm serve /path/to/model \
  --tensor-parallel-size 8 \
  --pipeline-parallel-size 2 \
  --distributed-executor-backend ray
```

含义：

```text
每个节点内部 8 卡 TP。
两个节点之间做 pipeline parallel。
```

为什么常这样配置？

```text
TP 通信频繁，最好放在节点内部高速互联上。
PP 通信频率相对低一些，更适合跨节点。
```

### 16.4 TP + DP 混合

如果有 8 张 GPU：

```text
TP=4, DP=2
```

含义是：

```text
两个模型副本。
每个模型副本由 4 张 GPU 做 TP。
```

可以理解为：

```text
DP group 0: GPU 0,1,2,3 → 一个 TP=4 的模型副本
DP group 1: GPU 4,5,6,7 → 另一个 TP=4 的模型副本
```

这样既能让大模型放下，又能通过多个副本提升并发吞吐。

## 17. TP 的性能分析

### 17.1 TP 的收益

| 收益 | 说明 |
|---|---|
| 降低单卡权重显存 | 每张卡只持有部分权重 |
| 降低单卡 KV Cache head 维度 | 每张卡只维护部分 heads 的 KV |
| 提升大 GEMM 并行度 | 大矩阵乘法分摊到多卡 |
| 支持更大模型 | 让单卡放不下的模型可以部署 |

### 17.2 TP 的代价

| 代价 | 说明 |
|---|---|
| 通信开销 | AllReduce / AllGather / Broadcast |
| 同步开销 | 每层通信要求所有 rank 进度一致 |
| 部署复杂度 | 需要正确配置 rank、进程组、GPU 可见性 |
| 故障影响更大 | 一个 rank 出错，整个 TP group 都会失败 |

### 17.3 TP 为什么不一定线性加速？

理想情况下：

```text
TP=4 → 每张卡计算量约 1/4 → 速度约 4 倍
```

真实情况下：

```text
总时间 = 计算时间 / TP + 通信时间 + 同步等待时间 + 调度开销
```

所以随着 TP size 增大：

1. 每张卡计算量下降；
2. 通信量和同步次数增加；
3. 如果通信慢，收益会被抵消。

因此 TP size 不是越大越好。

## 18. 常见面试问题与参考答案

### Q1：什么是张量并行？

张量并行是模型并行的一种，它把 Transformer 层内部的大张量计算切分到多张 GPU 上执行。最常见的是切分线性层权重矩阵，例如按输出维度做 Column Parallel，按输入维度做 Row Parallel。每张 GPU 只保存和计算权重的一部分，必要时通过 AllReduce 或 AllGather 合并结果。它主要用于解决大模型单卡显存不足和单卡计算压力过大的问题。

### Q2：TP 和 DP 有什么区别？

DP 是数据并行，每张 GPU 持有完整模型副本，不同 GPU 处理不同请求或 batch。TP 是张量并行，一个模型副本被切到多张 GPU 上，每张 GPU 只持有模型每层权重的一部分，多个 GPU 共同完成同一个请求的模型 forward。DP 提升请求吞吐，TP 解决单模型过大和层内计算压力。

### Q3：AllReduce 是什么？

AllReduce 是一种 collective communication。每个 rank 输入一个张量，系统对这些张量做 reduce 操作，例如求和，然后把结果返回给所有 rank。比如 TP 中 Row Parallel Linear 每个 rank 只算出 partial output，最终完整输出等于所有 partial output 之和，因此需要 AllReduce。

### Q4：为什么 Row Parallel 后面需要 AllReduce？

Row Parallel 是按输入维度切权重。假设 `X=[X0,X1]`，`W=[W0;W1]`，则完整输出是 `Y=X0W0+X1W1`。每个 rank 只能算一项 partial output，所以需要 AllReduce 把所有 rank 的 partial output 求和，并让每个 rank 都拿到完整输出。

### Q5：Column Parallel 后面一定需要通信吗？

不一定。Column Parallel 按输出维度切权重，每个 rank 得到输出的一部分。如果后续计算可以继续使用这个分片输出，例如 MLP 中的激活函数或 Attention 中每个 rank 计算自己的 heads，就可以暂时不通信。通常会等到 Row Parallel 输出需要恢复完整 hidden states 时才通信。

### Q6：Transformer Attention 怎么做 TP？

QKV projection 通常做 Column Parallel，按 head 维度切分。每个 rank 负责一部分 attention heads，并在本地计算这些 heads 的 attention。随后 output projection 做 Row Parallel，每个 rank 算一部分贡献，最后通过 AllReduce 得到完整 hidden states。

### Q7：Transformer MLP 怎么做 TP？

MLP 中 `gate_proj` 和 `up_proj` 通常做 Column Parallel，输出 intermediate_size 的一部分；SwiGLU 激活在每个 rank 本地完成；`down_proj` 做 Row Parallel，把分片 intermediate 映射回 hidden_size，最后通过 AllReduce 汇总得到完整输出。

### Q8：vLLM 中 `tensor_parallel_size=4` 表示什么？

表示一个模型副本由 4 张 GPU 共同执行。vLLM 会为 TP group 启动多个 Worker，每个 Worker 对应一个 GPU/rank。每个 rank 加载模型权重的一部分，执行自己负责的矩阵分片计算，并在需要时参与 AllReduce 等通信。

### Q9：TP 会降低 KV Cache 显存吗？

从单卡视角看，会降低，因为每个 rank 只负责部分 attention heads，因此只保存这些 heads 对应的 K/V Cache。从整个模型副本视角看，所有 rank 的 KV Cache 合起来仍然对应完整模型需要的 KV Cache。

### Q10：为什么 TP 在 Decode 阶段可能收益不明显？

Decode 阶段每轮通常只生成一个 token，矩阵乘法规模较小，GPU 计算利用率不如 prefill 阶段。同时每层仍可能需要 AllReduce，通信和同步开销在 decode 中占比更高。因此 TP 在 prefill 的大 GEMM 场景中更容易获得收益，而 decode 需要依赖 continuous batching 等机制提高批量规模。

### Q11：为什么多机部署时通常节点内 TP、节点间 PP？

TP 通信频繁，几乎每层都会有通信，适合放在 NVLink/NVSwitch 等高速节点内互联上。跨节点网络延迟和带宽通常不如节点内互联，因此跨节点直接做大 TP 可能通信开销很高。PP 按层切分，stage 间只传 hidden states，通信频率相对低，所以更适合跨节点。

### Q12：TP size 是越大越好吗？

不是。TP size 增大可以降低单卡显存和计算量，但也会增加通信和同步开销。当通信开销超过计算收益时，继续增大 TP size 反而可能降低性能。选择 TP size 时要考虑模型大小、GPU 互联、batch 大小、prefill/decode 比例、head 数和 hidden size 是否能整除。

### Q13：为什么 TP 要求各 rank 的 collective 调用一致？

因为 AllReduce、AllGather 这类 collective operation 要求同一进程组内所有 rank 以一致的顺序、数据类型和数据量参与。如果某个 rank 没有进入同一个 collective，其他 rank 会一直等待，导致 hang。

### Q14：TP 和 PagedAttention 是什么关系？

TP 负责切分模型权重和 attention heads，PagedAttention 负责管理 KV Cache 的分页存储。TP 下每个 rank 有自己的 KV Cache block pool，保存本 rank 负责的 KV heads。请求的逻辑 block table 可以一致，但每个 rank 的物理 KV block 内容是不同 head 分片。

### Q15：如果面试官让你描述 vLLM TP 的完整推理链路，你怎么回答？

用户请求进入 vLLM 后先被 tokenizer 转成 token ids，EngineCore 接收请求并由 Scheduler 决定本轮执行哪些 token。Executor 将调度结果广播给多个 TP Workers。每个 Worker 绑定一个 GPU/rank，由内部 ModelRunner 执行模型 forward。每层中 QKV 和 MLP gate/up 做 Column Parallel，本地计算分片；attention heads 和激活函数在本 rank 本地执行；o_proj 和 down_proj 做 Row Parallel，并通过 AllReduce 汇总 partial output。最终 lm_head 得到 logits，采样出 next token，更新 KV Cache 和请求状态，继续下一轮 decode 或结束请求。

## 19. 一句话总结

张量并行的本质是：

```text
把 Transformer 每层中最重的矩阵乘法切到多张 GPU 上，
通过 Column Parallel 减少立即通信，
通过 Row Parallel + AllReduce 恢复完整输出，
从而让大模型能部署、能推理、能获得更高吞吐。
```

对于 vLLM 面试来说，最重要的是能讲清楚：

```text
TP 为什么需要 → AllReduce 是什么 → Linear 怎么切 → Attention/MLP 怎么切 → vLLM Worker/ModelRunner 怎么对应 rank → TP 的收益和代价
```
