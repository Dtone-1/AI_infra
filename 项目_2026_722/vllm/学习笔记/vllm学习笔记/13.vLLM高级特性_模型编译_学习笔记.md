# vLLM 高级特性：模型编译学习笔记

> 课时 17：vLLM 高级特性：模型编译  
> 课程关键词：`torch.compile`、TorchDynamo、FX Graph、TorchInductor、AOTAutograd、graph break、guards、dynamic shape、vLLM compilation、piecewise compilation、splitting ops、Inductor backend、custom backend、CUDA Graph、Model Forward 编译

---

## 0. 本节课核心目标

本节课主要讲 **vLLM 为什么需要模型编译，以及 vLLM 如何在大模型推理中使用 PyTorch 编译体系提升性能**。

在普通 PyTorch eager 模式下，模型 forward 中的每个 Python 调用、每个算子调度、每个小 kernel 都可能产生额外开销。对于 LLM 推理来说，尤其是 decode 阶段：

```text
每轮 decode 只生成少量 token
        ↓
单次算子规模可能不大
        ↓
CPU 调度开销、Python overhead、kernel launch overhead 变得明显
        ↓
吞吐和 ITL 受到影响
```

模型编译要做的事情是：

```text
Python eager model
  ↓ 捕获计算图
FX Graph / IR
  ↓ 图优化
融合、消除冗余、调度优化、代码生成
  ↓ 编译后执行
更少 Python 调度、更少 kernel、更高执行效率
```

vLLM 中的模型编译并不是“把整个模型一次性变成静态图”这么简单，因为 vLLM 的推理输入非常动态：

- 请求数量动态；
- sequence 长度动态；
- prefill / decode 混合；
- KV Cache block table 动态；
- attention backend 动态；
- 分布式通信动态；
- LoRA / MoE / 量化 / speculative decoding 可能改变执行路径。

所以 vLLM 使用了更工程化的方案：

> **通过 torch.compile 进行模型子图编译，并通过 piecewise compilation 把适合编译的部分切出来，避开动态性强的 attention / KV Cache / 通信边界，从而在性能和灵活性之间折中。**

# 第一部分：为什么 LLM 推理需要模型编译？

## 1. PyTorch eager 模式是什么？

PyTorch 默认是 eager execution：

```python
y = model(x)
```

执行到哪一行，就立即运行哪一行。

优点：

- 易调试；
- 动态性强；
- Python 表达能力强；
- 适合研究和开发。

缺点：

- Python 调度开销高；
- 算子之间缺少全局优化；
- 小算子多时 kernel launch overhead 明显；
- 难以自动做算子融合；
- 对 decode 这种小 batch 场景不够高效。

例如一个 Transformer block 中可能有：

```text
RMSNorm
Linear QKV
RoPE
Attention
Linear O
Residual Add
RMSNorm
MLP Gate/Up
Activation
MLP Down
Residual Add
```

如果这些都按 eager 逐个调度，CPU 需要不断发起 GPU kernel。对于大 batch prefill，GPU 计算量很大，调度开销被摊薄；但对于 decode 小 batch，调度开销会更明显。

---

## 2. LLM 推理中的性能瓶颈

### 2.1 Prefill 阶段

Prefill 一次处理完整 prompt：

```text
input shape: [batch, prompt_len]
```

特点：

- token 数多；
- GEMM 大；
- Attention 矩阵大；
- GPU 利用率相对高；
- 更偏 compute-bound。

### 2.2 Decode 阶段

Decode 每一步每个请求只新增一个 token：

```text
input shape: [batch, 1]
```

特点：

- 每步只处理新 token；
- 需要读历史 KV Cache；
- 需要读模型权重；
- GEMM 相对小；
- kernel launch / Python overhead / memory bandwidth 更明显；
- 更容易 memory-bound 或 launch-bound。

因此在 decode 阶段，减少调度开销、减少小 kernel 数量、融合算子、固定执行路径，对延迟很关键。

---

## 3. 模型编译能优化什么？

模型编译通常能优化以下内容：

| 优化方向 | 解释 |
|---|---|
| 减少 Python overhead | 捕获计算图后，不再每个 op 都经过 Python 调度 |
| 算子融合 | 把多个小算子融合成一个 kernel |
| 内存访问优化 | 减少中间 tensor 写回显存 |
| 静态 shape 专用化 | 对常见 shape 生成高效代码 |
| 消除冗余计算 | 删除无用 reshape / cast / view 等 |
| 调度优化 | 更好安排 kernel 执行顺序 |
| 后端代码生成 | 生成 Triton / C++ / CUDA 等代码 |

例如：

```text
x = rmsnorm(x)
x = x * scale
x = x + residual
```

可能被融合成一个或少数几个 kernel，减少中间 tensor 读写。

# 第二部分：torch.compile 基础

## 4. torch.compile 是什么？

`torch.compile` 是 PyTorch 2.x 引入的模型编译入口。

基本用法：

```python
compiled_model = torch.compile(model)
out = compiled_model(x)
```

它的目标是：

```text
尽量保持 PyTorch 用户体验不变
        ↓
自动捕获 Python/PyTorch 代码中的 tensor 计算
        ↓
交给后端编译优化
        ↓
返回一个更快的 callable
```

它是“可选增强”：

```text
不用 torch.compile，模型仍然能跑；
用了 torch.compile，如果成功，可能更快。
```

---

## 5. torch.compile 的核心组件

### 5.1 TorchDynamo

TorchDynamo 负责：

```text
从 Python 字节码层捕获 PyTorch tensor 计算图
```

它会观察模型 forward 的执行，把 tensor 运算提取成 FX Graph。

简单理解：

```text
Python forward 函数
  ↓ TorchDynamo 捕获
FX Graph
```

它还会生成 guards，用于判断未来输入是否仍然适合复用同一个 compiled graph。

---

### 5.2 FX Graph

FX Graph 是 PyTorch 的图表示。

例如原始代码：

```python
def forward(x, w):
    y = x @ w
    z = torch.relu(y)
    return z
```

可能被捕获成类似：

```text
placeholder x
placeholder w
call_function matmul
call_function relu
output
```

FX Graph 的好处是：

- 可以被分析；
- 可以被变换；
- 可以被后端编译；
- 可以打印出来调试。

---

### 5.3 TorchInductor

TorchInductor 是 `torch.compile` 默认编译后端。

它负责：

```text
FX Graph
  ↓ 优化
Lowering
  ↓ 生成代码
Triton / C++ / CUDA kernel
```

在 GPU 上，Inductor 经常会生成 Triton kernel 来执行融合后的计算。

---

### 5.4 AOTAutograd

AOTAutograd 主要用于训练场景，它会把 forward 和 backward 图提前捕获并编译。

在 vLLM 推理中，重点不是 backward，而是 forward 推理图，所以你可以先把 AOTAutograd 理解为 PyTorch 编译体系的一部分，但 vLLM 推理学习中重点放在：

```text
TorchDynamo 捕获 forward 图
TorchInductor 编译 forward 子图
```

---

## 6. torch.compile 的执行过程

整体流程：

```text
第一次调用 compiled_model(x)
        ↓
TorchDynamo 观察 Python 执行
        ↓
捕获可编译的 tensor 运算
        ↓
形成 FX Graph
        ↓
生成 guards
        ↓
交给 backend，例如 Inductor
        ↓
backend 生成优化代码
        ↓
缓存 compiled graph
        ↓
执行编译后代码

后续调用 compiled_model(x2)
        ↓
检查 guards 是否满足
        ↓
满足：直接复用 compiled graph
        ↓
不满足：重新编译或 fallback
```

---

## 7. Guards 是什么？

Guards 是 torch.compile 生成的条件检查。

它们用于判断：

```text
当前输入是否仍然符合之前编译图的假设？
```

可能包括：

- tensor shape；
- tensor dtype；
- tensor device；
- tensor stride；
- Python 常量；
- module 属性；
- 分支条件；
- 动态 shape 范围。

例如第一次编译时输入是：

```text
x.shape = [8, 4096]
dtype = float16
device = cuda
```

后面来了：

```text
x.shape = [16, 4096]
```

如果原图没有支持动态 batch，那么 guard 可能失败，触发 recompile。

---

## 8. Graph Break 是什么？

Graph break 指的是：

```text
torch.compile 无法继续捕获完整计算图，被迫切断图，回到 eager 执行一段代码。
```

常见原因：

- Python 控制流依赖 tensor 值；
- 不支持的 Python 操作；
- print / logging；
- list / dict 动态修改；
- 某些自定义 C++ op；
- 数据依赖的 shape 改变；
- `.item()` 把 tensor 值取回 Python；
- 动态分支太复杂。

例如：

```python
if x.sum().item() > 0:
    y = x * 2
else:
    y = x - 2
```

这里 `.item()` 需要把 GPU tensor 值同步回 CPU，且 Python 分支依赖 tensor 值，很容易造成 graph break。

---

## 9. 为什么 graph break 对性能不好？

因为 graph break 会让一个大图变成多个小图：

```text
Graph 1 -> eager Python -> Graph 2 -> eager Python -> Graph 3
```

问题：

- 编译优化范围变小；
- fusion 机会减少；
- Python overhead 重新出现；
- CPU-GPU 同步可能增加；
- 编译缓存管理更复杂。

所以优化 torch.compile 时，常见目标是：

```text
减少 graph break
扩大可编译子图
控制 recompile 次数
```

# 第三部分：Triton / CUDA Graph / torch.compile 的区别

## 10. 三者分别解决什么问题？

| 技术 | 解决的问题 | 作用层次 |
|---|---|---|
| Triton | 写高性能 GPU kernel | 算子实现层 |
| torch.compile | 捕获 PyTorch 计算图并优化 | 模型图编译层 |
| CUDA Graph | 录制一段 GPU 操作并重复 replay | GPU launch 调度层 |

### 10.1 Triton

Triton 是写 GPU kernel 的语言 / 编译器。

你可以用 Triton 写：

- matmul；
- softmax；
- layernorm；
- attention；
- fused MoE；
- sampling kernel。

### 10.2 torch.compile

torch.compile 是更高层的编译入口：

```text
PyTorch Module -> FX Graph -> Inductor -> Triton/C++ code
```

它可能自动生成 Triton kernel，但用户不一定手写 Triton。

### 10.3 CUDA Graph

CUDA Graph 不关心模型语义，它记录的是一段 GPU 操作序列：

```text
kernel A
kernel B
memcpy C
kernel D
```

然后以后重复 replay，减少 CPU launch overhead。

---

## 11. 三者在 vLLM 中的关系

在 vLLM 中常见组合是：

```text
模型 forward 子图
  ↓ torch.compile / Inductor 编译
生成优化 kernel
  ↓ CUDA Graph capture
后续 decode 直接 replay
```

但并不是所有部分都适合同时编译和 capture：

- attention 可能有动态 KV Cache；
- MoE 可能有动态 token dispatch；
- speculative decoding shape 复杂；
- multi-LoRA 动态性强；
- 分布式通信有特殊要求。

所以 vLLM 需要选择性编译。

# 第四部分：vLLM 编译架构和优化技术

## 12. vLLM 为什么不能简单 full compile 整个模型？

LLM 服务推理不是普通离线模型推理，它有很多动态因素。

### 12.1 动态 batch

Continuous batching 中，每一轮调度的 batch 可能不同：

```text
step 1: 32 个 decode 请求
step 2: 30 个 decode + 2 个 prefill
step 3: 40 个 decode
```

### 12.2 动态序列长度

每个请求长度不同：

```text
request A: past_len = 128
request B: past_len = 4096
request C: past_len = 900
```

### 12.3 动态 KV Cache

PagedAttention 中 attention 需要：

```text
block_tables
slot_mapping
query_start_loc
seq_lens
```

这些元数据每一步都可能变化。

### 12.4 不同 backend

vLLM 可能根据硬件和配置选择：

- FlashAttention；
- FlashInfer；
- Triton attention；
- PagedAttention CUDA kernel；
- xFormers；
- CPU backend；
- ROCm backend；
- XPU / TPU / Ascend backend。

### 12.5 分布式通信

TP / EP 中有：

- AllReduce；
- AllGather；
- ReduceScatter；
- AllToAll；
- custom allreduce。

这些通信 op 对图捕获和编译有额外约束。

因此 full compile 可能面临：

```text
频繁 graph break
频繁 recompile
动态 shape 太多
编译开销过大
某些 op 不支持
收益不稳定
```

---

## 13. vLLM 的编译目标

vLLM 的编译目标不是“所有东西都编译”，而是：

```text
尽量编译稳定、重复、适合优化的计算部分；
保留动态性强的部分为 eager 或特殊 backend。
```

主要优化目标：

1. 减少 decode 阶段 CPU overhead；
2. 融合 Transformer block 中的非 attention 小算子；
3. 减少 kernel launch；
4. 为 CUDA Graph capture 创造稳定子图；
5. 避免 attention / KV Cache 动态部分拖累整个图；
6. 在不同模型和硬件上保持兼容性。

---

## 14. vLLM 编译配置

vLLM 通过 compilation config 控制编译行为。

命令行中常见形式：

```bash
--compilation-config '{"level":3}'
```

或者更完整：

```bash
--compilation-config '{
  "level": 3,
  "backend": "inductor",
  "custom_ops": [],
  "splitting_ops": ["vllm.unified_attention", "vllm.unified_attention_with_output"],
  "compile_sizes": [1, 2, 4, 8, 16, 32]
}'
```

不同版本字段可能变化，但核心含义通常包括：

| 字段 | 含义 |
|---|---|
| `level` | 编译等级，控制是否启用 eager / Dynamo / Inductor / piecewise |
| `backend` | 编译后端，如 `inductor`、`eager`、自定义 backend |
| `splitting_ops` | 用于切分图的 op，常用于 attention 边界 |
| `compile_sizes` | 针对特定 batch size / shape 编译专用图 |
| `cudagraph_mode` | CUDA Graph 模式 |
| `cudagraph_capture_sizes` | 需要捕获的 batch size |
| `use_cudagraph` | 是否使用 CUDA Graph |
| `max_capture_size` | 最大 capture batch size |

# 第五部分：分段编译 Piecewise Compilation

## 15. 什么是 Piecewise Compilation？

Piecewise Compilation 可以理解为：

> **不强行编译整个模型 forward，而是把模型图切成多个适合编译的片段，对片段分别编译。**

例如一个 Transformer 层：

```text
RMSNorm
QKV Linear
RoPE
Attention
O Projection
Residual
RMSNorm
MLP
Residual
```

其中 Attention 动态性强，可能不适合被 Inductor 编译。

vLLM 可以把 attention 作为切分点：

```text
[Norm + QKV + RoPE]  -> compiled piece 1
Attention            -> eager/custom attention backend
[OProj + MLP + Add]  -> compiled piece 2
```

这样既能保留 attention backend 的灵活性，又能编译大量稳定的 dense / elementwise 计算。

---

## 16. 为什么要按 attention 切分？

Attention 是 vLLM 中最复杂、最动态的部分之一。

它依赖：

- KV Cache；
- block table；
- slot mapping；
- seq len；
- query start loc；
- prefill / decode 状态；
- paged memory layout；
- attention backend；
- sliding window / prefix caching；
- speculative decode 形态。

如果强行把 attention 放入一个大 compile graph：

```text
可能 graph break
可能 recompile
可能 shape guard 爆炸
可能无法使用高性能手写 attention kernel
```

所以把 attention 作为 graph boundary 是合理的工程折中。

---

## 17. splitting_ops 的作用

`splitting_ops` 用于告诉 vLLM：

```text
遇到这些 op 时，把图切开。
```

常见切分 op 可能包括：

```text
vllm.unified_attention
vllm.unified_attention_with_output
```

示意：

```text
FX Graph:
  op1 -> op2 -> unified_attention -> op3 -> op4

切分后：
  piece A: op1 -> op2
  boundary: unified_attention
  piece B: op3 -> op4
```

这就是 piecewise compilation 的核心。

---

## 18. Piecewise Compilation 的优点

| 优点 | 解释 |
|---|---|
| 避开动态 attention | 减少 graph break 和 recompile |
| 保留高性能 attention backend | attention 仍可使用 FlashAttention / PagedAttention |
| 编译稳定子图 | dense / norm / activation / residual 更适合编译 |
| 更适合 CUDA Graph | 编译后的 piece 更容易 capture |
| 兼容性更好 | 不要求所有 op 都能被 Inductor 处理 |

---

## 19. Piecewise Compilation 的代价

| 代价 | 解释 |
|---|---|
| 图优化范围变小 | attention 前后不能跨边界融合 |
| 实现复杂 | 需要 wrapper、graph splitting、backend 管理 |
| 调试复杂 | 错误可能来自 Dynamo、Inductor、vLLM wrapper 或 backend |
| 编译缓存复杂 | 多个 piece、多种 shape 都要管理 |
| 不一定总是提升 | 小模型、短请求、频繁 recompile 可能收益有限 |

# 第六部分：vLLM 编译流程

## 20. vLLM 模型执行链路中的编译位置

普通 vLLM 推理链路：

```text
Engine
  ↓
Scheduler
  ↓
Executor
  ↓
Worker
  ↓
ModelRunner
  ↓
model.forward()
  ↓
Sampler
```

模型编译作用在：

```text
ModelRunner 调用 model.forward() 附近
```

即：

```text
model = load_model(...)
model = maybe_compile_model(model, compilation_config)
output = model(input_ids, positions, kv_caches, attn_metadata, ...)
```

---

## 21. 编译初始化阶段

服务启动时，vLLM 会读取配置：

```text
CompilationConfig
```

然后决定：

- 是否启用 compile；
- 使用什么 backend；
- 是否 piecewise；
- 是否 CUDA Graph；
- 需要 capture 哪些 size；
- 哪些 op 是 splitting_ops；
- 哪些 custom ops 需要特殊处理。

---

## 22. 第一次执行：捕获和编译

第一次遇到某种 shape / batch size 时：

```text
model.forward(inputs)
  ↓
TorchDynamo 捕获图
  ↓
根据 splitting_ops 切分图
  ↓
把可编译 piece 交给 Inductor
  ↓
Inductor 生成优化代码
  ↓
缓存 compiled piece
```

如果同时启用 CUDA Graph，可能还会：

```text
warmup
  ↓
capture
  ↓
保存 graph runnable
```

---

## 23. 后续执行：复用 compiled graph

后续请求如果满足 guards：

```text
shape / dtype / device / stride / config 没有违反假设
```

则直接复用已编译代码。

如果不满足：

```text
触发新图编译
或 fallback 到 eager
```

---

## 24. 编译 size 专用化

对于 decode 阶段，batch size 可能是：

```text
1, 2, 4, 8, 16, 32, 64
```

vLLM 可以针对常见 batch size 编译不同专用图：

```text
batch=1  -> compiled graph A
batch=2  -> compiled graph B
batch=4  -> compiled graph C
...
```

优点：

- shape 更固定；
- Inductor 优化更强；
- CUDA Graph capture 更容易；
- decode replay 更快。

缺点：

- 编译时间增加；
- 显存 / 缓存占用增加；
- 不在列表中的 shape 可能 fallback 或 padding。

---

## 25. vLLM 编译和 CUDA Graph 的关系

### 25.1 编译和 CUDA Graph 是正交概念

编译：

```text
优化计算图，生成更快代码
```

CUDA Graph：

```text
录制 GPU 操作序列，减少 launch overhead
```

它们可以同时使用，也可以单独使用。

### 25.2 vLLM 中的常见组合

```text
torch.compile piecewise compilation
        ↓
对编译后的稳定片段进行 CUDA Graph capture
        ↓
decode 时 replay
```

### 25.3 为什么 piecewise compilation 有助于 CUDA Graph？

CUDA Graph 需要执行形态稳定。

如果把动态 attention 排除在 graph 外，只 capture 稳定片段：

```text
compiled piece
  ↓
capture
  ↓
replay
```

稳定性更好。

# 第七部分：编译实例

## 26. torch.compile 最小例子

```python
import torch
import torch.nn as nn

class TinyMLP(nn.Module):
    def __init__(self, hidden_size):
        super().__init__()
        self.fc1 = nn.Linear(hidden_size, hidden_size * 4)
        self.act = nn.SiLU()
        self.fc2 = nn.Linear(hidden_size * 4, hidden_size)

    def forward(self, x):
        return self.fc2(self.act(self.fc1(x)))

model = TinyMLP(4096).cuda().half()
compiled_model = torch.compile(model, backend="inductor")

x = torch.randn(16, 4096, device="cuda", dtype=torch.float16)

# 第一次执行可能触发编译，较慢
y = compiled_model(x)

# 后续执行复用编译结果，通常更快
y = compiled_model(x)
```

重点：

```text
第一次慢：编译开销
后续快：复用 compiled graph
```

## 27. graph break 示例

```python
class BadModule(nn.Module):
    def forward(self, x):
        if x.sum().item() > 0:
            return x * 2
        else:
            return x - 2
```

问题：

```text
x.sum().item() 把 GPU tensor 值取回 Python
Python 分支依赖 tensor 数据
Dynamo 难以静态捕获完整图
```

更好的方式是使用 tensor 表达：

```python
class BetterModule(nn.Module):
    def forward(self, x):
        return torch.where(x.sum() > 0, x * 2, x - 2)
```

但这也要看具体 shape 和 backend 支持情况。

## 28. Transformer Block 编译示意

简化 Transformer block：

```python
class Block(nn.Module):
    def __init__(self):
        super().__init__()
        self.norm1 = RMSNorm()
        self.qkv = nn.Linear(...)
        self.attn = Attention()
        self.o_proj = nn.Linear(...)
        self.norm2 = RMSNorm()
        self.mlp = MLP()

    def forward(self, x, attn_metadata, kv_cache):
        residual = x
        x = self.norm1(x)
        qkv = self.qkv(x)
        attn_out = self.attn(qkv, kv_cache, attn_metadata)
        x = residual + self.o_proj(attn_out)

        residual = x
        x = self.norm2(x)
        x = residual + self.mlp(x)
        return x
```

Piecewise 后可以理解为：

```text
piece 1:
  norm1 + qkv

boundary:
  attention(qkv, kv_cache, attn_metadata)

piece 2:
  o_proj + residual + norm2 + mlp + residual
```

# 第八部分：常见问题与调试

## 30. 为什么第一次请求特别慢？

因为可能发生：

```text
模型加载
warmup
torch.compile 编译
Inductor 代码生成
CUDA Graph capture
```

所以第一次请求不能代表稳定性能。

Benchmark 时应区分：

```text
cold start latency
warmup latency
steady-state latency
```

---

## 31. 为什么开启编译后反而变慢？

可能原因：

1. 编译开销被算进测试时间；
2. batch shape 太动态，频繁 recompile；
3. graph break 太多，优化范围很小；
4. 模型太小，compile 收益小；
5. attention / communication 才是真瓶颈；
6. Inductor 生成代码不如手写 kernel；
7. 与量化 / LoRA / MoE / speculative decoding 组合不佳；
8. CUDA Graph capture sizes 设置不合理。

---

## 32. 如何判断有没有频繁 recompile？

可以观察：

- 日志中是否不断出现 compile；
- 第 N 次请求是否仍然慢；
- GPU 利用率是否不稳定；
- CPU 占用是否异常高；
- shape 变化是否非常多；
- batch size 是否不在 capture / compile sizes 中。

---

## 33. 如何减少 recompile？

常见办法：

- 固定 batch size 或使用 padding；
- 设置合理的 compile sizes；
- 减少动态 Python 控制流；
- 避免 `.item()` / data-dependent branch；
- 把动态部分切成 splitting op；
- 使用 piecewise compilation；
- 对 decode 常见 batch size 做 capture；
- 对复杂特性 fallback eager。

---

## 34. 编译和数值正确性

编译可能改变：

- 算子融合顺序；
- 浮点计算顺序；
- 中间精度；
- kernel 实现；
- reduction 顺序。

因此输出可能出现微小数值差异。

对于生成模型，微小 logits 差异可能在采样时放大成不同 token，尤其在 temperature > 0 时更明显。

验证时应区分：

```text
数值误差是否在可接受范围内
生成文本不同是否来自采样随机性
是否存在真正 correctness bug
```

# 第十部分：面试问答

## 39. 面试题 1：torch.compile 是什么？

答：

`torch.compile` 是 PyTorch 2.x 的模型编译入口。它通过 TorchDynamo 捕获 Python/PyTorch forward 中的 tensor 运算，生成 FX Graph，再交给后端如 TorchInductor 优化和代码生成。它可以减少 Python 调度开销，做算子融合、图优化和后端代码生成，从而提升训练或推理性能。

---

## 40. 面试题 2：TorchDynamo 和 TorchInductor 分别做什么？

答：

TorchDynamo 负责从 Python 字节码层捕获可编译的 tensor 计算图，并生成 guards。TorchInductor 是默认后端，负责对捕获到的 FX Graph 做优化和 lowering，在 GPU 上通常生成 Triton kernel 或相关低层代码执行。简单说，Dynamo 管“抓图”，Inductor 管“优化和生成代码”。

---

## 41. 面试题 3：什么是 graph break？

答：

Graph break 是指 torch.compile 在捕获图时遇到无法静态表示或不支持的 Python / tensor 操作，被迫中断当前图捕获，回到 eager 执行一段代码。常见原因包括 tensor `.item()`、数据依赖的 Python 分支、不支持的自定义 op、动态控制流、Python I/O 等。Graph break 会缩小编译优化范围，降低融合机会，并重新引入 Python overhead。

---

## 42. 面试题 4：为什么 vLLM 不直接 full compile 整个模型？

答：

因为 vLLM 的推理输入高度动态，包括 continuous batching、动态 seq_len、KV Cache block table、prefill/decode 混合、attention backend、TP/EP 通信、LoRA、MoE、投机解码等。如果强行 full compile，容易出现 graph break、recompile、shape guard 复杂、backend 不支持等问题。vLLM 更倾向于把稳定的 dense / elementwise 子图编译，把动态 attention / KV Cache / 通信边界保留为特殊 op 或 eager 路径。

---

## 43. 面试题 5：什么是 piecewise compilation？

答：

Piecewise compilation 是分段编译。它不编译整个模型 forward，而是根据 splitting ops 把计算图切成多个片段，对适合编译的片段分别交给 Inductor 编译。例如在 Transformer block 中，可以把 attention 作为边界，编译 attention 前后的 norm、linear、MLP、residual 等稳定子图，而 attention 本身继续使用 vLLM 的高性能 attention backend。

---

## 44. 面试题 6：为什么 attention 常被作为 splitting op？

答：

因为 attention 在 vLLM 中依赖 KV Cache、block table、slot mapping、seq_lens、query_start_loc、paged memory layout、prefill/decode 状态和不同 attention backend，动态性很强。如果把它放入大 compile graph，容易造成 graph break 或 recompile，也可能无法使用手写优化 kernel。把 attention 作为 splitting op 可以保留 attention backend 的灵活性，同时编译前后的稳定计算。

---

## 45. 面试题 7：torch.compile 和 CUDA Graph 有什么区别？

答：

torch.compile 是模型图编译技术，目标是捕获 PyTorch 计算图并优化生成更高效代码，例如通过 Inductor 生成 Triton kernel。CUDA Graph 是 GPU 执行图录制和 replay 技术，目标是减少重复 kernel launch 的 CPU overhead。前者优化“算什么、怎么生成代码”，后者优化“如何重复提交 GPU 工作”。二者可以组合使用。

---

## 46. 面试题 8：为什么第一次请求编译后会很慢？

答：

第一次请求可能包含模型 warmup、TorchDynamo 抓图、Inductor 编译、代码生成、kernel autotune、CUDA Graph capture 等过程。这些都是一次性或少量发生的准备开销。稳定性能应该看 warmup 后的 steady-state latency，而不是 cold start latency。

---

## 47. 面试题 9：开启编译后一定更快吗？

答：

不一定。编译收益取决于模型、batch shape、dynamic shape、graph break 数量、backend 质量、attention 是否是瓶颈、是否频繁 recompile、是否结合 CUDA Graph 等。如果请求 shape 太动态或 graph break 太多，编译收益可能很小甚至变慢。因此必须通过 benchmark 对比 eager、compile、compile+cudagraph 等模式。

---

## 48. 面试题 10：vLLM 编译对 decode 阶段有什么帮助？

答：

Decode 阶段每步 token 数少，算子规模小，CPU 调度和 kernel launch overhead 更明显。编译可以融合 decode 中 attention 以外的稳定小算子，减少 Python 调度和 kernel 数量，并为 CUDA Graph replay 提供更稳定的子图，因此通常更有利于降低 ITL / TPOT。

---

## 49. 面试题 11：guards 失败会发生什么？

答：

guards 用于检查当前输入是否满足之前编译图的假设，例如 shape、dtype、device、stride、module 属性等。如果 guards 失败，torch.compile 可能会触发重新编译，或者 fallback 到 eager。频繁 guards 失败会导致 recompile 过多，吞吐下降、延迟抖动。

---

## 50. 面试题 12：如何调试 vLLM 编译问题？

答：

可以先关闭编译确认 eager 正确性，再逐步开启 compile、piecewise compile、CUDA Graph。观察日志中是否有 graph break、recompile、capture 失败。检查 batch shape 是否过于动态，splitting ops 是否合理，attention / LoRA / MoE / quantization 是否兼容。必要时减小编译 level 或对问题模块 fallback eager。

---

# 第十一部分：本节课总结

本节课主线可以总结为：

```text
PyTorch eager 模式灵活但调度开销大
        ↓
LLM decode 阶段小 batch / 小算子 / 频繁 forward
        ↓
Python overhead 和 kernel launch overhead 影响 ITL
        ↓
torch.compile 用 Dynamo 抓图，用 Inductor 编译优化
        ↓
但 vLLM 输入动态，不能简单 full compile
        ↓
vLLM 使用 compilation config 控制编译等级和 backend
        ↓
通过 splitting ops 做 piecewise compilation
        ↓
attention / KV Cache 等动态部分作为边界
        ↓
dense / norm / MLP / residual 等稳定片段被编译
        ↓
进一步可结合 CUDA Graph capture / replay
        ↓
提升 decode 稳态性能
```

最重要的理解是：

> **vLLM 的模型编译不是简单调用 `torch.compile(model)`，而是在复杂在线推理系统中选择性编译稳定子图，把动态 attention、KV Cache 和通信边界留给专门后端处理。**
