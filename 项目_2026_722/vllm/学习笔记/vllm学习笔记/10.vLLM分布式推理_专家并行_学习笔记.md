## 0. 本节课在 vLLM / AI Infra 学习路线中的位置

前面课程已经分别讲过：

- **数据并行 DP**：复制完整模型，让不同 GPU / 进程处理不同请求；
- **张量并行 TP**：把一个 dense 层的矩阵切到多张 GPU 上，需要 AllReduce / AllGather 等通信；
- **KV Cache / PagedAttention**：解决长上下文推理中的显存管理问题；
- **量化**：减少权重、激活或 KV Cache 的显存占用；
- **CUDA Graph / Triton**：降低 CPU launch overhead 或自定义高性能算子。

本节课讲的 **专家并行 EP**，主要服务于 **MoE 模型**，例如 Mixtral、DeepSeek-V3 / R1、Qwen-MoE 等。

MoE 模型和普通 dense Transformer 最大区别是：

> 普通 dense FFN 层：每个 token 都经过同一套 FFN 参数。  
> MoE FFN 层：每个 token 只被路由到少数几个 expert 上计算。

因此，MoE 模型虽然总参数量非常大，但每个 token 实际激活的参数量较小。  
这就带来一个天然并行机会：

> 把不同 expert 放到不同 GPU 上，让 token 根据 router / gate 的结果跨 GPU 分发到对应 expert 计算。

这就是 **Expert Parallelism，专家并行**。

# 1. MoE 概述

## 1.1 什么是 MoE？

MoE 是 **Mixture of Experts**，即“专家混合模型”。

在 Decoder-only Transformer 中，每一层通常包含：

```text
输入 hidden_states
  ↓
Self-Attention
  ↓
MLP / FFN
  ↓
输出 hidden_states
```

普通 dense LLM 中，MLP / FFN 通常是所有 token 共享的一套参数：

```text
FFN(x) = W_down( act(W_gate x) * W_up x )
```

而 MoE 模型把 FFN 替换成多个 expert：

```text
Expert_0(x), Expert_1(x), Expert_2(x), ..., Expert_{E-1}(x)
```

每个 expert 本质上也是一个小型 FFN，例如 SwiGLU MLP：

```text
Expert_i(x) = W_down_i( SiLU(W_gate_i x) * W_up_i x )
```

然后用一个 gate / router 决定每个 token 应该送给哪些 expert。

---

## 1.2 MoE 层的核心组成

一个典型 MoE 层包括 3 个部分：

| 组成 | 作用 | 类比 |
|---|---|---|
| Router / Gate | 决定 token 应该给哪些 expert | 分诊台 |
| Experts | 多个 FFN 专家，每个 expert 处理一部分 token | 多个专科医生 |
| Combine | 把 expert 输出按权重合并回原 token 顺序 | 汇总结果 |

对于一个 token hidden state：

```text
x_t ∈ R^{hidden_size}
```

router 会计算：

```text
router_logits_t = x_t · W_router
```

其中：

```text
router_logits_t ∈ R^{num_experts}
```

表示这个 token 对每个 expert 的偏好分数。

然后选 Top-K 个 expert：

```text
topk_ids_t = TopK(router_logits_t, k)
topk_weights_t = Softmax(topk_logits_t)
```

如果 `top_k = 2`，说明每个 token 会被送到 2 个 expert 上计算。

最终 MoE 输出可以写成：

```text
y_t = Σ_{e ∈ TopK(t)} weight_{t,e} · Expert_e(x_t)
```

---

## 1.3 为什么 MoE 模型需要专家并行？

假设一个 MoE 模型有：

```text
num_experts = 256
top_k = 8
```

每个 token 只激活 8 个 expert，但模型总共保存 256 个 expert 的权重。

如果把所有 expert 都放在每张 GPU 上：

```text
每张 GPU 都保存完整 MoE 权重
```

问题是：

1. 显存压力极大；
2. expert 权重加载带宽压力大；
3. 很多 expert 在某一轮推理中可能根本没有被用到；
4. 多张 GPU 没有充分利用 expert 的天然独立性。

专家并行的做法是：

```text
GPU 0 保存 expert 0~31
GPU 1 保存 expert 32~63
GPU 2 保存 expert 64~95
...
```

或者 round-robin 保存：

```text
GPU 0 保存 expert 0, 8, 16, ...
GPU 1 保存 expert 1, 9, 17, ...
```

这样做的核心收益是：

| 收益 | 解释 |
|---|---|
| 降低单卡 expert 权重显存 | 每张 GPU 只持有部分 expert |
| 提高 expert 权重读取带宽 | 多 GPU 并行读取不同 expert 权重 |
| 适合大规模 MoE 模型 | DeepSeek、Mixtral、Qwen-MoE 等模型更容易部署 |
| 与 DP 结合提升吞吐 | DP 分请求，EP 分 expert |

---

## 1.4 MoE 和普通 dense Transformer 的区别

| 对比项 | Dense Transformer | MoE Transformer |
|---|---|---|
| FFN 参数 | 每层一套 FFN | 每层多个 expert FFN |
| 每个 token 经过的 FFN | 所有 token 经过同一套 FFN | 每个 token 只经过 Top-K expert |
| 参数规模 | 参数全部参与每次前向 | 总参数大，但激活参数少 |
| 推理瓶颈 | Attention、MLP GEMM、KV Cache | Router、AllToAll、Expert GEMM、负载均衡 |
| 并行重点 | TP / PP / DP | DP + EP / TP + EP / PP + EP |
| 通信模式 | AllReduce / AllGather 常见 | AllToAll 非常关键 |

# 2. AllToAll 通信原理

## 2.1 什么是 AllToAll？

AllToAll 是一种多进程 / 多 GPU 集合通信操作。

直观理解：

> 每个 rank 都有一批数据要发给其他所有 rank，同时也会从其他所有 rank 接收数据。

假设有 4 张 GPU：

```text
Rank 0
Rank 1
Rank 2
Rank 3
```

每个 rank 上都有一些 token。router 计算后发现：

```text
Rank 0 上的 token A 应该给 Rank 2 的 expert
Rank 0 上的 token B 应该给 Rank 3 的 expert
Rank 1 上的 token C 应该给 Rank 0 的 expert
...
```

于是需要一次通信：

```text
每个 rank 把 token 发到对应 expert 所在 rank
```

这就是 AllToAll 在 MoE 里的典型用途。

---

## 2.2 AllToAll 和 AllReduce 的区别

| 通信 | 典型场景 | 通信语义 |
|---|---|---|
| Broadcast | 一个 rank 发给所有 rank | 一对多 |
| Gather | 多个 rank 收集到一个 rank | 多对一 |
| AllGather | 每个 rank 收集所有 rank 的数据 | 多对多复制 |
| Reduce | 多个 rank 规约到一个 rank | 多对一聚合 |
| AllReduce | 所有 rank 规约，并让每个 rank 都拿到结果 | 多对多聚合 |
| AllToAll | 每个 rank 给每个 rank 发送不同数据 | 多对多交换 |

TP 中常见的是 AllReduce：

```text
每张 GPU 算一部分结果
  ↓
AllReduce 求和
  ↓
每张 GPU 拿到完整结果
```

EP 中常见的是 AllToAll：

```text
每张 GPU 上的 token 根据 expert 归属被重新分发
  ↓
每张 GPU 收到属于自己 expert 的 token
  ↓
本地 expert 计算
  ↓
结果再发回原来的 rank
```

---

## 2.3 为什么 EP 必须关心 AllToAll？

MoE 中 expert 是按 rank 分布的。

例如：

```text
num_experts = 8
ep_size = 4
```

如果采用线性分配：

```text
Rank 0: Expert 0, 1
Rank 1: Expert 2, 3
Rank 2: Expert 4, 5
Rank 3: Expert 6, 7
```

某个 token 在 Rank 0 上，但 router 选出的 expert 是 Expert 6，那么这个 token 必须跨 GPU 发到 Rank 3。

所以 EP 需要完成：

```text
token 当前所在 rank
  ↓
根据 topk_ids 找 expert_owner_rank
  ↓
把 token dispatch 到对应 rank
  ↓
对应 rank 执行 expert
  ↓
结果 combine 回原 rank
```

这天然就是 AllToAll。

---

## 2.4 AllToAll 的性能瓶颈

AllToAll 会成为 MoE 推理瓶颈，原因包括：

1. **通信数据大小不固定**  
   每个 expert 收到多少 token 取决于 gate 路由结果。

2. **负载不均衡**  
   有些 expert 很热门，有些 expert 很冷门，导致部分 rank 很忙，部分 rank 空闲。

3. **小 batch decode 场景通信效率差**  
   Decode 阶段每轮 token 数少，通信启动成本明显。

4. **跨机通信代价高**  
   单机 NVLink 速度高；多机 InfiniBand / RoCE 通信复杂度更高。

5. **需要和 expert GEMM 重排配合**  
   token 需要按 expert 分组，否则 expert 计算无法高效做 grouped GEMM。

# 3. vLLM EP 之 MoE 层架构和推理流程解析

## 3.1 vLLM 中 EP 的整体思想

vLLM 官方文档中，Expert Parallelism 用于把 MoE experts 部署在不同 GPU 上，以提升 locality、efficiency 和 throughput。当前 vLLM 的 EP 通常会和 DP 配合使用：

```text
Attention 层：使用 DP 或 TP
MoE Expert 层：使用 EP
```

在 vLLM 中启用 EP 后：

```text
EP_SIZE = TP_SIZE × DP_SIZE
```

也就是说，expert 层会跨所有 TP × DP rank 分片。

例如：

```text
TP = 2
DP = 4
总 GPU = 8
EP_SIZE = 8
```

此时：

```text
Attention 层：每个 DP group 内做 TP=2
MoE expert 层：8 张 GPU 共同组成 EP group，expert 分布到 8 个 rank 上
```

这点非常重要：

> EP 不是简单替代 DP 或 TP，而是在 MoE 层使用另一套并行策略。

---

## 3.2 vLLM 中 MoE 层的逻辑位置

一个 Decoder layer 可以简化为：

```text
DecoderLayer
  ├── input_layernorm
  ├── self_attention
  ├── post_attention_layernorm
  └── mlp
        ├── Dense MLP
        或
        └── MoE MLP
              ├── router / gate
              ├── experts
              └── combine
```

对于 MoE 模型，`mlp` 不再是一个普通的 dense MLP，而是类似：

```text
MoE.forward(hidden_states)
  ↓
router(hidden_states)
  ↓
topk routing
  ↓
dispatch tokens
  ↓
expert compute
  ↓
combine outputs
```

在 vLLM 的模型执行链路中，它位于：

```text
API Server / LLM 接收请求
  ↓
Engine
  ↓
Scheduler
  ↓
Executor
  ↓
Worker
  ↓
ModelRunner
  ↓
Model.forward()
  ↓
DecoderLayer.forward()
  ↓
Attention.forward()
  ↓
MoE.forward()
  ↓
FusedMoE / Modular MoE Kernel
```

---

## 3.3 vLLM EP 与 DP / TP 的关系

### 3.3.1 DP：请求级并行

DP 的核心：

```text
不同 DP rank 处理不同请求 batch
每个 DP rank 通常有完整 dense 模型副本
```

对于普通 dense 模型，DP 之间通常不需要在每个 forward 中通信。

### 3.3.2 TP：层内矩阵切分

TP 的核心：

```text
一个矩阵切到多个 rank
每个 rank 算一部分
再通过 AllReduce / AllGather 得到完整结果
```

TP 适合 dense attention / MLP。

### 3.3.3 EP：专家级并行

EP 的核心：

```text
expert 按 expert_id 分布到不同 rank
token 根据 topk expert 跨 rank 迁移
```

EP 适合 MoE 的 expert FFN。

---

## 3.4 EP 启用后的层行为

可以这样理解：

```text
Dense Attention 层：
  - 如果 TP=1：每个 DP rank 复制 attention 权重
  - 如果 TP>1：每个 DP group 内部用 TP 切 attention 权重

MoE Expert 层：
  - expert 权重被切到 EP group 的各个 rank 上
  - token 通过 AllToAll 分发到 expert 所在 rank
```

因此，MoE 模型中经常出现：

```text
Attention: DP 或 TP
Expert MLP: EP
```

这也是大模型推理系统中非常重要的“不同层使用不同并行策略”的思想。

# 4. vLLM EP 之 Dispatch-Compute-Combine 推理流程解析

MoE EP 的核心流程可以压缩成 3 个词：

```text
Dispatch → Compute → Combine
```

这也是本节课最重要的主线。

---

## 4.1 输入 hidden_states

假设当前 MoE 层输入：

```text
hidden_states.shape = [num_tokens, hidden_size]
```

其中 `num_tokens` 不是 batch size，而是当前 vLLM 调度步中被拼接到一起的 token 数。

在 vLLM continuous batching 中，多个请求会被拼到一个执行 batch 中：

```text
Request A: 3 个 token
Request B: 1 个 token
Request C: 5 个 token
```

拼接后：

```text
hidden_states.shape = [9, hidden_size]
```

MoE 层只关心 token 维度上的 hidden states。

---

## 4.2 Router / Gate 计算

MoE gate 通常是一个线性层：

```text
router_logits = hidden_states @ W_router
```

形状：

```text
hidden_states:  [num_tokens, hidden_size]
W_router:       [hidden_size, num_experts]
router_logits:  [num_tokens, num_experts]
```

然后对每个 token 选 Top-K expert：

```text
topk_weights, topk_ids = topk(router_logits, k=top_k)
```

形状：

```text
topk_ids:      [num_tokens, top_k]
topk_weights:  [num_tokens, top_k]
```

例如：

```text
token_0 → expert 3, expert 9
token_1 → expert 1, expert 7
token_2 → expert 9, expert 10
```

---

## 4.3 判断 expert 所在 rank

EP 下，每个 expert 有一个 owner rank。

例如：

```text
num_experts = 8
ep_size = 4
```

线性放置：

```text
Rank 0: expert 0, 1
Rank 1: expert 2, 3
Rank 2: expert 4, 5
Rank 3: expert 6, 7
```

如果：

```text
token_0 → expert 3
```

那么：

```text
expert 3 belongs to Rank 1
```

所以 token_0 要发到 Rank 1。

如果采用 round-robin 放置：

```text
Rank 0: expert 0, 4
Rank 1: expert 1, 5
Rank 2: expert 2, 6
Rank 3: expert 3, 7
```

则 expert_owner_rank 会不同。

---

## 4.4 Dispatch：把 token 发到 expert 所在 rank

Dispatch 的目标：

```text
把 token hidden_states 按 expert_owner_rank 重排并发送
```

输入：

```text
hidden_states
topk_ids
topk_weights
```

输出：

```text
dispatched_hidden_states
dispatched_topk_ids / expert_ids
dispatched_topk_weights
metadata_for_restore
```

直观流程：

```text
本地 rank 上的 token
  ↓
根据 topk_ids 计算每个 token 要去哪个 expert
  ↓
根据 expert → rank 映射计算目标 rank
  ↓
按目标 rank 对 token 分桶
  ↓
AllToAll 发送给对应 rank
  ↓
每个 rank 收到属于自己本地 expert 的 token
```

注意：如果 `top_k = 2`，一个 token 可能会被复制成两份，分别送给两个 expert。

---

## 4.5 Compute：本地 expert 计算

Dispatch 之后，每个 rank 收到一批 token，这些 token 都属于它本地持有的 expert。

此时每个 rank 做：

```text
for each local expert:
    找到路由到这个 expert 的 token
    执行 expert FFN
```

实际实现不会真的用 Python for 循环逐 expert 慢慢算，而会尽量使用：

```text
Grouped GEMM / Fused MoE Kernel
```

以提升 GPU 利用率。

例如 expert FFN 是 SwiGLU：

```text
up = x @ W_up_e
gate = x @ W_gate_e
hidden = SiLU(gate) * up
out = hidden @ W_down_e
```

如果某个 rank 有多个 expert，理想情况下会把多个 expert 的 GEMM 组织成 grouped GEMM：

```text
Expert 0 的 tokens → GEMM 0
Expert 1 的 tokens → GEMM 1
Expert 2 的 tokens → GEMM 2
...
```

Grouped GEMM 可以一次 launch 处理多个不同 shape 或不同权重的 GEMM，减少 kernel launch overhead，并更好利用 GPU。

---

## 4.6 Combine：把结果发回原 token 所在位置

Expert 计算完成后，每个 token-expert pair 有一个输出：

```text
expert_output_{t,e}
```

但最终每个原始 token 只需要一个 hidden state 输出：

```text
y_t = Σ weight_{t,e} · expert_output_{t,e}
```

所以 combine 要做两件事：

1. 把 expert 输出发回原来的 token 所在 rank；
2. 按原 token 顺序和 topk 权重做加权求和。

流程：

```text
local expert outputs
  ↓
根据 dispatch 阶段保存的 metadata 找原始 token 归属
  ↓
AllToAll / ReduceScatter / 自定义 combine kernel
  ↓
回到原始 rank
  ↓
按 token 顺序 restore
  ↓
对 Top-K expert 输出加权求和
```

最终输出：

```text
moe_output.shape = [num_tokens, hidden_size]
```

然后继续进入下一层 Transformer。

---

## 4.7 Dispatch-Compute-Combine 总图

```text
hidden_states [num_tokens, hidden_size]
        │
        ▼
Router / Gate
        │
        ├── topk_ids [num_tokens, top_k]
        └── topk_weights [num_tokens, top_k]
        │
        ▼
Dispatch
        │
        ├── token 按 expert_owner_rank 分桶
        ├── AllToAll 发送 token
        └── 每个 rank 收到属于本地 expert 的 token
        │
        ▼
Compute
        │
        ├── 本地 expert 权重
        ├── grouped GEMM / fused MoE kernel
        └── 得到 expert outputs
        │
        ▼
Combine
        │
        ├── AllToAll / ReduceScatter 返回结果
        ├── restore 原 token 顺序
        └── topk weighted sum
        │
        ▼
moe_output [num_tokens, hidden_size]
```

# 5. vLLM EP 之专家计算内核实现分析

## 5.1 为什么 MoE expert 计算需要专门内核？

普通 dense MLP 中，所有 token 经过同一组权重：

```text
X @ W
```

这是一个规整的大 GEMM，非常适合 GPU。

MoE expert 中，token 会被分到不同 expert：

```text
Expert 0: 50 tokens
Expert 1: 3 tokens
Expert 2: 200 tokens
Expert 3: 0 tokens
...
```

问题变成：

```text
很多个不同 expert 的小 GEMM
```

这会导致：

1. 单个 GEMM 太小，GPU 利用率低；
2. 每个 expert 一个 kernel launch，launch overhead 大；
3. token 分布不均，部分 expert 很忙；
4. 需要 token 重排、unpermute、weight apply、reduce 等额外操作。

所以 vLLM 需要 Fused MoE / Modular MoE Kernel。

---

## 5.2 Expert FFN 的计算形式

以常见 SwiGLU expert 为例：

```text
输入 x: [n_tokens_for_expert, hidden_size]

gate_proj = x @ W_gate_e
up_proj   = x @ W_up_e
act       = SiLU(gate_proj) * up_proj
out       = act @ W_down_e
```

权重形状通常类似：

```text
W_gate_e: [hidden_size, intermediate_size]
W_up_e:   [hidden_size, intermediate_size]
W_down_e: [intermediate_size, hidden_size]
```

如果有多个 expert：

```text
W_gate: [num_local_experts, hidden_size, intermediate_size]
W_up:   [num_local_experts, hidden_size, intermediate_size]
W_down: [num_local_experts, intermediate_size, hidden_size]
```

计算时要根据 `expert_id` 选择对应 expert 的权重。

---

## 5.3 Fused MoE Kernel 想融合什么？

MoE 计算中通常包含：

1. Top-K routing；
2. token 排序 / permute；
3. token 按 expert 分组；
4. expert MLP 计算；
5. expert 输出乘 topk weight；
6. top-k 输出 reduce；
7. unpermute 回原 token 顺序；
8. dispatch / combine 通信前后的数据整理。

Fused MoE 的目标：

```text
减少中间张量读写
减少 kernel launch 次数
提高 expert GEMM 利用率
降低调度和通信开销
```

---

## 5.4 vLLM Modular MoE Kernel 的拆分思想

vLLM 的 FusedMoE Modular Kernel 设计中，把复杂 MoE 操作拆成逻辑组件，核心目的有两个：

1. 防止不同 MoE 实现之间大量重复代码；
2. 让 AllToAll Dispatch / Combine 和 FusedMoE expert 计算可以相互解耦，独立开发和测试。

可以抽象成：

```text
FusedMoE Modular Kernel
  ├── Prepare / Dispatch
  ├── Expert Compute
  ├── TopK Weight Apply / Reduce
  └── Finalize / Combine
```

从工程角度看，这种拆分很重要：

> MoE 的难点不是某一个 GEMM，而是 router、dispatch、expert compute、combine、load balance、通信 backend、量化 expert 权重之间的组合爆炸。

---

## 5.5 Expert 计算中的数据结构

实现 EP / MoE 时常见元数据包括：

| 元数据 | 作用 |
|---|---|
| `topk_ids` | 每个 token 选择的 expert id |
| `topk_weights` | 每个 token 对每个 expert 的权重 |
| `expert_map` | global expert id 到 local expert id / rank 的映射 |
| `num_tokens_per_expert` | 每个 expert 收到多少 token |
| `sorted_token_ids` | 按 expert 分组后的 token 顺序 |
| `expert_offsets` | 每个 expert 在排序后 token buffer 中的起始位置 |
| `permute_indices` | token 原顺序到 expert 分组顺序的映射 |
| `unpermute_indices` | expert 输出恢复原 token 顺序的映射 |

这些元数据决定了：

```text
哪些 token 送给哪个 expert
每个 expert 处理哪段 token
计算完如何恢复 token 顺序
```

---

## 5.6 Expert 负载不均衡问题

MoE 中 router 可能会偏向少数 expert。

例如：

```text
Expert 0: 1000 tokens
Expert 1: 900 tokens
Expert 2: 10 tokens
Expert 3: 0 tokens
```

如果每个 expert 分布在不同 GPU 上，那么：

```text
Expert 0 所在 GPU 很忙
Expert 3 所在 GPU 几乎空闲
```

这会导致整体推理被最慢 rank 拖住。

因此 EP 系统需要考虑：

1. router 训练时的 load balancing loss；
2. 推理时 expert placement 策略；
3. redundant experts；
4. expert parallel load balancer；
5. token dispatch 的通信均衡；
6. grouped GEMM 中小 expert 的效率。

vLLM 文档中提到 EPLB（Expert Parallel Load Balancer）会收集 forward 过程中的 expert 负载统计，并周期性调整 expert 分布，以缓解 expert 负载倾斜。

# 6. vLLM EP 中的 All2All Backend

## 6.1 为什么 vLLM 要抽象 All2All backend？

不同硬件、不同网络拓扑、不同 workload 下，最佳 AllToAll 实现不同。

例如：

| 场景 | 更关注 |
|---|---|
| 单机 NVLink | GPU 间低延迟、高带宽 |
| 多机 InfiniBand | 跨机通信效率 |
| Prefill | 大 token batch，高吞吐 |
| Decode | 小 token batch，低延迟 |
| H100 / H200 | NVLink / NVSwitch / IB |
| 国产卡 / 自研芯片 | 自定义通信库和 runtime |

所以 vLLM 把 AllToAll 做成可配置 backend。

---

## 6.2 常见 All2All backend

根据 vLLM 当前文档和 API，常见 backend 包括：

| Backend | 适用场景 | 理解 |
|---|---|---|
| `allgather_reducescatter` | 默认通用 backend | 用 AllGather 做 dispatch，用 ReduceScatter 做 combine |
| `deepep_high_throughput` | Prefill / 大 batch | 高吞吐 MoE 通信 |
| `deepep_low_latency` | Decode / 小 batch | 低延迟 MoE 通信 |
| `flashinfer_nvlink_one_sided` | 多节点 NVLink / MNNVL | FlashInfer one-sided A2A |
| `flashinfer_nvlink_two_sided` | 多节点 NVLink | two-sided A2A |
| `nixl_ep` | elastic EP / 特定通信场景 | NIXL EP kernels |

默认 backend 容易理解，但在大规模线上推理中，专用 EP 通信 kernel 往往非常关键。

---

## 6.3 Prefill 和 Decode 对 EP 通信的不同要求

### Prefill 阶段

Prefill 一次处理 prompt 中大量 token：

```text
num_tokens 很大
```

特点：

- 计算量大；
- 通信数据量大；
- 更适合 high-throughput backend；
- 可以用更大的 batch 提高 GPU 利用率。

### Decode 阶段

Decode 每轮通常每个请求只生成一个 token：

```text
num_tokens ≈ batch_size
```

特点：

- token 数少；
- 通信启动开销明显；
- 对低延迟敏感；
- 更适合 low-latency backend。

所以 EP 通信经常需要区分：

```text
prefill 用 high-throughput
decode 用 low-latency
```

# 7. vLLM EP 部署方式

## 7.1 单机 EP 部署示例

以 8 GPU 单机为例：

```bash
vllm serve deepseek-ai/DeepSeek-V3-0324 \
  --tensor-parallel-size 1 \
  --data-parallel-size 8 \
  --enable-expert-parallel
```

含义：

```text
TP = 1
DP = 8
EP_SIZE = TP × DP = 8
```

也就是：

```text
Attention 权重复制到 8 个 DP rank
Expert 权重切到 8 个 EP rank
```

---

## 7.2 TP + DP + EP 混合示例

例如：

```bash
vllm serve <moe-model> \
  --tensor-parallel-size 2 \
  --data-parallel-size 4 \
  --enable-expert-parallel
```

含义：

```text
总 GPU = TP × DP = 2 × 4 = 8
EP_SIZE = 8
```

执行逻辑：

```text
Attention 层：
  每个 DP group 内部做 TP=2

Expert 层：
  8 个 rank 组成 EP group
  experts 分布到 8 张 GPU
```

这就是“同一个模型不同层使用不同并行策略”。

---

## 7.3 多机 EP 部署关注点

多机 EP 通常需要关注：

1. 网络地址；
2. 每个节点本地 DP size；
3. 每个节点的 start rank；
4. headless worker；
5. all2all backend；
6. 通信网卡配置；
7. API server 数量；
8. 集群拓扑，例如 NVLink / NVSwitch / IB。

示例结构：

```text
Node 0: DP rank 0~7，处理 API 请求
Node 1: DP rank 8~15，headless，只参与计算
```

多机场景通常更需要 DeepEP / NIXL / FlashInfer 等高性能通信 backend。

# 8. vLLM EP 之完整函数调用链总结

不同 vLLM 版本源码可能变化较快，但从概念调用链上，可以按下面主线理解。

## 8.1 从请求入口到模型执行

```text
用户请求
  ↓
API Server / LLM.generate
  ↓
Engine / AsyncLLMEngine
  ↓
Scheduler
  ↓
Executor
  ↓
Worker
  ↓
ModelRunner.execute_model
  ↓
model.forward
  ↓
DecoderLayer.forward
  ↓
MoE layer forward
```

其中：

- Scheduler 决定本轮哪些请求进入执行；
- ModelRunner 构造模型输入、位置、KV Cache 映射；
- Model.forward 执行 Transformer；
- 遇到 MoE 层时进入 EP / FusedMoE 路径。

---

## 8.2 MoE 层内部调用链

```text
MoE.forward(hidden_states)
  ↓
gate / router linear
  ↓
topk routing
  ↓
FusedMoE / Modular MoE
  ↓
prepare metadata
  ↓
dispatch hidden_states to expert ranks
  ↓
local expert compute
  ↓
apply topk weights / reduce
  ↓
combine outputs back
  ↓
return moe_output
```

---

## 8.3 Dispatch-Compute-Combine 对应的工程模块

概念上可以对应为：

```text
Router / Gate
  - 计算 topk_ids, topk_weights

All2All Manager
  - dispatch
  - combine

FusedMoE / Modular Kernel
  - token permute / unpermute
  - grouped GEMM
  - topk weight apply
  - reduce

Expert Weights
  - local experts only
```

实际源码中不同模型、不同 backend、不同硬件的实现会有差异，但你在面试中只要能把上述抽象讲清楚，就已经能说明你理解了 EP 的本质。

# 9. 从输入到输出：EP 推理完整流程

下面用一个端到端流程把本节课串起来。

## 9.1 请求进入 vLLM

```text
用户输入 prompt
  ↓
Tokenizer 编码成 token ids
  ↓
Engine 接收请求
  ↓
Scheduler 把请求加入调度队列
```

---

## 9.2 Scheduler 选择本轮要执行的 token

```text
waiting / running requests
  ↓
根据预算、KV Cache、调度策略选出本轮 token
  ↓
构造调度结果
```

本轮 token 可能来自：

- 新请求的 prefill；
- 旧请求的 decode；
- 多个请求混合组成 continuous batching。

---

## 9.3 ModelRunner 构造模型输入

```text
input_ids
positions
attention metadata
kv cache metadata
```

然后调用：

```text
model.forward(...)
```

---

## 9.4 执行 Attention

Attention 层会用：

```text
Q, K, V
KV Cache
PagedAttention metadata
```

输出新的 hidden states。

---

## 9.5 执行 MoE 层

进入 MoE：

```text
hidden_states [num_tokens, hidden_size]
```

计算 gate：

```text
router_logits = hidden_states @ W_router
topk_ids, topk_weights = topk(router_logits)
```

---

## 9.6 EP Dispatch

根据 expert 分布：

```text
expert_id → ep_rank
```

把 token 发到对应 rank：

```text
AllToAll dispatch
```

---

## 9.7 本地专家计算

每个 rank 使用本地 expert 权重：

```text
local expert grouped GEMM
```

得到 expert 输出。

---

## 9.8 EP Combine

把结果发回原 rank：

```text
AllToAll / ReduceScatter combine
```

恢复原 token 顺序，并加权求和：

```text
moe_output = Σ topk_weight * expert_output
```

---

## 9.9 后续层和输出 token

继续执行剩余 Transformer layer：

```text
final hidden state
  ↓
lm_head
  ↓
logits
  ↓
sampling / greedy / beam
  ↓
next token
```

然后：

- prefill 阶段：产生第一个 token；
- decode 阶段：每轮生成一个或多个 token；
- 如果未结束，继续下一轮调度。

---

# 10. EP、TP、DP 的统一对比

| 并行方式 | 切分对象 | 通信方式 | 适用层 | 主要目标 |
|---|---|---|---|---|
| DP | 请求 / batch | 通常推理时少通信 | 全模型副本 | 提升吞吐 |
| TP | dense 权重矩阵 | AllReduce / AllGather | Attention / Dense MLP | 单模型放进多卡 |
| EP | MoE experts | AllToAll | MoE FFN 层 | 大 MoE 模型高效部署 |
| PP | Transformer 层 | send / recv activation | 层间 | 超大模型跨设备放置 |
| CP | sequence / context | KV / attention 通信 | 长上下文 attention | 扩展上下文长度 |

一句话总结：

```text
DP 切请求；
TP 切矩阵；
EP 切专家；
PP 切层；
CP 切序列。
```

# 11. 面试重点总结

## 11.1 必须掌握的核心问题

### 问题 1：什么是 MoE？和普通 dense FFN 有什么区别？

**回答：**

MoE 是 Mixture of Experts。普通 Transformer 的 FFN 层是所有 token 共享一套 MLP 权重，而 MoE 层包含多个 expert，每个 expert 本质上是一个 FFN。输入 token 先经过 router / gate，得到每个 expert 的分数，然后选择 Top-K expert 进行计算，最后把多个 expert 的输出按 gate 权重加权求和。MoE 的优势是总参数量可以很大，但每个 token 只激活少量 expert，因此推理计算量相对可控。

---

### 问题 2：什么是专家并行 EP？

**回答：**

专家并行是专门针对 MoE 层的并行方式。它不是把每个 dense 矩阵切开，而是把不同 expert 分布到不同 GPU 上。推理时，每个 token 通过 gate 选出 Top-K expert，然后 token 会通过 AllToAll 发送到对应 expert 所在 rank，本地 expert 计算完成后再把结果发回原 rank 并加权合并。EP 的核心收益是降低单卡 expert 权重显存，提高 expert 权重读取带宽，并适合大规模 MoE 模型部署。

---

### 问题 3：EP 和 TP 有什么区别？

**回答：**

TP 是张量并行，通常把一个 dense 层的权重矩阵按列或按行切到多个 GPU 上，每个 GPU 计算一部分结果，然后通过 AllReduce / AllGather 等通信合并。EP 是专家并行，只针对 MoE expert 层，把不同 expert 放到不同 GPU 上，token 根据 router 结果跨 GPU 分发到对应 expert。TP 的通信以 AllReduce 为主，EP 的通信以 AllToAll 为主。

---

### 问题 4：为什么 MoE 推理需要 AllToAll？

**回答：**

因为 token 当前所在 rank 和它选择的 expert 所在 rank 不一定相同。router 计算出的 topk expert 可能分布在其他 GPU 上，所以 token hidden states 必须发送到 expert 所在 rank 计算。每个 rank 都可能向其他所有 rank 发送 token，同时也从其他 rank 接收属于自己 expert 的 token，因此这是典型的 AllToAll 通信模式。

---

### 问题 5：MoE 的 Dispatch-Compute-Combine 是什么？

**回答：**

Dispatch 是根据 topk_ids 和 expert 到 rank 的映射，把 token hidden states 发送到对应 expert 所在 GPU。Compute 是每个 GPU 对自己本地 expert 收到的 token 执行 expert FFN，通常使用 grouped GEMM 或 fused MoE kernel。Combine 是把 expert 输出发回原 token 所在位置，并按照 topk_weights 对多个 expert 输出做加权求和，恢复为 `[num_tokens, hidden_size]` 的输出。

---

### 问题 6：vLLM 中 EP 和 DP 如何配合？

**回答：**

vLLM 中 EP 通常和 DP 配合。DP 负责请求级并行，不同 DP rank 处理不同请求 batch；EP 负责 MoE expert 层，把 expert 权重分布到 `TP_SIZE × DP_SIZE` 个 rank 上。启用 EP 后，expert 层使用 EP，而 attention 层根据 TP 配置使用 DP 或 TP。例如 `TP=1, DP=8` 时，attention 权重在 8 个 DP rank 上复制，而 expert 权重分布在 8 个 EP rank 上。

---

### 问题 7：EP 为什么可能需要负载均衡？

**回答：**

因为 router 对 expert 的选择可能不均匀。有些 expert 会收到大量 token，有些 expert 可能很少被选中。如果 expert 分布在不同 GPU 上，就会导致部分 GPU 忙、部分 GPU 空闲，整体延迟由最忙的 rank 决定。vLLM 中的 EPLB 会收集 forward 过程中的 expert 负载统计，并周期性调整 expert 映射或引入冗余 expert，缓解负载倾斜。

---

### 问题 8：MoE expert compute 为什么要用 fused / grouped GEMM？

**回答：**

因为每个 expert 收到的 token 数不同，如果逐 expert 调用 GEMM，会产生大量小 GEMM 和 kernel launch overhead，GPU 利用率低。Grouped GEMM 可以把多个 expert 的 GEMM 组织到一起执行，Fused MoE kernel 还可以融合 token permute、expert 计算、topk weight apply、reduce、unpermute 等操作，减少中间张量读写和 kernel launch 次数。

---

### 问题 9：Prefill 和 Decode 阶段对 EP backend 有什么不同要求？

**回答：**

Prefill 阶段一次处理大量 prompt token，通信和计算规模大，更关注吞吐，适合 high-throughput backend。Decode 阶段每轮每个请求通常只处理一个 token，通信数据量小但延迟敏感，AllToAll 启动开销明显，因此更关注 low-latency backend。大规模 MoE 推理中可能会针对 prefill 和 decode 选择不同通信优化策略。

---

### 问题 10：如果面试官问“DP、TP、EP 分别切什么”，怎么回答？

**回答：**

DP 切请求或 batch，每个 rank 通常有完整模型副本，用于提升吞吐；TP 切 dense 层的矩阵权重，需要 AllReduce / AllGather 等通信，用于让单个模型跨多卡执行；EP 切 MoE experts，每个 rank 持有部分 expert，token 通过 AllToAll 路由到 expert 所在 rank，用于大规模 MoE 模型部署。

---

# 12. 常见追问与简洁答案

## 12.1 为什么不用 TP 来切 MoE expert？

可以用 TP，但 MoE expert 有天然的 expert 维度。  
如果每个 token 只激活少量 expert，把 expert 分散到不同 GPU 可以减少每张 GPU 持有的 expert 权重，并利用多 GPU 的内存带宽。TP 切的是矩阵内部，而 EP 切的是 expert 集合。对于大 MoE 模型，EP 往往更符合模型结构。

---

## 12.2 EP 会不会增加通信？

会。  
EP 需要 Dispatch 和 Combine 两次跨 rank 通信，核心通信是 AllToAll。但它换来了 expert 权重显存和带宽压力的下降。是否划算取决于：

- expert 数量；
- top_k；
- batch/token 数；
- 网络拓扑；
- expert 负载均衡；
- prefill/decode 比例；
- 通信 backend 性能。

---

## 12.3 top_k 越大越好吗？

不是。  
top_k 越大，每个 token 使用更多 expert，模型表达能力可能更强，但推理时：

- token 复制更多份；
- expert 计算量增加；
- dispatch/combine 通信量增加；
- combine 加权求和开销增加。

所以 top_k 是模型质量和推理效率之间的权衡。

---

## 12.4 AllToAll 的输入输出形状固定吗？

不一定。  
因为每个 expert 收到多少 token 取决于 router 结果，所以每个 rank 发给其他 rank 的 token 数可能不一样。这会带来 variable-size AllToAll 问题。工程中需要 token count 统计、prefix sum、buffer 分配、metadata 记录等步骤。

---

## 12.5 EP 和 KV Cache 有什么关系？

EP 主要作用在 MoE expert FFN 层，而 KV Cache 主要服务于 Attention 层。  
二者作用点不同：

```text
KV Cache：减少 decode attention 中重复计算，管理 K/V 显存
EP：分布式执行 MoE experts，降低 expert 权重显存和带宽压力
```

但它们会共同影响显存分配。比如启用 EP 后 expert 权重显存降低，可能给 KV Cache 留出更多空间；但 EPLB 引入冗余 expert 又会增加显存压力。

---

# 13. 本节课一句话总结

vLLM 专家并行的核心是：

> 对 MoE 模型，把 expert 权重分布到不同 GPU；每轮推理时通过 router 决定 token 去哪个 expert，再通过 AllToAll 完成 token 的 Dispatch 和 Combine，中间用 FusedMoE / Grouped GEMM 高效执行本地 expert 计算。

更短地说：

```text
MoE 决定“哪个 token 找哪个 expert”；
EP 决定“expert 放在哪张 GPU”；
AllToAll 负责“把 token 送过去再拿回来”；
FusedMoE 负责“把 expert 计算做快”。
```

---

# 14. 学习路线建议

如果你刚学完 DP / TP，本节课建议按下面顺序复习：

1. 先搞懂 MoE 层数学结构；
2. 再搞懂 router / top-k；
3. 再搞懂 expert 到 rank 的映射；
4. 再画一遍 Dispatch-Compute-Combine；
5. 对比 EP 和 TP 的通信差异；
6. 最后看 vLLM 的 All2All backend 和 FusedMoE Modular Kernel。

最重要的是不要一上来死扣源码，而要先形成这个抽象：

```text
hidden_states
  → gate
  → topk
  → dispatch
  → local experts
  → combine
  → next layer
```

只要这条链路清楚，后面看 vLLM 源码时就不会迷路。
