## 0. 本节课的主线

本节课不是单纯讲“量化算法原理”，而是把量化放进 **vLLM 推理框架** 中来看：

```text
模型权重 / 量化配置
        ↓
vLLM 读取模型 config / quant_config
        ↓
选择 QuantizationConfig
        ↓
在构建 Linear / MoE / Attention 等层时选择 QuantizeMethod
        ↓
create_weights：创建量化权重参数，如 qweight、qzeros、scales
        ↓
load_weights：加载 safetensors / bin 中的量化权重
        ↓
process_weights_after_loading：权重后处理、packing、scale 处理
        ↓
ModelRunner 执行 forward
        ↓
quant_method.apply 调用对应量化 kernel
        ↓
输出 logits / sampled token
```

所以这节课的核心问题是：

> vLLM 为什么能支持这么多量化格式？  
> 这些量化格式是如何接入到 vLLM 模型执行流程中的？  
> 在实际部署中，应该如何选择、加载、验证和排查量化模型？

# 1. vLLM 量化功能总结

## 1.1 为什么 vLLM 需要量化

大模型推理主要受三类资源约束：

1. **模型权重显存**
2. **KV Cache 显存**
3. **显存带宽 / 内存读写带宽**

以 Decoder-only LLM 为例，推理时显存大头通常来自：

```text
总显存占用 ≈ 模型权重 + KV Cache + 中间激活 + CUDA Graph / workspace / 通信 buffer
```

其中：

- 模型越大，权重越吃显存；
- 上下文越长、batch 越大，KV Cache 越吃显存；
- decode 阶段每次只生成一个 token，计算量相对小，但每一步都要读取大量权重和 KV Cache，因此经常受显存带宽限制。

量化的目标是：

```text
用更低 bit 的数据类型表示权重 / 激活 / KV Cache
        ↓
减少显存占用
        ↓
减少显存带宽压力
        ↓
在硬件和 kernel 支持良好时提升吞吐或降低延迟
```

但量化不是无代价的。它会带来：

- 精度损失；
- 反量化 / 动态量化开销；
- kernel 支持限制；
- 硬件兼容性限制；
- 与 TP / MoE / LoRA / CUDA Graph / Attention backend 的兼容问题。

所以面试中不能只说“量化能变快”，更准确的表达是：

> 量化首先确定性地降低显存占用；是否加速取决于量化格式、硬件指令、kernel 实现、batch 形态和瓶颈位置。如果推理瓶颈是 memory bandwidth，量化通常有明显收益；如果瓶颈转移到反量化或算子不支持，可能不加速甚至变慢。

---

## 1.2 vLLM 支持哪些量化方式

vLLM 官方文档将量化作为一个独立 feature，当前支持多种量化实现，包括：

- AutoAWQ
- BitsAndBytes
- GPTQModel
- Intel Neural Compressor
- NVIDIA Model Optimizer
- Online Quantization
- AMD Quark
- TorchAO
- LLM Compressor
  - FP8 W8A8
  - INT4 W4A16
  - INT8 W4A8
  - INT8 W8A8
- Quantized KV Cache
- FP8 ViT Encoder Attention

这些方法可以按不同维度分类。

---

## 1.3 按量化对象分类

### 1.3.1 Weight-only Quantization：只量化权重

典型方法：

- AWQ
- GPTQ
- INT4 W4A16
- 部分 BitsAndBytes 4-bit / 8-bit

核心思想：

```text
权重 W：FP16/BF16 → INT4/INT8
激活 X：仍然使用 FP16/BF16
计算：X_fp16 × W_int4
```

实际 kernel 中通常不会真的直接用 `int4` 张量做普通 PyTorch matmul，而是：

```text
packed int4 weight + scale/zero_point
        ↓
kernel 内部解包 / 反量化 / fused GEMM
        ↓
得到 FP16/BF16 输出
```

优点：

- 显著降低权重显存；
- 对模型加载和部署友好；
- 激活不量化，精度损失相对可控；
- AWQ / GPTQ 是目前常见的开源量化模型格式。

缺点：

- 主要节省权重显存，对 KV Cache 没有帮助；
- 对长上下文和大 batch 场景，如果 KV Cache 成为瓶颈，weight-only 不够；
- 速度高度依赖 kernel，例如 Marlin、AWQ kernel、GPTQ kernel 等。

---

### 1.3.2 Weight + Activation Quantization：权重和激活都量化

典型方法：

- FP8 W8A8
- INT8 W8A8
- INT8 W4A8

核心思想：

```text
权重 W：FP16/BF16 → FP8/INT8
激活 X：FP16/BF16 → FP8/INT8
计算：X_lowbit × W_lowbit
```

这种方式相比 weight-only 更进一步：

- 权重读带宽下降；
- 激活读写带宽下降；
- 如果硬件支持 FP8 Tensor Core / INT8 Tensor Core，GEMM 可以真正低精度加速。

但问题也更多：

- 激活是运行时产生的，量化 scale 如何确定很关键；
- 如果动态量化，每一步都要统计 scale，有额外开销；
- 如果静态量化，需要校准数据；
- 对 outlier activation 更敏感。

---

### 1.3.3 KV Cache Quantization：量化 KV Cache

典型方式：

- FP8 KV Cache
- 部分 backend 支持 per-tensor / per-head scale

KV Cache 是推理系统中很特殊的对象：

```text
Prefill 阶段：为 prompt 中每个 token 计算 K/V 并写入 KV Cache
Decode 阶段：新 token 的 Query 会和历史 K/V 做 attention
```

对于长上下文、大并发服务，KV Cache 可能比权重更限制吞吐。KV Cache 量化可以：

- 降低每个 token 的 KV Cache 显存占用；
- 容纳更多 token；
- 支持更长上下文；
- 提高 batch capacity；
- 降低 attention 读 KV 的带宽压力。

但它也会影响注意力计算的数值精度，所以 scale 校准非常重要。

vLLM 的 FP8 KV Cache 支持多种 scale 方式：

```text
1. 不校准：scale = 1.0
2. warmup 随机 token 校准
3. 使用 llm-compressor 基于数据集校准
```

如果要做严肃部署，推荐使用校准数据集得到更可靠的 KV scale。

---

## 1.4 按量化发生时间分类

### 1.4.1 离线量化 / 预量化模型

离线量化指模型在部署前已经量化好，并保存为新的 checkpoint。

例子：

```text
原始 BF16 模型
        ↓
AWQ / GPTQ / FP8 工具量化
        ↓
保存量化权重 + quantization config
        ↓
vLLM 加载量化模型进行推理
```

优点：

- 服务启动时开销小；
- 量化结果可复现；
- 可以用校准集优化精度；
- 更适合生产环境。

缺点：

- 需要额外量化流程；
- 不同硬件、kernel 可能要求不同格式；
- 模型版本更新时需要重新量化。

---

### 1.4.2 在线量化 / Load-time Quantization

在线量化指加载原始 BF16/FP16 模型时，在 vLLM 内部或相关工具中直接转成低精度格式。

流程类似：

```text
原始 BF16 checkpoint
        ↓
vLLM load model
        ↓
加载时根据 quantization 参数进行量化
        ↓
量化权重常驻 GPU
        ↓
执行推理
```

优点：

- 不需要提前保存量化模型；
- 部署尝试方便；
- 适合快速评估。

缺点：

- 启动时间增加；
- 量化精度可能不如离线校准；
- 对生产可控性较差。

---

## 1.5 按量化粒度分类

量化本质公式通常可以写成：

```text
x_q = round(x_fp / scale) + zero_point
x_fp ≈ (x_q - zero_point) × scale
```

关键问题是：`scale` 和 `zero_point` 多细？

### 1.5.1 Per-tensor

整个张量共用一个 scale。

```text
W 整个矩阵共用一个 scale
```

优点：实现简单、元数据少、kernel 友好。  
缺点：如果张量中存在 outlier，scale 会被 outlier 拉大，小值区域精度差。

### 1.5.2 Per-channel

每个输出通道或输入通道使用一个 scale。

```text
W[out_channel, :] 每一行一个 scale
```

优点：精度明显优于 per-tensor，对 Linear 层权重更友好。  
缺点：scale 数量增加，kernel 实现更复杂。

### 1.5.3 Per-group / Group-wise

每一组连续元素使用一个 scale。AWQ / GPTQ 常见 `group_size=128`。

```text
每 128 个权重共享一个 scale
```

优点：精度和元数据开销折中，INT4 weight-only 常用。  
缺点：group_size 不同会影响精度、速度和 kernel 支持；与 Tensor Parallel 切分维度需要对齐，否则可能加载失败。

### 1.5.4 Block-wise

将矩阵按二维 block 分块，每个 block 一个 scale。

```text
W 被切成若干 block
每个 block 一个 scale
```

FP8 / MXFP4 等方法中常见 block-wise 量化。

# 2. vLLM 量化推理实践

## 2.1 实践目标

量化实践不是“能跑起来”就结束，而是要完成四件事：

1. **能加载量化模型**
2. **能提供 OpenAI-compatible API 或离线推理**
3. **能比较显存、吞吐、延迟和精度**
4. **能定位量化不兼容或性能异常问题**

建议你在学习和项目中做如下对比：

```text
BF16 / FP16 baseline
        vs
AWQ INT4
        vs
GPTQ INT4
        vs
FP8 W8A8
        vs
FP8 KV Cache
```

观察指标：

- GPU memory usage
- TTFT
- TPOT
- tokens/s
- requests/s
- max concurrent requests
- max context length
- 输出质量
- 是否存在乱码、重复、拒答、格式错误

---

## 2.2 离线推理：Python LLM 接口

基础形式：

```python
from vllm import LLM, SamplingParams

sampling_params = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    max_tokens=128,
)

llm = LLM(
    model="your-quantized-model",
    quantization="awq",   # 也可能由模型 config 自动识别
    dtype="half",
)

outputs = llm.generate(
    ["请用一句话介绍 vLLM。"],
    sampling_params,
)

for output in outputs:
    print(output.outputs[0].text)
```

注意：

- 有些量化模型会在 Hugging Face config 中写入 `quantization_config`，vLLM 可以自动识别；
- 有些情况下需要显式指定 `quantization="awq"` / `"gptq"` / `"fp8"`；
- 有些格式还需要指定 `load_format`；
- 是否需要显式传参取决于模型 checkpoint 的配置文件和 vLLM 版本。

```text

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓

  ↓
流式返回
```

## 2.4 AWQ 模型加载实践

AWQ 是 vLLM 中常见的 INT4 weight-only 量化格式。典型特点：

```text
W4A16
W：4-bit
A：FP16
scale：通常 group-wise
zero_point：可选
```

启动示例：

```bash
vllm serve your-awq-model \
  --quantization awq \
  --dtype half
```

常见问题：

### 问题 1：模型加载时报 group_size 或 shape 不对

可能原因：

- checkpoint 的 group_size 与 vLLM kernel 要求不匹配；
- Tensor Parallel 切分后，某个 rank 上的维度不能被 group_size 整除；
- 模型结构与量化配置不一致；
- 某些层不应该被量化，但 checkpoint 里量化了。

排查方向：

```text
1. 查看 quant_config.json / quantize_config.json
2. 查看 group_size、bits、zero_point
3. 查看 tensor_parallel_size
4. 降低 TP 试一下
5. 换用 vLLM 支持更好的量化模型
```

### 问题 2：能加载但速度不理想

可能原因：

- 没有走高性能 AWQ / Marlin kernel；
- GPU 架构不适合该 kernel；
- batch 太小，kernel launch / 反量化开销占比高；
- decode 阶段瓶颈不在权重读取，而在 KV Cache / 调度 / 通信。

---

## 2.5 GPTQ 模型加载实践

GPTQ 也是常见 INT4 weight-only PTQ 方法。它和 AWQ 都常用于压缩权重，但思路不同：

- GPTQ 更偏二阶近似误差补偿；
- AWQ 更强调 activation-aware，通过激活统计保护重要通道。

启动方式类似：

```bash
vllm serve your-gptq-model \
  --quantization gptq \
  --dtype half
```

常见注意点：

- GPTQ 有不同实现格式，如 AutoGPTQ、GPTQModel；
- 不同格式的 config 字段可能不完全相同；
- 某些 GPTQ checkpoint 在某些 GPU 或 kernel 上可能存在兼容性问题；
- 实际部署前必须做质量和性能回归测试。

---

## 2.6 FP8 W8A8 推理实践

FP8 W8A8 是当前生产推理中很重要的方向，尤其适合 Hopper / Ada / AMD MI300 等支持良好的硬件。

核心区别：

```text
AWQ / GPTQ：
  权重量化为 INT4，激活仍 FP16

FP8 W8A8：
  权重 FP8，激活 FP8
```

FP8 通常有两种使用方式：

### 方式 1：加载预量化 FP8 checkpoint

```bash
vllm serve your-fp8-model \
  --quantization fp8
```

### 方式 2：在线 FP8 量化

```bash
vllm serve your-bf16-model \
  --quantization fp8
```

是否支持、效果如何，取决于 vLLM 版本、硬件、模型结构和 kernel 路径。

FP8 推理中最关键的是 scale：

```text
x_fp8 = quantize(x_fp16, scale)
x_fp16 ≈ dequantize(x_fp8, scale)
```

如果 scale 过大，小值区分度差；如果 scale 过小，容易溢出。所以 FP8 经常需要：

- per-tensor scale；
- per-channel scale；
- block-wise scale；
- dynamic activation scale；
- static calibrated scale。

---

## 2.7 FP8 KV Cache 实践

vLLM 支持配置 KV Cache dtype：

```python
from vllm import LLM, SamplingParams

llm = LLM(
    model="meta-llama/Llama-3.1-8B-Instruct",
    kv_cache_dtype="fp8",
    calculate_kv_scales=True,
)

outputs = llm.generate(
    ["London is the capital of"],
    SamplingParams(max_tokens=32),
)
```

常见配置含义：

```text
kv_cache_dtype="auto"
    使用默认 KV Cache dtype，通常跟模型 dtype 相关

kv_cache_dtype="fp8"
    使用 FP8 KV Cache

calculate_kv_scales=False
    不校准，scale 默认为 1.0

calculate_kv_scales=True
    warmup 时用随机 token 估计 scale
```

生产建议：

```text
如果只是本地实验：
    可以先用 calculate_kv_scales=True 快速试跑

如果要严肃部署：
    推荐用 llm-compressor 和校准数据集生成 KV scale
```

KV Cache 量化最适合：

- 长上下文；
- 大 batch；
- 多轮对话；
- KV Cache 显存成为主要瓶颈；
- 希望提高并发容量。


---

## 3.2 vLLM 量化抽象的核心思想

vLLM 的量化抽象可以简化成两层：

```text
QuantizationConfig
        ↓
QuantizeMethod / LinearMethod / MoEMethod / KVCacheMethod
```

### 3.2.1 QuantizationConfig 是“量化方案配置”

它回答：

```text
这是什么量化方法？
支持什么激活 dtype？
最低需要什么 GPU capability？
从哪些 config 文件读取参数？
如何从 config 创建对象？
某个 layer 应该使用哪种量化执行方法？
```

典型接口：

```python
class QuantizationConfig:
    def get_name(self): ...
    def get_supported_act_dtypes(self): ...
    def get_min_capability(self): ...
    def get_config_filenames(): ...
    def from_config(config): ...
    def get_quant_method(self, layer, prefix): ...
```

你可以把它理解为：

> QuantizationConfig 不直接执行计算，而是负责“识别、解析和分发”。

### 3.2.2 QuantizeMethod 是“某一层如何量化执行”

它回答：

```text
这个 Linear 层需要创建什么参数？
如何加载量化权重？
forward 时如何调用 kernel？
```

对于 Linear 层，核心接口是：

```python
class LinearMethodBase:
    def create_weights(...):
        ...

    def apply(layer, x, bias=None):
        ...
```

`create_weights` 在模型初始化时执行，负责创建参数；`apply` 在 forward 时执行，负责真正计算。

所以量化层的生命周期是：

```text
模型构建
  ↓
Linear 层初始化
  ↓
quant_config.get_quant_method(layer, prefix)
  ↓
method.create_weights(...)
  ↓
加载 checkpoint 权重
  ↓
method.process_weights_after_loading(...)  可选
  ↓
forward 时 method.apply(...)
```

---

## 3.3 `__init__.py`：量化方法注册中心

`quantization/__init__.py` 的职责可以理解为：

```text
维护 vLLM 支持的量化方法名
        ↓
根据 quantization 字符串找到对应 QuantizationConfig 类
        ↓
支持自定义 out-of-tree quantization plugin
```

核心机制：

```python
@register_quantization_config("my_quant")
class MyQuantConfig(QuantizationConfig):
    ...
```

这意味着第三方或硬件厂商可以不直接改 vLLM 主仓库，而是通过注册机制接入自己的量化方案。

面试表达：

> vLLM 量化模块并不是把 AWQ、GPTQ、FP8 全部写死在模型代码里，而是通过 QuantizationConfig 注册表和 get_quant_method 分发机制，把“模型结构”和“量化实现”解耦。这样新增量化方法时，通常不需要大规模修改每个模型类，而是实现新的 config 和 method。

---

## 3.4 `base_config.py`：所有量化配置的基类

`base_config.py` 定义了统一协议。

重点接口：

### `get_name`

返回量化方法名，例如：

```text
awq
gptq
fp8
compressed-tensors
bitsandbytes
```

### `get_supported_act_dtypes`

说明该量化方法支持什么激活 dtype。

例如 AWQ 通常是：

```text
activation dtype：FP16
```

因为 AWQ 是 W4A16：权重 INT4，激活 FP16。

### `get_min_capability`

说明最低 GPU 架构要求。

例如某些 kernel 要求：

```text
Turing / Ampere / Ada / Hopper
```

这不是随便限制，而是因为低 bit GEMM kernel 依赖特定硬件指令或内存布局。

### `get_config_filenames`

告诉 vLLM 去模型目录里找哪些量化配置文件。

例如 AWQ 常见：

```text
quant_config.json
quantize_config.json
```

### `from_config`

把 checkpoint 里的 JSON config 解析成 Python 对象。

例如从 config 中读取：

```text
bits
group_size
zero_point
modules_to_not_convert
```

### `get_quant_method`

最关键。它根据 layer 类型返回不同 method：

```text
LinearBase → AWQLinearMethod / Fp8LinearMethod / ...
FusedMoE / RoutedExperts → MoE quant method
Attention → KV Cache quant method
其他层 → None
```

这就是 vLLM 能把同一种量化配置作用到不同模块的原因。

---

## 3.5 Linear 层中的量化分发

大模型中最多的计算通常是 Linear：

```text
QKV projection
O projection
MLP gate/up/down projection
LM Head
MoE expert projection
```

普通 Linear 计算：

```text
Y = X @ W^T + b
```

量化 Linear 计算：

```text
Y = X @ dequantize(W_q, scale, zero_point)^T + b
```

高性能 kernel 不会真的先完整反量化出 W_fp16，而是做融合：

```text
读取 packed low-bit weight
  ↓
局部解包 / 反量化
  ↓
GEMM
  ↓
输出 FP16/BF16
```

vLLM 的 `LinearMethodBase` 把这件事抽象成：

```text
create_weights：准备权重参数
apply：执行矩阵乘
```

所以：

- 未量化 Linear 使用 `UnquantizedLinearMethod`
- AWQ Linear 使用 `AWQLinearMethod`
- FP8 Linear 使用 `Fp8LinearMethod`
- compressed-tensors 使用 `CompressedTensorsLinearMethod`

---

## 3.6 AWQ 源码解析

AWQ 文件：

```text
vllm/model_executor/layers/quantization/awq.py
```

核心类：

```text
AWQConfig
AWQLinearMethod
```

### 3.6.1 AWQConfig 做什么

AWQConfig 主要保存：

```text
weight_bits
group_size
zero_point
modules_to_not_convert
pack_factor
```

其中：

```python
pack_factor = 32 // weight_bits
```

如果 `weight_bits=4`：

```text
pack_factor = 8
```

含义是：

> 一个 int32 可以打包 8 个 int4 权重。

所以 AWQ 的 qweight 往往不是普通 int4 张量，而是用 int32 作为存储容器，内部 packed 了多个 4-bit 值。

### 3.6.2 AWQ 的参数结构

AWQLinearMethod 通常会创建：

```text
qweight：打包后的 int4 权重，实际 dtype 常用 int32 存储
qzeros：打包后的 zero point
scales：group-wise scale
```

简化理解：

```text
原始 W_fp16
        ↓
按 group_size 分组
        ↓
每组计算 scale / zero_point
        ↓
量化成 int4
        ↓
多个 int4 打包进 int32
        ↓
保存为 qweight / qzeros / scales
```

forward 时：

```text
X_fp16
  ↓
AWQ kernel 读取 qweight/qzeros/scales
  ↓
局部反量化 + GEMM
  ↓
Y_fp16
```

### 3.6.3 AWQ 为什么是 W4A16

AWQ 的设计目标是低 bit weight-only：

```text
W：4-bit
A：16-bit
```

所以它只减少权重存储和读取，不会减少激活大小，也不会减少 KV Cache。

这也是面试中要特别说明的点：

> AWQ 适合权重显存瓶颈明显的场景；如果长上下文下 KV Cache 成为瓶颈，AWQ 本身不能解决 KV Cache 显存问题，需要结合 PagedAttention、KV Cache 量化、prefix caching 或更合理的调度。

---

## 3.7 GPTQ 源码理解

GPTQ 和 AWQ 一样，常见也是 INT4 weight-only，但算法思想不同。

GPTQ 的核心是：

```text
使用近似二阶信息，逐列/逐块量化权重，并补偿量化误差
```

从 vLLM 接入角度看，它和 AWQ 类似：

```text
GPTQConfig
  ↓
GPTQLinearMethod
  ↓
create_weights 创建 qweight / qzeros / scales / g_idx 等
  ↓
apply 调用 GPTQ / Marlin kernel
```

常见 GPTQ 元数据：

```text
bits
group_size
desc_act
sym
true_sequential
g_idx
```

不同 GPTQ 工具导出的格式可能不同，所以 vLLM 需要适配不同字段。

面试中可以这样对比 AWQ 和 GPTQ：

| 对比点 | AWQ | GPTQ |
|---|---|---|
| 类型 | PTQ / weight-only | PTQ / weight-only |
| 常见 bit | INT4 | INT4 |
| 激活是否量化 | 否 | 否 |
| 核心思想 | activation-aware，保护重要通道 | 近似二阶误差补偿 |
| 校准数据 | 需要激活统计 | 需要校准数据估计误差 |
| vLLM 执行 | AWQLinearMethod / AWQ kernel | GPTQLinearMethod / Marlin 等 kernel |

---

## 3.8 FP8 源码解析

FP8 文件：

```text
vllm/model_executor/layers/quantization/fp8.py
```

核心类：

```text
Fp8Config
Fp8LinearMethod
Fp8KVCacheMethod
Fp8MoEMethod
```

FP8 和 AWQ / GPTQ 最大不同：

```text
AWQ / GPTQ：主要是 Linear 的 weight-only quant
FP8：可能覆盖 Linear、MoE、Attention KV Cache
```

### 3.8.1 Fp8Config 关键字段

常见字段包括：

```text
is_checkpoint_fp8_serialized
activation_scheme
ignored_layers
weight_block_size
store_dtype
```

含义：

| 字段 | 含义 |
|---|---|
| `is_checkpoint_fp8_serialized` | checkpoint 是否已经是 FP8 权重 |
| `activation_scheme` | 激活 scale 是 static 还是 dynamic |
| `ignored_layers` | 哪些层不量化 |
| `weight_block_size` | block-wise FP8 量化粒度 |
| `store_dtype` | 权重存储格式，如 FP8 / MXFP4 等 |

### 3.8.2 FP8 get_quant_method 的分发

FP8Config 会根据 layer 类型返回不同方法：

```text
LinearBase → FP8 Linear Method
RoutedExperts / SharedExperts → FP8 MoE Method
Attention → FP8 KV Cache Method
```

这说明 FP8 在 vLLM 中不是只服务于 Linear，而是可能参与：

- Dense Linear；
- MoE expert；
- KV Cache；
- Attention 相关 scale。

### 3.8.3 FP8 在线量化与离线量化

如果：

```text
is_checkpoint_fp8_serialized = True
```

说明 checkpoint 已经保存为 FP8，vLLM 主要负责读取并按 scale 执行。

如果：

```text
is_checkpoint_fp8_serialized = False
```

说明 checkpoint 不是 FP8，需要在线量化路径。

这两条路径对启动时间、精度稳定性和可控性影响很大。

---

## 3.9 Quantized KV Cache 源码理解

KV Cache 量化不是 Linear 层量化，它作用在 Attention 模块。

普通 KV Cache：

```text
K_cache: FP16/BF16
V_cache: FP16/BF16
```

FP8 KV Cache：

```text
K_cache: FP8
V_cache: FP8
k_scale / v_scale: FP16/FP32 scale
```

Attention 计算时需要：

```text
Q 与 K 做 attention score
score 再与 V 做加权求和
```

如果 K/V 是 FP8，就需要在 attention backend 中处理 scale：

```text
K_fp16 ≈ K_fp8 × k_scale
V_fp16 ≈ V_fp8 × v_scale
```

或者在支持 FP8 attention 的 backend 中直接低精度执行。

KV Cache 量化和 PagedAttention 的关系：

```text
PagedAttention 解决 KV Cache 怎么分页存、怎么映射
KV Cache Quantization 解决每个 KV Cache slot 用什么 dtype 存
```

两者不是替代关系，而是叠加关系。

---

## 3.10 compressed-tensors 与 LLM Compressor

现在 vLLM 推荐关注 LLM Compressor / compressed-tensors 路线，因为它更像一个统一压缩格式入口。

思路：

```text
使用 llm-compressor 离线量化模型
        ↓
保存 compressed-tensors 格式
        ↓
vLLM 读取压缩格式 config
        ↓
通过 CompressedTensorsConfig 分发到 Linear / MoE / Attention
        ↓
执行对应 kernel
```

它的意义是：

- 支持更多量化算法；
- 支持统一配置格式；
- 支持 FP8、INT8、INT4、KV Cache 等；
- 更适合生产部署和跨工具链。

# 4. 从输入到输出：量化在 vLLM 推理链路中的位置

下面用一次请求来串起来。

## 4.1 服务启动阶段

```text
用户启动：
vllm serve qwen-awq --quantization awq
```

vLLM 做：

```text
读取模型 config
读取 quant_config
创建 ModelConfig / LoadConfig
选择 QuantizationConfig
初始化 EngineCore
初始化 Worker
初始化 ModelRunner
构建模型层
```

当构建 Linear 层时：

```text
LinearBase.__init__
  ↓
quant_config.get_quant_method(layer, prefix)
  ↓
AWQLinearMethod / GPTQLinearMethod / Fp8LinearMethod
  ↓
create_weights
```

这一步决定这个 Linear 层到底是普通 FP16 Linear，还是量化 Linear。

---

## 4.2 权重加载阶段

```text
读取 safetensors / bin
        ↓
根据参数名映射到 vLLM 模型参数
        ↓
加载 qweight / qzeros / scales / input_scale / weight_scale
        ↓
必要时做 packing / transposition / format conversion
```

例如 AWQ：

```text
qweight 进入 layer.qweight
qzeros 进入 layer.qzeros
scales 进入 layer.scales
```

FP8：

```text
weight 可能是 FP8 storage
weight_scale 进入对应 scale parameter
activation scale 可能动态计算或从 config 加载
```

---

## 4.3 请求进入推理阶段

```text
Prompt
  ↓
Tokenizer
  ↓
input_ids
  ↓
Scheduler 调度 prefill / decode
  ↓
ModelRunner 构建 input tensors
  ↓
model.forward
```

走到模型层时：

```text
Embedding
  ↓
Transformer Block
  ↓
Attention
  ↓
MLP
  ↓
LM Head
```

其中大量 Linear 调用会进入：

```text
quant_method.apply(layer, x, bias)
```

而不是普通：

```text
torch.nn.functional.linear(x, weight, bias)
```

---

## 4.4 量化 Linear 的计算阶段

以 AWQ 为例：

```text
输入 X_fp16
  ↓
读取 qweight/qzeros/scales
  ↓
kernel 内部解包 int4
  ↓
根据 scale/zero_point 反量化
  ↓
执行 GEMM
  ↓
输出 Y_fp16
```

以 FP8 W8A8 为例：

```text
输入 X_fp16/BF16
  ↓
如果 dynamic activation quant：
    计算 input scale
    X → X_fp8
  ↓
读取 W_fp8 + weight_scale
  ↓
FP8 scaled GEMM
  ↓
输出 Y_fp16/BF16
```

---

## 4.5 KV Cache 量化阶段

Prefill：

```text
计算 K/V
  ↓
根据 kv scale 量化成 FP8
  ↓
写入 Paged KV Cache block
```

Decode：

```text
新 token 计算 Q/K/V
  ↓
新 K/V 写入 FP8 KV Cache
  ↓
Q 读取历史 FP8 K/V
  ↓
Attention backend 使用 scale 计算 attention
```

这一步影响的是长上下文和 batch capacity。

---

## 4.6 输出阶段

```text
最后一层 hidden states
  ↓
LM Head
  ↓
logits
  ↓
Sampler
  ↓
next token
  ↓
detokenize / stream output
```

量化对输出质量的影响最终表现为：

- token 分布轻微变化；
- 采样结果变化；
- 格式遵循能力变化；
- 数学 / 代码能力变化；
- 长上下文召回能力变化。

因此部署时必须做质量回归。

# 5. 常见量化方法对比

| 方法 | 类型 | 量化对象 | 常见格式 | 优点 | 缺点 | 适合场景 |
|---|---|---|---|---|---|---|
| AWQ | PTQ | Weight-only | W4A16 | 显存省，精度较稳 | 不省 KV Cache | 中小 batch、权重显存瓶颈 |
| GPTQ | PTQ | Weight-only | W4A16 | 压缩率高，生态广 | 格式复杂，兼容性要测 | 单卡/多卡部署开源量化模型 |
| FP8 W8A8 | PTQ/在线 | Weight + Activation | FP8 | 硬件支持好时速度强 | scale 复杂，硬件依赖 | Hopper/Ada/MI300 等 |
| INT8 W8A8 | PTQ/在线 | Weight + Activation | INT8 | 成熟，硬件广 | outlier 敏感 | 通用推理加速 |
| BitsAndBytes | 在线/加载时 | Weight | INT8/INT4 | 使用方便 | 性能不一定最优 | 快速实验 |
| FP8 KV Cache | KV Cache | K/V Cache | FP8 | 长上下文省显存 | 影响 attention 精度 | 长上下文、大并发 |

# 6. 实践排错指南

## 6.1 加载失败

常见报错：

```text
weight shape mismatch
group_size not aligned
unsupported quantization method
no kernel found
GPU capability not supported
```

排查顺序：

```text
1. 确认 vLLM 版本
2. 确认 GPU 架构
3. 查看 quant_config.json
4. 查看模型 config 中 quantization_config
5. 降低 tensor_parallel_size 试跑
6. 换一个官方推荐或社区高频使用的量化 checkpoint
7. 查看是否有 ignored_layers / modules_to_not_convert
```

---

## 6.2 输出质量下降

可能原因：

```text
1. 量化 bit 太低
2. group_size 太大
3. 校准数据不匹配真实业务
4. KV Cache scale 不合理
5. 动态量化 scale 不稳定
6. 某些敏感层被量化，如 lm_head、embed、router
```

解决方向：

```text
1. 使用更高 bit，如 INT8/FP8 替代 INT4
2. 减小 group_size
3. 增加校准数据
4. 关键层跳过量化
5. 使用 BF16 baseline 对比定位
6. 对业务 prompt 做回归测试
```

---

## 6.3 显存省了但速度没提升

原因可能是：

```text
1. kernel 不够高效
2. batch 太小，额外开销占比高
3. decode 瓶颈在 KV Cache，不在权重
4. prefill 瓶颈在 attention，不在 Linear
5. 反量化开销抵消了低 bit 读取收益
6. 没有走到 Marlin / CUTLASS / 硬件 FP8 kernel
```

面试回答：

> 量化不等于必然加速。是否加速取决于瓶颈。如果原来瓶颈是显存容量，量化能让模型放得下；如果原来瓶颈是权重带宽，weight-only 可能加速；如果瓶颈是 KV Cache，应该关注 KV Cache 量化；如果 kernel 不匹配，低 bit 反而可能变慢。

# 7. 面试题与参考答案

## Q1：vLLM 中量化模块的核心抽象是什么？

答：

vLLM 量化模块核心是 `QuantizationConfig` 和 `QuantizeMethod`。`QuantizationConfig` 负责表示量化方案本身，包括方法名、支持的激活 dtype、最低硬件能力、从哪些 config 文件解析参数，以及对不同 layer 返回什么量化 method。`QuantizeMethod` 负责某一层具体如何创建量化权重、如何加载和后处理权重、forward 时如何执行量化 kernel。这样模型结构和量化实现解耦，新增量化方法不需要改每个模型类。

---

## Q2：AWQ 在 vLLM 中大概怎么执行？

答：

AWQ 是一种 INT4 weight-only 量化方法，通常是 W4A16，即权重 4-bit、激活 FP16。vLLM 加载 AWQ 模型时会读取 `quant_config.json` 或 `quantize_config.json`，解析 `bits`、`group_size`、`zero_point` 等参数，创建 `AWQConfig`。模型构建 Linear 层时，`AWQConfig.get_quant_method` 会返回 `AWQLinearMethod`。`create_weights` 会创建 `qweight`、`qzeros`、`scales` 等参数，其中多个 int4 权重通常 packed 到 int32 中。forward 时 `apply` 调用 AWQ kernel，在 kernel 内部完成解包、反量化和 GEMM。

---

## Q3：AWQ 和 GPTQ 有什么区别？

答：

两者都是常见 PTQ weight-only 低 bit 量化方法，常用于 INT4。AWQ 的核心是 activation-aware，它认为不是所有权重同等重要，通过激活统计找到重要通道并保护它们，从而降低量化误差。GPTQ 则使用近似二阶信息做逐块或逐列量化误差补偿。部署角度看，两者在 vLLM 中都通过量化 config 和 linear method 接入，都会创建 qweight、scale 等量化参数，并依赖对应 kernel 执行。

---

## Q4：什么是 W4A16、W8A8？

答：

W 表示 weight，A 表示 activation。W4A16 表示权重使用 4-bit，激活使用 16-bit，常见于 AWQ/GPTQ。W8A8 表示权重和激活都使用 8-bit，常见于 FP8 或 INT8 推理。W4A16 主要节省权重显存，精度相对稳；W8A8 不仅节省权重，也减少激活带宽，并可能利用硬件低精度计算单元加速，但对 scale 和 kernel 支持要求更高。

---

## Q5：为什么量化后不一定更快？

答：

因为量化的直接收益是减少数据大小，不是自动减少所有计算时间。是否更快取决于是否存在高效 low-bit kernel、硬件是否支持对应低精度指令、瓶颈是否在权重带宽或 KV Cache 带宽。如果 kernel 需要额外反量化，batch 又很小，反量化开销可能抵消收益。对于长上下文，如果瓶颈是 KV Cache，单纯 weight-only 量化也未必能提升 decode 性能。

---

## Q6：KV Cache 量化和模型权重量化有什么区别？

答：

权重量化压缩模型参数，比如 Linear 层的 W；KV Cache 量化压缩推理过程中为每个 token 保存的 K/V。权重量化主要解决模型太大、权重读带宽高的问题；KV Cache 量化主要解决长上下文和高并发下 KV Cache 显存占用大的问题。二者可以同时使用，例如模型权重 FP8/W4，KV Cache 也使用 FP8。

---

## Q7：vLLM 的 FP8 KV Cache scale 如何得到？

答：

vLLM 支持几种方式。第一种是不校准，scale 默认 1.0；第二种是在 warmup 时通过随机 token 估计 scale；第三种是使用 llm-compressor 基于校准数据集生成 scale。生产部署更推荐第三种，因为它更能匹配真实输入分布，精度更稳。

---

## Q8：如果量化模型加载失败，你会怎么排查？

答：

我会先确认 vLLM 版本和 GPU 架构是否支持该量化方法；然后检查模型目录中的 `quant_config.json`、`quantize_config.json` 或 Hugging Face config 里的 `quantization_config`；再检查 bits、group_size、zero_point、desc_act 等字段是否符合 vLLM 支持；如果使用 Tensor Parallel，会检查切分后的维度是否能被 group_size 或 pack_factor 对齐；最后尝试降低 TP、换官方推荐 checkpoint 或查看是否某些层需要跳过量化。

---

## Q9：vLLM 为什么要设计 QuantizationConfig，而不是每个模型手写量化逻辑？

答：

因为 vLLM 要支持大量模型和大量量化后端。如果每个模型都手写 AWQ/GPTQ/FP8 逻辑，代码会爆炸且难以维护。`QuantizationConfig + get_quant_method` 的设计把模型结构与量化执行解耦：模型层只声明自己是 Linear、MoE 或 Attention，量化配置决定该层使用哪种执行 method。这样新增量化方法、硬件后端或插件时更容易扩展。

---

## Q10：AWQ 的 qweight 为什么常用 int32 存？

答：

因为硬件和 PyTorch 张量通常没有真正方便的 int4 参数类型。AWQ 会把多个 4-bit 权重打包到一个 int32 中。如果 weight_bits=4，那么一个 int32 可以存 8 个 int4，pack_factor=32/4=8。这样可以降低存储空间，并让 kernel 按 packed 格式读取和解包。

---

## Q11：量化粒度会怎么影响精度和性能？

答：

粒度越粗，比如 per-tensor，scale 越少，元数据和 kernel 处理简单，但容易受 outlier 影响，精度差。粒度越细，比如 per-channel、per-group、block-wise，scale 更多，能更好适应不同通道或块的数值范围，精度更好，但元数据增加，kernel 更复杂。实际部署中 group-wise 是 INT4 weight-only 常见折中，FP8 中也常见 block-wise 策略。

---

## Q12：vLLM 中 FP8 和 AWQ 的源码接入有何差异？

答：

AWQ 主要作用于 Linear 和部分 MoE，属于 W4A16 weight-only；`AWQConfig.get_quant_method` 对 Linear 返回 `AWQLinearMethod`。FP8 更广，可以覆盖 Linear、MoE 和 Attention 的 KV Cache；`Fp8Config.get_quant_method` 对 Linear 返回 FP8 Linear method，对 MoE 返回 FP8 MoE method，对 Attention 返回 FP8 KV Cache method。所以 FP8 在 vLLM 中不仅是权重量化，也可能和 KV Cache、Attention backend 相关。

---

## Q13：什么时候优先选 AWQ/GPTQ，什么时候选 FP8？

答：

如果硬件是消费级或常规 NVIDIA GPU，并且主要目标是让模型省显存、能单卡或少卡跑起来，AWQ/GPTQ 是容易上手的选择。如果硬件支持 FP8 加速，例如 Hopper/Ada/部分 AMD GPU，且希望获得更好的吞吐和生产性能，则优先评估 FP8 W8A8。对于长上下文并发服务，还要考虑 FP8 KV Cache。最终选择不能只看格式，要看 vLLM 版本、模型、硬件、kernel 和质量评测结果。

---

## Q14：量化模型部署前要做哪些验证？

答：

至少做四类验证。第一是可加载性，确认模型可以在目标 vLLM 版本和硬件上启动。第二是性能验证，比较显存、TTFT、TPOT、tokens/s、并发容量。第三是质量验证，使用业务 prompt、数学、代码、JSON、长上下文等测试。第四是稳定性验证，长时间压测，观察是否有 CUDA error、OOM、输出异常或吞吐抖动。

# 9. 本节课总结

本节课可以浓缩成一句话：

> vLLM 的量化能力不是一个单独的“压缩开关”，而是贯穿模型加载、层构建、权重参数创建、kernel 执行、KV Cache 管理和硬件后端选择的一套模块化机制。

最重要的理解是：

```text
量化算法负责“如何把高精度数值压到低 bit”
vLLM 量化模块负责“如何把这种低 bit 表示接入推理框架”
量化 kernel 负责“如何让低 bit 表示真正高效执行”
Benchmark 负责“证明它是否真的省显存、提吞吐、保质量”
```

对面试来说，你至少要能讲清楚：

1. AWQ/GPTQ/FP8/KV Cache 量化分别解决什么问题；
2. vLLM 如何通过 QuantizationConfig 和 QuantizeMethod 接入量化；
3. AWQ 的 qweight/qzeros/scales 是什么；
4. FP8 为什么比 AWQ 更依赖硬件和 scale；
5. 量化后为什么不一定变快；
6. 部署量化模型如何做性能和质量验证。
