> 适用对象：正在学习 AI Infra / 大模型推理系统 / vLLM / CUDA / PyTorch 的同学。  
> 本笔记围绕课程目录“CUDA Graph 原理、核心注意事项、CUDA Graph + Model Forward 实战、vLLM 中的 CUDA Graph”展开，目标是让你能理解 CUDA Graph 为什么能加速 LLM 推理、怎么写、怎么在 vLLM 中落地，以及面试时怎么讲清楚。

## 0. 本节课的核心主线

这节课的核心不是单纯介绍一个 CUDA API，而是解释：

> **为什么大模型推理，尤其是 Decoder-only LLM 的 decode 阶段，会被 CPU launch overhead 拖慢；CUDA Graph 如何把一串固定的 GPU 操作提前捕获成图，然后反复 replay，从而减少 CPU 逐 kernel 发射的开销；vLLM 又如何在动态请求调度、KV Cache、Attention backend、batch size 变化之间折中使用 CUDA Graph。**

可以用一句话概括：

> **CUDA Graph 是把“每一步都由 CPU 临时调度 GPU kernel”变成“CPU 一次性提交预先录好的 GPU 执行图”。**

LLM 推理中，prefill 和 decode 的特点不同：

- **Prefill 阶段**：一次处理 prompt 的所有 token，计算量大，通常更偏 GPU compute-bound，但输入长度变化大，shape 更动态。
- **Decode 阶段**：每轮通常每个请求只生成 1 个 token，单步计算较小，但要循环很多轮，kernel launch 次数多，更容易暴露 CPU 调度开销。

因此，CUDA Graph 在 LLM 推理中最典型的收益点是：

- 小 batch / 低延迟场景；
- decode-only batch；
- MoE 或小模型中 GPU kernel 较碎、CPU launch overhead 更明显的场景；
- 同一类 batch shape 被反复执行的场景。

## 1. 为什么 Attention / LLM 推理会出现性能瓶颈

### 1.1 LLM 推理不是一次 kernel 完成

一次 Transformer layer forward 通常包含很多操作：

1. RMSNorm / LayerNorm；
2. QKV Linear；
3. RoPE 位置编码；
4. Attention；
5. O Projection；
6. Residual Add；
7. FFN / MLP：Gate Up Projection、激活函数、Down Projection；
8. 多层重复；
9. 最后 LM Head 得到 logits；
10. Sampling 得到下一个 token。

这些操作背后会触发很多 CUDA kernel 或库调用，例如 GEMM、elementwise、softmax、attention kernel、sampling kernel 等。

在普通 eager 执行中，CPU 大致要做：

```text
Python / C++ 逻辑
  ↓
准备 kernel 参数
  ↓
调用 CUDA Runtime / Driver API
  ↓
GPU 执行 kernel
  ↓
下一个 kernel 再重复一遍
```

如果一个 decode step 只有很小的计算量，但包含几十甚至上百个 GPU kernel，那么 CPU 每次 launch kernel 的开销就会变得明显。

### 1.2 Decode 阶段为什么特别适合 CUDA Graph

以 Decoder-only LLM 为例：

```text
prefill：输入 prompt = N 个 token，一次性算出 N 个位置的 hidden states 和 KV Cache

decode step 1：输入上一个 token，生成 token 1
decode step 2：输入 token 1，生成 token 2
decode step 3：输入 token 2，生成 token 3
...
```

decode 阶段的特点是：

- 每步 query token 数通常是 1；
- 每步执行路径高度重复；
- 每步 kernel 序列相似；
- 每步都要访问历史 KV Cache；
- 如果输出 512 个 token，就要执行 512 次 decode forward。

所以 decode 的问题是：

> 单步计算不一定大，但重复次数极多，CPU 每步调度 GPU 的开销累计起来很可观。

CUDA Graph 的作用就是把这种重复执行路径捕获下来。

## 2. CUDA Graph 原理

### 2.1 什么是 CUDA Graph

CUDA Graph 是 CUDA 提供的一种 GPU 工作提交方式。普通 CUDA Stream 是“来一个 kernel，CPU launch 一个 kernel”；CUDA Graph 则是把一组 GPU 操作表示成一个图：

```text
Node 1: memcpy / kernel / memset / event ...
   ↓
Node 2: kernel
   ↓
Node 3: kernel
   ↓
Node 4: memcpy / kernel ...
```

这个图包含两类信息：

- **节点 node**：具体的 GPU 操作，例如 kernel launch、memcpy、memset、event 等。
- **边 edge**：操作之间的依赖关系，表示哪个操作必须在哪个操作之后执行。

CUDA Graph 的典型流程是：

```text
1. Warmup：先普通 eager 跑几次，让 kernel、内存、cuBLAS/cuDNN/Triton 等初始化完成
2. Capture：捕获一段固定 GPU 执行流程
3. Instantiate：把捕获到的 graph 转成可执行 graph executable
4. Replay：后续反复重放这个 graph
```

核心收益：

> 第一次捕获时付出构图成本，后续 replay 时 CPU 只需要一次 graph launch，而不是逐个 kernel launch。

### 2.2 普通执行 vs CUDA Graph 执行

#### 普通 eager 执行

```text
for each decode step:
    launch RMSNorm kernel
    launch QKV GEMM
    launch RoPE kernel
    launch Attention kernel
    launch O Projection GEMM
    launch MLP GEMM
    launch activation kernel
    launch MLP Down GEMM
    launch logits kernel
    launch sampling kernel
```

CPU 每个 kernel 都要做 launch。

#### CUDA Graph 执行

```text
capture once:
    record RMSNorm → QKV → RoPE → Attention → MLP → logits → sampling

for each decode step:
    copy new input token into static input buffer
    replay graph once
    read output buffer
```

CPU 不再逐 kernel launch，而是 replay 整个图。

### 2.3 CUDA Graph 的本质收益

CUDA Graph 主要减少的是：

- Python 调用开销；
- C++ dispatcher 开销；
- CUDA driver launch 开销；
- 多 kernel 之间反复提交的 CPU overhead。

它不是把 GEMM 本身变得更快，也不是替代 FlashAttention / Triton / cuBLAS。它更像是：

> 把多个已经存在的 GPU 操作打包成一个固定执行计划，减少 CPU 端重复调度成本。

## 3. CUDA Graph 使用的核心注意事项

CUDA Graph 很强，但限制也很多。它适合“静态、重复、可提前录制”的计算路径。

### 3.1 shape 要稳定

CUDA Graph 捕获的是一条固定的执行图。如果 capture 时输入 shape 是：

```python
input_ids.shape = [8]
positions.shape = [8]
```

那么 replay 时最好仍然是相同 shape。否则可能出现：

- 不能 replay；
- 需要重新 capture；
- fallback 到 eager；
- 或者因为内存访问不匹配导致错误。

LLM 推理中请求长度、batch size、prefill token 数都可能变化，所以 vLLM 需要维护多个 capture size，例如：

```text
capture batch size = 1, 2, 4, 8, 16, 32, ...
```

实际运行时，选择一个合适的已捕获 graph。

### 3.2 内存地址要稳定

CUDA Graph replay 时不仅要求 shape 类似，还要求输入输出 tensor 的内存地址稳定。

错误理解：

```text
只要 tensor shape 一样，就可以 replay。
```

正确理解：

```text
CUDA Graph 捕获时记录的是 kernel 参数，其中包含 tensor 指针地址。
Replay 时这些地址不能随便变。
```

因此实际写法通常是：

```python
static_input = torch.empty_like(real_input)
static_output = None

# 每次 replay 前，把新数据 copy 到 static_input 对应的固定内存地址
static_input.copy_(real_input)
graph.replay()
```

这里不是把新的 tensor 直接传给 graph，而是把新数据复制到捕获时使用的静态 buffer。

### 3.3 capture 内部不能有不安全 CPU 行为

捕获过程中不能出现典型的 CPU-GPU 同步行为，例如：

```python
x.item()
x.cpu()
torch.cuda.synchronize()
print(cuda_tensor)  # 可能触发同步
```

因为 CUDA Graph 捕获的是 GPU 异步操作序列。如果捕获过程中突然要求 CPU 等 GPU 结果，就破坏了图的异步执行模型。

### 3.4 capture 内部最好不要发生动态内存分配

捕获前应该尽量完成：

- 模型权重加载；
- KV Cache 分配；
- 临时 buffer 预分配；
- cuBLAS / Triton / attention backend warmup；
- shape 对应的静态输入输出 buffer 分配。

如果 capture 中发生新的 GPU memory allocation，可能导致 capture 失败，或者导致额外 graph memory pool 占用。

### 3.5 控制流要稳定

下面这种逻辑不适合直接完整捕获：

```python
if input_len > 1024:
    use_kernel_A()
else:
    use_kernel_B()
```

如果每次 replay 路径不同，graph 就不再是固定图。

这也是为什么 vLLM 要区分：

- prefill batch；
- decode-only batch；
- mixed batch；
- uniform decode batch；
- attention backend 是否支持 CUDA Graph。

### 3.6 CUDA Graph 会占额外显存

CUDA Graph 不是免费优化。它会增加 GPU memory footprint，原因包括：

- 静态输入输出 buffer；
- graph private memory pool；
- 多个 capture size 各自对应 graph；
- full graph / piecewise graph 可能各自需要缓存。

因此如果显存紧张，可以：

- 减少 `cudagraph_capture_sizes`；
- 降低 `max_num_seqs`；
- 降低 `max_model_len`；
- 使用 `enforce_eager=True` 关闭 graph capture；
- 在 vLLM 中调整 `compilation_config`。

## 4. PyTorch 中 CUDA Graph 的基础写法

下面是一个简化版的 PyTorch CUDA Graph 代码，用来理解 capture / replay 模式。

### 4.1 最小模型 forward 示例

```python
import torch
import torch.nn as nn

class TinyModel(nn.Module):
    def __init__(self, hidden_size=1024):
        super().__init__()
        self.linear1 = nn.Linear(hidden_size, hidden_size)
        self.act = nn.SiLU()
        self.linear2 = nn.Linear(hidden_size, hidden_size)

    def forward(self, x):
        return self.linear2(self.act(self.linear1(x)))

model = TinyModel().cuda().eval()

batch_size = 8
hidden_size = 1024

# 静态输入 buffer：后续 replay 都复用这块内存地址
static_x = torch.randn(batch_size, hidden_size, device="cuda")

# 1. warmup：先普通执行几次
warmup_stream = torch.cuda.Stream()
warmup_stream.wait_stream(torch.cuda.current_stream())
with torch.cuda.stream(warmup_stream):
    for _ in range(3):
        y = model(static_x)
torch.cuda.current_stream().wait_stream(warmup_stream)

# 2. capture
cuda_graph = torch.cuda.CUDAGraph()
with torch.cuda.graph(cuda_graph):
    static_y = model(static_x)

# 3. replay
for _ in range(10):
    real_x = torch.randn(batch_size, hidden_size, device="cuda")
    static_x.copy_(real_x)      # 复制数据，不换地址
    cuda_graph.replay()         # 重放捕获的 forward
    y = static_y                # static_y 中保存最新输出
```

### 4.2 这段代码的关键点

| 代码动作 | 含义 |
|---|---|
| `static_x = ...` | 创建固定输入地址 |
| warmup | 让模型、kernel、库完成初始化 |
| `with torch.cuda.graph(cuda_graph)` | 捕获 CUDA 操作序列 |
| `static_x.copy_(real_x)` | 把新数据复制进固定地址 |
| `cuda_graph.replay()` | 以极低 CPU overhead 重放整段 GPU 工作 |
| `static_y` | 固定输出 buffer，replay 后内容更新 |

### 4.3 为什么不能直接换输入 tensor

错误写法：

```python
for real_x in real_inputs:
    static_x = real_x
    cuda_graph.replay()
```

这只是让 Python 变量 `static_x` 指向另一个 tensor，graph 内部记录的 GPU 地址并没有变。

正确写法：

```python
static_x.copy_(real_x)
cuda_graph.replay()
```

也就是：

> **graph 认的是地址，不是 Python 变量名。**

## 5. CUDA Graph + Model Forward 实战思路

如果把上面的 Toy Model 换成 LLM 的 `model.forward()`，整体思路是一样的：

```text
1. 准备固定 shape 的 input_ids / positions / attention metadata / block_table / slot_mapping
2. warmup 几次 model.forward
3. 捕获 model.forward
4. 每次 decode 时更新静态输入 buffer 的内容
5. replay graph
6. 从静态输出 buffer 中读取 logits / hidden states
```

### 5.1 LLM forward 输入通常包含什么

在 vLLM / LLM 推理中，模型 forward 不只是 `input_ids`，通常还包括：

| 输入 | 含义 |
|---|---|
| `input_ids` | 当前要计算的 token id |
| `positions` | 每个 token 的位置，用于 RoPE 等位置编码 |
| `intermediate_tensors` | pipeline parallel 或内部中间结果场景下使用 |
| `attn_metadata` | attention 后端需要的元数据 |
| `block_tables` | 每个请求逻辑 block 到物理 KV block 的映射 |
| `slot_mapping` | token 对应写入 KV Cache 的物理 slot |
| `kv_caches` | 每层 Attention 的 K/V 缓存空间 |

### 5.2 为什么 LLM CUDA Graph 比普通 MLP 难

普通 MLP 的输入可能只有：

```python
x: [batch_size, hidden_size]
```

LLM 推理的输入更复杂：

```text
input_ids: 当前 token
positions: 当前 token 的位置
KV Cache: 历史 token 的 K/V
block_table: 每个请求的 block 映射
slot_mapping: 当前 token 写入哪个 KV slot
attention metadata: attention kernel 如何访问 Q/K/V
sampling metadata: 如何采样下一个 token
```

而且这些东西会随着请求调度变化：

- 新请求加入；
- 老请求结束；
- batch size 变化；
- prompt 长度变化；
- decode token 位置变化；
- KV block 分配变化；
- chunked prefill 与 decode 混合。

所以 vLLM 不可能简单地“捕获一次整个模型然后永远复用”。它必须做更精细的 graph 管理。

## 6. vLLM 中的 CUDA Graph

### 6.1 vLLM 为什么需要 CUDA Graph

vLLM 的目标是高吞吐、低延迟服务。它会同时处理大量请求，并通过 continuous batching 把多个请求合并成 batch。

在 decode 阶段，vLLM 每个 step 大致做：

```text
Scheduler 选出本轮要执行的请求
  ↓
分配/更新 KV Cache block
  ↓
ModelRunner 构建 input_ids / positions / attn_metadata / slot_mapping / block_tables
  ↓
Worker 调用 model.forward
  ↓
GPU 执行 Transformer forward
  ↓
Sampler 得到新 token
  ↓
更新请求状态
  ↓
流式返回 token
```

其中 `model.forward` 会触发大量 GPU kernel。如果每轮 decode 都由 CPU 逐 kernel launch，低延迟场景会吃亏。

CUDA Graph 在 vLLM 中的作用是：

> **对形状稳定、执行路径稳定的 forward 子图进行 capture，后续 decode step 直接 replay，减少 CPU 调度开销。**

### 6.2 vLLM 中 full graph 与 piecewise graph

vLLM 中 CUDA Graph 可以粗略分为两类：

#### 1. Full CUDA Graph

捕获整个模型 forward：

```text
RMSNorm → Attention → MLP → ... → logits
```

优点：

- CPU overhead 最低；
- replay 粒度最大；
- 对 decode-only batch 低延迟收益明显。

缺点：

- 对 attention backend 要求高；
- 对 shape / metadata 稳定性要求高；
- capture 时间更长；
- 显存占用更高；
- prefill / mixed batch 支持更复杂。

#### 2. Piecewise CUDA Graph

只捕获部分子图，把不适合 capture 的部分留在 eager 中执行。例如 attention 不支持 CUDA Graph 时，可以让 attention eager，其他 MLP / norm / elementwise 部分进入 graph。

优点：

- 兼容性更好；
- 不要求所有 attention backend 都支持 full graph；
- 更适合动态 shape 或混合 batch。

缺点：

- CPU overhead 降低不如 full graph 彻底；
- graph 与 eager 混合，调试复杂；
- 仍需要 runtime dispatch。

### 6.3 vLLM 的 CUDA Graph runtime mode

vLLM 当前的 CUDA Graph 设计中，常见模式包括：

| 模式 | 含义 | 适合场景 |
|---|---|---|
| `NONE` | 关闭 CUDA Graph，纯 eager | 调试、排查 graph 问题、显存紧张 |
| `PIECEWISE` | 只捕获部分 capture-safe 子图 | 兼容性优先，attention 不适合 full graph |
| `FULL` | 尽量捕获完整 forward | attention backend 支持、shape 稳定 |
| `FULL_DECODE_ONLY` | 只对 uniform decode 使用 full graph | P/D 分离中的 decode 实例、低延迟 decode |
| `FULL_AND_PIECEWISE` | uniform decode 用 full graph，其他用 piecewise | 默认倾向的高性能折中 |

### 6.4 为什么 vLLM 要区分 prefill / decode / mixed batch

因为它们的 attention 形态不同。

#### Prefill

```text
一个请求有 N 个 prompt token
Q 长度 = N
K/V 长度 = N
attention 形状随 prompt 长度变化
```

特点：

- 输入 token 数变化大；
- attention mask / metadata 变化大；
- 更难统一捕获；
- 计算量大，CPU launch overhead 不是唯一瓶颈。

#### Decode

```text
每个请求本轮通常只算 1 个新 token
Q 长度 = 1
K/V 长度 = 历史上下文长度 + 当前 token
```

特点：

- 每个请求 query length 常常相同；
- batch 内更容易形成 uniform decode；
- 执行路径重复；
- 很适合 CUDA Graph。

#### Mixed batch

vLLM 可能把 prefill 和 decode 混在同一轮调度中：

```text
请求 A：prefill chunk
请求 B：decode 1 token
请求 C：decode 1 token
```

这种 batch 的 query length 不统一，attention metadata 更复杂，full CUDA Graph 的兼容难度更高。

### 6.5 vLLM CUDA Graph 的运行时选择过程

可以把 vLLM 的 CUDA Graph 逻辑理解为：

```text
当前 batch 到来
  ↓
构建 BatchDescriptor：描述 batch size / token 数 / decode or prefill / uniform 情况
  ↓
CudagraphDispatcher 判断应该使用哪种 runtime mode
  ↓
如果已有匹配 graph：replay
  ↓
如果没有匹配 graph 但允许 capture：capture 后缓存
  ↓
如果不适合 graph：fallback eager
```

核心思想：

> vLLM 不是“盲目使用 CUDA Graph”，而是根据 batch 形态和 attention backend 能力动态选择 full、piecewise 或 eager。

### 6.6 vLLM 中 attention backend 对 CUDA Graph 的影响

Attention 是 LLM forward 中最复杂、最动态的部分。不同 attention backend 对 CUDA Graph 的支持程度不同。

可以大致分成：

| 支持等级 | 含义 |
|---|---|
| `ALWAYS` | prefill / mixed / decode 都比较适合 CUDA Graph |
| `UNIFORM_BATCH` | 只支持 query length 统一的 batch，例如 uniform decode |
| `UNIFORM_SINGLE_TOKEN_DECODE` | 只支持每个请求 query length = 1 的 decode |
| `NEVER` | 不支持 CUDA Graph |

如果 attention backend 只支持 decode CUDA Graph，那么 vLLM 就不能强行对 mixed prefill/decode batch 做 full graph capture，而要自动降级到 piecewise 或 eager。

## 7. CUDA Graph 与 KV Cache / PagedAttention 的关系

### 7.1 KV Cache 是动态的，但底层大块内存可以固定

vLLM 的 KV Cache 通常提前分配成很多 block：

```text
KV Cache memory pool
  ├── physical block 0
  ├── physical block 1
  ├── physical block 2
  ├── ...
```

每个请求逻辑上看到的是：

```text
request 0 logical block 0 → physical block 7
request 0 logical block 1 → physical block 3
request 1 logical block 0 → physical block 10
```

也就是说：

- KV Cache 大内存池地址相对固定；
- 每个请求使用哪些 block 是动态的；
- block_table / slot_mapping 的内容会变；
- 但 block_table / slot_mapping 本身可以放在固定 shape 的 tensor buffer 中。

这为 CUDA Graph 提供了可能：

> graph 捕获固定的 kernel 序列和 tensor 地址；每次 replay 前只更新 block_table / slot_mapping / input_ids 的内容。

### 7.2 CUDA Graph 不等于固定请求

一个常见误区是：

> CUDA Graph 捕获后是不是只能处理同一批请求？

不是。

只要静态 buffer 的 shape 和地址不变，buffer 里面的值可以变。例如：

```text
第一次 replay：block_table = [7, 3, 9]
第二次 replay：block_table = [1, 8, 4]
```

只要 `block_table` 这个 tensor 地址没变，kernel 在 replay 时会读取新的内容。

这就是 vLLM 能把 CUDA Graph 和动态请求调度结合起来的关键。

## 8. CUDA Graph + Model Forward 的伪代码实现

下面用一个简化版伪代码展示 LLM forward 的 CUDA Graph 封装逻辑。

```python
class CUDAGraphModelRunner:
    def __init__(self, model, batch_size, device="cuda"):
        self.model = model
        self.batch_size = batch_size
        self.device = device

        # 1. 分配静态输入 buffer
        self.static_input_ids = torch.empty((batch_size,), dtype=torch.long, device=device)
        self.static_positions = torch.empty((batch_size,), dtype=torch.long, device=device)
        self.static_block_tables = torch.empty((batch_size, 128), dtype=torch.int32, device=device)
        self.static_slot_mapping = torch.empty((batch_size,), dtype=torch.int64, device=device)

        # 2. CUDA Graph 对象
        self.graph = torch.cuda.CUDAGraph()
        self.static_logits = None
        self.captured = False

    def warmup(self):
        for _ in range(3):
            _ = self.model(
                input_ids=self.static_input_ids,
                positions=self.static_positions,
                block_tables=self.static_block_tables,
                slot_mapping=self.static_slot_mapping,
            )

    def capture(self):
        self.warmup()
        with torch.cuda.graph(self.graph):
            self.static_logits = self.model(
                input_ids=self.static_input_ids,
                positions=self.static_positions,
                block_tables=self.static_block_tables,
                slot_mapping=self.static_slot_mapping,
            )
        self.captured = True

    def replay(self, input_ids, positions, block_tables, slot_mapping):
        # 3. 更新静态 buffer 的内容，但不换 tensor 地址
        self.static_input_ids.copy_(input_ids)
        self.static_positions.copy_(positions)
        self.static_block_tables.copy_(block_tables)
        self.static_slot_mapping.copy_(slot_mapping)

        # 4. replay
        self.graph.replay()
        return self.static_logits
```

这段伪代码表达了 vLLM 中 CUDA Graph 的核心思想，但真实 vLLM 会更复杂，因为它还要处理：

- 多层 KV Cache；
- tensor parallel；
- pipeline parallel；
- attention backend 差异；
- batch descriptor；
- capture size 缓存；
- full / piecewise graph；
- compilation_config；
- warmup dummy run；
- request 调度与输出采样。

## 10. CUDA Graph 小结

### 10.1 一句话总结

CUDA Graph 的本质：

> **把一段重复执行的 GPU 操作提前录制成图，后续用一次 graph launch 重放，减少 CPU 逐 kernel launch 的开销。**

### 10.2 什么时候收益大

| 场景 | 收益 |
|---|---|
| decode-only | 通常明显 |
| 小 batch 低延迟 | 明显 |
| 小模型 | 明显，因为 GPU 计算短，CPU launch overhead 占比高 |
| MoE 模型 | 可能明显，因为 kernel 更碎、调度更复杂 |
| 大 prefill | 不一定明显，因为通常 GPU compute 占主导 |
| 动态 shape 很强 | 受限，可能频繁 fallback eager |

### 10.3 什么时候可能没收益甚至负收益

- batch shape 变化过多，频繁 capture；
- 显存紧张，graph 占用导致 KV Cache 变小；
- kernel 本身很大，CPU launch overhead 占比很小；
- capture size 配置过多，启动耗时和显存开销增加；
- 代码中有 CPU sync 或动态控制流导致 capture 失败。

## 11. 从输入到输出：vLLM + CUDA Graph 完整推理流程

下面把整节课内容串成一条完整链路。

```text
用户请求进入 vLLM
  ↓
API Server / AsyncLLM 接收请求
  ↓
EngineCore 将请求放入调度队列
  ↓
Scheduler 选择本轮要执行的请求
  ↓
KV Cache Manager 分配或复用 block
  ↓
GPU ModelRunner 构建本轮模型输入：
    - input_ids
    - positions
    - block_tables
    - slot_mapping
    - attention metadata
  ↓
判断当前 batch 形态：
    - prefill?
    - decode?
    - mixed?
    - uniform decode?
    - batch size 是否命中 capture size?
  ↓
CudagraphDispatcher 选择 runtime mode：
    - FULL
    - PIECEWISE
    - NONE/eager
  ↓
如果 graph 已捕获：
    - 更新静态 buffer 内容
    - replay CUDA Graph
  ↓
如果 graph 未捕获但可捕获：
    - dummy_run / warmup
    - capture graph
    - replay 或缓存供后续使用
  ↓
如果不适合 graph：
    - eager 执行 model.forward
  ↓
Transformer forward 执行：
    - embedding / norm / attention / MLP / logits
  ↓
Sampler 根据 logits 采样下一个 token
  ↓
更新请求状态、KV Cache、输出 token
  ↓
返回给上层 Engine / API Server
  ↓
用户看到流式输出
```

这条链路里，CUDA Graph 主要卡在：

```text
ModelRunner 调用 model.forward 的执行阶段
```

它不负责调度，不负责采样策略本身，也不负责 KV Cache 分配策略；它优化的是 GPU workload 的提交方式。

## 12. 面试问题与参考答案

### Q1：CUDA Graph 解决的核心问题是什么？

**答：**  
CUDA Graph 主要解决 CPU 端反复 launch GPU kernel 的 overhead。普通 eager 执行中，每个 kernel 都要经过 Python/C++/CUDA driver 的调度路径。LLM decode 阶段每步计算量较小但 kernel 数多、重复次数多，所以 CPU launch overhead 会明显。CUDA Graph 把固定 GPU 操作序列提前 capture 成 graph，后续通过一次 replay 提交整段工作，从而降低 CPU overhead。

### Q2：CUDA Graph 为什么要求静态 shape？

**答：**  
因为 CUDA Graph 捕获的是固定的 GPU 操作拓扑和 kernel 参数。shape 变化可能导致 kernel grid/block 参数、访问范围、临时 buffer 大小、attention metadata 都发生变化，使原来的 graph 不再合法。因此通常需要为不同 batch size / token shape 分别捕获 graph，或者不满足条件时 fallback eager。

### Q3：CUDA Graph 为什么要求固定内存地址？

**答：**  
CUDA Graph capture 时 kernel 参数中包含输入输出 tensor 的底层指针地址。Replay 时 CUDA 会使用捕获时的地址。如果 replay 时换了新的 tensor 地址，graph 不会自动识别 Python 变量变化，可能读写错误地址。因此常见做法是维护长期存在的 static input/output buffer，每次 replay 前用 `copy_` 把新数据复制进去。

### Q4：为什么 LLM decode 阶段比 prefill 阶段更适合 CUDA Graph？

**答：**  
Decode 阶段每个请求通常只处理 1 个新 token，query length 更统一，执行路径高度重复，并且要循环很多次生成 token，CPU launch overhead 累计明显。Prefill 阶段 prompt 长度变化大，batch 形态更动态，且计算量更大，通常 GPU compute 占主导，所以 CUDA Graph 的收益和兼容性都不如 decode 稳定。

### Q5：vLLM 中 full CUDA Graph 和 piecewise CUDA Graph 有什么区别？

**答：**  
Full CUDA Graph 尽量捕获整个 model forward，CPU overhead 降得最多，但要求 attention backend 和 batch 形态都支持，显存和 capture 成本更高。Piecewise CUDA Graph 只捕获 capture-safe 的子图，把不适合 capture 的操作，比如某些 attention backend，留在 eager 中执行。Piecewise 兼容性更好，但性能收益不如 full graph。

### Q6：为什么 vLLM 需要 `cudagraph_capture_sizes`？

**答：**  
因为不同 batch size 对应的输入 shape 不同，通常需要不同的 CUDA Graph。`cudagraph_capture_sizes` 指定为哪些 batch size 捕获 graph。捕获 size 越多，命中 graph 的机会越大，但启动时间和显存占用也越高；捕获 size 越少，显存更省，但更多请求可能 fallback eager。

### Q7：CUDA Graph 会减少 KV Cache 显存吗？

**答：**  
不会。CUDA Graph 优化的是 GPU workload 提交开销，不是 KV Cache 的存储结构。KV Cache 显存优化主要来自 PagedAttention、block 管理、prefix caching、quantized KV cache 等。CUDA Graph 甚至会额外占用显存，因为它需要 static buffer 和 graph private memory pool。

### Q8：CUDA Graph 和 PagedAttention 是否冲突？

**答：**  
不冲突。PagedAttention 负责把 KV Cache 切成 block 并通过 block table 管理逻辑到物理 block 的映射；CUDA Graph 负责捕获和 replay GPU 执行路径。只要 KV Cache 大内存池、block table、slot mapping 等 tensor 的地址稳定，内容可以在 replay 前更新，因此二者可以结合。

### Q9：为什么 vLLM 有时候会 fallback 到 eager？

**答：**  
可能原因包括：当前 batch shape 没有对应 graph；attention backend 不支持当前 CUDA Graph mode；batch 是复杂 mixed prefill/decode；代码路径中有 CUDA Graph 不支持的操作；capture size 未配置；显存不足；调试时开启 `enforce_eager`。

### Q10：CUDA Graph 的缺点是什么？

**答：**  
主要缺点是牺牲动态灵活性：要求 shape、控制流、内存地址稳定；capture 阶段可能耗时；需要额外显存；调试复杂；不适合高度动态的 workload；如果 batch 变化太多或 GPU 计算本身很重，收益可能不明显。

### Q11：`enforce_eager=True` 有什么作用？

**答：**  
它强制 vLLM 使用 eager 执行，关闭 CUDA Graph capture。这通常用于调试、排查 CUDA Graph capture 失败、降低 graph 额外显存，或者确认某个问题是否由 graph replay 引起。

### Q12：为什么第一次请求可能比较慢？

**答：**  
因为第一次请求可能触发 warmup、kernel 初始化、编译、CUDA Graph capture 等操作。这些成本在第一次出现某个 batch shape 时支付，后续命中同一 graph 后 replay 才会变快。

### Q13：CUDA Graph 和 `torch.compile` 是什么关系？

**答：**  
二者不是同一个东西。`torch.compile` 更偏图捕获、图优化、算子融合和代码生成；CUDA Graph 更偏执行提交优化，把已经确定的一段 GPU workload capture 后 replay。实际系统中二者可以结合：先通过编译得到更高效的子图，再用 CUDA Graph 减少该子图反复执行时的 CPU launch overhead。

### Q14：如何判断 CUDA Graph 是否值得开启？

**答：**  
看 workload 是否 CPU launch overhead 占比较高。典型判断方法是 profiling：如果 GPU kernel 很碎、CPU launch 间隙明显、decode batch 小且重复多，CUDA Graph 值得开启。如果 GPU 一直满载且单个 kernel 很大，收益可能有限。还要综合显存、启动时间、capture size 配置和延迟目标。

### Q15：面试中如何一句话讲 vLLM 中 CUDA Graph 的价值？

**答：**  
vLLM 使用 CUDA Graph 主要是为了降低 decode 阶段反复执行 model forward 时的 CPU kernel launch overhead；它根据 batch 形态和 attention backend 能力，在 full graph、piecewise graph 和 eager 之间动态选择，从而在性能、兼容性和显存占用之间折中。

## 13. 面试复述模板

如果面试官问：“你了解 vLLM 里的 CUDA Graph 吗？”可以这样回答：

> 我理解 CUDA Graph 主要优化的是 CPU 端 launch GPU kernel 的开销。LLM 推理尤其是 decode 阶段，每轮通常每个请求只算一个 token，单步 GPU 计算不一定很大，但要重复很多轮，并且每轮会触发很多 kernel。如果每个 kernel 都走 Python/C++/CUDA driver 的 launch 流程，CPU overhead 会明显。CUDA Graph 的做法是先 warmup，再把一段稳定的 forward GPU 操作 capture 成 graph，后面每轮把新的 input_ids、positions、block_table、slot_mapping 等数据复制到固定 buffer，然后 replay graph。
>
> 但 CUDA Graph 要求 shape、控制流和内存地址稳定，所以在 vLLM 这种动态 batching 系统中不能简单地捕获一次全模型就一直用。vLLM 会根据 batch 形态和 attention backend 能力区分 full graph、piecewise graph 和 eager，比如 uniform decode 更适合 full graph，mixed prefill/decode 可能走 piecewise 或 eager。同时 CUDA Graph 会占额外显存，因此可以通过 capture sizes 或 enforce_eager 在性能和显存之间折中。
