> 课时 16：vLLM 高级特性：采样和投机解码  
> 课程关键词：Transformer Decode、GPU 性能瓶颈、Sampling、Greedy Search、Temperature、Top-k、Top-p、Speculative Decoding、Draft Model、Rejection Sampling、Medusa、EAGLE、MTP、vLLM Spec Decode、Proposer、Scorer、Verifier、Sampler

---

## 0. 本节课核心目标

本节课主要讲两个相互关联的问题：

1. **普通 Transformer 解码为什么慢**
   - Decoder-only LLM 是自回归模型；
   - 生成阶段必须一个 token 一个 token 地往后生成；
   - 每生成一个 token 都要跑一次模型 forward；
   - Decode 阶段常常不是算力瓶颈，而是显存带宽、kernel launch、调度和同步瓶颈。

2. **如何通过采样和投机解码提高推理效率**
   - 采样决定“下一个 token 怎么选”；
   - 投机解码尝试“一次猜多个 token，再让大模型验证”；
   - 如果猜对多个 token，就可以减少大模型 forward 次数；
   - vLLM 通过 speculative decoding 组件，把 draft / proposer、target model、rejection sampler、KV Cache、continuous batching 结合起来。

一句话概括：

> **采样解决的是“如何从 logits 选下一个 token”，投机解码解决的是“如何减少逐 token 串行 decode 的大模型调用次数”。**

# 第一部分：Transformer 解码与 GPU 性能瓶颈

## 1. Decoder-only LLM 的生成方式

Decoder-only LLM，例如 GPT、LLaMA、Qwen、DeepSeek 等，本质上是自回归模型：

```text
P(x1, x2, ..., xn) = Π P(xt | x1, x2, ..., x(t-1))
```

也就是说，第 t 个 token 的概率依赖前面所有 token。

生成时流程是：

```text
prompt
  ↓ tokenizer
input_ids
  ↓ model forward
logits for next token
  ↓ sampling
next_token
  ↓ append 到序列末尾
新的 input_ids
  ↓ 下一轮 model forward
...
```

例如：

```text
输入：今天 天气
模型输出下一个 token：很
序列变成：今天 天气 很
模型再输出下一个 token：好
序列变成：今天 天气 很 好
```

这就是自回归 decode。

---

## 2. Prefill 和 Decode 的区别

LLM 推理通常分成两个阶段。

### 2.1 Prefill 阶段

Prefill 处理用户输入 prompt。

假设 prompt 长度为：

```text
prompt_len = S
```

模型一次性处理整个 prompt：

```text
input_ids: [S]
```

每一层 Attention 会为这 S 个 token 计算 Q、K、V，并把 K、V 写入 KV Cache。

Prefill 的特点：

| 特点 | 解释 |
|---|---|
| 输入 token 多 | 一次处理整个 prompt |
| GEMM 大 | 矩阵乘法规模大，GPU 利用率高 |
| 计算密集 | 更容易吃满 Tensor Core |
| 主要影响 TTFT | Time To First Token，第一个 token 出来的时间 |

Prefill 中每层 attention 的核心计算可以简化为：

```text
Q = X Wq
K = X Wk
V = X Wv

Attention(Q, K, V) = softmax(QK^T / sqrt(d)) V
```

其中：

```text
X: [S, hidden_size]
Q: [S, num_heads, head_dim]
K: [S, num_kv_heads, head_dim]
V: [S, num_kv_heads, head_dim]
```

---

### 2.2 Decode 阶段

Decode 从生成第一个新 token 开始。

每一步只输入当前最新 token：

```text
input_ids: [1]
```

但它需要关注历史所有 token 的 KV Cache：

```text
K_cache: [past_len, num_kv_heads, head_dim]
V_cache: [past_len, num_kv_heads, head_dim]
```

Decode 的特点：

| 特点 | 解释 |
|---|---|
| 每步只生成一个 token | 强串行依赖 |
| 单次 GEMM 小 | GPU 并行度不够 |
| 需要频繁读权重和 KV Cache | 容易 memory bandwidth bound |
| 影响 TPOT / ITL | 每个输出 token 的耗时 |

Decode 每一步的流程：

```text
新 token embedding
  ↓
每层 Transformer forward
  ↓
读取历史 KV Cache
  ↓
写入当前 token 的 K/V
  ↓
得到最后 hidden state
  ↓
LM Head 得到 logits
  ↓
sampling 得到下一个 token
```

---

## 3. 为什么 Decode 是性能瓶颈？

### 3.1 自回归依赖导致串行

生成第 t+1 个 token 之前，必须知道第 t 个 token 是什么：

```text
token_t = sample(logits_t)
token_(t+1) = model(token_t, history)
```

所以不能简单把未来 100 个 token 全部并行生成。

这和训练阶段不同。训练时有完整句子，可以并行计算所有位置的 loss；推理时未来 token 不知道，只能边生成边推。

---

### 3.2 Decode 小 batch 时 GPU 利用率低

Decode 每一步只处理每个请求的 1 个新 token。

如果 batch 很小：

```text
batch_size = 1 或 2
```

每次矩阵乘法规模很小，GPU 可能大量时间花在：

- kernel launch；
- memory load；
- 同步；
- 调度；
- 读模型权重；
- 读 KV Cache。

这会导致 GPU 算力没有充分利用。

---

### 3.3 Decode 常常是 memory-bound

对一个 7B / 14B / 70B 模型来说，每一步 decode 都要访问大量模型权重。

如果只生成一个 token：

```text
计算量不大
但权重还是要读一遍
```

所以 Decode 阶段经常是：

```text
memory bandwidth bound
```

而不是：

```text
compute bound
```

这也是为什么投机解码有意义：

> 如果一次 target model forward 能验证多个 token，那么相当于一次读权重，多产出几个 token，摊薄每个 token 的权重读取成本。

# 第二部分：普通采样解码

## 4. 采样在 LLM 推理中的位置

模型 forward 的输出不是直接的文字，而是 logits：

```text
logits: [vocab_size]
```

每个位置对应词表中一个 token 的分数。

例如词表大小是 151936，则模型每一步输出：

```text
logits.shape = [151936]
```

采样模块要做的是：

```text
logits -> probabilities -> selected token id
```

完整链路：

```text
hidden state
  ↓ LM Head
logits
  ↓ logits processor / penalty
processed logits
  ↓ temperature / top-k / top-p / min-p
filtered logits
  ↓ softmax
probabilities
  ↓ sample / argmax
next token id
```

---

## 5. Greedy Decoding

Greedy decoding 是最简单的解码方式：

```text
next_token = argmax(logits)
```

也就是每一步都选择概率最大的 token。

优点：

- 确定性强；
- 速度快；
- 结果稳定；
- 适合代码补全、结构化输出、评测。

缺点：

- 容易重复；
- 输出保守；
- 创造性弱；
- 可能陷入局部最优。

例子：

```text
logits -> softmax probabilities

A: 0.50
B: 0.30
C: 0.20

Greedy 永远选 A
```

---

## 6. Temperature Sampling

Temperature 用来调整分布的尖锐程度。

公式：

```text
p_i = softmax(logits_i / T)
```

其中：

```text
T = temperature
```

### 6.1 T 小于 1

```text
T < 1
```

会让概率分布更尖锐：

```text
高概率 token 更高
低概率 token 更低
```

结果更稳定、更保守。

### 6.2 T 大于 1

```text
T > 1
```

会让概率分布更平滑：

```text
低概率 token 也有更多机会被选中
```

结果更多样、更随机。

### 6.3 T 等于 0

工程上通常把：

```text
temperature = 0
```

解释为 greedy decoding。

---

## 7. Top-k Sampling

Top-k 只保留概率最高的 k 个 token。

例如：

```text
top_k = 5
```

则只在概率最高的 5 个 token 中采样，其余 token 概率置 0。

流程：

```text
logits
  ↓ 取 top-k
只保留 k 个候选 token
  ↓ softmax
重新归一化
  ↓ sample
```

优点：

- 排除极低概率 token；
- 避免采到明显胡说的 token；
- 控制输出范围。

缺点：

- k 是固定值；
- 如果分布很尖锐，top_k 可能太宽；
- 如果分布很平坦，top_k 可能太窄。

---

## 8. Top-p / Nucleus Sampling

Top-p 也叫 nucleus sampling。

它不是固定保留 k 个 token，而是保留累计概率达到 p 的最小 token 集合。

例如：

```text
top_p = 0.9
```

表示按概率从高到低排序，选出累计概率达到 90% 的 token。

例子：

```text
A: 0.50
B: 0.25
C: 0.10
D: 0.08
E: 0.04
F: 0.03
```

如果 top_p = 0.9：

```text
A + B + C + D = 0.93
```

则候选集合为：

```text
A, B, C, D
```

优点：

- 自适应候选数量；
- 分布尖锐时候选少；
- 分布平坦时候选多。

---

## 9. Min-p Sampling

Min-p 是按照最大概率 token 的相对概率过滤候选。

假设最大概率是：

```text
p_max = 0.5
```

如果：

```text
min_p = 0.1
```

则保留概率大于：

```text
0.5 × 0.1 = 0.05
```

的 token。

它的作用是排除相对最大 token 太小的候选。

---

## 10. Penalty 类采样参数

采样前通常还会对 logits 做惩罚处理。

### 10.1 Repetition Penalty

用于惩罚已经出现过的 token：

```text
如果 token 已经出现过，则降低它的 logit
```

目的：

- 减少重复；
- 避免模型一直复读；
- 改善长文本质量。

### 10.2 Presence Penalty

只关心 token 是否出现过。

出现过就惩罚一次，不看频率。

### 10.3 Frequency Penalty

根据 token 出现频率惩罚。

出现越多，惩罚越大。

---

## 11. 采样和推理性能的关系

采样本身通常不是最大计算瓶颈，但会影响：

- 输出质量；
- acceptance rate；
- speculative decoding 收益；
- 是否容易重复；
- 是否容易产生长尾 token；
- batch 内不同请求的完成长度。

### 11.1 对投机解码的影响

投机解码需要 draft token 被 target model 接受。

如果采样非常随机：

```text
temperature 高
top_p 大
```

draft model 更难猜中 target model 的采样结果，acceptance rate 下降。

如果采样较确定：

```text
temperature 低
top_p 小
greedy
```

draft token 更容易被接受，投机解码收益更高。

# 第三部分：推测解码 / 投机解码基本框架

## 12. 投机解码要解决什么问题？

普通 decode：

```text
大模型 forward -> 采 1 个 token
大模型 forward -> 采 1 个 token
大模型 forward -> 采 1 个 token
...
```

如果要生成 K 个 token，需要 K 次大模型 forward。

投机解码希望：

```text
小模型 / draft head 先猜多个 token
大模型一次 forward 验证这些 token
如果接受多个 token，就一次前进多个位置
```

目标是减少 target model 的 decode step 数。

---

## 13. 投机解码的核心思想

投机解码包含两个模型或两个角色：

| 角色 | 含义 |
|---|---|
| Draft / Proposer | 便宜的提案者，负责快速猜未来 token |
| Target / Scorer | 原始大模型，负责验证 draft token 是否符合自己的分布 |

流程：

```text
当前上下文
  ↓
Draft model 快速生成 k 个候选 token
  ↓
Target model 对这 k 个 token 一次性并行评分
  ↓
Rejection sampler 判断接受几个 token
  ↓
接受的 token 直接加入输出
  ↓
如果拒绝，在拒绝位置从 target 分布重新采样
```

---

## 14. 为什么 target model 可以一次验证多个 token？

假设 draft 猜了：

```text
draft_tokens = [a, b, c, d]
```

target model 可以把：

```text
context + a + b + c + d
```

作为输入，一次 forward 得到多个位置的 logits：

```text
位置 1：P_target(a | context)
位置 2：P_target(b | context + a)
位置 3：P_target(c | context + a + b)
位置 4：P_target(d | context + a + b + c)
```

这和训练时 teacher forcing 类似：

> 给定完整前缀，Transformer 可以并行计算多个位置的 logits。

所以投机解码的关键是：

```text
draft 串行或并行地产生多个 token
target 一次并行验证多个位置
```

---

## 15. 接受率 acceptance rate

投机解码性能高度依赖接受率。

假设每轮 draft 生成：

```text
k = 5
```

如果 target 每轮平均接受：

```text
accepted = 4
```

那么一次 target forward 大约能推进 4 个 token，收益很高。

如果每轮只接受：

```text
accepted = 1
```

那么投机解码几乎没有收益，甚至因为多跑 draft model 和验证逻辑变慢。

常用指标：

```text
acceptance_rate = accepted_tokens / proposed_tokens
```

影响接受率的因素：

- draft model 和 target model 是否相似；
- draft model 是否足够强；
- 采样参数是否随机；
- 任务类型；
- prompt 分布；
- 代码 / 数学 / 翻译 / 问答等任务差异；
- target model 是否本身带 MTP / Medusa head。

---

## 16. Rejection Sampling 的基本含义

为了保证输出分布仍然等价于 target model，需要用 rejection sampling。

设：

```text
q(x)：draft model 对 token x 的概率
p(x)：target model 对 token x 的概率
```

如果 draft 提出 token x，则接受概率大致与：

```text
min(1, p(x) / q(x))
```

有关。

直观理解：

- 如果 target 比 draft 更喜欢这个 token，则接受；
- 如果 target 不如 draft 喜欢这个 token，则按比例接受；
- 如果拒绝，则从修正后的 target 分布重新采样。

这样理论上可以保证最终采样分布仍然来自 target model，而不是 draft model。

---

## 17. 投机解码为什么理论上可以无损？

普通误解是：

> “投机解码用了小模型，所以输出会变差。”

严格的 speculative sampling 不是直接采用小模型输出，而是：

```text
小模型只负责提案
大模型负责验证和纠正
```

只要 rejection sampling 正确实现，输出分布可以保持与 target model 一致，误差主要来自硬件浮点数、batch 数值差异、非确定性 kernel 等工程因素。

---

## 18. 投机解码什么时候有效？

适合：

- Decode 阶段 memory-bound；
- 中低 QPS latency 优先场景；
- target model 很大；
- draft model 很快；
- draft 与 target 分布接近；
- acceptance rate 高；
- batch 不太大；
- 生成长度较长。

不适合：

- 高 QPS 下 GPU 已经被 continuous batching 填满；
- draft model 太慢；
- acceptance rate 很低；
- target model 已经 compute-bound；
- 输出极短；
- 采样温度很高；
- 多卡通信和 KV Cache 管理开销抵消收益。

# 第四部分：Medusa：无 Draft 小模型的多头并行解码

## 19. Medusa 要解决什么问题？

传统投机解码需要一个额外 draft model。

问题是：

- 需要找一个和 target 匹配的小模型；
- 小模型要加载额外权重；
- 小模型也要占显存；
- 小模型和大模型的 tokenizer / architecture 要兼容；
- 维护成本高。

Medusa 的想法是：

> **不再额外加载小模型，而是在主模型顶部加多个 decoding heads，让这些 heads 预测未来多个 token。**

---

## 20. Medusa 的结构

普通 LLM：

```text
Transformer backbone
  ↓
LM Head
  ↓
next token logits
```

Medusa：

```text
Transformer backbone
  ↓
LM Head              -> 第 1 个 token
  ↓
Medusa Head 1        -> 第 2 个 token 候选
Medusa Head 2        -> 第 3 个 token 候选
Medusa Head 3        -> 第 4 个 token 候选
...
```

也就是说，Medusa 在主干模型上添加多个轻量预测头。

这些头通常是：

```text
Linear / MLP / small decoding head
```

目标是基于当前 hidden state 预测未来若干 token。

---

## 21. Medusa 的 Tree Attention

Medusa 不只是简单输出多个 token。

它会构造多个候选路径，例如：

```text
候选 1: A B C
候选 2: A B D
候选 3: A E F
候选 4: G H I
```

这些候选路径形成一棵树。

然后 target model 通过 tree attention 一次验证多条路径中的 token。

Tree Attention 的目的：

- 并行验证多个候选 continuation；
- 提高每轮能接受的 token 数；
- 减少 target model forward 次数。

---

## 22. Medusa 的优点

| 优点 | 解释 |
|---|---|
| 不需要独立 draft model | 减少额外模型维护 |
| 与 target backbone 共享大部分计算 | 只增加少量 head |
| 适合单模型部署 | 工程集成相对直接 |
| 可以一次产生多个候选 token | 提高 decode 并行度 |

---

## 23. Medusa 的缺点

| 缺点 | 解释 |
|---|---|
| 需要训练 Medusa heads | 不是任意模型直接可用 |
| head 预测能力有限 | 可能不如专门 draft model |
| tree attention 实现复杂 | 需要特殊 attention mask |
| batch / continuous batching 集成复杂 | 每个请求候选树不同 |
| 随机采样下 acceptance 可能下降 | 温度越高越难猜 |

---

## 24. Medusa 和普通 Draft Model 的区别

| 维度 | Draft Model | Medusa |
|---|---|---|
| 是否额外模型 | 是 | 否 |
| 是否额外 head | 否 | 是 |
| 是否需要训练 | 需要匹配小模型或训练 | 需要训练 Medusa heads |
| 显存开销 | draft model 权重 | head 权重 |
| 工程复杂度 | 双模型调度 | tree attention + head |
| 适用场景 | draft 模型可得 | target 模型可加 head |

# 第五部分：EAGLE 投机解码

## 25. EAGLE 的核心思想

EAGLE 是一种基于特征预测的 speculative decoding 方法。

它的核心观察是：

> **直接预测未来 token 很难，但预测靠近输出层的 hidden feature 可能更容易。**

普通 draft model 是在 token 空间预测：

```text
context -> token_{t+1}, token_{t+2}, ...
```

EAGLE 更关注 feature 空间：

```text
context feature -> future feature -> token
```

也就是说，它尝试预测 target model 高层 hidden states，再映射到 token。

---

## 26. 为什么预测 feature 可能更好？

Token 是离散变量：

```text
词表大小可能 32k / 100k / 150k
```

预测 token 等于在巨大词表上做分类。

而 hidden feature 是连续向量：

```text
hidden_state: [hidden_size]
```

连续空间中的预测可能更平滑，更容易学习。

EAGLE 认为：

- feature-level autoregression 更直接；
- 但是 feature 预测存在不确定性；
- 需要结合 token 信息来减少不确定性。

---

## 27. EAGLE 的基本流程

简化理解：

```text
target model 得到当前 hidden feature
  ↓
EAGLE draft module 根据 feature 预测未来 feature
  ↓
用 LM Head 将 feature 映射成 token logits
  ↓
生成 draft tokens
  ↓
target model 验证这些 tokens
  ↓
rejection sampler 接受或拒绝
```

它仍然遵循 speculative decoding 的框架：

```text
propose -> score -> verify -> accept
```

只是 proposer 的生成方式不同。

---

## 28. EAGLE 的优点

| 优点 | 解释 |
|---|---|
| draft 质量通常较高 | 利用 target hidden feature |
| 可获得较高 acceptance rate | 比简单 n-gram 更强 |
| target 分布仍由大模型验证 | 可以保持无损采样思想 |
| 适合通用 LLM 加速 | vLLM 中属于重要 speculation 方法 |

---

## 29. EAGLE 的缺点

| 缺点 | 解释 |
|---|---|
| 需要训练 EAGLE head / draft module | 不是任意模型开箱即用 |
| 需要访问 hidden states | 对模型 forward 和接口有要求 |
| 工程复杂度高 | 要管理 hidden states、draft KV、target KV |
| 与 batch / CUDA Graph / TP 组合复杂 | 需要框架级适配 |

---

# 第六部分：推测解码的分类与设计

## 30. 按 proposer 类型分类

### 30.1 独立 Draft Model

```text
target model: 70B
draft model: 7B / 1.5B / 0.5B
```

流程：

```text
draft model 连续生成 k 个 token
target model 一次验证 k 个 token
```

优点：

- 算法清晰；
- draft model 可单独优化；
- 容易理解。

缺点：

- 额外显存；
- 双模型调度；
- draft 与 target 匹配难；
- 多卡部署复杂。

---

### 30.2 N-gram / Prompt Lookup

不使用模型，而是在 prompt 或历史输出里查找重复片段。

例子：

```text
上下文中出现过：
"北京是中国的首都"

当前生成到：
"北京是中国"

可以猜：
"的 首都"
```

优点：

- 不需要额外模型；
- 开销极低；
- 适合重复文本、代码、文档补全。

缺点：

- 通用能力弱；
- 对开放式对话收益有限；
- acceptance rate 依赖重复模式。

---

### 30.3 Medusa / Multi-head

在 target model 上加多个 head：

```text
head1 -> token t+1
head2 -> token t+2
head3 -> token t+3
```

优点：

- 不需要独立 draft model；
- 共享 backbone；
- 适合模型提供 Medusa head 的情况。

缺点：

- 需要训练 head；
- 需要 tree attention；
- 集成复杂。

---

### 30.4 EAGLE

预测未来 hidden feature，再生成 token。

优点：

- draft 质量好；
- acceptance rate 可能更高；
- 适合通用加速。

缺点：

- 需要额外 speculator；
- 需要 hidden state；
- 工程复杂。

---

### 30.5 MTP：Multi-Token Prediction

MTP 是模型原生支持多 token 预测的一类方法。

一些模型在训练时就带有 MTP 模块，可以在推理时直接提出多个未来 token。

优点：

- target 模型原生支持；
- 不需要外部 draft model；
- 通常更适合生产部署。

缺点：

- 依赖模型本身是否提供 MTP checkpoint；
- 框架需要专门支持。

---

## 31. 按验证方式分类

### 31.1 Strict Rejection Sampling

严格按照 speculative sampling 公式接受 / 拒绝。

优点：

- 理论分布最严谨；
- 适合需要保持 target distribution 的场景。

缺点：

- 实现复杂；
- 对数值稳定性敏感。

### 31.2 Greedy Verification

如果是 greedy decoding，可以简单判断：

```text
draft_token == target_argmax_token
```

如果相等就接受，否则拒绝。

优点：

- 简单；
- 快；
- 适合 deterministic 输出。

缺点：

- 只适用于 greedy 或近似 greedy 场景。

### 31.3 Probabilistic Verification

对采样场景进行概率接受。

优点：

- 支持随机采样；
- 更符合开放式生成。

缺点：

- 复杂度更高；
- acceptance rate 受采样参数影响大。

---

# 第七部分：vLLM 中的投机采样

## 32. vLLM 为什么需要框架级支持投机解码？

投机解码不是简单加一个小模型就完事。

在 vLLM 中，它必须和以下系统机制配合：

- continuous batching；
- PagedAttention；
- KV Cache block manager；
- Scheduler；
- ModelRunner；
- CUDA Graph；
- distributed inference；
- sampling；
- request state update；
- streaming output。

核心难点是：

> 每个请求每轮可能接受不同数量的 token，而 vLLM 的 scheduler 和 KV Cache 必须正确更新每个请求的状态。

---

## 33. vLLM speculative decoding 的抽象流程

可以抽象成：

```text
Scheduler 选出一批 running requests
  ↓
Speculator / Proposer 为每个请求提出 draft tokens
  ↓
Target model 对 draft tokens 做 forward / score
  ↓
Rejection sampler 计算 accepted tokens
  ↓
Sampler 生成必要的 corrected token
  ↓
更新每个请求的 token ids、KV Cache、position、block table
  ↓
返回 accepted tokens 给上层
```

---

## 34. vLLM 中常见 speculative config

vLLM 通过 `--speculative-config` 传入投机解码配置。

示例：draft model

```bash
vllm serve <target-model> \
  --speculative-config '{
    "method": "draft_model",
    "model": "<draft-model>",
    "num_speculative_tokens": 5
  }'
```

示例：n-gram

```bash
vllm serve <target-model> \
  --speculative-config '{
    "method": "ngram",
    "num_speculative_tokens": 4,
    "prompt_lookup_min": 2,
    "prompt_lookup_max": 5
  }'
```

示例：suffix decoding

```bash
vllm serve <target-model> \
  --speculative-config '{
    "method": "suffix",
    "num_speculative_tokens": 8,
    "suffix_decoding_max_tree_depth": 24,
    "suffix_decoding_max_cached_requests": 10000,
    "suffix_decoding_max_spec_factor": 1.0,
    "suffix_decoding_min_token_prob": 0.1
  }'
```

常见字段：

| 字段 | 含义 |
|---|---|
| `method` | 投机方法，如 `draft_model`、`ngram`、`suffix`、`mtp`、`eagle3` |
| `model` | draft model、EAGLE head 或辅助模型 |
| `num_speculative_tokens` | 每轮最多提出多少个 speculative tokens |
| `draft_tensor_parallel_size` | draft model 使用的 TP 规模 |
| `parallel_drafting` | 是否启用并行 draft |
| `rejection_sample_method` | rejection sampler 方法 |
| `prompt_lookup_min/max` | n-gram 查找窗口 |
| `suffix_decoding_*` | suffix decoding 相关参数 |

注意：

```text
temperature、top_p、top_k 是 sampling 参数，不是 speculative_config 字段。
```

---

## 35. vLLM 中的投机采样和 SamplingParams 的关系

用户请求通常包含 SamplingParams：

```python
SamplingParams(
    temperature=0.7,
    top_p=0.9,
    top_k=50,
    max_tokens=128,
)
```

这部分决定 target model 的最终输出分布。

投机解码不能绕过这些参数。

正确关系是：

```text
draft/proposer 只提出候选
target scorer 按 SamplingParams 对应的分布验证
最终输出必须服从 target model + SamplingParams
```

所以：

- speculative_config 控制“怎么猜”；
- SamplingParams 控制“最终怎么采”。

---

## 36. vLLM 中的核心组件

不同 vLLM 版本代码目录可能有变化，但从概念上看，投机解码核心组件包括：

| 组件 | 作用 |
|---|---|
| `SpeculativeConfig` | 保存投机解码配置 |
| `Speculator / Proposer` | 生成 draft tokens |
| `Target Model / Scorer` | 对 draft tokens 计算 logits |
| `RejectionSampler` | 判断接受 / 拒绝 |
| `Sampler` | 从 target logits 采样 token |
| `ModelRunner` | 构建模型输入并执行 forward |
| `Scheduler` | 决定哪些请求进入本轮执行 |
| `KV Cache Manager` | 维护 accepted tokens 对应的 KV |
| `Request / Sequence State` | 更新每个请求已生成 token 状态 |

---

## 37. vLLM 投机解码的关键状态更新

普通 decode 每轮只更新一个 token：

```text
request.output_token_ids.append(next_token)
num_computed_tokens += 1
KV Cache 写入 1 个位置
```

投机解码每轮可能更新多个 token：

```text
accepted_tokens = [t1, t2, t3]
request.output_token_ids.extend(accepted_tokens)
num_computed_tokens += len(accepted_tokens)
KV Cache 写入多个位置
```

如果第 4 个 token 被拒绝，还要：

```text
从 target 分布采样 corrected token
append corrected token
```

这意味着 vLLM 必须正确处理：

- 每个请求接受数量不同；
- 每个请求当前位置不同；
- KV Cache 位置不同；
- block table 可能扩展；
- streaming 输出需要返回多个 token；
- scheduler 下一轮要接着正确位置执行。

---

## 38. vLLM 投机解码与 KV Cache

投机解码会带来一个重要问题：

> 被拒绝的 draft token 的 KV Cache 怎么办？

通常理解：

- target model 验证 draft tokens 时，需要计算这些 token 对应的 hidden states 和 KV；
- 如果 token 被接受，它们的 KV 可以保留；
- 如果 token 被拒绝，拒绝位置之后的 draft KV 不能进入正式上下文；
- 需要丢弃或覆盖无效 KV。

所以工程实现中要谨慎维护：

```text
accepted prefix 的 KV
rejected suffix 的 KV
corrected token 的 KV
```

在 PagedAttention 里，还要保证：

```text
block_table
slot_mapping
positions
query_start_loc
```

与最终接受的 token 序列一致。

---

## 39. vLLM 投机解码与 Continuous Batching

Continuous batching 的特点是：

```text
每轮调度中混合多个请求
不同请求处于不同阶段
不同请求长度不同
```

投机解码又引入：

```text
不同请求每轮接受 token 数不同
```

这会让调度更复杂。

例如：

```text
request A 接受 5 个 token
request B 接受 1 个 token
request C 接受 0 个 draft token，但补采 1 个 token
```

下一轮 scheduler 需要知道：

```text
A 已前进 5 或 6 个位置
B 前进 1 或 2 个位置
C 前进 1 个位置
```

这也是 vLLM 需要专门 spec_decode 模块的原因。

---

## 40. vLLM 投机解码与 CUDA Graph

CUDA Graph 喜欢固定 shape。

投机解码会带来动态性：

- 每个请求 speculative tokens 数量可能不同；
- accepted tokens 数量不同；
- tree attention shape 可能不同；
- batch expansion 可能不同。

因此它和 CUDA Graph 的组合更难。

工程上通常需要：

- 固定 `num_speculative_tokens`；
- padding 到固定 shape；
- 限制支持的 attention backend；
- 对不同 batch size / seq len capture 多个 graph；
- 不满足条件时 fallback 到 eager。

---

# 第八部分：投机解码核心组件与目录结构

## 41. 目录结构如何理解？

在 vLLM 中，投机解码相关代码可能分布在：

```text
vllm/
  config.py
  sampling_params.py
  v1/
    sample/
      sampler.py
      ...
    spec_decode/
      rejection_sampler.py
      speculator.py
      utils.py
      eagle/
      mtp/
      ...
```

不同版本中路径可能变化，但通常有这些逻辑模块：

```text
配置层：SpeculativeConfig
提案层：Speculator / Proposer
验证层：Target model forward
采样层：RejectionSampler / Sampler
执行层：ModelRunner / Worker
调度层：Scheduler / Engine
```

---

## 42. Proposer / Speculator

Proposer 的职责：

```text
输入当前请求上下文
输出若干 draft token
```

它可能来自：

- draft model；
- n-gram matcher；
- suffix tree；
- EAGLE；
- Medusa；
- MTP；
- custom proposer。

统一接口大致是：

```text
propose(request_states) -> draft_token_ids
```

---

## 43. Target Scorer

Target scorer 其实就是原始大模型 forward。

职责：

```text
对 context + draft tokens 计算 logits
```

输出：

```text
target_logits: [num_positions, vocab_size]
```

然后 rejection sampler 用这些 logits 判断 draft tokens 是否接受。

---

## 44. RejectionSampler

RejectionSampler 的职责：

```text
比较 draft probabilities 和 target probabilities
决定接受多少个 draft tokens
必要时从 corrected distribution 采样新 token
```

它是保证“投机但不改变 target 分布”的核心。

---

## 45. Output Processor

投机解码后，输出处理要完成：

- 把 accepted tokens 加入 request；
- 更新 finish reason；
- 检查 EOS；
- 检查 stop strings；
- 处理 logprobs；
- 返回 streaming token；
- 更新请求状态。

# 第九部分：推理主流程总览

## 46. 普通 decode 主流程

```text
用户请求
  ↓
API Server / LLM.generate
  ↓
Engine.add_request
  ↓
Scheduler 选择 running requests
  ↓
ModelRunner 构造 input_ids / positions / block_tables
  ↓
模型 forward
  ↓
LM Head 得到 logits
  ↓
Sampler 采样 1 个 token
  ↓
更新 KV Cache 和 request 状态
  ↓
返回 token
  ↓
下一轮 decode
```

---

## 47. 投机 decode 主流程

```text
用户请求
  ↓
Engine.add_request
  ↓
Scheduler 选择 running requests
  ↓
Speculator 为每个请求提出 k 个 draft tokens
  ↓
ModelRunner 构造 target verification input
  ↓
Target model 一次 forward 计算多个位置 logits
  ↓
RejectionSampler 判断 accepted tokens
  ↓
必要时从 target logits 采样 corrected token
  ↓
更新 request token ids
  ↓
更新 KV Cache / block table / positions
  ↓
返回多个 token
  ↓
下一轮继续
```

区别在于：

```text
普通 decode：每轮 target 产出 1 个 token
投机 decode：每轮 target 可能产出多个 token
```

---

## 48. 用例子理解投机解码

当前上下文：

```text
I love
```

draft model 猜：

```text
New York City very much
```

即：

```text
draft = [New, York, City, very, much]
```

target model 一次验证：

```text
P(New | I love)
P(York | I love New)
P(City | I love New York)
P(very | I love New York City)
P(much | I love New York City very)
```

如果 target 接受前三个：

```text
accepted = [New, York, City]
```

第四个 `very` 被拒绝，并由 target 重新采样得到：

```text
.
```

则本轮最终输出：

```text
New York City .
```

一次大模型 forward 推进 4 个 token。

# 第十部分：面试问答

## 49. 面试题 1：为什么 LLM decode 比 prefill 更容易成为瓶颈？

答：

Prefill 一次处理整个 prompt，矩阵乘法规模大，GPU 利用率高，通常更偏 compute-bound。Decode 每步只生成一个 token，单次 GEMM 小，但每步仍要读取大量模型权重和历史 KV Cache，因此容易 memory-bound。同时 decode 存在自回归依赖，必须等待上一步 token 出来才能生成下一步，串行性强，所以 TPOT / ITL 往往成为在线推理性能瓶颈。

---

## 50. 面试题 2：采样中的 temperature 是什么？

答：

Temperature 是对 logits 做缩放的参数。公式是 `softmax(logits / T)`。当 T 小于 1 时，分布更尖锐，模型更保守；当 T 大于 1 时，分布更平滑，输出更随机；当 temperature 等于 0 时，工程上通常使用 greedy decoding，即选择概率最大的 token。

---

## 51. 面试题 3：Top-k 和 Top-p 有什么区别？

答：

Top-k 固定保留概率最高的 k 个 token，然后在这些 token 中重新归一化采样。Top-p 不固定 token 数量，而是按概率从高到低排序，保留累计概率达到 p 的最小集合。Top-k 控制候选数量，Top-p 控制候选概率质量，因此 Top-p 更自适应。

---

## 52. 面试题 4：投机解码的核心思想是什么？

答：

投机解码用一个便宜的 proposer，例如小 draft model、EAGLE、Medusa head、MTP 或 n-gram，先提出多个未来 token，然后用 target model 一次 forward 并行验证这些 token。被接受的 token 直接加入输出，被拒绝的位置从 target 分布重新采样。这样如果每轮能接受多个 token，就可以减少 target model 的 decode forward 次数，降低 inter-token latency。

---

## 53. 面试题 5：投机解码为什么可以无损？

答：

因为 draft model 只负责提案，不直接决定最终输出。最终 token 是否接受由 target model 的概率分布和 rejection sampling 决定。如果 rejection sampling 正确实现，最终采样分布理论上等价于 target model 自己逐 token 采样。实际工程中可能存在浮点误差、batch 数值差异、非确定性 kernel 等细微差异。

---

## 54. 面试题 6：投机解码的收益取决于什么？

答：

主要取决于 acceptance rate、draft/proposer 成本、target model 大小、batch size、QPS、采样参数和任务类型。如果 draft 很便宜且 acceptance rate 高，一次 target forward 可以推进多个 token，收益明显。如果 draft 太慢或 acceptance rate 低，投机解码可能反而变慢。高 QPS 下 continuous batching 已经让 GPU 很满时，收益也可能下降。

---

## 55. 面试题 7：Medusa 和普通 draft model 有什么区别？

答：

普通 draft model 是一个独立小模型，用它生成候选 token。Medusa 不使用独立小模型，而是在 target model 主干上增加多个 decoding heads，用这些 head 预测未来多个 token，并通过 tree attention 并行验证候选路径。Medusa 减少了独立 draft model 的维护成本，但需要训练额外 heads，并要求框架支持 tree attention。

---

## 56. 面试题 8：EAGLE 的核心思想是什么？

答：

EAGLE 不是直接在 token 空间预测未来 token，而是利用 target model 的高层 hidden feature，预测未来 feature，再通过 LM Head 映射到 token。它认为 feature-level autoregression 比 token-level 预测更容易，同时结合 token 序列减少 feature 预测的不确定性。EAGLE 通常可以提供较高质量的 draft，从而提高 acceptance rate。

---

## 57. 面试题 9：投机解码和 KV Cache 有什么关系？

答：

投机解码验证多个 draft token 时，会产生这些 token 的 KV。被接受的 token 的 KV 可以保留，拒绝位置之后的 draft KV 必须丢弃或覆盖，否则上下文就会污染。vLLM 使用 PagedAttention 管理 KV Cache，因此还要保证 block table、slot mapping、positions、num_computed_tokens 等状态与最终 accepted tokens 完全一致。

---

## 58. 面试题 10：为什么投机解码和 continuous batching 集成困难？

答：

Continuous batching 中不同请求长度不同、状态不同。投机解码又导致每个请求每轮接受 token 数不同，有的请求接受 5 个，有的只接受 1 个，有的拒绝后补采一个 token。Scheduler、KV Cache manager、ModelRunner 和 output processor 都要正确处理这种不规则前进，否则会出现位置错乱、KV 错乱或输出错误。

---

## 59. 面试题 11：vLLM 中 speculative_config 和 SamplingParams 的区别是什么？

答：

`speculative_config` 控制投机解码怎么进行，例如使用 draft model、EAGLE、MTP、ngram，提出多少个 speculative tokens，draft model 的 TP size 等。SamplingParams 控制最终输出怎么采样，例如 temperature、top_p、top_k、max_tokens、penalty 等。投机解码不能替代 SamplingParams，最终输出仍要服从 target model 和 SamplingParams 定义的分布。

---

## 60. 面试题 12：什么时候不建议开投机解码？

答：

如果请求很短、QPS 很高、batch 已经很大、GPU 已经 compute-bound、draft model 成本高、acceptance rate 低、采样很随机，或者 speculative decoding 与当前模型 / 并行 / attention backend 不兼容，就不建议盲目开启。投机解码一定要通过 benchmark 验证，而不是默认开启。

---

# 第十一部分：本节课总结

本节课的主线是：

```text
Decoder-only LLM 自回归生成
        ↓
Decode 每步只能生成一个 token
        ↓
GPU 在 decode 阶段容易 memory-bound / launch-bound
        ↓
采样决定每一步如何从 logits 选 token
        ↓
普通 decode 需要一次 forward 产出一个 token
        ↓
投机解码用 proposer 先猜多个 token
        ↓
target model 一次 forward 并行验证多个 token
        ↓
rejection sampler 保证输出分布不偏离 target
        ↓
accepted tokens 越多，target forward 次数越少
        ↓
vLLM 将 speculator、sampler、KV Cache、Scheduler、ModelRunner 串起来
```

最重要的理解是：

> **投机解码不是让小模型替代大模型，而是让小模型或轻量 proposer 帮大模型“提前猜答案”，再由大模型验证。它的目标是在保持 target model 输出分布的前提下，减少 decode 阶段大模型 forward 的次数。**
