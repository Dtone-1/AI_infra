# vLLM PD 分离部署与 KV 传输技术学习笔记

> 课时 19：vLLM PD 分离部署与 KV 传输技术  
> 课程关键词：Prefill-Decode Disaggregation、PD 分离、KV Cache Transfer、KVConnector、KVTransferConfig、KV Offloading Connector、P2pNcclConnector、NixlConnector、LMCache、TTFT、ITL、尾延迟、跨实例 KV Cache 注入

---

## 0. 本节课核心目标

本节课讲的是 vLLM 推理服务中一个非常重要的高级部署形态：

```text
PD 分离部署 = Prefill 和 Decode 分别部署在不同 vLLM 实例 / GPU / 节点上
```

在普通 vLLM 服务中，一个请求的 Prefill 和 Decode 通常在同一组 GPU 上完成：

```text
用户请求
  ↓
Prefill：处理 prompt，生成 KV Cache
  ↓
Decode：基于 KV Cache 逐 token 生成
```

而 PD 分离会把这两个阶段拆开：

```text
用户请求
  ↓
Prefill Instance：只负责 prompt 计算，生成 KV Cache
  ↓
KV Transfer：把 KV Cache 从 P 端传到 D 端
  ↓
Decode Instance：加载 / 注入 KV Cache，逐 token 生成输出
```

本节课的核心问题是：

> **为什么要把 Prefill 和 Decode 拆开？拆开后 KV Cache 怎么传？vLLM 的 KV Connector、KV Offloading Connector、P2pNcclConnector 分别负责什么？**

---

## 1. 为什么需要 PD 分离？

### 1.1 Prefill 和 Decode 的瓶颈不同

LLM 推理分为两个阶段。

#### Prefill 阶段

Prefill 处理完整 prompt：

```text
prompt tokens = [x1, x2, ..., xn]
```

一次 forward 处理所有 prompt token，计算每层的 K/V，并写入 KV Cache。

特点：

| 项目 | Prefill |
|---|---|
| 输入 token 数 | 多 |
| GEMM 规模 | 大 |
| Attention 计算 | 大 |
| GPU 利用率 | 通常高 |
| 瓶颈类型 | 更偏 compute-bound |
| 主要影响 | TTFT，也就是首 token 延迟 |

---

#### Decode 阶段

Decode 每一步只生成一个新 token：

```text
step t:
  输入上一步生成的新 token
  读取历史 KV Cache
  计算 logits
  采样 next token
```

特点：

| 项目 | Decode |
|---|---|
| 每步输入 token 数 | 每请求通常 1 个 |
| GEMM 规模 | 小 |
| KV Cache 访问 | 频繁 |
| GPU 利用率 | 小 batch 时可能低 |
| 瓶颈类型 | 更偏 memory-bound / launch-bound |
| 主要影响 | ITL / TPOT，也就是 token 间延迟 |

所以 Prefill 和 Decode 对硬件、并行策略、batch 策略的需求不同。

---

### 1.2 Prefill 会干扰 Decode

在线服务中，一个 GPU 上可能同时处理：

```text
已有请求的 decode
新请求的 prefill
```

如果一个很长 prompt 的 prefill 被插入进来，它可能会占用 GPU 很长时间，导致正在 decode 的请求 token 间隔突然变大：

```text
decode token 1
decode token 2
  ↓ 插入长 prefill
很久之后
decode token 3
```

用户看到的现象就是：

```text
前面输出还很顺，突然卡住一段时间
```

这会造成：

- ITL 抖动；
- P99 / P95 尾延迟升高；
- 流式输出体验变差；
- decode 请求被长 prefill 阻塞。

PD 分离的一个重要目的就是：

> **让 Prefill 和 Decode 互不干扰，分别用不同资源池优化 TTFT 和 ITL。**

---

### 1.3 PD 分离不等于吞吐一定提升

PD 分离主要改善：

- TTFT 和 ITL 可以分别调优；
- Decode 尾延迟更稳定；
- 大 prompt 不容易打断 decode；
- 不同阶段可以使用不同并行策略；
- 可以独立扩缩容 P / D 节点。

但它也引入新成本：

```text
KV Cache 必须从 P 端传到 D 端
```

如果 KV 传输很慢，PD 分离可能反而增加首 token 延迟。

所以 PD 分离的关键不只是“拆开部署”，而是：

> **能否低延迟、高带宽、正确地传输 KV Cache。**

---

## 2. PD 分离部署概述

### 2.1 普通部署

普通部署：

```text
vLLM Instance
  ├── Prefill
  ├── KV Cache
  └── Decode
```

请求从头到尾在同一个实例中完成。

优点：

- 架构简单；
- KV Cache 不需要跨实例传输；
- 调试容易；
- 适合中小规模场景。

缺点：

- Prefill 和 Decode 互相干扰；
- 两阶段无法独立扩缩容；
- 很难分别优化 TTFT 和 ITL；
- 长 prompt 可能导致 decode 尾延迟升高。

---

### 2.2 PD 分离部署

PD 分离：

```text
Prefill Instance / Prefill Pool
  ├── 接收 prompt
  ├── 执行 prefill
  └── 生成 KV Cache

          KV Transfer

Decode Instance / Decode Pool
  ├── 接收 KV Cache
  ├── 注入本地 KV Cache blocks
  └── 执行 decode
```

系统中通常还需要一个 proxy / router：

```text
Client
  ↓
Proxy
  ├── 把 prompt 发到 Prefill Instance
  ├── 通知 Decode Instance 准备接收 KV
  ├── 协调 KV 传输
  └── 把 decode 流式结果返回给用户
```

---

### 2.3 P 端和 D 端分别做什么？

#### Prefill Instance

P 端负责：

1. 接收 prompt；
2. tokenizer 后得到 input_ids；
3. 执行 prefill forward；
4. 每层 attention 生成 K/V；
5. 将 KV 写入本地 KV Cache；
6. 通过 connector 暴露 / 发送 KV Cache；
7. 将必要元数据传给 D 端。

---

#### Decode Instance

D 端负责：

1. 接收请求元数据；
2. 为即将 decode 的请求分配本地 KV Cache blocks；
3. 通过 connector 获取 P 端 KV Cache；
4. 将远端 KV 注入本地 KV Cache blocks；
5. 从正确位置开始 decode；
6. 采样生成 token；
7. 流式返回输出。

---

## 3. PD 分离的设计方案

### 3.1 逻辑架构

可以抽象为：

```text
Client
  ↓
PD Proxy / Router
  ↓
Prefill vLLM Instance
  ↓
KV Connector
  ↓
Decode vLLM Instance
  ↓
Streaming Output
```

核心模块：

| 模块 | 作用 |
|---|---|
| Proxy / Router | 选择 P / D 实例，转发请求，协调 KV 传输 |
| Prefill Instance | 执行 prompt prefill，产生 KV Cache |
| Decode Instance | 消费 KV Cache，执行自回归生成 |
| KV Connector | 在 P / D 实例之间传输 KV Cache |
| LookupBuffer | 临时保存 KV，支持按请求查找和消费 |
| Scheduler Connector | 与 Scheduler 同进程，安排 KV 传输操作 |
| Worker Connector | 与 Worker 同进程，实际执行 KV store / load |

---

### 3.2 vLLM 中的 KV Transfer 抽象

vLLM 的 PD 分离相关实现集中在：

```text
vllm/distributed/kv_transfer
```

核心抽象可以理解为：

```text
Connector:
  负责让 KV consumer 从 KV producer 获取 KV Cache

LookupBuffer:
  负责临时保存 KV Cache，并支持按条件取出

Scheduler Connector:
  负责调度 KV transfer 操作

Worker Connector:
  负责执行真实的 KV store/load 操作
```

---

### 3.3 KVTransferConfig

vLLM 通过 `KVTransferConfig` 配置 KV 传输。

常见字段：

| 字段 | 含义 |
|---|---|
| `kv_connector` | 使用哪个 KV connector，例如 `P2pNcclConnector`、`NixlConnector`、`LMCacheConnectorV1` |
| `kv_role` | 当前实例角色：`kv_producer`、`kv_consumer`、`kv_both` |
| `kv_rank` | 当前实例在 KV transfer group 中的 rank，典型是 P=0、D=1 |
| `kv_parallel_size` | KV transfer 并行实例数 |
| `kv_ip` | connector 建连 IP |
| `kv_port` | connector 建连端口 |
| `kv_buffer_device` | KV buffer 放在 `cuda`、`cpu` 或 `xpu` |
| `kv_buffer_size` | buffer 大小 |
| `kv_load_failure_policy` | KV 加载失败时是 `fail` 还是 `recompute` |
| `kv_connector_extra_config` | connector 私有配置 |

典型角色：

```text
Prefill instance:
  kv_role = kv_producer

Decode instance:
  kv_role = kv_consumer

某些缓存复用 / 双向传输场景:
  kv_role = kv_both
```

---

### 3.4 一个最小 P/D 配置示意

Prefill 端：

```bash
CUDA_VISIBLE_DEVICES=0 \
vllm serve Qwen/Qwen3-0.6B \
  --port 8100 \
  --kv-transfer-config '{
    "kv_connector": "P2pNcclConnector",
    "kv_role": "kv_producer",
    "kv_rank": 0,
    "kv_parallel_size": 2,
    "kv_connector_extra_config": {
      "send_type": "PUT_ASYNC",
      "http_port": 8100
    }
  }'
```

Decode 端：

```bash
CUDA_VISIBLE_DEVICES=1 \
vllm serve Qwen/Qwen3-0.6B \
  --port 8200 \
  --kv-transfer-config '{
    "kv_connector": "P2pNcclConnector",
    "kv_role": "kv_consumer",
    "kv_rank": 1,
    "kv_parallel_size": 2,
    "kv_connector_extra_config": {
      "send_type": "PUT_ASYNC",
      "http_port": 8200
    }
  }'
```

然后还需要一个 proxy，把用户请求转给 P / D 并协调 KV 传输。

注意：实际参数名和 connector 支持情况会随 vLLM 版本变化，真实部署必须以当前版本官方文档和 examples 为准。

## 4. PD 分离端到端流程解析

下面从一个用户请求出发，理顺 PD 分离完整流程。

---

### 4.1 Step 1：用户请求进入 Proxy

用户发起请求：

```text
prompt = "请解释 vLLM 的 PagedAttention"
max_tokens = 256
temperature = 0.7
```

Proxy 需要做两件事：

1. 选择一个 Prefill Instance；
2. 选择一个 Decode Instance。

选择依据可能包括：

- P 端当前负载；
- D 端当前负载；
- GPU 空闲程度；
- KV cache hit rate；
- 网络距离；
- 请求长度；
- 是否有 prefix cache；
- 多租户策略。

---

### 4.2 Step 2：Proxy 把 prompt 发给 P 端

P 端执行：

```text
tokenizer.encode(prompt)
  ↓
input_ids
  ↓
prefill forward
```

每层 Transformer 中：

```text
Q = X Wq
K = X Wk
V = X Wv
```

K/V 会写入 P 端本地 KV Cache。

---

### 4.3 Step 3：P 端生成 KV Cache

对于每一层 attention，P 端会生成：

```text
K_cache[layer]
V_cache[layer]
```

它们的形状通常与以下因素有关：

```text
num_layers
num_tokens
num_kv_heads
head_dim
dtype
```

如果是 TP 并行，每个 rank 只持有自己 shard 的 K/V。

如果是 PagedAttention，KV Cache 不是一整块连续内存，而是分成 block：

```text
logical token positions
  ↓ block table
physical KV blocks
```

所以传输时不仅要传 tensor 数据，还要传必要元数据。

---

### 4.4 Step 4：P 端通过 Connector 暴露或发送 KV

根据 connector 和传输模式不同，P 端可能：

#### PUT

```text
P 主动把 KV 发给 D
```

#### PUT_ASYNC

```text
P 用独立线程 / stream 异步把 KV 发给 D
主流程尽量不阻塞
```

#### GET

```text
P 把 KV 放入 buffer
D 分配好本地空间后主动从 P 拉取 KV
```

三种方式的本质区别是：

| 模式 | 谁主动 | 是否阻塞 P 主流程 | 特点 |
|---|---|---|---|
| PUT | P 主动发送 | 可能阻塞 | 实现直观，但影响 prefill 主流程 |
| PUT_ASYNC | P 异步发送 | 尽量不阻塞 | 通常更适合低延迟 |
| GET | D 主动拉取 | P 保存后等待 D 拉 | D 能在分配好本地 KV 后再拉 |

---

### 4.5 Step 5：D 端分配本地 KV Cache blocks

D 端不能直接“拿过来就用”，因为 D 端也有自己的 KV Cache 管理器。

D 端需要：

```text
为该请求分配本地 physical KV blocks
```

并建立：

```text
request token positions
  ↓
block table
  ↓
local physical KV blocks
```

也就是说，远端 KV 必须被放到 D 端本地分配好的 slot 里。

---

### 4.6 Step 6：D 端加载 / 注入 KV Cache

D 端 connector 收到 KV 后，将其写入本地 KV Cache：

```text
remote KV tensors
  ↓
temporary GPU / CPU buffer
  ↓
copy / reshape / permute
  ↓
local KV Cache blocks
```

这里要保证：

- layer 对齐；
- token position 对齐；
- KV head 对齐；
- dtype 对齐；
- TP rank shard 对齐；
- block table 对齐；
- slot mapping 对齐；
- request id 对齐。

如果这些有任何一个错，decode 结果就会错误。

---

### 4.7 Step 7：D 端开始 Decode

KV 注入完成后，D 端相当于已经拥有完整 prompt 的 KV Cache。

此时它可以从 prompt 末尾继续生成：

```text
input = last prompt token 或特殊 decode input
  ↓
读取本地 KV Cache
  ↓
decode step
  ↓
sample next token
  ↓
streaming output
```

从用户角度看：

```text
Prefill 和 KV Transfer 在首 token 前完成；
之后 decode 稳定输出。
```

---

### 4.8 Step 8：流式返回

D 端生成 token 后：

```text
next_token_id
  ↓
detokenizer
  ↓
text delta
  ↓
Proxy / Client
```

用户看到流式输出。

---

## 5. KV Cache 传输到底传什么？

### 5.1 KV Cache 的组成

Decoder-only Transformer 每层 attention 会保存：

```text
K: key cache
V: value cache
```

如果有：

```text
num_layers = L
num_tokens = S
num_kv_heads = H_kv
head_dim = D
dtype_size = bytes
```

KV 大小大致是：

```text
KV bytes = L × S × H_kv × D × 2 × dtype_size
```

其中 `2` 表示 K 和 V。

---

### 5.2 为什么 KV 传输可能成为瓶颈？

如果 prompt 很长：

```text
S = 8192
```

或者模型层数 / hidden size 很大，KV Cache 会非常大。

PD 分离后，首 token 之前必须完成：

```text
Prefill compute
+ KV transfer
+ D 端 KV injection
```

因此 TTFT 可能变成：

```text
TTFT ≈ queueing + prefill_compute + kv_transfer + kv_injection + first_decode
```

如果 KV transfer 太慢，PD 分离的优势会被抵消。

---

### 5.3 KV 传输不仅是 memcpy

看起来 KV transfer 是：

```text
P GPU -> D GPU
```

但工程上要处理：

- 跨进程；
- 跨 GPU；
- 跨机器；
- 网络传输；
- RDMA / TCP / NCCL；
- 元数据协商；
- buffer 管理；
- 异步传输；
- 错误恢复；
- backpressure；
- KV block layout；
- dtype / shape；
- HND / NHD layout 转换；
- 和主模型计算 stream 避免互相阻塞。

---

## 6. KV Offloading Connector

### 6.1 什么是 KV Offloading？

KV Offloading 指的是：

```text
把 KV Cache 从 GPU 显存临时转移到 GPU 外的存储介质
```

常见介质：

- CPU 内存；
- 本地磁盘；
- 远端 KV store；
- 分布式缓存系统；
- LMCache server；
- NIXL 远程节点。

它解决的问题是：

> **GPU 显存有限，但长上下文、多轮对话、多请求复用需要保存大量 KV Cache。**

---

### 6.2 KV Offloading 和 PD KV Transfer 的区别

| 项目 | PD KV Transfer | KV Offloading |
|---|---|---|
| 主要目的 | P 端 KV 传给 D 端 | GPU 显存不足时把 KV 放到外部存储 |
| 典型方向 | Prefill GPU -> Decode GPU | GPU -> CPU / Disk / Remote Store |
| 使用场景 | PD 分离部署 | 长上下文、多轮复用、KV 共享、显存扩展 |
| 关键指标 | 传输延迟、TTFT | 命中率、换入换出延迟、显存节省 |
| 组件 | P2pNcclConnector、NixlConnector 等 | LMCacheConnector、LMCacheMPConnector 等 |

二者可以结合：

```text
PD 分离 + KV Offloading + KV Sharing
```

例如：

```text
P 端产生 KV
  ↓
存入 LMCache / 远端 KV store
  ↓
多个 D 端按需读取
```

---

### 6.3 LMCache 这类 connector 的作用

LMCache 类 connector 通常用于：

- CPU offload；
- Disk offload；
- 远端 KV cache storage；
- 多 vLLM 实例之间 KV cache sharing；
- PD 分离中的 KV 中转；
- prefix cache 跨实例复用。

典型结构：

```text
vLLM Instance 1
  ↓ store KV
LMCache Server / Storage
  ↓ retrieve KV
vLLM Instance 2
```

这类方案更像“KV 存储系统”，而不仅仅是点对点传输。

---

### 6.4 KV Offloading 的代价

KV Offloading 不是免费。

代价：

- CPU / Disk / Remote Store 带宽低于 HBM；
- 换入换出增加 latency；
- buffer 管理复杂；
- cache miss 可能导致 recompute；
- 多实例一致性复杂；
- 网络传输可能成为瓶颈。

适合场景：

- 长上下文；
- 多轮对话；
- prefix 大量复用；
- GPU 显存不足；
- KV reuse 命中率高；
- 对 TTFT / ITL 可接受一定换取。

不适合场景：

- 输出非常短；
- KV 几乎不复用；
- 网络慢；
- 对首 token 延迟极端敏感；
- GPU 显存足够且 batch 不大。

---

## 7. P2pNcclConnector 组件

### 7.1 P2pNcclConnector 解决什么问题？

P2pNcclConnector 是 vLLM 中用于 **P/D 实例之间点对点传输 KV Cache** 的一种 connector。

核心目标：

```text
用 NCCL 做 GPU 之间 KV tensor 传输
用 ZMQ / HTTP 等控制通道做元数据协商
```

它适合：

- 单机多 GPU；
- 多进程 P/D 实例；
- P 和 D 之间需要直接传输 KV；
- 希望减少 CPU staging；
- 希望利用 GPU-GPU 高带宽通信。

---

### 7.2 P2pNcclConnector 的基本结构

可以抽象为：

```text
P2pNcclConnector
  ├── 控制面：ZMQ / HTTP / metadata exchange
  ├── 数据面：NCCL point-to-point transfer
  ├── P2pNcclEngine
  ├── Send / Recv buffer
  ├── KV metadata
  └── transfer mode: PUT / PUT_ASYNC / GET
```

控制面负责：

- 建立连接；
- 交换地址；
- 交换 tensor shape；
- 交换 dtype；
- 交换 request id；
- 协商 NCCL group；
- 传递 KV metadata。

数据面负责：

- 真正传输 K/V tensor；
- GPU-GPU 数据搬运；
- 尽量避免主流程阻塞。

---

### 7.3 为什么需要 ZMQ + NCCL？

NCCL 擅长做 GPU 间数据传输，但它不负责高层业务控制。

P/D 实例之间需要先知道：

```text
我要传哪个 request 的 KV？
有多少层？
每层 shape 是多少？
dtype 是什么？
对端地址是什么？
是否已有 NCCL group？
```

这些属于控制信息，通常通过 ZMQ / HTTP 等机制完成。

真正的大 tensor 数据则交给 NCCL：

```text
K/V tensor data
  ↓
NCCL send/recv
```

所以可以理解为：

```text
ZMQ：发“说明书”
NCCL：搬“真正的货”
```

---

### 7.4 PUT、GET、PUT_ASYNC

P2pNcclConnector 支持不同 KV 传输模式。

#### PUT

P 端主动发送：

```text
P finishes prefill
  ↓
P sends KV to D synchronously
  ↓
D receives and injects
```

优点：

- 逻辑简单；
- P 主动推送。

缺点：

- 可能阻塞 P 端主流程；
- 如果 D 没准备好，可能等待。

---

#### PUT_ASYNC

P 端异步发送：

```text
P finishes prefill
  ↓
P hands KV transfer to dedicated thread / async path
  ↓
P main process continues
  ↓
D receives KV
```

优点：

- 不阻塞 P 主流程；
- 对线上服务更友好；
- 更容易隐藏传输开销。

缺点：

- 实现复杂；
- 需要处理线程 / stream / buffer 生命周期；
- 需要保证 KV 不被提前释放。

---

#### GET

D 端主动拉取：

```text
P finishes prefill
  ↓
P saves KV to buffer
  ↓
D allocates local KV space
  ↓
D pulls KV from P
```

优点：

- D 端在准备好本地 KV block 后再拉；
- 生命周期更明确。

缺点：

- D 端等待 P 完成后才能拉；
- 拉取路径可能增加关键路径延迟。

---

### 7.5 P2pNcclConnector 的端到端流程

以 PUT_ASYNC 为例：

```text
1. P / D 启动，各自创建 P2pNcclEngine
2. 控制面监听端口
3. 请求到达 Proxy
4. Proxy 将 prompt 发到 P
5. P 执行 prefill，产生 KV
6. P 将 KV metadata 发给 D
7. P / D 首次建立 NCCL group
8. P 异步把 KV tensor 发给 D
9. D 收到 KV tensor 后写入本地 KV blocks
10. D scheduler 将请求放入 decode 队列
11. D 开始 decode 并流式返回
```

---

## 8. PD 分离下的 Scheduler 与 KV Connector 协作

### 8.1 普通 vLLM Scheduler

普通场景下 Scheduler 主要决定：

```text
哪些 waiting 请求进入 prefill？
哪些 running 请求进入 decode？
KV Cache block 是否足够？
每轮 max_num_batched_tokens 是否满足？
```

---

### 8.2 PD 分离后 Scheduler 多了什么状态？

D 端 Scheduler 需要处理“KV 是否已经就绪”。

请求可能有新状态：

```text
WAITING_FOR_KV
```

也就是说：

```text
请求已经提交给 D
但 prompt KV 还没从 P 端传过来
所以不能开始 decode
```

只有当 connector 完成 KV load / injection 后，D 端才能把请求放入 running decode 队列。

---

### 8.3 Scheduler Connector 和 Worker Connector

vLLM 文档中提到两个层次：

```text
Scheduler Connector:
  和 Scheduler 在同一进程，负责安排 KV transfer ops

Worker Connector:
  和 Worker 在同一进程，负责执行实际 KV transfer ops
```

可以理解为：

```text
Scheduler Connector：决定什么时候传、传哪个请求
Worker Connector：真正执行 store/load
```

这样符合 vLLM 的架构：

```text
Scheduler 不直接碰 GPU tensor
Worker / ModelRunner 更接近真实 GPU 执行
```

---

## 9. PD 分离与 KV Cache Block 的关系

### 9.1 为什么不能只传连续 KV？

vLLM 使用 PagedAttention，KV Cache 被拆成 block：

```text
block_size = 16 / 32 / ...
```

每个请求的逻辑 token 序列通过 block table 映射到物理 blocks：

```text
logical block id -> physical block id
```

P 端和 D 端的物理 block id 不一样。

所以不能简单说：

```text
把 P 端 physical block id = 10 的数据放到 D 端 physical block id = 10
```

正确逻辑是：

```text
P 端根据 request/token/layer 找到 KV 数据
  ↓
传输 KV 数据和必要 metadata
  ↓
D 端根据自己的 block table 写入本地 physical blocks
```

---

### 9.2 需要保证哪些映射正确？

D 端注入 KV 时要保证：

```text
token position -> D local slot
layer id -> correct KV layer
K/V -> correct tensor
head shard -> correct TP rank
dtype/layout -> correct backend expectation
```

常见元数据：

- request id；
- token count；
- block ids；
- slot mapping；
- layer id；
- kv head id；
- dtype；
- tensor shape；
- device；
- optional hash / prefix information。

---

## 10. PD 分离与性能指标

### 10.1 TTFT

PD 分离后：

```text
TTFT = 排队 + P prefill + KV transfer + D KV injection + first decode
```

可能降低 TTFT 的情况：

- P 池资源充足；
- P 使用更适合 prefill 的并行策略；
- prefix cache / KV sharing 命中；
- D 不被 prefill 干扰；
- KV transfer 很快。

可能升高 TTFT 的情况：

- KV transfer 慢；
- P/D 之间网络差；
- D 端 KV injection 慢；
- Proxy 调度慢；
- P 和 D 资源不匹配。

---

### 10.2 ITL / TPOT

PD 分离通常更有利于 ITL，因为 Decode Instance 不再被 Prefill 抢占。

普通部署：

```text
decode step
decode step
long prefill inserted
decode step delayed
```

PD 分离：

```text
D pool 专注 decode
P pool 专注 prefill
```

所以 decode token 间隔更稳定。

---

### 10.3 吞吐

PD 分离不必然提高总体吞吐。

可能提高：

- 避免 P/D 互相干扰；
- 独立扩容资源；
- 更好匹配硬件；
- 大规模服务中调度更灵活。

可能降低：

- KV transfer 成为额外开销；
- P/D 资源比例不匹配；
- 网络瓶颈；
- buffer / connector 开销大。

所以必须 benchmark。

---

## 11. PD 分离的部署策略

### 11.1 什么时候适合 PD 分离？

适合：

- 长 prompt 多；
- Decode 尾延迟要求高；
- 流式输出体验重要；
- Prefill 和 Decode 资源需求差异大；
- 有足够 GPU / 节点做资源池拆分；
- 网络带宽足够；
- 大模型或大规模线上服务；
- 需要独立扩缩容 P / D 池。

不适合：

- 小模型；
- prompt 很短；
- 请求量低；
- 单机单卡；
- 网络差；
- KV transfer 开销大于收益；
- 运维复杂度不可接受。

---

### 11.2 P / D 资源比例怎么选？

没有固定答案，要根据 workload。

如果：

```text
prompt 很长，output 较短
```

Prefill 更重，应增加 P 资源。

如果：

```text
prompt 较短，output 很长
```

Decode 更重，应增加 D 资源。

经验公式：

```text
P pool capacity ≈ prompt token processing demand
D pool capacity ≈ output token generation demand
```

实际要通过压测确定：

- P 队列长度；
- D 队列长度；
- P GPU utilization；
- D GPU utilization；
- KV transfer bandwidth；
- TTFT / ITL / P99。

---

### 11.3 P / D 可以使用不同并行策略

PD 分离后，P 端和 D 端可以配置不同并行方式。

例如：

```text
P 端：TP=4，适合大 prompt prefill
D 端：TP=2 或 TP=1，减少 decode 通信
```

原因：

- Prefill 更 compute-bound，大 TP 可能更合适；
- Decode 更 memory-bound / communication-sensitive，过大的 TP 可能通信开销重；
- P/D 分离后可以分别调优。

---

## 12. 常见问题和故障定位

### 12.1 KV 加载失败

可能原因：

- P/D connector 配置不一致；
- `kv_role` 配错；
- `kv_rank` 配错；
- IP / port 不通；
- NCCL group 建立失败；
- tensor shape / dtype 不匹配；
- P 端 KV 被释放；
- D 端 block 分配失败；
- 网络超时。

定位方式：

- 看 P/D 两侧日志；
- 检查 `kv-transfer-config`；
- 检查端口；
- 检查 NCCL 环境变量；
- 用小模型小 prompt 复现；
- 设置 `kv_load_failure_policy` 为 `fail` 暴露错误；
- 必要时用 Nsight Systems 看是否卡在通信。

---

### 12.2 TTFT 变高

可能原因：

```text
KV transfer + injection 时间超过 PD 分离带来的收益
```

排查：

- 对比普通部署和 PD 部署；
- 分别测 P prefill 时间、KV transfer 时间、D injection 时间；
- 看 D 是否等待 KV；
- 看网络带宽；
- 看 connector 是否同步阻塞。

---

### 12.3 D 端 GPU 空闲

可能原因：

- P 端 prefill 跟不上；
- KV transfer 慢；
- Proxy 路由不均；
- D 端等待 KV；
- P/D 比例不合理。

优化：

- 增加 P 资源；
- 换更快 connector；
- 增大 P batch；
- 优化 P/D 调度；
- 用 prefix cache / KV sharing。

---

### 12.4 P 端 GPU 空闲

可能原因：

- 请求流量不够；
- D 端成为瓶颈，proxy 不再向 P 发请求；
- P/D 资源比例中 P 过多；
- KV buffer 满，P 被 backpressure。

优化：

- 减少 P 节点；
- 增加 D 节点；
- 优化 KV transfer；
- 调整 proxy 调度。

---

## 13. 与其他 vLLM 特性的关系

### 13.1 PD 分离与 Chunked Prefill

Chunked Prefill 是在同一实例内把长 prefill 切块，避免长 prefill 长时间阻塞 decode。

PD 分离是把 prefill 放到单独实例。

| 特性 | 思路 |
|---|---|
| Chunked Prefill | 同实例内切小块调度 |
| PD 分离 | 物理上拆分 P/D 资源池 |

Chunked Prefill 更简单；PD 分离隔离更彻底，但运维和 KV transfer 更复杂。

---

### 13.2 PD 分离与 Prefix Caching

Prefix Caching 可以减少重复 prompt 的 prefill。

PD 分离中，如果 P 端命中 prefix cache：

```text
prefill compute 下降
```

如果 KV 可以跨 D 实例共享：

```text
D 端也可能复用已有 KV
```

所以 PD 分离与 KV sharing / prefix caching 结合很重要。

---

### 13.3 PD 分离与 Speculative Decoding

Speculative Decoding 主要优化 decode 阶段。

PD 分离主要隔离 prefill 和 decode。

二者可以组合：

```text
P 端负责 prefill
D 端负责 speculative decode
```

但组合后状态更复杂：

- D 端 speculative tokens 的 KV 管理；
- accepted / rejected KV；
- P 端只产生 prompt KV；
- D 端继续产生 output KV。

---

### 13.4 PD 分离与 TP / DP / EP

PD 分离后可以：

```text
P pool 使用一种 TP/DP/EP 策略
D pool 使用另一种 TP/DP/EP 策略
```

但要注意：

- KV layout 必须兼容；
- TP shard 需要匹配或支持转换；
- 不同并行策略下 KV head shard 位置可能不同；
- MoE 模型中 EP 与 D 端 decode 配置要谨慎。

---

## 14. 面试问答

### 14.1 面试题 1：什么是 PD 分离？

答：

PD 分离是 Prefill-Decode Disaggregation，即把 LLM 推理中的 prefill 阶段和 decode 阶段部署到不同 vLLM 实例、GPU 或节点上。Prefill 实例负责处理 prompt 并生成 KV Cache，Decode 实例通过 KV Connector 获取这些 KV Cache，然后基于 KV Cache 继续逐 token 生成。它的主要目的是隔离 prefill 和 decode，分别优化 TTFT 和 ITL，并降低 decode 尾延迟。

---

### 14.2 面试题 2：为什么要做 PD 分离？

答：

因为 prefill 和 decode 的性能特征不同。Prefill 一次处理大量 prompt token，更偏 compute-bound，主要影响 TTFT；decode 每步处理少量 token，需要频繁读取权重和 KV Cache，更偏 memory-bound，主要影响 ITL。在普通部署中，长 prefill 可能插入 decode 过程，导致 token 间延迟抖动。PD 分离可以让 P 池专注 prefill，D 池专注 decode，从而更稳定地控制 ITL 和尾延迟。

---

### 14.3 面试题 3：PD 分离一定提高吞吐吗？

答：

不一定。PD 分离引入了 KV Cache 传输和 D 端 KV 注入的额外开销。它主要解决 TTFT/ITL 分别调优和 decode 尾延迟问题，而不是保证吞吐提升。如果 KV transfer 很慢、网络带宽不足或 P/D 资源比例不合理，吞吐甚至可能下降。因此 PD 分离必须结合 workload benchmark 判断。

---

### 14.4 面试题 4：PD 分离中 KV Cache 为什么必须传？

答：

Prefill 阶段已经为 prompt 中每个 token 计算了每层 attention 的 K/V。Decode 阶段需要这些历史 K/V 来计算新 token 对历史上下文的注意力。如果 D 端没有 prompt KV，就无法从 prompt 后继续生成，只能重新计算 prefill。因此 P 端必须把 KV Cache 传给 D 端，或者 D 端重新 prefill。

---

### 14.5 面试题 5：KV Cache 大小怎么估算？

答：

KV Cache 大小约等于：

```text
num_layers × seq_len × num_kv_heads × head_dim × 2 × dtype_size
```

其中 2 表示 K 和 V。对于长上下文、大层数、大 head_dim 的模型，KV Cache 非常大。PD 分离把 KV Cache 变成跨实例传输的数据，因此长 prompt 下 KV transfer 可能成为 TTFT 的重要组成部分。

---

### 14.6 面试题 6：KV Connector 是什么？

答：

KV Connector 是 vLLM 中负责跨实例传输 KV Cache 的抽象。它让 KV consumer，也就是 decode instance，能够从 KV producer，也就是 prefill instance，获取某个请求的 KV Cache。不同 connector 可以用不同传输后端，例如 P2pNcclConnector 使用 NCCL 点对点传输，NixlConnector 使用 NIXL/UCX/LIBFABRIC 等后端，LMCacheConnector 可以对接外部 KV cache 存储。

---

### 14.7 面试题 7：P2pNcclConnector 的基本原理是什么？

答：

P2pNcclConnector 用控制通道交换 KV metadata 和连接信息，用 NCCL 做真正的 GPU 间 KV tensor 传输。控制面负责 request id、tensor shape、dtype、地址和 NCCL group 协商；数据面负责传 K/V tensor。它适合 P/D 实例之间的点对点 GPU KV 传输。

---

### 14.8 面试题 8：PUT、GET、PUT_ASYNC 有什么区别？

答：

PUT 是 P 端主动同步发送 KV 到 D 端，可能阻塞 P 主流程。PUT_ASYNC 也是 P 主动发送，但使用异步线程或异步路径，尽量不阻塞主流程。GET 是 P 端先把 KV 放到 buffer，D 端在分配好本地 KV Cache 空间后主动拉取。PUT_ASYNC 通常更有利于降低阻塞，但实现和生命周期管理更复杂。

---

### 14.9 面试题 9：D 端拿到远端 KV 后为什么还要“注入”本地 KV Cache？

答：

因为 vLLM 使用 PagedAttention，每个实例都有自己的 KV Cache block manager，P 端和 D 端的 physical block id 不一致。D 端必须先为请求分配本地 KV blocks，然后把远端 KV 数据按照 layer、token position、head、dtype、layout 写入 D 端本地 blocks。只有这样后续 decode 才能通过 D 端 block table 正确读取历史 KV。

---

### 14.10 面试题 10：KV Offloading 和 PD KV Transfer 的区别是什么？

答：

PD KV Transfer 的目标是把 P 端生成的 KV 传给 D 端，用于 PD 分离。KV Offloading 的目标是把 KV 从 GPU 显存转移到 CPU、磁盘或远端 KV store，以节省显存或支持 KV sharing。前者是跨 P/D 实例的执行链路，后者更像缓存/存储层能力。它们可以结合，例如用 LMCache 做 PD 分离中的 KV 中转和跨实例共享。

---

### 14.11 面试题 11：PD 分离和 Chunked Prefill 有什么区别？

答：

Chunked Prefill 是在同一个实例内把长 prefill 拆成多个小块插入调度，减少对 decode 的阻塞；PD 分离是把 prefill 和 decode 部署到不同实例或 GPU，物理上隔离两类工作负载。Chunked Prefill 简单，但调参难；PD 分离隔离更彻底，但需要 KV transfer 和更复杂的部署运维。

---

### 14.12 面试题 12：如何判断 PD 分离是否值得开启？

答：

可以看 workload 是否有长 prompt、decode 尾延迟是否严重、P/D 是否互相干扰、是否有足够 GPU 和网络带宽、KV transfer 是否足够快。应分别测普通部署和 PD 部署的 TTFT、ITL、P99、P/D GPU 利用率、KV transfer 时间。如果 PD 分离降低了 ITL 和尾延迟，并且 KV transfer 没有显著拉高 TTFT，就值得考虑。

---

## 15. 本节课总结

本节课主线可以总结为：

```text
LLM 推理分为 Prefill 和 Decode
        ↓
Prefill 更偏 compute-bound，Decode 更偏 memory-bound
        ↓
普通部署中长 Prefill 会干扰 Decode，造成 ITL 尾延迟
        ↓
PD 分离把 P 和 D 放到不同实例 / GPU / 节点
        ↓
P 端计算 prompt KV Cache
        ↓
KV Connector 把 KV 从 P 端传到 D 端
        ↓
D 端分配本地 KV blocks 并注入远端 KV
        ↓
D 端基于 KV Cache 执行稳定 Decode
        ↓
系统可分别优化 TTFT 和 ITL
```

最重要的理解是：

> **PD 分离的本质不是“多开两个服务”，而是把 LLM 推理中计算特征完全不同的 Prefill 和 Decode 解耦；它真正的技术难点在于 KV Cache 的正确、快速、异步传输与注入。**
