# vLLM 性能分析和瓶颈定位学习笔记

> 课时 18：vLLM 性能分析和瓶颈定位  
> 课程关键词：PyTorch Profiler、NVIDIA Nsight Systems、NSYS、NVTX、CUDA Kernel Timeline、CPU Overhead、GPU Idle、Prefill / Decode、TTFT、TPOT、ITL、Throughput、Bottleneck Analysis、Profiling Methodology

---

## 0. 本节课核心目标

本节课的核心不是“介绍一个工具怎么点按钮”，而是建立一套 **vLLM 推理服务性能分析方法论**。

前面课程已经学习了：

- vLLM 架构；
- Scheduler / Executor / Worker / ModelRunner；
- PagedAttention / KV Cache；
- CUDA Graph；
- Triton 算子；
- 量化；
- TP / DP / EP / EPLB；
- 投机解码；
- 模型编译。

这些技术最终都要服务于一个目标：

> **让大模型推理服务在给定 GPU、模型、请求长度和并发条件下，获得更低延迟、更高吞吐、更高 GPU 利用率和更稳定的尾延迟。**

但工程中不能只凭感觉优化。真正做 AI Infra 时，常见问题是：

```text
吞吐低，是调度问题、显存问题、通信问题，还是 kernel 问题？
TTFT 高，是 prefill 慢、排队慢，还是 CPU 侧处理慢？
TPOT 高，是 decode memory-bound，还是 CUDA Graph 没生效？
GPU 利用率低，是 batch 不够，还是 CPU 没及时提交 kernel？
多卡慢，是 AllReduce / AllToAll 通信拖慢，还是某个 rank 负载不均？
```

所以本节课主线是：

```text
先明确性能指标
        ↓
再用 PyTorch Profiler 看模型 / 框架级执行结构
        ↓
再用 Nsight Systems 看 CPU-GPU 时间线和 CUDA kernel 细节
        ↓
最后根据证据判断瓶颈位置
        ↓
再选择对应优化手段
```

# 第一部分：vLLM 性能分析的基本指标

## 1. 为什么不能只看“快不快”？

“模型快不快”是一个不完整问题，因为推理服务至少包含多个维度：

| 指标 | 英文 | 含义 |
|---|---|---|
| 首 token 延迟 | TTFT | 从请求发出到第一个 token 返回的时间 |
| 每 token 延迟 | TPOT / ITL | Decode 阶段相邻 token 之间的间隔 |
| 总延迟 | E2E Latency | 一个请求从提交到完成的总时间 |
| 吞吐 | Throughput | 单位时间处理多少 tokens 或 requests |
| 请求吞吐 | QPS / RPS | 每秒处理多少请求 |
| token 吞吐 | TPS | 每秒生成多少 token |
| GPU 利用率 | GPU Utilization | GPU 计算资源是否被充分利用 |
| 显存占用 | Memory Usage | 权重、KV Cache、临时 buffer 占用 |
| 尾延迟 | P95 / P99 Latency | 最慢一批请求的延迟表现 |

不同指标可能互相冲突：

```text
提高 batch size
  → 吞吐可能提升
  → 单请求延迟可能变高

开启量化
  → 显存下降
  → 吞吐可能提升
  → 精度和 kernel backend 可能成为新问题

开启 TP
  → 单卡显存压力下降
  → 但通信开销上升
```

所以做性能分析时，要先明确优化目标：

```text
目标是降低 TTFT？
目标是降低 TPOT？
目标是提高整体吞吐？
目标是降低 P99？
目标是减少显存？
目标是定位 GPU idle？
```

---

## 2. vLLM 推理服务中的关键阶段

一个请求从输入到输出，大致经过：

```text
HTTP / Python Client
  ↓
API Server
  ↓
Tokenizer
  ↓
Engine / Scheduler
  ↓
Prefill
  ↓
KV Cache 写入
  ↓
Decode loop
  ↓
Sampler
  ↓
Detokenizer
  ↓
Streaming Output
```

性能瓶颈可能出现在任何阶段。

### 2.1 输入侧瓶颈

可能表现为：

- API Server CPU 占用高；
- tokenizer 慢；
- 请求排队时间长；
- batch 构建慢；
- Python 线程 / 进程通信阻塞。

### 2.2 Prefill 瓶颈

Prefill 处理 prompt，一次性计算大量 token。

常见瓶颈：

- 长 prompt；
- attention 计算大；
- chunked prefill 配置不合理；
- prefill 抢占 decode；
- TP 通信开销；
- KV Cache 写入；
- prompt 太长导致 TTFT 高。

### 2.3 Decode 瓶颈

Decode 每步生成 token。

常见瓶颈：

- batch 太小，GPU 不饱和；
- 每步只处理少量 token，kernel launch overhead 明显；
- 读取模型权重和 KV Cache，memory bandwidth bound；
- CUDA Graph 没有命中；
- sampler / logits processing 开销大；
- 多卡通信同步拖慢。

### 2.4 输出侧瓶颈

可能表现为：

- detokenize 慢；
- streaming flush 频繁；
- 客户端消费慢；
- 日志或 tracing 太重；
- Python event loop 处理不过来。

# 第二部分：性能瓶颈定位方法论

## 3. 一套标准分析流程

不要一上来就开 Nsight Systems 抓完整服务，也不要一上来就改参数。推荐流程：

```text
Step 1：确定 benchmark 场景
Step 2：记录宏观指标
Step 3：区分 prefill / decode
Step 4：判断 GPU 是否繁忙
Step 5：用 PyTorch Profiler 看框架级耗时
Step 6：用 Nsight Systems 看 CPU-GPU 时间线
Step 7：锁定瓶颈类型
Step 8：选择优化策略
Step 9：重新 benchmark 验证
```

---

## 4. 固定 benchmark 场景

性能问题必须在固定 workload 下讨论。

至少要记录：

```text
model name
GPU 型号和数量
dtype / quantization
TP / DP / EP 配置
max_model_len
gpu_memory_utilization
input_len
output_len
concurrency
request rate
sampling params
是否开启 CUDA Graph
是否开启 torch.compile
是否开启 speculative decoding
是否开启 chunked prefill
```

否则两个结果不能对比。

例如：

```text
模型：Qwen2.5-7B-Instruct
GPU：1 × A100 80GB
dtype：float16
TP：1
输入长度：1024 tokens
输出长度：128 tokens
并发：32
采样：temperature=0
测试时间：5 min
```

---

## 5. 宏观指标先行

在动 profiler 前，先看：

```text
TTFT
TPOT / ITL
E2E latency
tokens/s
requests/s
GPU utilization
GPU memory
CPU utilization
```

原因是：

> **Profiler 会引入额外开销，不能直接把 profiler 下的延迟当作真实延迟。**

Profiler 的作用是定位“时间花在哪里”，不是直接评估最终吞吐。

---

## 6. 区分几类瓶颈

性能瓶颈通常可以归为几类。

### 6.1 GPU Compute Bound

特征：

- GPU utilization 高；
- Tensor Core 忙；
- GEMM / Attention kernel 占主要时间；
- CPU 没有明显空洞；
- batch 足够大。

优化方向：

- 更快 kernel；
- torch.compile / Triton fusion；
- FlashAttention / FlashInfer；
- 量化；
- TP / EP；
- 更强 GPU。

### 6.2 GPU Memory Bandwidth Bound

特征：

- GPU utilization 可能不满；
- memory throughput 高；
- decode 阶段明显；
- 每 token 需要读大量权重和 KV Cache；
- arithmetic intensity 低。

优化方向：

- 量化权重；
- KV Cache 量化；
- 增大 batch；
- CUDA Graph 降 launch overhead；
- speculative decoding；
- better attention backend；
- 减少 KV Cache 访问。

### 6.3 CPU / Python Overhead Bound

特征：

- GPU timeline 有大量空洞；
- CPU 线程在忙；
- kernel launch 不连续；
- Python 函数耗时明显；
- tokenizer / scheduler / sampler / IPC 可能耗时高。

优化方向：

- CUDA Graph；
- torch.compile；
- 减少 Python 逻辑；
- 调整 batch；
- 减少日志；
- 优化 tokenizer / detokenizer；
- 降低 profiling / tracing 开销。

### 6.4 Communication Bound

特征：

- 多卡下 NCCL kernel / allreduce / alltoall 占时间；
- GPU 等待通信；
- TP / EP / DP 规模变化影响大；
- 单卡快，多卡扩展差。

优化方向：

- 调整 TP / DP / EP；
- 使用更合适的 All2All backend；
- EP load balancing；
- 通信计算 overlap；
- 减少跨机通信；
- 优化 batch / microbatch。

### 6.5 Memory Capacity Bound

特征：

- OOM；
- KV Cache 不够；
- batch size 上不去；
- 显存碎片；
- 被权重 / 冗余 experts / LoRA / KV Cache 占满。

优化方向：

- 量化；
- 降低 max_model_len；
- 降低 gpu_memory_utilization 之外的额外占用；
- 减少 LoRA 数量；
- 减少 redundant experts；
- KV Cache 量化；
- 增加 GPU。

# 第三部分：vLLM 使用 PyTorch Profiler 进行分析

## 7. PyTorch Profiler 适合看什么？

PyTorch Profiler 更适合回答：

```text
哪个 PyTorch op / module 耗时高？
CPU 和 CUDA 时间分别是多少？
哪些 op 分配显存多？
shape 是什么？
Python stack 在哪里？
模型 forward 内部结构是什么？
```

它的优点：

- 和 PyTorch 集成好；
- 能看 CPU / CUDA op；
- 能记录 shape、memory、stack；
- 可导出 Chrome trace；
- 适合理解模型与框架级执行结构。

它的缺点：

- 开销比 Nsight Systems 更高；
- 打开 record_shapes / with_memory / with_stack 后更慢；
- trace 文件可能很大；
- 不适合直接作为最终 benchmark；
- 对 CUDA kernel 低层细节不如 Nsight。

---

## 8. vLLM 中开启 PyTorch Profiler

vLLM 官方 profiling 文档说明，较新版本可以通过 server 启动时设置 `--profiler-config` 来启用 profiler。

示例：

```bash
vllm serve Qwen/Qwen2.5-7B-Instruct \
  --profiler-config '{
    "profiler": "torch",
    "torch_profiler_dir": "./vllm_profile",
    "torch_profiler_record_shapes": true,
    "torch_profiler_with_memory": true,
    "torch_profiler_with_stack": true,
    "torch_profiler_with_flops": false,
    "torch_profiler_use_gzip": true
  }'
```

核心字段：

| 字段 | 含义 |
|---|---|
| `profiler` | 使用哪种 profiler，这里是 `torch` |
| `torch_profiler_dir` | trace 输出目录 |
| `torch_profiler_record_shapes` | 是否记录 tensor shape |
| `torch_profiler_with_memory` | 是否记录内存 |
| `torch_profiler_with_stack` | 是否记录 Python stack |
| `torch_profiler_with_flops` | 是否估算 FLOPs |
| `torch_profiler_use_gzip` | 是否压缩 profiling 文件 |

注意：

> 记录 shape、memory、stack 都会增加额外开销，不建议在正式 benchmark 时打开。

---

## 9. 离线推理中手动开启 profiler

如果你用的是 Python 脚本：

```python
from vllm import LLM, SamplingParams

llm = LLM(model="Qwen/Qwen2.5-7B-Instruct")
sampling_params = SamplingParams(max_tokens=128, temperature=0)

prompts = ["请用三句话介绍 vLLM。"] * 8

# warmup
llm.generate(prompts, sampling_params)

# profiling
llm.start_profile()
outputs = llm.generate(prompts, sampling_params)
llm.stop_profile()
```

实际可用 API 会随版本变化。如果你使用的 vLLM 版本不支持 `start_profile()` / `stop_profile()`，应以当前官方 profiling 文档为准。

PyTorch Profiler 常见输出包括：


## 11. 如何读 PyTorch Profiler？

重点看几个方向。

### 11.1 CPU time vs CUDA time

如果某个 op：

```text
CPU time 高
CUDA time 低
```

可能是：

- Python 调度；
- 数据准备；
- tokenizer；
- scheduler；
- sampler；
- CPU 后处理；
- 同步等待。

如果某个 op：

```text
CUDA time 高
```

说明 GPU kernel 本身耗时大。

---

### 11.2 Self time vs Total time

| 指标 | 含义 |
|---|---|
| Self CPU Time | 当前 op 自己消耗的 CPU 时间，不包含子调用 |
| CPU Total Time | 当前 op 加子调用的总 CPU 时间 |
| Self CUDA Time | 当前 op 自己对应 CUDA kernel 时间 |
| CUDA Total Time | 当前 op 及子调用 CUDA 总时间 |

如果 total 高但 self 低，说明时间主要在子调用。

---

### 11.3 Shapes

打开 `record_shapes` 后可以看到输入 shape。

对于 vLLM，要重点确认：

```text
Prefill shape 是否很大？
Decode batch size 是否太小？
是否出现很多不同 shape 导致 compile / graph capture 不能复用？
attention 输入是否符合预期？
```

---

### 11.4 Memory

打开 `with_memory` 后可以看到 memory allocation。

重点排查：

- 是否频繁分配临时 tensor；
- 是否有 CPU / GPU memory spike；
- 是否有 unexpected allocation；
- decode 是否仍在分配本应复用的 buffer；
- profiler 本身是否造成显存压力。

---

### 11.5 Stack

打开 `with_stack` 后能看到 Python 调用栈。

它适合定位：

```text
这个 op 是从 vLLM 哪个模块触发的？
是 ModelRunner？
是 Sampler？
是 Scheduler？
是 Attention backend？
是 LoRA / Quantization？
```

但 stack 开销很高，建议只在小规模 profiling 中使用。

---

## 12. 用 PyTorch Profiler 定位 vLLM 瓶颈示例

### 12.1 发现 sampler 慢

现象：

```text
torch.multinomial / logits processor / softmax 占比较高
```

可能原因：

- vocab_size 大；
- batch 大；
- top_p / top_k 处理重；
- logprobs 输出太多；
- guided decoding / grammar decoding；
- CPU 后处理多。

优化方向：

- 使用 greedy / temperature=0 对比；
- 减少 logprobs；
- 关闭不必要 guided decoding；
- 使用更优 sampler backend；
- batch 维度合理化。

---

### 12.2 发现 attention 慢

现象：

```text
paged_attention / flash_attention kernel 占比高
```

可能原因：

- 序列太长；
- KV Cache 访问重；
- attention backend 不合适；
- prefix caching 未命中；
- chunked prefill 参数不合理；
- decode batch 太小。

优化方向：

- 切换 attention backend；
- 开启 / 检查 prefix cache；
- 调整 max_model_len；
- 调整 batch；
- 使用 CUDA Graph；
- KV Cache 量化；
- speculative decoding。

---

### 12.3 发现 graph / compile 没命中

现象：

```text
频繁出现 eager path
频繁 compile
形状变化很多
```

可能原因：

- batch size 不在 capture sizes；
- dynamic shape 太多；
- graph break；
- attention 或 LoRA / MoE 动态性强；
- compilation config 不合理。

优化方向：

- 设置 capture sizes；
- 关闭复杂动态特性做对比；
- 调整 compilation level；
- 使用 piecewise compilation；
- 对 benchmark 做 warmup。

# 第四部分：vLLM 使用 NVIDIA Nsight Systems 进行性能分析

## 13. Nsight Systems 适合看什么？

Nsight Systems 是系统级时间线 profiler，适合回答：

```text
CPU 什么时候提交 kernel？
GPU 什么时候真正执行 kernel？
kernel 之间有没有空洞？
CUDA memcpy / cudaMalloc 是否频繁？
NCCL 通信是否占时间？
CUDA Graph 是否在 replay？
不同进程 / 线程之间如何交互？
GPU 是否在等 CPU？
CPU 是否在等 GPU？
```

它比 PyTorch Profiler 更适合看：

- CPU-GPU overlap；
- CUDA kernel timeline；
- NCCL 通信；
- CUDA Graph；
- 多进程；
- 系统级等待；
- GPU idle；
- kernel launch gap。

---

## 14. Nsight Systems 和 PyTorch Profiler 的区别

| 维度 | PyTorch Profiler | Nsight Systems |
|---|---|---|
| 层次 | PyTorch op / module | 系统级 CPU-GPU timeline |
| 开销 | 中等到较高 | 通常更低 |
| 适合 | 快速理解模型结构、op 级耗时 | 性能关键路径、kernel launch、通信 |
| 能否看 CUDA timeline | 可以，但不如 NSYS 深 | 强 |
| 能否看 Python stack | 可以 | 可通过 Python sampling / functions trace |
| 能否看 NCCL | 一般 | 强 |
| 能否看 CUDA Graph | 一般 | 强 |
| 是否适合最终 benchmark | 不适合 | 也有开销，但更接近系统分析 |

可以这样选：

```text
先用 PyTorch Profiler 看大概是哪类 op 慢；
再用 Nsight Systems 看 CPU-GPU timeline 和 kernel 层细节。
```

---

## 15. Nsight Systems 基本命令

离线脚本：

```bash
nsys profile \
  -o vllm_nsys_report \
  --trace=cuda,nvtx,osrt,cublas,cudnn,nccl \
  --cuda-graph-trace=node \
  python benchmark_vllm.py
```

服务模式：

```bash
nsys profile \
  -o vllm_server_report \
  --trace=cuda,nvtx,osrt,cublas,cudnn,nccl \
  --cuda-graph-trace=node \
  --trace-fork-before-exec=true \
  vllm serve Qwen/Qwen2.5-7B-Instruct
```

常见参数解释：

| 参数 | 含义 |
|---|---|
| `-o` | 输出报告名 |
| `--trace=cuda,nvtx,...` | 采集 CUDA、NVTX、系统 runtime、NCCL 等 |
| `--cuda-graph-trace=node` | 以 CUDA Graph node 粒度显示 graph |
| `--trace-fork-before-exec=true` | 追踪 fork 出来的子进程，vLLM 多进程很重要 |
| `--sample=cpu` | CPU 采样 |
| `--python-sampling=true` | Python 采样 |
| `--pytorch=functions-trace` | 自动标注 PyTorch 函数 |
| `--capture-range=nvtx` | 只采集 NVTX 标记范围内的代码 |

---

## 16. 为什么 vLLM profiling 要注意多进程？

vLLM 可能包含：

```text
API server process
EngineCore process
Worker process
TP ranks
DP ranks
Tokenizer process / thread
NCCL communicators
```

如果你只 profile 主进程，可能看不到真正执行模型的 worker。

所以常用：

```bash
--trace-fork-before-exec=true
```

或者保证 nsys 能跟踪子进程。

---

## 17. NVTX 是什么？

NVTX 是 NVIDIA 提供的标注机制，可以在 timeline 中添加自定义范围。

例如：

```python
import torch.cuda.nvtx as nvtx

nvtx.range_push("prefill")
# run prefill
nvtx.range_pop()

nvtx.range_push("decode")
# run decode
nvtx.range_pop()
```

在 Nsight Systems 中会看到：

```text
[prefill] 区间
[decode] 区间
```

这样更容易对齐：

```text
哪段 timeline 是 prefill？
哪段是 decode？
哪段是 sampler？
哪段是 NCCL？
```

vLLM 自身也会在部分路径上使用 NVTX 标记，结合 NSYS 更容易读 timeline。

---

## 18. 如何阅读 Nsight Systems Timeline？

重点看这些轨道：

```text
CPU Threads
CUDA API
CUDA Kernels
CUDA Memory
CUDA Graphs
NCCL Kernels
NVTX Ranges
GPU Utilization
```

---

### 18.1 看 GPU 是否有空洞

如果 GPU kernel timeline 中有大量空白：

```text
kernel A     空白      kernel B      空白      kernel C
```

说明 GPU 没有连续工作。

可能原因：

- CPU 来不及 launch；
- Python 调度慢；
- 同步等待；
- batch 太小；
- scheduler 处理慢；
- 数据准备慢；
- 多进程通信慢。

优化方向：

- CUDA Graph；
- torch.compile；
- 增大 batch；
- 减少 Python overhead；
- 检查 scheduler / IPC；
- 减少同步操作。

---

### 18.2 看 CUDA API 是否密集

如果 CPU 侧出现大量：

```text
cudaLaunchKernel
cudaMemcpyAsync
cudaStreamSynchronize
cudaEventSynchronize
cudaMalloc
cudaFree
```

要分别判断：

| CUDA API | 可能含义 |
|---|---|
| `cudaLaunchKernel` 很多 | kernel launch overhead 高 |
| `cudaMemcpyAsync` 很多 | CPU-GPU 或 GPU-GPU 数据搬运多 |
| `cudaStreamSynchronize` | CPU 等 GPU，可能同步过多 |
| `cudaEventSynchronize` | event 等待，可能影响 pipeline |
| `cudaMalloc/cudaFree` | 运行时动态分配，通常不理想 |

vLLM 稳态推理中，应尽量避免频繁 `cudaMalloc/cudaFree`。

---

### 18.3 看 CUDA Graph 是否生效

如果 CUDA Graph 生效，timeline 中应能看到 graph launch / graph replay 相关事件，kernel launch overhead 会减少。

如果没生效，可能原因：

- batch size 不在 capture sizes；
- shape 动态；
- attention backend 不支持；
- LoRA / speculative / MoE 等动态路径不满足；
- compilation config 不匹配；
- fallback 到 eager。

---

### 18.4 看 NCCL 通信

多卡 TP / DP / EP 下，重点看：

```text
ncclKernel_AllReduce
ncclKernel_AllGather
ncclKernel_ReduceScatter
ncclKernel_AllToAll
```

如果 NCCL kernel 占比高：

```text
通信是瓶颈
```

进一步看：

- 是否 TP size 太大；
- 是否跨机通信；
- EP AllToAll 是否太重；
- expert load 是否不均；
- 是否可用更优 all2all backend；
- batch 是否太小导致通信摊不薄；
- 是否存在 rank straggler。

---

### 18.5 看 CPU 线程状态

如果看到 CPU 线程大量时间在：

```text
poll
epoll_wait
futex
pthread_cond_wait
recv
send
```

要结合上下文判断。

可能是：

- 正常等待请求；
- 进程间通信；
- worker 等 scheduler；
- API server 等 engine；
- NCCL / CUDA 同步；
- Python GIL 竞争。

如果 GPU 同时空闲，就说明这类等待可能影响性能。

# 第五部分：vLLM 常见瓶颈案例分析

## 19. 案例 1：TTFT 高

### 现象

```text
用户很久才看到第一个 token
但后续 token 速度还可以
```

### 可能原因

- prefill 长；
- prompt 太长；
- prefill batch 太大；
- chunked prefill 未开启或参数不合理；
- 队列排队；
- tokenizer 慢；
- CPU 到 engine 通信慢；
- prefix cache 未命中；
- GPU prefill compute-bound。

### profiler 证据

PyTorch Profiler：

```text
attention / matmul 在 prefill 中占比高
```

Nsight Systems：

```text
prefill NVTX range 很长
GPU kernel 连续且忙
```

如果 GPU 忙，说明 prefill 计算本身重；如果 GPU 空洞多，说明输入侧 / CPU 侧有问题。

### 优化方向

- 启用 chunked prefill；
- 调整 max_num_batched_tokens；
- 使用 prefix caching；
- 减少 prompt 长度；
- 使用更快 attention backend；
- 量化；
- 增加 TP；
- 分离 prefill/decode。

---

## 20. 案例 2：TPOT / ITL 高

### 现象

```text
第一个 token 出来还可以
但后续一个 token 一个 token 很慢
```

### 可能原因

- decode batch 太小；
- CUDA Graph 没命中；
- decode memory-bound；
- KV Cache 读取开销大；
- sampler 慢；
- TP 通信开销；
- MoE expert imbalance；
- speculative decoding 未开启或收益低。

### profiler 证据

PyTorch Profiler：

```text
decode loop 中 attention / sampler / linear 占比高
```

Nsight Systems：

```text
kernel 小且密集
launch gap 明显
GPU 空洞多
```

或者：

```text
NCCL / AllToAll 占比高
```

### 优化方向

- 提高 batch / concurrency；
- 开启 CUDA Graph；
- 检查 capture sizes；
- torch.compile；
- weight-only / FP8 quantization；
- KV Cache quantization；
- speculative decoding；
- EP load balancing；
- 调整 TP / DP / EP。

---

## 21. 案例 3：GPU 利用率低

### 现象

```text
nvidia-smi 显示 GPU 利用率低
tokens/s 也不高
```

### 可能原因

- 请求量不足；
- batch 太小；
- CPU 调度慢；
- tokenizer 慢；
- 频繁同步；
- stream 没填满；
- CUDA Graph 未生效；
- profiler 或日志本身开销大。

### NSYS 证据

```text
GPU timeline 大量空洞
CPU timeline 有 Python / CUDA API 间隔
```

### 优化方向

- 增加并发；
- 调整 scheduler；
- 减少日志；
- CUDA Graph；
- 编译；
- 减少同步；
- 使用 benchmark 模拟稳定请求流。

---

## 22. 案例 4：多卡扩展性差

### 现象

```text
1 卡速度不错
2/4/8 卡后吞吐没有线性提升
甚至变慢
```

### 可能原因

- TP 通信开销大；
- batch 太小，通信摊不薄；
- NCCL 配置问题；
- 跨 NUMA / PCIe 拓扑差；
- 多机网络慢；
- EP AllToAll 太重；
- rank 负载不均；
- 某个 worker straggler。

### NSYS 证据

```text
NCCL kernel 占比高
rank 之间 timeline 不对齐
某些 rank 更慢
GPU 在等待通信
```

### 优化方向

- 调整 TP/DP 比例；
- 增加 batch；
- 检查 NCCL topology；
- 使用更合适 AllToAll backend；
- 开启 EPLB；
- 尽量单机 NVLink 内通信；
- 减少跨机 TP。

---

## 23. 案例 5：显存不足导致吞吐上不去

### 现象

```text
并发一高就 OOM
max_num_seqs 上不去
KV Cache block 不够
```

### 可能原因

- max_model_len 太大；
- 模型权重太大；
- FP16/BF16 未量化；
- KV Cache 太大；
- LoRA 多；
- EPLB redundant experts 多；
- GPU memory utilization 配置不合理；
- fragmentation / 临时 buffer 高。

### profiler / 监控证据

PyTorch Profiler memory：

```text
某些 op 有大额 allocation
```

vLLM 日志：

```text
KV Cache blocks 数量低
```

nvidia-smi：

```text
显存接近满
```

### 优化方向

- 权重量化；
- KV Cache 量化；
- 降低 max_model_len；
- 降低并发；
- 调整 gpu_memory_utilization；
- 减少 redundant experts；
- 使用更多 GPU；
- 开启 prefix caching 减少重复计算。

## 24. 推荐组合流程

### 24.1 第一步：普通 benchmark

先跑不带 profiler 的 benchmark：

```bash
python benchmark_serving.py \
  --model Qwen/Qwen2.5-7B-Instruct \
  --num-prompts 1000 \
  --request-rate 16 \
  --input-len 1024 \
  --output-len 128
```

记录：

```text
TTFT / TPOT / throughput / GPU memory / GPU util
```

---

### 24.2 第二步：PyTorch Profiler 小规模分析

用较小请求数：

```text
10 ~ 50 requests
```

打开 profiler，记录：

- op 级耗时；
- shape；
- memory；
- stack。

目标：

```text
找到是 attention、MLP、sampler、scheduler、通信还是其他模块明显耗时。
```

---

### 24.3 第三步：Nsight Systems 时间线分析

使用 nsys 抓一小段稳态执行：

```bash
nsys profile \
  -o vllm_steady \
  --trace=cuda,nvtx,osrt,cublas,cudnn,nccl \
  --cuda-graph-trace=node \
  --trace-fork-before-exec=true \
  python run_vllm_workload.py
```

目标：

```text
确认 CPU-GPU 是否连续
确认 kernel gap
确认 CUDA Graph
确认 NCCL
确认 rank 是否同步
```

---

### 24.4 第四步：做对照实验

不要只看一次 profile，要做变量控制：

```text
CUDA Graph on/off
torch.compile on/off
TP=1/2/4
batch=1/8/32/128
input_len=128/1024/4096
output_len=32/128/512
quantization on/off
speculative decoding on/off
```

每次只改一个变量，观察指标变化。

## 25. vLLM 性能分析常见对照表

| 现象 | PyTorch Profiler 看什么 | Nsight Systems 看什么 | 可能优化 |
|---|---|---|---|
| TTFT 高 | prefill attention / matmul | prefill GPU timeline | chunked prefill、prefix cache |
| TPOT 高 | decode attention / sampler | kernel gap / CUDA Graph | CUDA Graph、spec decode |
| GPU 空闲 | CPU op / scheduler | GPU timeline 空洞 | 增大 batch、减少 CPU overhead |
| 多卡慢 | NCCL op | NCCL kernel timeline | 调整 TP/DP/EP |
| OOM | memory allocation | cudaMalloc / memory | 量化、降 max len |
| sampler 慢 | softmax / topk / multinomial | CPU/GPU sampler kernel | greedy、减少 logprobs |
| MoE 慢 | fused_moe / all2all | alltoall / rank imbalance | EPLB、All2All backend |
| 编译无收益 | graph break / recompile | graph capture miss | piecewise compile、capture sizes |

# 第八部分：面试问答

## 30. 面试题 1：vLLM 性能分析应该先看什么？

答：

先看宏观指标，包括 TTFT、TPOT/ITL、E2E latency、tokens/s、requests/s、GPU 利用率、显存占用和 P99 延迟。不要一开始就看 profiler，因为 profiler 会引入额外开销。先明确瓶颈是首 token 慢、decode 慢、吞吐低、显存不够还是多卡扩展差，再选择 PyTorch Profiler 或 Nsight Systems。

---

## 31. 面试题 2：PyTorch Profiler 和 Nsight Systems 有什么区别？

答：

PyTorch Profiler 更偏 PyTorch op / module 级别，适合看哪些 PyTorch 算子耗时、shape、memory、stack 和 CPU/CUDA 时间。Nsight Systems 是系统级 profiler，适合看 CPU-GPU 时间线、CUDA kernel launch gap、CUDA Graph、NCCL 通信、多进程和 GPU idle。一般先用 PyTorch Profiler 定位大类模块，再用 Nsight Systems 看底层时间线和通信细节。

---

## 32. 面试题 3：为什么 profiler 结果不能直接当 benchmark 结果？

答：

Profiler 会显著改变程序运行状态。PyTorch Profiler 记录 shapes、memory、stack 时开销更大，trace 文件也可能很大；Nsight Systems 也会增加一定 tracing 开销。因此 profiler 适合定位瓶颈，不适合作为最终性能指标。最终性能应该用不带 profiler 的稳定 benchmark 测量。

---

## 33. 面试题 4：TTFT 高通常怎么排查？

答：

TTFT 主要受排队、tokenization、prefill 和首轮调度影响。排查时先看请求是否排队，再看 prompt 长度和 prefill kernel 耗时。PyTorch Profiler 中看 prefill attention、matmul 是否占比高；Nsight Systems 中看 prefill 区间 GPU 是否忙。如果 GPU 忙，说明 prefill 计算重；如果 GPU 空洞多，可能是 CPU、scheduler 或输入侧瓶颈。优化方向包括 chunked prefill、prefix caching、减少 prompt 长度、优化 attention backend、量化或增加并行。

---

## 34. 面试题 5：TPOT / ITL 高通常怎么排查？

答：

TPOT / ITL 高说明 decode 每步慢。先看 decode batch 是否太小、CUDA Graph 是否命中、sampler 是否耗时、KV Cache 访问是否重、多卡通信是否占比高。Nsight Systems 中如果 kernel 之间有空洞，可能是 CPU launch 或调度问题；如果 NCCL kernel 占比高，可能是通信瓶颈；如果 attention / linear kernel 连续且耗时高，可能是 GPU 计算或显存带宽瓶颈。优化方向包括增大 batch、CUDA Graph、torch.compile、量化、speculative decoding、调整 TP/DP/EP。

---

## 35. 面试题 6：如何判断 GPU idle 是 CPU 造成的？

答：

在 Nsight Systems 中看 GPU kernel timeline。如果 kernel 之间有大量空白，同时 CPU 线程在执行 Python、scheduler、CUDA API 或进程间通信，那么说明 GPU 没有及时收到工作，可能是 CPU 侧瓶颈。如果 CUDA API 中 cudaLaunchKernel 不连续，或者存在频繁同步，也说明 CPU 可能在拖慢 GPU。优化可以考虑 CUDA Graph、减少 Python overhead、提高 batch、减少同步和日志。

---

## 36. 面试题 7：多卡推理慢应该看什么？

答：

主要看 NCCL / AllReduce / AllGather / AllToAll kernel 的占比和 rank 间同步情况。TP 常见 AllReduce / AllGather 通信，EP 常见 AllToAll 通信。如果通信 kernel 占比较高，或者某个 rank 明显更慢，说明通信或负载不均可能是瓶颈。可以调整 TP/DP/EP 比例、增加 batch 摊薄通信、检查 NCCL topology、开启 EPLB、选择更合适的 AllToAll backend。

---

## 37. 面试题 8：Nsight Systems 中看到 cudaMalloc/cudaFree 很多说明什么？

答：

稳态推理中频繁 cudaMalloc/cudaFree 通常不是好现象，说明运行时可能存在动态显存分配，可能带来同步和碎片化开销。vLLM 理想情况下应尽量预分配 KV Cache、workspace 和通信 buffer。需要定位这些分配来自哪里，可能是某些动态 tensor、profile 本身、attention backend、LoRA、MoE 或未复用 buffer。

---

## 38. 面试题 9：如何确认 CUDA Graph 是否生效？

答：

在 Nsight Systems 中查看 CUDA Graph 相关事件，例如 graph launch / graph node。若 CUDA Graph 生效，decode 阶段的 kernel launch overhead 应减少，CPU 侧 cudaLaunchKernel 调用也会减少。如果没有生效，要检查 batch size 是否在 capture sizes 中、shape 是否固定、attention backend 是否支持、是否有 LoRA/MoE/spec decode 等动态路径导致 fallback。

---

## 39. 面试题 10：为什么要用 NVTX？

答：

NVTX 可以在 Nsight Systems timeline 上标注自定义代码区间，例如 prefill、decode、sampler、scheduler、model forward。没有 NVTX 时，timeline 只有大量 kernel 和线程事件，很难知道它们对应哪段业务逻辑。有了 NVTX，可以把高层逻辑和底层 CUDA kernel 对齐，方便定位瓶颈。

---

## 40. 面试题 11：如何定位 sampler 是否是瓶颈？

答：

PyTorch Profiler 中看 softmax、topk、multinomial、logits processor、guided decoding、logprobs 等算子耗时；Nsight Systems 中看 sampler 相关 NVTX 区间是否长，以及是否造成 GPU 空等。可以用 greedy decoding、减少 logprobs、关闭 guided decoding、降低 top-k/top-p 复杂度做对照实验。如果性能明显改善，说明 sampler 或 logits processing 是瓶颈之一。

---

## 41. 面试题 12：做性能优化时为什么要一次只改一个变量？

答：

因为 vLLM 中很多配置会相互影响，例如 batch size、CUDA Graph、TP、量化、chunked prefill、speculative decoding 都可能同时改变性能。如果一次改多个变量，无法判断性能变化来自哪个因素。正确方法是固定 workload 和环境，一次只改一个参数，用 benchmark 和 profiler 证据验证因果关系。

---

# 第九部分：本节课总结

本节课可以用一条主线总结：

```text
先定义性能目标和 workload
        ↓
记录 TTFT / TPOT / throughput / GPU util / memory
        ↓
区分 prefill、decode、scheduler、sampler、communication、memory
        ↓
用 PyTorch Profiler 看 PyTorch op / shape / memory / stack
        ↓
用 Nsight Systems 看 CPU-GPU timeline / kernel gap / NCCL / CUDA Graph
        ↓
判断瓶颈类型
        ↓
选择对应优化策略
        ↓
重新 benchmark 验证
```

最重要的理解是：

> **性能分析不是打开一个 profiler 看哪个条最长，而是先建立假设，再用 PyTorch Profiler 和 Nsight Systems 收集证据，最后用对照实验验证优化是否真的有效。**
