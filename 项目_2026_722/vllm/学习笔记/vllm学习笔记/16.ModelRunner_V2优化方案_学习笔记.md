# ModelRunner V2 优化方案学习笔记

> 课时 20：ModelRunner V2 优化方案  
> 课程关键词：ModelRunner V2、MRV2、Persistent Batch V2、GPU-Native Input Preparation、Async Scheduling、StagedWriteTensor、Triton Sampler、ModelState、CUDA Graph、Speculative Decoding、CPU/GPU Overlap、Input Metadata 构建优化

---

## 0. 本节课核心目标

本节课讲的是 vLLM 推理链路中非常靠近模型执行的一层：**ModelRunner**。

前面课程已经学习过：

```text
API Server / LLM.generate
  ↓
Engine / EngineCore
  ↓
Scheduler
  ↓
Executor
  ↓
Worker
  ↓
ModelRunner
  ↓
Model forward
  ↓
Sampler
```

其中 ModelRunner 是真正把 Scheduler 的调度结果转成模型可执行输入的组件。它要负责：

- 管理当前 batch 中有哪些请求；
- 准备 `input_ids`、`positions`；
- 准备 attention metadata；
- 准备 `block_table`、`slot_mapping`、`query_start_loc`、`seq_lens`；
- 调用模型 forward；
- 调用 sampler；
- 处理输出 token；
- 更新请求状态；
- 与 CUDA Graph、torch.compile、speculative decoding 等高级特性配合。

ModelRunner V2，也常写作 **MRV2**，就是 vLLM 对这条模型执行路径的重构和优化。它的核心目标不是改变用户 API，而是让模型执行核心更快、更模块化、更适合异步调度。

本节课主线可以概括为：

```text
V1 ModelRunner 中 CPU 侧 bookkeeping 和 persistent batch 复杂
        ↓
异步调度、投机解码、CUDA Graph、复杂模型支持让 V1 维护困难
        ↓
MRV2 重新设计 persistent batch、输入构建、采样和模块边界
        ↓
把更多小型输入准备工作搬到 GPU / Triton 上
        ↓
减少 CPU overhead 和 CPU-GPU 同步
        ↓
让 Scheduler 准备下一步、GPU 执行当前步可以更自然重叠
        ↓
提高 decode 阶段吞吐和稳定性
```

一句话理解：

> **ModelRunner V2 是 vLLM 为了解决 V1 模型执行路径中 persistent batch 状态耦合、CPU 输入构建开销、异步调度复杂和采样内存开销等问题，对 ModelRunner 做的一次面向 GPU-native 和 async-first 的重构。**

# 第一部分：ModelRunner 在 vLLM 中的位置

## 1. vLLM 完整推理链路

一个在线请求进入 vLLM 后，通常经过：

```text
Client
  ↓
OpenAI-compatible API Server
  ↓
AsyncLLM / LLMEngine
  ↓
EngineCore
  ↓
Scheduler
  ↓
Executor
  ↓
Worker
  ↓
ModelRunner
  ↓
Model forward
  ↓
Sampler
  ↓
Output Processor
  ↓
Streaming response
```

其中：

| 组件 | 职责 |
|---|---|
| API Server | 接收 HTTP 请求，兼容 OpenAI API |
| Engine | 请求入口、结果出口、流式返回 |
| Scheduler | 决定本轮哪些请求 prefill / decode |
| Executor | 管理 Worker，分发执行命令 |
| Worker | 绑定 GPU rank，持有 ModelRunner |
| ModelRunner | 构建模型输入，调用 forward 和 sampler |
| Model | Transformer 模型本体 |
| Sampler | 根据 logits 采样下一个 token |

ModelRunner 是 **Scheduler 输出和模型 forward 之间的桥梁**。

Scheduler 给出的信息大概是：

```text
本轮哪些请求要运行？
每个请求本轮跑多少 token？
哪些请求是 prefill？
哪些请求是 decode？
哪些请求新增了 KV block？
哪些请求结束了？
```

ModelRunner 要把这些调度结果变成模型实际需要的张量：

```text
input_ids
positions
attention_metadata
block_tables
slot_mapping
query_start_loc
seq_lens
sampling_metadata
```

---

## 2. 为什么 ModelRunner 很关键？

大模型推理的模型 forward 看起来只是：

```python
logits = model(input_ids, positions, kv_caches, attn_metadata)
```

但真实服务中，难点不在这一行，而在这一行之前和之后：

```text
模型输入怎么拼？
不同请求长度不同怎么办？
prefill 和 decode 混合怎么办？
KV Cache block 怎么映射？
attention backend 需要什么 metadata？
采样参数怎么和每个 logits 对齐？
请求结束后状态怎么删？
新请求加入后 persistent batch 怎么更新？
```

这些都由 ModelRunner 管理。

所以 ModelRunner 的性能瓶颈通常不是大 GEMM 本身，而是：

- Python bookkeeping；
- CPU tensor 构建；
- CPU → GPU 小 tensor 拷贝；
- batch 内请求重排；
- block table 更新；
- sampling metadata 构建；
- sampler 中 full-vocab softmax / logprobs；
- CPU-GPU 同步；
- 与 CUDA Graph / async scheduling 的配合。

这些开销在 decode 阶段尤其明显。

---

## 3. 为什么 Decode 阶段更容易暴露 ModelRunner 问题？

Prefill 阶段：

```text
每次处理很多 prompt token
GEMM 大
GPU 计算时间长
CPU 输入构建开销容易被 GPU 计算掩盖
```

Decode 阶段：

```text
每个请求每步通常只处理 1 个 token
单步 GPU 计算相对短
每一步都要重新构建输入和采样
CPU overhead 更容易变成瓶颈
```

如果每个 decode step 都要 CPU 做大量小操作：

```text
构造 input_ids
构造 positions
构造 block table
构造 seq_lens
构造 sampling metadata
CPU 拷贝到 GPU
GPU 执行模型
GPU 拷贝 sampled token 回 CPU
```

GPU 就可能出现空洞：

```text
GPU 执行 step N
        ↓ 等 CPU 准备 step N+1
GPU 执行 step N+1
        ↓ 等 CPU 准备 step N+2
```

MRV2 的重要目标就是减少这些 CPU-side 小开销，并让 CPU 准备下一步和 GPU 执行当前步更好重叠。

# 第二部分：V1 ModelRunner 的问题

## 4. V1 的 Persistent Batch 是什么？

vLLM V1 为了减少每步重建输入的成本，引入了 **Persistent Batch**。

普通做法是：

```text
每一步从所有请求状态重新构建 input tensors
```

例如每一步都重新构建：

```text
block_tables: [num_reqs, max_num_blocks_per_req]
temperatures: [num_reqs]
top_p: [num_reqs]
top_k: [num_reqs]
seq_lens: [num_reqs]
```

这在 Python 中很慢，尤其是 `block_tables` 这种大张量。

Persistent Batch 的想法是：

> 连续两个 decode step 的 batch 通常非常相似，所以不必每步从零构建所有输入，只需要在上一轮状态基础上增量更新。

例如：

```text
step N:
  running requests = A, B, C, D

step N+1:
  running requests = A, B, C, D, E
```

只新增了 E，那么可以只更新 E 的行。

---

## 5. V1 Persistent Batch 的核心问题

V1 的 persistent batch 虽然减少了输入构建开销，但它有一个设计问题：

```text
persistent state tensors 直接被当作 per-step model input tensors 使用
```

也就是说：

```text
持久状态表 = 模型本轮输入表
```

这导致强耦合：

1. persistent state 的行顺序必须符合本轮模型输入顺序；
2. attention backend 如果要求 prefill / decode 分组，可能要重排整张表；
3. 请求加入、结束、抢占时，需要复杂的行移动；
4. 某些行被覆盖时，还需要额外 `CachedRequestState` 做备份；
5. 异步调度下 CPU 和 GPU 可能同时访问状态，容易出现 race condition。

这使得代码变复杂，也使新特性更难加入。

---

## 6. V1 中输入重排的例子

假设 persistent batch 当前为：

```text
row 0 -> request A
row 1 -> request B
row 2 -> request C
row 3 -> request D
```

某个 attention backend 要求本轮输入顺序是：

```text
prefill requests first, decode requests later
```

如果当前：

```text
A: decode
B: prefill
C: decode
D: prefill
```

模型输入可能需要顺序：

```text
B, D, A, C
```

如果 persistent state 直接就是模型输入，就要重排整张 persistent table：

```text
row 0 -> B
row 1 -> D
row 2 -> A
row 3 -> C
```

这会导致：

- row 对 request 的映射变化；
- 旧状态要备份；
- CPU/GPU 拷贝复杂；
- 状态一致性难维护。

---

## 7. 为什么异步调度让 V1 更复杂？

vLLM 的异步调度目标是：

```text
GPU 正在执行 step N
CPU / Scheduler / Worker 准备 step N+1
```

这样可以重叠 CPU 和 GPU 工作：

```text
时间轴：

CPU:   prepare N      prepare N+1      prepare N+2
GPU:          run N          run N+1          run N+2
```

但如果 CPU 正在修改 persistent batch，而 GPU 还在读取上一轮 persistent batch，就可能出现 race：

```text
GPU 正在读 states[row=3]
CPU 同时把 states[row=3] 改成新请求
```

V1 用 async barrier 等方式规避，但这会增加同步、复杂度和维护风险。

# 第三部分：Persistent Batch V2

## 8. Persistent Batch V2 的核心思想

MRV2 的关键改造是：

```text
persistent state tensors 不再直接等于 per-step input tensors
```

它把两者拆开：

```text
Persistent State Table：稳定保存每个 active request 的状态
Per-step Input Tensors：每一轮根据当前执行顺序 gather 出来的模型输入
```

也就是说：

```text
persistent state 是“数据库”
per-step input 是“本轮查询结果”
```

这样 persistent state 不需要为了每一轮的执行顺序而大规模重排。

---

## 9. Stable Row：每个请求有稳定行

MRV2 会为每个 active request 分配一个固定 row：

```text
row 0 -> request A
row 1 -> request B
row 2 -> request C
row 3 -> request D
```

只要请求还活着，它的 row 就基本不变。

如果本轮 attention backend 要求顺序：

```text
B, D, A, C
```

不重排 persistent table，而是执行 gather：

```text
input_rows = [row(B), row(D), row(A), row(C)]
per_step_block_tables = gather(persistent_block_tables, input_rows)
```

这样：

```text
persistent state 保持稳定
per-step input 可以自由排序
```

---

## 10. Persistent Batch V2 的好处

### 10.1 去掉复杂重排

V1 中：

```text
为了满足本轮输入顺序，可能需要重排 persistent table
```

MRV2 中：

```text
persistent table 不动
本轮需要什么顺序就 gather 什么顺序
```

这样减少了 tensor-wide reorder。

---

### 10.2 去掉部分冗余状态

V1 需要 `CachedRequestState` 之类备份，因为 persistent tensor row 可能被覆盖或重排。

MRV2 中每个 active request 有稳定 row，状态不再因为本轮 batch 顺序变化而被覆盖，因此可以减少重复状态。

---

### 10.3 更适合异步调度

Persistent state 和 per-step input 解耦后：

```text
CPU 更新 persistent state
GPU 使用上一轮已经 gather 好的 per-step input
```

二者生命周期更清晰，更容易避免 race。

---

### 10.4 更适合不同 attention backend

不同 attention backend 对输入排序可能有不同要求：

- prefill / decode 是否分组；
- MLA / paged attention metadata 是否需要特殊排列；
- speculative decode 是否有 draft / verify 特殊顺序；
- CUDA Graph 是否需要固定 shape。

MRV2 可以让 attention backend 决定本轮 ordering，然后从 persistent state gather 出对应 input。

---

## 11. Persistent Batch V2 的抽象例子

假设系统最大支持：

```text
max_num_reqs = 1024
```

MRV2 预分配状态表：

```text
block_table_state: [1024, max_blocks_per_req]
seq_len_state:     [1024]
sampling_state:    [1024, ...]
request_state:     [1024, ...]
```

当前 active requests：

```text
req A -> row 10
req B -> row 77
req C -> row 5
```

本轮 Scheduler 输出顺序：

```text
scheduled = [B, C]
```

ModelRunner 做：

```text
rows = [77, 5]

block_tables = gather(block_table_state, rows)
seq_lens     = gather(seq_len_state, rows)
sampling     = gather(sampling_state, rows)
```

最终模型看到的是：

```text
batch row 0 -> request B
batch row 1 -> request C
```

但 persistent state 本身仍然是：

```text
row 10 -> A
row 77 -> B
row 5  -> C
```

# 第四部分：异步调度与内存传输优化

## 12. Async-first 是什么？

MRV2 的第二个核心原则是：

```text
async-first
```

意思是：异步执行不是后来补丁，而是从设计一开始就假设：

```text
CPU 负责调度和准备未来 step
GPU 负责执行当前 step
二者应该尽量重叠
中间尽量不发生 CPU-GPU 同步
```

理想时间线：

```text
time →
CPU:  schedule N+1 | prepare N+1 | process output N
GPU:       run N   |     run N+1  |     run N+2
```

---

## 13. 什么会破坏异步执行？

会破坏异步的操作包括：

### 13.1 显式同步

例如：

```python
torch.cuda.synchronize()
```

这会强制 CPU 等待 GPU 完成。

---

### 13.2 隐式同步

例如：

```python
x.item()
```

把 GPU tensor 的值取回 Python，CPU 必须等 GPU 算完。

又如某些未 pinned memory 的 CPU → GPU copy 可能不能真正异步。

---

### 13.3 CPU 修改 GPU 正在读取的 buffer

例如：

```python
# CPU pinned buffer
states[req_idx] = new_data
states_gpu = states.to("cuda", non_blocking=True)
```

如果下一步 CPU 又修改 `states`，而 GPU 还在异步读它，就可能出现 race。

---

## 14. MRV2 如何减少 CPU-GPU race？

MRV2 的做法是把：

```text
CPU persistent state
```

和：

```text
真正被异步 copy 的 pinned temporary tensor
```

分开。

简化理解：

```text
CPU persistent state：普通 CPU memory，可安全修改
temporary pinned copy：当前 step 传给 GPU 的快照
GPU input：从 temporary pinned copy 异步拷贝得到
```

这样 CPU 后续修改 persistent state 时，不会影响 GPU 正在读取的 temporary pinned copy。

---

## 15. StagedWriteTensor 是什么？

MRV2 中还引入了 `StagedWriteTensor` 这样的思想，用于优化大型状态张量的增量更新。

背景：

`block_table` 很大，如果每一步都把整张表从 CPU 拷贝到 GPU：

```text
[1024, max_blocks_per_req]
```

开销很大。

但每一步通常只修改很少部分：

- 某个请求新增一个 block；
- 某个请求 seq_len 增加；
- 某个请求结束；
- 某些 speculative tokens 被接受。

所以可以只传 diff。

---

## 16. StagedWriteTensor 的流程

可以理解为：

```text
1. 大状态 tensor 常驻 GPU
2. CPU 只记录本轮修改了哪些 row / offset / value
3. 把这些 diff 打包成连续小 buffer
4. 异步拷贝 diff buffer 到 GPU
5. 启动一个小 kernel 把 diff apply 到 GPU 大状态 tensor
```

伪代码：

```python
state.stage_write(row=2, start=3, value=[3, 1, 2])
state.stage_write(row=0, start=1, value=[-1, -2, -5])
state.apply_write()
```

逻辑是：

```text
CPU 不拷贝整张 block table
只把本轮变化传给 GPU
GPU kernel 在 device 上更新大状态表
```

---

## 17. StagedWriteTensor 的收益

| 收益 | 解释 |
|---|---|
| 减少 CPU→GPU 拷贝量 | 只传 diff，不传整张表 |
| 减少 Python 操作 | 多个小修改打包 |
| 更适合异步 | diff copy 可异步执行 |
| 减少同步点 | GPU 直接 apply |
| 适合 ragged update | 每个请求修改长度不同也能处理 |

它特别适合：

- block table；
- num_computed_tokens；
- speculative decoding accepted tokens；
- 混合 CPU/GPU 写入状态；
- 请求增删频繁的场景。

---

## 18. GPU-Native Input Preparation

MRV2 的另一个重要优化是：

```text
用 Triton kernel 在 GPU 上准备输入 metadata
```

比如：

- `input_ids`
- `positions`
- `query_start_loc`
- `seq_lens`
- `slot_mapping`
- 部分采样相关索引
- speculative decoding 的 accepted token 相关状态

传统方式：

```text
CPU Python 构建小 tensor
  ↓
拷贝到 GPU
  ↓
GPU forward
```

MRV2 方式：

```text
状态尽量保存在 GPU
  ↓
Triton kernel 直接构建 input metadata
  ↓
GPU forward
```

---

## 19. 为什么 input metadata 适合放到 GPU 构建？

因为这些工作通常有以下特点：

- 每一步都要做；
- 张量不大但很多；
- Python 循环多；
- CPU-GPU 小拷贝多；
- 逻辑规则相对固定；
- GPU 并行生成很快；
- decode 阶段 CPU overhead 占比高。

例如构造 `positions`：

```text
request A 当前 position = 100
request B 当前 position = 2048
request C 当前 position = 17
```

CPU 可以循环填，但 GPU kernel 也可以根据每个请求状态并行生成。

---

## 20. UVA：Universal Virtual Addressing

MRV2 某些路径会利用 UVA，让 GPU kernel 可以访问 CPU-resident tensor。

直观理解：

```text
某些很大的 CPU 数据不一定先完整复制到 GPU
GPU 通过统一虚拟地址访问需要的部分
```

典型用途：

```text
prefill_token_ids
```

如果 prompt token ids 很长、放在 CPU 上，MRV2 可以避免不必要的完整复制。

不过需要注意：

- UVA 访问 CPU 内存带宽远低于 HBM；
- 适合减少重复复制和简化路径；
- 不适合高频大量随机访问；
- 是否收益取决于 workload 和硬件。

# 第五部分：Triton 算子与模块架构优化

## 21. 为什么 MRV2 重视 Triton？

Triton 适合写 GPU kernel，尤其适合处理：

- 小型输入构建 kernel；
- sampling kernel；
- top-k / logprob 处理；
- index mapping；
- ragged update；
- layout transform；
- device-side bookkeeping。

MRV2 的思路是：

```text
不要让 CPU 用 Python 做大量小 bookkeeping
尽量让 GPU 用 Triton kernel 做这些规则明确的工作
```

这和前面 Triton 课的主线一致：

```text
Python 写 kernel
  ↓
Triton 编译成 GPU code
  ↓
减少 CPU overhead / 自定义内存访问
```

---

## 22. Triton-Native Sampler

采样模块原本也可能有较多开销。

普通 sampling 流程：

```text
logits
  ↓ logits processors
  ↓ temperature / top-k / top-p
  ↓ softmax
  ↓ multinomial / argmax
  ↓ next_token
```

问题：

- full-vocab logits 很大；
- full softmax 会 materialize 大张量；
- logprobs 可能需要保存全词表概率；
- 每个请求 sampling params 不同；
- speculative decoding 中一个请求可能对应多个 logits vector；
- CPU/GPU state 对齐复杂。

MRV2 将 sampling 大量逻辑迁移到 Triton kernel 中。

---

## 23. Gumbel-Max Sampling

Gumbel-Max 是一种从 categorical distribution 采样的方法。

给定概率分布：

```text
p_i = softmax(logits_i)
```

可以采样：

```text
sample = argmax(logits_i + gumbel_noise_i)
```

好处是：

```text
可以避免显式 materialize softmax 概率
```

MRV2 的 Triton Gumbel sampling kernel 使用 device-side stateless RNG，根据 seed 在 kernel 内生成随机数。

这样可以减少：

- softmax 中间张量；
- 显存峰值；
- CPU 采样控制；
- 不必要的 memory write/read。

---

## 24. Efficient Top-K Logprobs

V1 中一种低效做法是：

```text
先为整个 vocab 计算 logprobs
再从 full-vocab logprobs 中取 top-k
```

如果词表很大：

```text
vocab_size = 100k / 150k
```

这会产生大量内存开销。

MRV2 更合理的思路是：

```text
先从 logits 中找 top-k token
再只对 top-k token 计算 logprobs
```

这样减少：

- full-vocab logprobs materialization；
- peak GPU memory；
- memory bandwidth；
- prompt logprobs 场景下的内存尖峰。

---

## 25. Prompt Logprobs 的内存优化

Prompt logprobs 指的是：

```text
对 prompt 中每个 token 计算它在模型分布下的 logprob
```

长 prompt 时，如果一次性保存所有 token 的 full vocab logprobs，显存会爆炸。

MRV2 支持更细粒度 chunking：

```text
一个长 prompt 可以在内部切成更小 chunk 处理
```

这样减少显存峰值。

---

## 26. Sampling 与 speculative decoding 的兼容优化

投机解码中，一个请求不再只是对应一个 logits vector。

例如 draft 提出 5 个 token，target 验证时可能产生多个位置 logits：

```text
request A -> logits A0, A1, A2, A3, A4
request B -> logits B0, B1
```

如果把每个请求的 sampling state 复制扩展到每个 logits vector，状态会膨胀。

MRV2 使用类似：

```text
idx_mapping
```

的间接映射：

```text
logits vector i -> 对应 request state j
```

这样 kernel 内根据映射读取对应采样参数，而不是复制采样状态。

---

## 27. 模块架构优化：ModelState

MRV2 另一个核心是模块化。

vLLM 支持很多模型类型：

- 普通 decoder-only dense 模型；
- MoE 模型；
- MLA 模型；
- Mamba / hybrid 模型；
- 多模态模型；
- speculative decoding 模型；
- 带特殊 attention metadata 的模型；
- 内部私有模型。

如果所有逻辑都塞进一个巨大的 `gpu_model_runner.py`，代码会越来越难维护。

MRV2 引入 `ModelState` 抽象，把模型特定逻辑从通用 runner 中隔离出来。

---

## 28. ModelState 负责什么？

`ModelState` 可以理解为“模型专属适配层”。

它负责：

```text
add_request
remove_request
get_mm_embeddings
prepare_inputs
prepare_attn
prepare_dummy_inputs
CUDA Graph capture 相关逻辑
模型特殊输入
模型特殊 attention metadata
```

通用 ModelRunner 只关心：

```text
调度结果来了
  ↓
调用 ModelState 准备模型需要的东西
  ↓
调用 forward
  ↓
调用 sampler
  ↓
处理输出
```

这样新模型支持时，不必把特殊逻辑到处塞进主 runner。

---

## 29. 模块化带来的好处

| 好处 | 解释 |
|---|---|
| 降低主路径复杂度 | 通用执行逻辑更清晰 |
| 模型特定逻辑隔离 | Qwen、DeepSeek、Kimi、MLA、多模态等可独立适配 |
| 更容易测试 | 每类 ModelState 可以单独验证 |
| 更适合贡献者 | 开发者只关注自己模型家族 |
| 更适合未来扩展 | 新 attention / spec decode / CUDA Graph 逻辑可模块化添加 |

面试时可以这样说：

> **MRV2 不只是性能优化，也是软件架构优化。它把模型通用执行路径和模型特定状态准备分离，降低了 vLLM 支持多模型、多后端、多高级特性时的复杂度。**

---

# 第六部分：架构设计与代码执行流程

## 30. MRV2 执行流程总览

一次 decode step 中，MRV2 大致可以理解为：

```text
1. Scheduler 产生 scheduler_output
2. ModelRunner 接收本轮调度结果
3. 更新 persistent state
4. 对大型状态使用 diff / staged write 更新 GPU state
5. 根据本轮 request ordering gather per-step input
6. Triton kernel 在 GPU 上准备 input_ids / positions / metadata
7. ModelState 准备模型特定输入和 attention metadata
8. 调用 model forward
9. 得到 logits / hidden states
10. Triton sampler 执行采样或 logprobs
11. 输出 token 异步拷贝回 CPU
12. CPU 在下一轮调度时消费结果
```

---

## 31. 和 V1 的主要区别

| 维度 | V1 ModelRunner | MRV2 |
|---|---|---|
| Persistent batch | 状态和输入耦合 | 状态和 per-step input 解耦 |
| Request row | 可能因重排变化 | active 生命周期内稳定 |
| 输入构建 | CPU/Python 较多 | GPU/Triton 更多 |
| block table 更新 | 可能全量或复杂重排 | staged diff update |
| async scheduling | 后期补丁式支持 | async-first 设计 |
| CPU-GPU 同步 | 更容易出现 barrier | 目标是减少同步点 |
| sampling | CPU/PyTorch 逻辑更多 | Triton-native sampler |
| 模块化 | 大文件复杂 | ModelState 隔离模型逻辑 |
| spec decode | 状态对齐复杂 | GPU-side prep 更自然 |
| CUDA Graph | 混杂在 runner 中 | 更显式管理 |

---

## 32. Persistent state 更新流程

请求进入或状态变化时：

```text
new request A
  ↓
分配 persistent row
  ↓
写入 sampling params / block table / seq len 等状态
```

decode 每步生成新 token 后：

```text
request A accepted 1 token
  ↓
num_computed_tokens += 1
  ↓
seq_len += 1
  ↓
如果跨 block boundary，追加 new block id
  ↓
stage_write 更新 block table diff
```

请求结束：

```text
request A finished
  ↓
释放 row
  ↓
释放 KV blocks
  ↓
清理状态
```

抢占 / preemption：

```text
MRV2 可把 preemption 当作 completion
resume 时重新 add request state
```

这样避免复杂的半活跃状态维护。

---

## 33. Per-step input 构建流程

本轮 Scheduler 输出：

```text
scheduled reqs = [B, D, A]
```

attention backend 可能要求该顺序。

MRV2：

```text
rows = [row(B), row(D), row(A)]
  ↓
gather persistent state
  ↓
得到本轮 input batch
```

然后 GPU 准备：

```text
input_ids
positions
query_start_loc
seq_lens
slot_mapping
```

---

## 34. Model forward 执行

模型 forward 仍然是常规 Transformer 推理：

```text
embedding
  ↓
layer 0 attention + MLP
  ↓
layer 1 attention + MLP
  ↓
...
  ↓
final norm
  ↓
lm_head
  ↓
logits
```

MRV2 的优化不是改 Transformer 数学，而是优化：

```text
forward 前：输入准备
forward 中：metadata / attention 配合
forward 后：sampling 和输出处理
```

---

## 35. Output 异步返回

MRV2 中输出从 GPU 到 CPU 的传输也尽量异步。

普通同步方式：

```text
GPU sample next token
CPU 等待 token
CPU 处理输出
CPU 再准备下一步
```

异步方式：

```text
GPU sample next token
token 在单独 stream 异步 D2H
CPU 同时准备其他工作
下一轮需要时再消费
```

这样减少 CPU-GPU 同步。

---

## 36. 与 CUDA Graph 的关系

CUDA Graph 要求执行形态稳定。

MRV2 通过：

- 稳定 persistent state；
- per-step input 与 persistent state 解耦；
- 显式 CUDA Graph 管理；
- GPU-native input prep；
- 模块化 ModelState；
- 减少 CPU-GPU sync；

使得 CUDA Graph 更容易在 decode 稳态场景下生效。

不过 MRV2 并不等于 CUDA Graph。两者关系是：

```text
MRV2：重构 model runner 执行路径
CUDA Graph：减少 GPU kernel launch overhead
```

MRV2 可以为 CUDA Graph 提供更干净的执行基础。

---

## 37. 与 torch.compile 的关系

torch.compile 主要优化模型计算图：

```text
PyTorch model graph -> FX / Inductor / Triton
```

MRV2 主要优化模型执行框架：

```text
request state -> input metadata -> forward -> sampler -> output
```

两者可以配合：

```text
MRV2 准备更稳定的输入和执行路径
torch.compile 编译模型子图
CUDA Graph capture 稳定执行图
```

---

## 38. 与 speculative decoding 的关系

投机解码的复杂点是：

```text
每个请求每轮可能接受不同数量的 draft tokens
GPU 上 rejection sampler 得到 accepted count
CPU 如果必须马上知道 accepted count，就会发生同步
```

MRV2 的 GPU-native prep 可以让后续输入构建直接消费 GPU 上的 rejection sampling 结果，从而减少 CPU-GPU 同步。

流程：

```text
GPU rejection sampler 得到 accepted tokens
  ↓
GPU input prep kernel 根据 accepted tokens 更新下一步 input
  ↓
CPU 不必立即同步读取所有中间结果
```

这就是 MRV2 对 speculative decoding 友好的关键。

---

# 第七部分：性能对比与优化效果

## 39. MRV2 主要提升来自哪里？

MRV2 的性能收益主要来自：

1. **减少 CPU bookkeeping**
   - 不再每步大量 Python 构建输入；
   - 不再复杂重排 persistent batch。

2. **减少 CPU-GPU 拷贝**
   - 大状态常驻 GPU；
   - 只传 diff；
   - input metadata 直接 GPU 构建。

3. **减少 CPU-GPU 同步**
   - async-first；
   - output 异步返回；
   - spec decode 结果可被 GPU input prep 消费。

4. **采样更高效**
   - Triton sampler；
   - 避免显式 softmax materialization；
   - top-k logprobs 更省显存。

5. **更适合复杂特性组合**
   - speculative decoding；
   - CUDA Graph；
   - multimodal；
   - heterogeneous model state。

---

## 40. 哪些场景收益更明显？

MRV2 更可能在这些场景收益明显：

| 场景 | 原因 |
|---|---|
| 小模型 + 强 GPU | GPU forward 很快，CPU overhead 占比高 |
| Decode-heavy | 每步都要输入构建和采样 |
| 高并发 continuous batching | persistent batch 更新频繁 |
| Speculative decoding | GPU accepted tokens 可直接驱动输入构建 |
| 多 sampling params / logprobs | Triton sampler 和 idx_mapping 有收益 |
| 长 prompt logprobs | chunking 降低显存峰值 |
| CUDA Graph 场景 | 更稳定执行路径利于 capture |

---

## 41. 哪些场景收益可能不明显？

收益可能不明显或需要谨慎：

| 场景 | 原因 |
|---|---|
| 大模型 prefill compute-bound | 时间主要花在大 GEMM / attention |
| batch 极大且 GPU 已满 | CPU overhead 被摊薄 |
| unsupported feature fallback | MRV2 不支持时回退 |
| attention backend 本身是瓶颈 | input prep 优化无法解决所有问题 |
| 多机通信瓶颈 | 通信占主导 |
| 用户开启复杂 logits processor | 如果特性尚未完全支持，可能 fallback |

---

## 42. 官方性能数据如何理解？

官方博客中用小模型 `Qwen3-0.6B` 在 `1×GB200` 上测试，是为了放大 host-side overhead 的影响。因为小模型 forward 很快，如果 CPU 输入准备慢，就更容易成为瓶颈。MRV2 在该场景通过把输入准备搬到 GPU 等方式获得显著吞吐提升。

这说明：

```text
MRV2 的重点不是让大 GEMM 变快
而是让模型执行路径周边的 CPU / bookkeeping / sampler 更轻
```

所以面试中不能说“MRV2 优化了矩阵乘法本身”，更准确说法是：

> **MRV2 主要优化模型执行框架中的输入构建、状态管理、采样、异步调度和模块化，而不是改变 Transformer forward 的数学计算。**

# 第八部分：和前面课程知识串联

## 43. MRV2 和 PagedAttention

PagedAttention 需要大量 metadata：

```text
block_table
slot_mapping
seq_lens
query_start_loc
```

V1 中这些 metadata 很多由 CPU 构建并传 GPU。

MRV2 将更多 metadata 构建放到 GPU/Triton 上，并通过 persistent state + gather + staged diff 管理 block table。

所以：

```text
PagedAttention 解决 KV Cache 显存管理
MRV2 优化 PagedAttention 所需 metadata 的构建和维护
```

---

## 44. MRV2 和 CUDA Graph

CUDA Graph 解决：

```text
CPU launch overhead
```

MRV2 解决：

```text
CPU bookkeeping overhead
CPU-GPU sync
输入准备不稳定
```

两者可以互补：

```text
MRV2 让执行路径更稳定
CUDA Graph replay 减少 kernel launch
```

---

## 45. MRV2 和 Triton

前面 Triton 课讲过：

```text
Triton 用 Python 写 GPU kernel
```

MRV2 使用 Triton 做：

- input metadata preparation；
- staged update apply；
- sampling；
- gumbel-max；
- top-k logprobs；
- prompt logprobs chunking；
- index mapping。

所以 Triton 在 MRV2 中不是单纯写 attention 算子，而是深入到了模型执行框架的 bookkeeping 层。

---

## 46. MRV2 和 Speculative Decoding

Spec decode 的关键状态来自 GPU：

```text
accepted tokens
rejected tokens
corrected token
accepted count
```

如果每轮都把这些信息同步到 CPU，再由 CPU 准备下一轮输入，会破坏异步。

MRV2 希望：

```text
GPU 上的 spec decode 结果
  ↓
GPU 上的 input prep kernel
  ↓
下一轮 forward
```

这减少同步，是 MRV2 与投机解码结合的重要价值。

---

## 47. MRV2 和性能分析

如果用 Nsight Systems 看 V1 可能发现：

```text
GPU kernel 之间有空洞
CPU 在准备输入 / 采样 / 同步
```

MRV2 目标是减少这些空洞。

在 profiling 中可观察：

- CPU Python 时间是否下降；
- cudaMemcpyAsync 小拷贝是否减少；
- cudaStreamSynchronize 是否减少；
- decode kernel 间 gap 是否减少；
- sampler 显存峰值是否下降；
- TPOT / output tok/s 是否改善。

# 第十部分：面试问答

## 51. 面试题 1：ModelRunner 在 vLLM 中负责什么？

答：

ModelRunner 位于 Worker 内部，是 Scheduler 输出和模型 forward 之间的执行组件。它负责维护当前 batch 的请求状态，构建 `input_ids`、`positions`、attention metadata、block tables、slot mapping、seq_lens 等模型输入，调用模型 forward，执行 sampler，并更新输出 token 和请求状态。它是 vLLM 中最贴近模型执行的框架层。

---

## 52. 面试题 2：为什么需要 ModelRunner V2？

答：

V1 ModelRunner 随着 persistent batch、async scheduling、speculative decoding、CUDA Graph、多模型支持等功能不断叠加，出现了状态耦合、CPU bookkeeping 重、异步支持脆弱、采样和输入构建复杂等问题。MRV2 通过重新设计 persistent batch、GPU-native input preparation、async-first 执行、Triton-native sampler 和 ModelState 模块化，降低 CPU overhead 和同步开销，提高可维护性和性能。

---

## 53. 面试题 3：什么是 Persistent Batch？

答：

Persistent Batch 是一种减少每步输入构建开销的优化。因为连续 decode step 中运行的请求集合通常变化很小，所以没必要每轮从零构建 block tables、sampling params、seq_lens 等输入张量，而是维护一份持久 batch state，每轮只增量更新变化部分。

---

## 54. 面试题 4：V1 Persistent Batch 的问题是什么？

答：

V1 把 persistent state tensor 直接作为 per-step model input 使用，导致持久状态和本轮输入布局耦合。如果请求加入、结束，或者 attention backend 要求特殊排序，就可能需要重排整张 persistent batch，代码复杂且容易出错。同时为了防止状态被覆盖，还需要维护冗余的 `CachedRequestState`。异步调度下 CPU/GPU 同时访问状态也更容易出现 race。

---

## 55. 面试题 5：Persistent Batch V2 怎么改进？

答：

Persistent Batch V2 将 persistent state 和 per-step input 解耦。每个 active request 在生命周期内拥有一个稳定 row，persistent table 不随每轮执行顺序重排。每轮执行时，根据 Scheduler 或 attention backend 确定的 request ordering，从 persistent state 中 gather 出本轮 input tensor。这样既保留增量更新收益，又避免复杂重排和冗余状态。

---

## 56. 面试题 6：为什么 MRV2 要把输入准备搬到 GPU？

答：

Decode 阶段每步 GPU 计算相对短，而 CPU 构建 `input_ids`、`positions`、`query_start_loc`、`seq_lens`、block table 等小张量会成为瓶颈。把这些输入准备逻辑用 Triton kernel 放到 GPU 上，可以减少 Python overhead 和 CPU-GPU 小拷贝，也更适合异步调度和投机解码，因为某些下一步输入依赖 GPU 上刚产生的结果。

---

## 57. 面试题 7：什么是 async-first？

答：

async-first 指 MRV2 从设计上假设 CPU 和 GPU 应该重叠执行：GPU 执行 step N 时，CPU 准备 step N+1，输出也尽量异步传回 CPU。它要求避免显式或隐式 CPU-GPU 同步，避免 CPU 修改 GPU 正在读取的 buffer，并用更清晰的状态生命周期消除 race。

---

## 58. 面试题 8：StagedWriteTensor 解决什么问题？

答：

它解决大型状态张量频繁小更新的问题，例如 block table。MRV2 不每步把整张表从 CPU 拷贝到 GPU，而是让大状态 tensor 常驻 GPU，CPU 只记录本轮修改的 diff，把 diff 打包传到 GPU，再用一个 kernel apply 到状态表。这样减少拷贝量、Python 操作和同步开销，适合 ragged update。

---

## 59. 面试题 9：MRV2 的 Triton-native sampler 有什么优化？

答：

MRV2 用 Triton 重写大量采样逻辑，包括 Gumbel-Max sampling、top-k logprobs、prompt logprobs chunking 和 speculative decoding 的 idx_mapping。它可以避免显式 materialize softmax，先找 top-k logits 再计算 selected logprobs，减少显存峰值，并让每个 logits vector 通过间接映射读取对应请求的 sampling state，提升对投机解码和复杂采样参数的兼容性。

---

## 60. 面试题 10：ModelState 是什么？

答：

ModelState 是 MRV2 引入的模型特定逻辑抽象。它封装 add/remove request、multimodal embeddings、prepare_inputs、prepare_attn、dummy inputs、CUDA Graph capture 等模型相关逻辑，让通用 ModelRunner 只关注公共执行路径。这样可以把 Qwen、DeepSeek、Kimi、多模态、hybrid attention 等模型的特殊逻辑隔离出来，降低主 runner 复杂度。

---

## 61. 面试题 11：MRV2 和 CUDA Graph 有什么关系？

答：

MRV2 和 CUDA Graph 是不同层面的优化。MRV2 优化 ModelRunner 的状态管理、输入构建、异步调度和采样；CUDA Graph 优化重复 GPU kernel launch 的 CPU overhead。MRV2 通过更稳定、更 GPU-native 的执行路径和显式 CUDA Graph 管理，使 decode 场景更容易被 capture 和 replay。

---

## 62. 面试题 12：MRV2 为什么对投机解码更友好？

答：

投机解码中每轮 accepted tokens、rejection sampling 结果等都在 GPU 上产生。如果 V1 需要把这些结果同步回 CPU 再准备下一步输入，就会引入 CPU-GPU 同步。MRV2 的 input preparation 在 GPU 上执行，可以直接消费 GPU 上的 rejection sampling 结果，减少同步点，因此更适合 speculative decoding 与 async scheduling 的组合。

---

## 63. 面试题 13：MRV2 主要优化矩阵乘法本身吗？

答：

不是。MRV2 主要优化模型执行框架周边，包括 persistent batch 状态管理、input metadata preparation、sampling、CPU-GPU overlap、异步输出和模块化。矩阵乘法本身通常由 cuBLAS、Triton、CUTLASS 或量化 kernel 负责。MRV2 的收益更多来自减少 CPU overhead、减少小拷贝和同步、提升调度执行路径效率。

---

## 64. 面试题 14：什么时候 MRV2 收益更明显？

答：

当 host-side overhead 占比较高时收益更明显，例如小模型配强 GPU、decode-heavy、高并发 continuous batching、speculative decoding、复杂 sampling/logprobs、CPU 输入构建较重的场景。如果瓶颈主要是大模型 prefill compute、跨机通信、attention kernel 本身或显存容量，MRV2 收益可能不明显。

---

## 65. 面试题 15：如何用 profiling 验证 MRV2？

答：

可以对比 MRV1/MRV2 的 TTFT、TPOT、output tokens/s、CPU utilization、GPU kernel gap、cudaMemcpyAsync 次数、cudaStreamSynchronize 次数和 sampler 显存峰值。用 PyTorch Profiler 看输入构建和 sampler 是否下降，用 Nsight Systems 看 GPU timeline 空洞是否减少、CPU-GPU 同步是否减少、CUDA Graph 是否更稳定。

# 第十一部分：本节课总结

本节课主线：

```text
ModelRunner 是 vLLM 中把 Scheduler 输出转成模型输入并执行 forward/sampling 的核心组件
        ↓
V1 为减少输入构建开销引入 Persistent Batch
        ↓
但 V1 把 persistent state 与 per-step input 耦合，导致重排复杂、状态冗余、异步困难
        ↓
MRV2 将 persistent state 和本轮 input 解耦
        ↓
每个 active request 拥有 stable row，本轮执行通过 gather 生成 input
        ↓
大型状态用 StagedWriteTensor 做 diff 更新
        ↓
input_ids / positions / seq_lens / query_start_loc 等 metadata 用 GPU/Triton 构建
        ↓
sampling 也改成 Triton-native，减少 softmax/logprobs 显存和 CPU overhead
        ↓
通过 async-first 设计减少 CPU-GPU 同步
        ↓
通过 ModelState 模块化隔离模型特定逻辑
        ↓
最终提升性能、降低复杂度，并更好支持 CUDA Graph / speculative decoding / 多模型扩展
```

最重要的理解：

> **ModelRunner V2 不是一个新模型，也不是一个新算子，而是 vLLM 模型执行核心的一次系统性重构：它把 request state、input preparation、sampling、async execution 和 model-specific logic 重新拆分，使 vLLM 在 decode-heavy 和复杂特性组合场景下更高效、更可维护。**
