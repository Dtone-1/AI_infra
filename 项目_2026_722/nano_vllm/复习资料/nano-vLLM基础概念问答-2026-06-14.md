# 基础概念问答复习笔记

## 整理范围说明

本文件整理的是从最近一次【复习整理起点】之后，到当前对话结束之间的基础概念问答内容。整理范围包括：Benchmark、推理性能指标、warmup、Decode batch size、最大上下文长度、长上下文与 KV Cache、EOS token、next token 生成流程、KV Cache block 与 sequence 的关系、推理显存构成等问题。

## 问答复习整理

## 1. 问题：Benchmark 层 / 性能测试层 / 用户调用层，这里的 benchmark 什么意思？

### 复习版答案

**benchmark = 性能测试 / 基准测试。**

在大模型推理里，benchmark 用固定测试方式衡量系统性能，例如：

```text
吞吐量 throughput
延迟 latency
TTFT 首 token 延迟
TPOT 每 token 时间
显存占用
并发能力
```

它不是模型核心代码，而是站在用户调用层测试推理引擎表现。比如 `bench.py` 通常负责构造 prompts、调用 `llm.generate()`、记录时间、统计 token 数、计算吞吐和延迟。

一句话：

> **benchmark 是给推理系统“测速度、测吞吐、测延迟、测显存”的性能测试脚本。**

---

## 2. 问题：推理阶段的测试指标有哪些，请大致列举一下

### 复习版答案

大模型推理指标主要分为几类：

### 1）延迟类

```text
End-to-End Latency：请求到完整回答结束的总时间
TTFT：Time To First Token，首 token 延迟，主要受 Prefill 影响
TPOT：Time Per Output Token，每个输出 token 的平均生成时间
ITL：Inter-Token Latency，相邻 token 输出间隔
```

### 2）吞吐类

```text
tokens/s：单位时间生成多少 token
requests/s / QPS：单位时间完成多少请求
output tokens/s：只统计生成 token
total tokens/s：输入 + 输出 token 都统计
```

### 3）显存类

```text
Peak GPU Memory：峰值显存
KV Cache Memory：KV Cache 占用
Memory Utilization：显存利用率
```

### 4）并发与资源类

```text
Concurrency：同时处理的请求数
Batch Size：一次 forward 中处理的 sequence 数
Queueing Time：排队时间
GPU Utilization：GPU 利用率
CPU Utilization：CPU 调度开销
```

### 5）稳定性与质量

```text
是否 OOM
是否超时
吞吐是否波动
长时间压测是否崩溃
输出是否乱码、重复、提前结束
```

一句话：

> **延迟看用户体验，吞吐看系统能力，显存看并发上限，GPU 利用率看硬件是否吃满。**

---

## 3. 问题：warmup 推理中，这里的 warmup 什么意思？

### 复习版答案

**warmup = 预热推理。**

正式 benchmark 前先跑一次或几次推理，但不计入测试结果。目的不是看输出，而是提前消耗首次运行开销，例如：

```text
CUDA / PyTorch 上下文初始化
模型权重搬到 GPU
显存分配
KV Cache 初始化
kernel 加载或编译
算子缓存
推理引擎内部状态初始化
```

如果不 warmup，第一次推理会包含大量额外初始化时间，导致 benchmark 结果偏慢、不准确。

一句话：

> **warmup 是正式性能测试前的预热，让模型、CUDA、显存和推理引擎先进入稳定运行状态。**

---

## 4. 问题：Decode 阶段通常每条 sequence 每轮只生成 1 个 token。如果当前有 512 条 running sequence，那么一轮 decode 的 batch size 可能就是 512。怎么理解，是不是说有 512 个用户同时在 ask，但是每个用户依旧对话一次生成 1 个 token，batch size 存的是 512 个提示词吗？

### 复习版答案

大方向对，但要修正一点：

> **Decode 阶段 batch size = 512，不是 batch 里存 512 个完整 prompt，而是这一轮有 512 条正在生成的 sequence，每条 sequence 输入最新的 1 个 token，并结合自己的 KV Cache，各自生成 1 个新 token。**

普通情况下：

```text
512 条 running sequence ≈ 512 个正在生成的用户请求
```

但更准确地说是 sequence，因为 beam search / best_of 等场景中一个请求可能对应多条 sequence。

Prefill 阶段处理完整 prompt，并生成对应 KV Cache。  
Decode 阶段不再反复输入完整 prompt，而是：

```text
输入：每条 sequence 的最新 token
读取：每条 sequence 的历史 KV Cache
输出：每条 sequence 的 next token
```

如果有 512 条 sequence，一轮 decode 后总共生成 512 个 token。

一句话：

> **Decode batch size = 512，表示这一轮有 512 条 sequence 同时各生成 1 个 token；完整历史已经存在 KV Cache 里。**

---

## 5. 问题：最大上下文长度是什么意思，指的是 prompt tokens + generated tokens 吗，还是一个聊天对话框所有历史记录？例如 GPT 的一个聊天对话框可以无限聊下去吗？

### 复习版答案

**最大上下文长度 = 模型一次推理最多能看见的 token 总数。**

通常包括：

```text
prompt tokens + generated tokens
```

也就是：

```text
input tokens + output tokens <= max_context_len
```

在多轮聊天中，历史记录如果被带入当前输入，就会占用 prompt tokens。所以聊天窗口里的历史不是无限进入模型的。

聊天界面可以一直聊，但模型每次回答时只能使用当前上下文窗口内的内容。对话太长时，系统可能会：

```text
保留最近内容
保留重要历史
压缩/摘要旧内容
丢弃不相关内容
```

要区分三个概念：

```text
上下文窗口：本次推理能直接看到的 token 范围
记忆：系统可能长期保存的用户偏好或背景
聊天记录：界面上保存的历史消息
```

一句话：

> **最大上下文长度限制的是模型一次推理能处理的 token 总量；聊天可以持续，但模型不能无限读取完整历史。**

---

## 6. 问题：最大上下文宽度越大，KV Cache 越多，回答就会越全面吗，还有什么好处？

### 复习版答案

不一定。**上下文越大，只表示模型一次推理能容纳更多 token，不代表回答一定更全面、更正确。**

主要好处：

```text
能放更长 prompt
能保留更多历史对话
能分析更长文档、代码、论文、课程字幕
RAG 场景能放更多检索结果
复杂任务中更容易保留约束和背景
```

但长上下文也有问题：

```text
无关内容多会干扰模型
长上下文中间信息可能被忽略
回答长度还受 max_new_tokens 限制
模型能力本身仍然有限
Prefill 更慢，TTFT 增加
KV Cache 更大，显存压力更高
并发能力可能下降
```

所以：

```text
大上下文 = 看更多的能力
不等于 = 一定答得更好
```

一句话：

> **大上下文提供“更多材料容量”，但回答质量还取决于材料相关性、结构清晰度、模型能力、提示词和生成长度。**

## 7. 问题：EOS 通常由 tokenizer 或模型 config 提供。这个怎么理解，tokenizer 生成的 id 每个 sequence 都不同吗，所以每次推理的过程这些都会变？

### 复习版答案

**EOS = End Of Sequence，序列结束 token。**

模型生成到 EOS token 时，推理引擎通常认为这条 sequence 已结束，可以停止生成。

“EOS 由 tokenizer 或模型 config 提供”的意思是：

> **推理引擎不应该自己猜哪个 token 表示结束，而应该从当前模型的 tokenizer/config 中读取 `eos_token_id`。**

要区分两种 id：

### 1）tokenizer 的词表映射 id

同一个模型和 tokenizer 下通常固定：

```text
"你好" -> 某个固定 token id
"<eos>" -> eos_token_id
```

同一文本一般会得到相同 token ids。

### 2）每条 sequence 的 input_ids / generated_ids

这个会变，因为不同请求文本不同、生成结果不同。

EOS token id 对同一模型通常固定；不同的是：

```text
不同 sequence 什么时候生成 EOS
是否因为 max_tokens 截断
是否 ignore_eos
```

一句话：

> **tokenizer/config 提供固定的特殊 token id；推理过程中动态变化的是每条 sequence 的 token 内容和生成状态。**

---

## 8. 问题：决定模型输出下一个 token 的是什么参数，KV Cache 历史和最新的一个 token 联合生成下一个 token，这个过程发生了什么？

### 复习版答案

要分清两个层面：

```text
模型权重 + 当前上下文 -> 计算 logits
logits + 采样参数 -> 选出 next token
```

决定因素主要有：

```text
模型权重：Embedding、Attention、MLP、LayerNorm、LM Head 等参数
上下文：历史 KV Cache + 最新 token
采样参数：temperature、top-k、top-p、eos、max_tokens 等
```

Decode 过程简化如下：

```text
1. 最新 token id 经过 embedding 变成向量
2. 在每层 Transformer 中计算当前 token 的 Q/K/V
3. 当前 token 的 Q 去匹配历史 KV Cache 中的 K
4. 根据注意力权重汇总历史 V
5. Attention + MLP 多层加工得到最终 hidden state
6. LM Head 把 hidden state 映射成 logits
7. sampler 根据 logits 和采样参数选出 next token
8. 新 token 的 K/V 追加进 KV Cache，供下一轮使用
```

KV Cache 的作用不是直接决定答案，而是保存历史 token 的 K/V，避免每次重新计算完整历史。

一句话：

> **KV Cache 保存历史，最新 token 发起查询，Attention 从历史中取信息，模型层层加工得到 logits，采样器再选出下一个 token。**

## 9. 问题：block_size = 256，sequence 长度 = 600，那么该 sequence 至少需要 ceil(600 / 256) = 3 个 block。KV Cache 的数量和 sequence 一样多吗？

### 复习版答案

不是。要区分三个层级：

```text
sequence 数量
token 数量
KV Cache block 数量
```

逻辑上，每条 sequence 都有自己的历史 KV Cache。  
物理上，KV Cache 是按 block 存储和分配的，一条 sequence 可能占多个 block。

例如：

```text
block_size = 256
sequence_len = 600
需要 block 数 = ceil(600 / 256) = 3
```

表示：

```text
block 0：token 0 ~ 255 的 KV Cache
block 1：token 256 ~ 511 的 KV Cache
block 2：token 512 ~ 599 的 KV Cache
```

如果有多条 sequence，总 block 数大致是：

```text
sum(ceil(sequence_len_i / block_size))
```

在 vLLM / nano-vLLM 中，系统通常维护全局物理 block 池，每条 sequence 通过 block table 记录自己占用了哪些物理 block。

一句话：

> **sequence 是请求单位，token 是生成单位，block 是 KV Cache 显存分配单位；1 条 sequence 不等于 1 个 block。**

---

## 10. 问题：GPU 总显存 - 模型权重显存 - 临时运行开销 = 可用于 KV Cache 的显存，这些比例大概是多少，什么东西最吃显存？

### 复习版答案

推理显存可以看成：

```text
GPU 总显存
- 模型权重显存
- 临时运行开销
- 系统/框架预留
= 可用于 KV Cache 的显存
```

### 1）模型权重显存

固定成本，近似：

```text
权重显存 ≈ 参数量 × 每个参数字节数
```

常见估算：

```text
7B FP16/BF16 约 14GB
14B FP16/BF16 约 28GB
70B FP16/BF16 约 140GB
```

### 2）临时运行开销

包括：

```text
CUDA context
中间 activation
logits buffer
attention workspace
采样 buffer
通信 buffer
框架预留和碎片
```

推理阶段一般比训练少，粗略可能占总显存 5%~15%。

### 3）KV Cache 显存

动态成本，随这些因素增长：

```text
并发 sequence 数
上下文长度
生成长度
层数
KV heads
head_dim
数据类型
```

近似关系：

```text
KV Cache ∝ 2 × layers × kv_heads × head_dim × token数 × bytes
```

其中 2 表示 K 和 V。

### 什么最吃显存？

```text
低并发、短上下文：模型权重通常最吃显存
高并发、长上下文：KV Cache 可能成为最大瓶颈
量化模型后：权重变小，KV Cache 更容易成为主要显存压力
```

一句话：

> **推理阶段显存大户主要是模型权重和 KV Cache；权重是固定成本，KV Cache 是随上下文和并发增长的动态成本。**
