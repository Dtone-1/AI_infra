## 1. 从 nano-vLLM 框架角度讲，一个请求从进入系统到最终结束的完整生命周期是什么？

### 面试中暴露的问题
你第一次从模型计算角度回答了 Attention、MLP、LM Head，面试官随后明确要求你从 **nano-vLLM 框架层**重新回答。第二次虽然提到了 `Sequence`、`waiting/running/finished`，但没有把 `LLMEngine → Scheduler → BlockManager → ModelRunner → Sampler → Scheduler` 串起来。

### 建议面试回答

一个请求进入 nano-vLLM 以后，我会把它分成“请求管理”和“模型执行”两条线来看。首先 `LLMEngine` 接收用户请求，Tokenizer 把文本转成 token id，然后封装成一个 `Sequence`，新请求先进入 Scheduler 的 waiting 队列。之后每一轮推理，Scheduler 会根据当前显存里的 KV Cache Block、token 预算和 running 请求情况决定这一轮哪些请求可以执行。

如果是第一次执行，这个 Sequence 走 Prefill；Scheduler 会让 BlockManager 给它分配 KV Cache 对应的物理 Block，并生成这个请求的 block table。Scheduler 再把本轮要执行的 Sequence 和相关元数据交给 ModelRunner。ModelRunner 根据这是 Prefill 还是 Decode 准备 token、position、slot mapping、block table 等输入，然后真正执行模型 forward。

模型最后产生 logits，Sampler 采出下一个 token，再把 token 写回 Sequence。这个 Sequence 如果还没有遇到 EOS，也没有达到最大输出长度，就继续留在 running 队列，下一轮再执行 Decode；Decode 每次通常只处理最新的一个 token，同时复用前面已经保存的 KV Cache。如果请求完成，Scheduler 把它标记为 finished，同时让 BlockManager 回收这个请求占用的 KV Block。然后 Engine 把生成结果返回给用户。

所以整个生命周期可以概括成：

`请求进入 → Sequence → waiting → Scheduler 调度 → BlockManager 分配缓存 → ModelRunner 执行 Prefill/Decode → Sampler 生成 token → 更新 Sequence → 继续 Decode 或 finished → 回收缓存 → 返回结果。`

## 2. ModelRunner 和 BlockManager 到底是什么关系？两者之间传递什么信息？

### 面试中暴露的问题
面试中你回答“BlockManager 相当于是 ModelRunner 的一个子系统”，这个说法不准确。面试官继续追问“ModelRunner 传什么给 BlockManager”时，你没有回答出来。

### 建议面试回答

我会先澄清一点：**BlockManager 一般不是 ModelRunner 的子模块，它们属于不同职责。**

BlockManager 主要在调度侧负责“显存里的 KV Cache 放在哪里”，也就是管理物理 Block 的分配、释放以及一个请求对应哪些 Block。ModelRunner 主要在执行侧负责“这一轮模型怎么算”，它最终需要知道请求的 KV Cache 在 GPU 的哪些位置。

所以严格来说，并不是 ModelRunner 主动把数据传给 BlockManager 再让它分配。更典型的流程是：Scheduler 在调度请求时调用 BlockManager，BlockManager 给 Sequence 分配物理 Block，并维护 block table；然后 Scheduler 把 Sequence、block table、slot mapping 等执行元数据交给 ModelRunner。ModelRunner 根据这些元数据准备 Attention 的输入，让 Attention Kernel 知道当前 token 的 K、V 应该写到哪个物理位置，以及历史 KV 应该从哪些 Block 读取。

可以把两者简单理解成：

- BlockManager：**管地址、管显存、管生命周期。**
- ModelRunner：**拿着这些地址去真正执行模型。**
- Scheduler：**在两者中间做协调。**

## 3. BlockManager 这个类从初始化、allocate 到 deallocate 到底做了什么？

### 面试中暴露的问题
面试官明确让你解释：

- `__init__` 做什么？
- `allocate` 做什么？
- `deallocate` 做什么？

你回答“管理 Cache”，但没有进入实现层。

### 建议面试回答

BlockManager 的本质是给 Paged KV Cache 做“显存页管理”。

初始化的时候，它首先知道系统一共预留了多少 KV Cache Block，每个 Block 能存多少个 token。然后建立一个空闲 Block 池，比如所有 Block 一开始都在 free list 里面。同时它还会维护一个 Block 到引用次数、哈希值或者 Sequence block table 的相关状态，具体数据结构根据实现会有区别。

当一个新 Sequence 做 Prefill 时，`allocate` 会先根据这个请求当前需要保存多少 token，计算需要几个 Block。例如 block size 是 64，一个 150 token 的请求至少需要 3 个 Block。然后从空闲池里面取出对应数量的物理 Block，把这些 Block 的编号记录到这个 Sequence 的 block table 中。以后 Attention 并不要求这些 Block 在物理显存上连续，只需要根据 block table 找到真实位置。

Decode 阶段每生成新的 token，如果当前最后一个 Block 还有空间，就继续写；如果最后一个 Block 已经满了，就再从 free list 取一个新 Block，追加到 block table。

当请求结束，或者因为抢占需要释放缓存时，`deallocate/free` 就遍历这个请求占用的物理 Block，把引用计数减掉；如果已经没有 Sequence 使用这个 Block，就重新放回空闲池，让之后的请求复用。

所以 BlockManager 解决的核心问题是：**KV Cache 不再要求每个请求占一整块连续显存，而是像操作系统分页一样，以固定大小 Block 动态分配和回收。**

## 4. Prefix KV Cache 为什么要做哈希？哈希到底是按 token 还是按 Block 算？

### 面试中暴露的问题
这是面试里最明显的知识断点之一。你把“哈希”理解成了 token 在 Block 内的地址偏移，但面试官问的是 Prefix Cache 的内容匹配。

### 建议面试回答

Prefix KV Cache 做哈希不是为了算 token 在显存里的地址，而是为了判断：**两个请求前面的 token 内容是不是完全相同，如果相同，就可以直接复用之前已经算好的 KV Cache。**

通常匹配粒度是 **Block**。比如 block size 是 64，那么会把连续 64 个 token ID 作为一个逻辑 Block。系统根据这个 Block 里的 token 内容，再结合前一个 Block 的哈希等信息计算当前 Block 的哈希值。

比如请求 A：

`[token 0 ... token 63] [token 64 ... token 127]`

请求 B 的前 128 个 token 如果和 A 完全一样，那么前两个 Block 的哈希就能依次匹配上，于是对应 KV Cache 可以直接复用。

为什么一般按 Block 而不是每个 token 做？因为 Paged KV Cache 本身就是以 Block 为管理单位，如果按 token 做缓存索引，元数据和查找开销会非常大。按 Block 做可以在复用粒度和管理开销之间取得平衡。

所以它确实意味着：**通常只有一个完整 Block 的前缀一致，才能复用这个完整 Block。** 最后一个没有填满的 Block 是否缓存，要看具体实现，一般会比完整 Block 更谨慎。

## 5. 多模态输入里，image placeholder 的数量到底怎么确定？

### 面试中暴露的问题
面试官连续追问“placeholder 数量怎么确定”和“THW 最后对应多少 image token”，你没有真正解释清楚。

### 建议面试回答

placeholder 的数量不是随便固定一个值，也不是直接按原始图片的像素数量决定，而是和**图片经过视觉预处理后会生成多少个视觉 token**对应。

图片进入 Processor 后，会先 resize、切 patch，得到视觉 patch 的网格信息，通常用 `image_grid_thw` 这类变量表示。这里的 T、H、W 更接近“视觉 patch 网格尺寸”，而不是简单的原图高和宽。

视觉 Encoder 会把这些 patch 编码成视觉隐藏状态。有些 Qwen-VL 结构在 Vision Encoder 后还会进行 spatial merge，也就是几个相邻 patch 合并成一个最终视觉 token。因此最终 placeholder 数量应该和**merge 之后实际送进语言模型的视觉 token 数量**一致。

可以把它理解成：

`原图 → resize/patchify → T×H×W 个视觉 patch → Vision Encoder → spatial merge → N 个视觉 token`

那么文本序列中给图片预留的位置最终也应该对应 N 个视觉 token，后续才能把视觉 embedding 正好填进去。

如果面试官继续问公式，我会说具体公式要以项目里的 processor 参数为准。例如 merge size 为 2 时，空间维通常每 2×2 个 patch 合成一个 token，那么视觉 token 数大致和 `T × H × W / 4` 成正比，但实际还要以仓库中的 patch size、merge size 和 processor 实现为准。

## 6. Pixel Values 和 image_grid_thw 分别给谁？Vision Encoder 最后输出什么？

### 面试中暴露的问题
你当时说“Pixel Values 和 THW 一起进入 Vision Encoder”，方向不算错，但没有说明两者角色，也没有讲清楚输出如何进入语言模型。

### 建议面试回答

这两个输入的作用不一样。

`pixel_values` 是图片真正的数值内容，经过 resize、归一化、patch 化以后形成，它是 Vision Encoder 做视觉特征提取的主要数据。

`image_grid_thw` 更像是这张图片对应的视觉网格元数据，描述时间维、纵向 patch 数和横向 patch 数。它不是图片内容本身，主要用来帮助视觉模型恢复每个 patch 的空间结构、生成视觉位置编码，或者在后面计算 merge 之后的视觉 token 数量。

所以流程可以说成：

`图片 → Processor → pixel_values + image_grid_thw → Vision Encoder → image hidden states → projector/merger → 最终 image embeddings`

然后语言模型这边已经提前在 token 序列中放好了图片占位位置，ModelRunner 会把这些位置原来的占位 embedding 替换成视觉 Encoder 输出的 image embeddings。替换完成以后，对后面的 Transformer 来说，文本 token 和图片 token 都已经统一成相同 hidden size 的向量，可以一起进入后续层计算。

## 7. RoPE / MRoPE 的输入是什么、输出是什么？它在一次 forward 的什么位置？

### 面试中暴露的问题
你只回答了“给 Q、K 加位置信息”，但没有回答输入输出。面试官随后直接追问“你不了解怎么实现了这个东西”。

### 建议面试回答

RoPE 本身不是单独生成一个新的 token embedding，它作用在 Attention 里面的 Q 和 K 上。

在一次 Transformer 层 forward 里，hidden states 先经过 QKV 投影，得到 Q、K、V。与此同时系统会准备当前 token 的 position id。RoPE 根据 position id 计算对应的旋转角度，然后对 Q 和 K 的部分维度做二维旋转。

所以它的输入主要是：

- Q；
- K；
- position ids；
- 预先计算或者动态生成的 cos、sin。

输出仍然是和原来形状一样的 **旋转后的 Q 和 K**。V 一般不做 RoPE。

顺序可以记成：

`hidden states → QKV 投影 → 对 Q/K 做 RoPE → Attention`

普通 RoPE 只有一维 token 位置。多模态里的 MRoPE 可以理解为把位置拆成多个维度，例如文本主要是一维顺序，而图片需要表达二维空间位置，视频还需要表达时间维。最终还是生成对应位置的旋转角度，并作用到 Q、K 上。

一句话总结：**RoPE 不改变 Q、K 的 shape，而是通过旋转 Q、K，把相对位置信息编码进 Attention 点积。**

## 8. 你的 SnapKV 压缩到底借鉴了什么？重要 token 是怎么筛选的？和原版有什么区别？

### 面试中暴露的问题
你能说出“Top-K 保留重要 token”，但把“当前一个 token 和历史 Key 做计算”说得过于简单，也没有明确你自己的工程版本和论文原版之间的区别。

### 建议面试回答

我的实现不是自己发明一套新的压缩算法，核心筛选思想是借鉴 SnapKV，也就是利用**最近一小段 query 对历史 KV 的注意力分布，估计哪些历史 token 更重要**，然后只保留重要度更高的一部分 KV。

更准确地说，不应该简单理解成“拿当前一个 token 和所有历史 Key 算一下”。SnapKV 的核心思路是使用一个 observation window，也就是最近的一段 token 作为观察窗口，统计这些 query 对更早历史 Key 的注意力得分。某些历史位置如果持续被最近的 query 高度关注，就说明后续生成时更可能继续有用，因此优先保留；重要度低的历史 KV 可以丢弃。

我项目里的重点不是重新提出 SnapKV 算法，而是把类似的 Top-K 选择思路接入 nano-vLLM 的 Paged KV Cache。因为 nano-vLLM 的 KV 是按 Block 管的，所以我需要解决压缩之后 token 如何重新整理、Block 如何释放、block table 如何更新，以及 Decode 后续怎样继续正确读取压缩后的 KV。

另外我的版本是周期性触发压缩，而不是每生成一个 token 都压缩，这主要是为了降低压缩本身带来的额外计算和数据搬运开销。

所以如果面试官问创新点，我不会说“我发明了 SnapKV”，而会说：**算法思路借鉴论文，我做的是针对 nano-vLLM / Qwen3.5 Hybrid 的工程化接入和缓存管理改造。**

## 9. FlashAttention 和 Softmax 分别是什么？为什么 FlashAttention 能加速 Attention？

### 面试中暴露的问题
这是面试官用来检查基础知识的连续追问。你对 FlashAttention 只回答“加快 Attention”，Softmax 基本没有回答出来。面试官随后明确评价你的基础偏薄。

### 建议面试回答

Softmax 的作用是把一组任意实数变成和为 1 的权重。Attention 里面先算：

`S = QK^T / sqrt(d)`

得到每个 query 对所有 key 的相关性分数，然后对每一行做 Softmax，把它变成注意力权重：

`P = softmax(S)`

最后再算：

`O = PV`

所以 Softmax 的核心作用就是把相关性分数归一化成注意力权重。

FlashAttention 并没有改变这个数学公式，它得到的结果和标准 Attention 是一致的。它主要优化的是 GPU 上的数据访问。

普通实现通常会先完整算出很大的 `QK^T` 矩阵，写回显存，再读出来做 Softmax，再把结果写回显存，然后再读出来乘 V。长序列下，大量时间不是花在算术本身，而是花在显存读写。

FlashAttention 会把 Q、K、V 按块搬到更快的片上存储中，一小块一小块完成 Attention，并使用 online softmax，在不保存完整注意力矩阵的情况下逐块维护 Softmax 的最大值和归一化项。

所以 FlashAttention 的核心可以概括为：

**数学结果不变，通过分块计算 + online softmax，减少中间矩阵对显存的反复读写，从而提高速度并降低显存占用。**

## 10. 手写 GEMM 和 cuBLAS 做性能对比时，应该怎么正确测速？

### 面试中暴露的问题
面试官问“cuBLAS 是怎么测速的、用什么实现”，你只说了“开始计时、CUDA 计算、结束计时”，没有讲 GPU 异步执行、CUDA Event、warmup 和多次重复。

### 建议面试回答

CUDA Kernel 默认是异步执行的，所以不能简单用 CPU 的普通计时函数，在 launch 前后直接做时间差，否则很可能测到的只是 Kernel launch 的时间，而不是 GPU 真正执行 GEMM 的时间。

我做 GEMM benchmark 时更规范的方式是用 CUDA Event。

首先准备相同的矩阵 A、B、C，并提前完成显存申请和 H2D 数据拷贝，避免把这些开销算进 GEMM 时间。然后先做若干次 warmup，让 CUDA Context、缓存以及 cuBLAS 内部算法选择进入稳定状态。

正式测试时：

1. `cudaEventRecord(start)`；
2. 调用自己的 GEMM Kernel，或者调用 `cublasGemmEx / cublasSgemm`；
3. `cudaEventRecord(stop)`；
4. `cudaEventSynchronize(stop)`，保证 GPU 真正执行完成；
5. 用 `cudaEventElapsedTime` 得到 GPU 执行时间。

一般会重复几十次甚至更多，再取平均值或者中位数。

如果矩阵是 `M×K` 乘 `K×N`，GEMM 的浮点运算量近似是：

`2 × M × N × K`

所以吞吐可以算成：

`TFLOPS = 2MNK / time / 10^12`

我自己的 Kernel 和 cuBLAS 必须使用相同的矩阵尺寸、数据类型、输入数据和计时范围，这样性能比例才有意义。

如果面试官继续问为什么用 CUDA Event，我会回答：**因为它是在 CUDA stream 时间线上记录事件，可以正确测量 GPU 异步 Kernel 的实际执行时间。**

# 最后复习优先级

如果只剩很短时间准备下一场面试，我建议按下面顺序补：

1. **BlockManager：init / allocate / append / free / block table / Prefix Cache**
2. **nano-vLLM 一次完整 Scheduler → ModelRunner 执行链路**
3. **RoPE / MRoPE 的输入输出**
4. **多模态 image token 数量和 Vision Encoder 数据流**
5. **SnapKV 真正的筛选逻辑**
6. **FlashAttention + online softmax**
7. **CUDA Event + GEMM Benchmark**

其中前四项和你的 nano-vLLM 项目直接绑定。如果简历继续把 Qwen3.5、多模态、KV Cache 压缩写成核心工作，这些问题最好做到不需要现场回忆，能够顺着完整链路直接讲出来。
