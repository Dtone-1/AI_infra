**面试官：** 行。那我们先简单聊第一个项目，再重点讨论第二个。你先介绍一下你自己做的部分。

第一个项目主要针对大模型在长上下文、高并发场景下 KV Cache 显存不足的问题，做了 KV Cache 压缩和显存调度两个方面的优化。

第二个项目主要针对 MoE 计算流程中大量小 kernel、频繁 kernel launch，以及中间 tensor 反复读写 HBM 的问题，做了三阶段融合来加速。

## 2. 项目一：KV Cache 压缩策略

**面试官：** 你刚才说，在序列比较长、并发比较高的时候，会发生抢占或者重计算。你这里对进入 KV Cache 的 token 做了选择，相当于有几种策略结合。你简单介绍一下：比如原来有 4096 个 token，现在只想保留 2304 个，你到底怎么挑？

**候选人：** 首先我会离线选出一些比较有语义代表性的 attention head，然后用这些 head 的 query 和历史 token 的 KV 做 attention 计算，得到每个历史 token 的重要性分数。之后按照分数选择 Top-K token 进行保留。

同时我还会保留 anchor token 和 recent token，也就是头部和尾部的一部分 token。因为我在实验里发现，如果只按照 Top-K 分数保留 token，准确性不够稳定。

头部 token 一般包含一些基础的关键事实，比如时间、地点等；最近的 token 和用户当前输入的相关性通常比较强。所以整体上是保留头部和尾部，主要压缩中间那部分 token。

**面试官：** 也就是说，一个是重要性选择，一个是固定保留头部和尾部？

**候选人：** 对。

## 3. KV Cache 压缩后的 Compaction / 数据搬移

**面试官：** 你这样选完以后，保留下来的 token 在物理上其实是离散的。那最后还要把它们重新整理，对吧？

**候选人：** 对。选中之后，会先确定需要保留的索引，再通过代码里的 compact 模块把需要保留的 KV 搬到前部。这样尾部的 block 就都变成可释放状态，然后由 block manager 把尾部 block 释放掉。

**面试官：** 相当于这个 compact 本质上是在做一次 gather / 拼接式的数据搬移。你当时是自己写 kernel 做的，还是直接在框架层面实现？

**候选人：** 我当时直接在框架层面做，没有单独写 kernel。

**面试官：** 没关系。那我们讨论一下：如果现在让你把这个 compaction 写成一个 kernel，你觉得怎么优化？

**候选人：** 因为这里需要频繁搬移，把需要保留的 token 搬到前面。基础实现可能是一个一个搬，我会考虑按块搬移，一块一块地把数据搬到前面，这样效率会高一些。

**面试官：** 除了“按块搬”，还有呢？比如读写的时候你会怎么设置？

**候选人：** 我理解可以结合 GPU 的访存特性，让每次读写尽量搬更多连续数据，减少过于零散的访问。

**面试官：** 对。核心就是尽量做更宽的 load/store。比如一条指令一次只读一个元素，和一次读一组连续元素，发出的指令数量是不一样的。尽量使用 vectorized load/store，一条指令搬更多数据，效率通常会更高。

**候选人：** 明白。这部分我之前确实没有了解这么深入。

## 4. 项目二：MoE 小算子融合与数据重排

**面试官：** 那第二个项目呢？

**候选人：** 第二个项目主要针对 MoE 里多个小算子做融合。融合以后可以减少频繁的 kernel launch，也可以减少中间 tensor 对 HBM 的反复读写。

**面试官：** MoE routing 之后，会选出不同的 expert。你这里 expert 对应的 token 是怎么排序、怎么组织的？是做了一次显式的内存重排，还是别的方式？

**候选人：** 我记得 routing 阶段主要是根据分数做 Top-K 选择，然后把每个 expert 对应的 token 选出来。

**面试官：** 比如 token 1 选了 expert 1、8，另一个 token 选了 expert 8、20、30。真正做 expert 计算时，通常是以 expert 为单位组织计算。那从“token 视角”到“expert 视角”，你这里怎么变？

**候选人：** 需要先把属于同一个 expert 的 token 聚到一起，再进行计算，所以会有一次维度或者数据布局上的转换。

**面试官：** 对。因为从 token 视角看，这些 expert id 是离散的；但真正做 expert GEMM 时，希望以 expert 为单位处理，所以中间必须有 grouping / reorder。

**候选人：** 对。

## 5. Persistent Kernel 与 Expert 负载不均衡

**面试官：** 你后面写了 persistent kernel。这个东西到底解决了什么问题？

**候选人：** 这里每个 expert 要处理的 token 数量是不一样的。

**面试官：** 对。每个 expert 的 token 数不同，就会带来负载不均衡。比如有的 expert 只收到 3 个 token，有的收到 100 个。如果直接给两个不同的 block 去做，一个很快结束，一个要算很久，会造成资源利用率不均衡。你当时怎么解决？

**候选人：** 我记得当时确实遇到过这个问题。我当时是对 token 数量比较短的 expert 做 padding，把它们补到统一长度之后再计算。

**面试官：** 那这样其实会浪费很多计算。如果都补到最长的长度，效率不会高。

**候选人：** 是，这种方法确实不算高效。

**面试官：** 那如果采用这种做法，为什么还需要 persistent kernel？

**候选人：** 这个点我现在确实有点记不清了。当时的实现里应该有 padding，但这样看的话，persistent kernel 的必要性我现在没有办法很好解释。

**面试官：** 这个地方你回去需要再看。persistent 的价值一般要和任务调度、负载均衡、减少 launch 等具体问题对应起来，不能只写在简历上。

## 6. 融合 Up Projection + 激活，以及中间 Tensor 的 HBM 流量

**面试官：** 你这里还写了一个融合。你是把 up projection 和后面的激活操作融合在一起，对吧？

**候选人：** 对。原来 up projection 的输出会先写回 HBM，然后后续激活再从 HBM 读出来。融合以后，中间结果可以直接在片上存储中继续计算，不需要先写回 HBM 再读出来。

所以我简历里也写了，这部分能够减少中间激活的显存占用，大概减少几十 MB。主要目的还是降低 HBM 的中间读写流量。

**面试官：** 对，关键不只是“省几十 MB 显存”，而是减少中间 tensor 对 HBM 的 round trip。

## 7. CUDA / GEMM：并行度、Grid、Block 与 Tile

**面试官：** 你这个融合 kernel 里还涉及矩阵乘法。那你的并行度是怎么设计的？

**面试官：** 我们先不讨论整个融合，就单看一个 GEMM。假设你一个 thread block 要算输出矩阵里 64×64 的一个 tile，那输入矩阵需要的 tile 是什么形状？

**候选人：** 应该是 64×K 和 K×64。

**面试官：** 对。那 grid 怎么定义？哪些维度可以并行？

**面试官：** 你之前真正写过 CUDA kernel 吗？这些 grid、block 的概念熟吗？

**面试官：** CUDA kernel 写之前，一般先要规划几件事情：grid 怎么设计、一个 block 有多少线程、每个线程负责什么、shared memory 和 register 怎么分配。这些都需要先想清楚。

## 8. Shared Memory 的作用与 Bank Conflict

**面试官：** 你做这些的时候用 shared memory 吗？

**候选人：** 用。shared memory 是 block 内共享的片上存储，可以先把一块数据从 global memory 搬进来，再由 block 内多个线程重复使用。

**面试官：** 它能跨 block 吗？

**候选人：** 不能。

**面试官：** 对，它主要是 block 内线程之间做数据共享。你遇到过 bank conflict 吗？

**候选人：** 遇到过，也做过相关优化。但具体细节我现在记得不是特别清楚。

**面试官：** 你知道 bank conflict 是怎么产生的吗？

**候选人：** 我当时理解是要尽量让 warp 内线程访问的地址更规整，不要形成冲突。

**面试官：** 更典型的例子是二维 shared memory。比如一行恰好是 32 个元素，如果按列访问，很容易让一个 warp 的多个线程映射到同一个 bank，导致严重 bank conflict。常见解决方式之一是做 padding，例如把第二维从 32 改成 33，打散 bank 映射。

**候选人：** 明白。

## 9. Nsight Systems / Nsight Compute 与性能分析思路

**面试官：** 你简历上写了用 Nsight 做性能分析。具体怎么用？

**候选人：** 用 Nsight Systems 时，我主要先看整体 timeline。如果两个 kernel 之间空隙比较大，就可能需要优化调度逻辑；如果某个 kernel 占总时间很高，就需要进一步针对这个 kernel 做优化。

**面试官：** 那 Nsight Compute 呢？举个具体例子。比如看一个 GEMM kernel，你主要看什么？

**候选人：** 我主要会看 memory、SM 利用率和 occupancy，判断它更偏 memory-bound 还是 compute-bound。

如果是访存受限，我会考虑做分块，让每次从 HBM 读取一块数据到片上存储，然后在片上完成更多计算，减少反复访问 HBM。

**面试官：** 分块有两个意义。一个是一次尽量抓更多、连续的数据回来；另一个更重要的是提高数据复用。那为什么要放到 shared memory，而不是每个线程都直接从 global memory 读？

**候选人：** 因为一块数据如果会被多个线程共同使用，就可以先加载一次到 shared memory，让 block 内线程复用，不需要每个线程都单独从 HBM 重新读取。

**面试官：** 对。如果每个线程都自己从 global memory 抓同一份数据，读取量会被放大。shared memory 的意义之一，就是让 block 内多个 warp / 线程共享同一份 tile，减少重复的 global memory traffic。

**候选人：** 对，不好意思，刚才这部分我表达得有点绕，需要您引导。

## 12. FP32 Atomic Reduce：为什么要原子操作

**面试官：** 你后面还写了一个点：routing 之后，一个 token 可能会被多个 expert 处理，最后不同 expert 的输出需要加权求和。你这里用了 FP32 atomic reduce。为什么要用 atomic？

**候选人：** 因为同一个输出位置可能会由多个 expert 的结果共同累加。如果多个线程或者多个执行单元同时更新同一个地址，就可能发生写冲突，所以需要原子加来保证累加结果正确。

**面试官：** 对。那这个 atomic 最终作用在哪个存储层级？你这里所谓“融合写回阶段”，写回到哪里？

**候选人：** 最终是写回 global memory。

**面试官：** 对。原子操作本质上是在解决多个执行者对同一个 global memory 地址并发更新时的竞争问题。

如果不让你用 atomic，你怎么做？

**候选人：** 可以把各个 expert 的结果先分别写出去，再增加一个独立的 reduce kernel，统一完成加权累加。

**面试官：** 对。也可以通过重新设计输出布局，尽量避免多个线程写同一个地址。但这里没有绝对唯一的实现，要比较 atomic 的开销和额外一个 reduce kernel 的 launch、访存开销之间的 trade-off。

**候选人：** 明白。

## 13. 为什么累加用 FP32，而不是 FP16 / BF16

**候选人：** 因为多个 expert 输出在累加时，如果直接使用 FP16，精度损失会比较明显，所以累加阶段使用 FP32 更稳妥。

**面试官：** 这个回答方向没问题，不过你还要继续想清楚：到底是数值范围、有效位数、累加误差，还是硬件实现上的其他原因。不要只停留在“FP16 精度不够”这一句。

## 16. 从这场面试中能看出的主要追问链（便于转发阅读）

> 本节仅对原对话的追问结构做归纳，不新增技术结论。

1. **项目是不是自己做的** → 为什么选这个方向 → 自己负责哪一部分。
2. **KV Cache 压缩** → token 怎么打分 → 为什么保留 anchor/recent → 压缩后离散 KV 怎么 compact。
3. **Compaction** → 框架层还是 kernel 层 → 如果让你写 kernel，怎么提高数据搬移效率 → vectorized load/store。
4. **MoE routing** → token-to-expert 如何转成 expert-to-token → 是否需要 reorder / grouping。
5. **Persistent kernel** → 每个 expert token 数不同怎么办 → 负载不均衡 → padding 是否浪费 → persistent 到底解决什么。
6. **Kernel fusion** → 融合掉了什么中间 tensor → 为什么能减少 HBM round trip。
7. **GEMM / CUDA 基础** → tile 怎么切 → grid/block 怎么定 → thread/shared memory/register 如何规划。
8. **Shared memory** → 能否跨 block → 为什么能减少 global memory traffic → bank conflict → padding。
9. **Nsight** → Systems 看什么 → Compute 看什么 → 如何判断 memory-bound / compute-bound → 对应什么优化。
10. **Atomic reduce** → 为什么会有写冲突 → atomic 作用在哪里 → 不用 atomic 怎么实现 → trade-off。
11. **FP32 accumulate** → 为什么不是 FP16/BF16 → 数值精度问题是否真正理解。
12. **Benchmark** → 4.39× 的 baseline 是什么 → 最大收益来自哪里 → 有没有逐项 ablation。
13. **真实性验证** → kernel 是否真的自己写过 → AI 在项目中扮演什么角色 → 能否脱离代码解释底层原理。
