## 2. KV Cache 压缩与显存压力调度

### 2.1 KV 压缩具体怎么做？会不会影响精度？

**面试官 [01:23]：**  
看一下具体项目。你这里写了基于 SRHKV 和显存压力调度的优化。背景里提到 KV Cache 持续增长、物理 Block 不足的情况下做 KV Cache 压缩。你这个压缩具体怎么做？会不会影响原先的精度？

**候选人 [01:59]：**  
做 KV 压缩时，我首先考虑的是采用什么算法，比较过 SnapKV 和目前采用的 SRHKV。这类方法确实会对输出正确性产生影响，所以需要做校验。

SRHKV 大致是先离线识别语义头，也就是从 GQA 的 Attention Head 中识别语义相关的 Head。识别后，用这些语义头的 Query 对历史 Token 的 KV 做注意力计算和打分，选出分数最高的 Top-K Token，得到需要保留的索引。

之后交给代码里的 KV Compaction 模块，把需要保留的 Token 压缩到前部，再释放尾部空闲的 Block，大致是这样一个逻辑。

对于输出正确性，我用了大约 500 条校准数据，在每个请求的不同位置插入多个事实，再输入模型，看模型能不能找到这些关键事实，以此判断压缩后的输出准确性。

### 2.2 压缩带来的收益是什么？

**面试官 [03:51]：**  
你做过输出准确性的判断。那压缩之后具体带来了什么收益？比如能放下更多 KV Cache，或者显存利用率提高多少，这部分有没有分析？

**候选人 [04:09]：**  
有。主要有两部分收益。

第一，KV Block 能够得到明显释放。第二，Block 释放之后，Preemption 的次数会降低，进而减少重计算，以及显存不足时长序列搬移、重计算等开销。主要是这两部分。

### 2.3 Sink / Anchor / Recent / Top-K 混合保留策略

**面试官 [04:53]：**  
你这里写了 Sink、Anchor、Top-K 等混合保留策略。能分别讲一下这些策略的思路吗？

**候选人 [05:10]：**

## 3. MoE 推理优化与 Kernel Fusion

**候选人 [07:13]：**

## 6. vLLM 核心机制追问

### 6.1 Continuous Batching 和 Static Batching 的区别

**面试官 [18:27]：**  
刚才提到了 Continuous Batching。它和静态 Batching 有什么区别？

**候选人 [18:37]：**  
静态 Batching 是把一批输入打包进行处理。如果其中有一个比较长的 Prompt、计算时间比较长，就可能拖累同一个 Batch 里的其他请求，因为其他请求往往要等这一批统一处理完，再进入下一批。

Continuous Batching 是动态的，可以动态地往 Batch 里加入或者移出序列。比如某个序列计算结束后，可以立刻把它移出，然后放入新的等待序列，从而让 GPU 尽量保持较高利用率。

### 6.2 Continuous Batching 对 TTFT / TPOT 的影响

**面试官 [19:33]：**

### 6.3 PagedAttention 的核心思想

**面试官 [21:48]：**  
PagedAttention 的核心思想是什么？

**候选人 [21:54]：**  
原来的方式下，一个输入可能需要分配一段连续的物理空间，这样容易造成 Block 浪费。

PagedAttention 把 KV Cache 划分成多个较小的物理 Block。对一个序列来说，逻辑上仍然是连续的，但可以映射到实际不连续的物理 Block，从而更充分地利用 KV Cache，减少显存浪费。

### 6.4 Prefix Cache 如何匹配命中？

**面试官 [22:57]：**  
vLLM 里 KV Cache 的前缀匹配机制了解吗？

**候选人 [23:10]：**  
了解。序列进入 Scheduler 后，在 Prefill 阶段可以先检查缓存是否命中。如果它的前缀之前已经缓存过，就可以直接复用，没必要重复计算。

**面试官 [23:32]：**  
那它具体用什么方式匹配命中？树还是哈希？

**候选人 [23:39]：**  
是哈希。会计算每个 KV Block 的哈希值。新的输入进来后，同样计算对应的哈希值，看有没有相同的哈希值；如果有，就可以复用。

### 6.6 什么时候发生 Preemption？

**面试官 [25:25]：**
