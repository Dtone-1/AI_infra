# ② 推理框架层

## 请求入口、Tokenizer 与 Sequence

### 1. 当一条文本信息首先进入一个推理系统，首先将文本转成tokenid，这个id是固定的吗，是不是每个文本都对应自己固定的id，这个id的值由什么决定，举个实际工程上这个tokenid的例子让我明白这一步

可以这样理解：**Token ID 不是“每一段文本都有一个固定 ID”，而是“Tokenizer 词表里的每一个 Token 都有一个固定 ID”**。一条文本进来以后，**Tokenizer 会先按照它自己的分词规则把文本切成若干个 Token，然后再去词表里查每个 Token 对应的整数编号。**这个编号是在模型训练时就和词表一起确定好的，所以**对于同一个模型、同一个 Tokenizer，同一个 Token 对应的 ID 通常是固定的**，但是换一个模型或者换一个 Tokenizer，ID 就可能完全不一样。比如工程上我输入一句 `"Hello world"`，假设使用 GPT\-2 的 Tokenizer，它可能会被切成 `"Hello"` 和 `" world"` 两个 Token，对应的 Token ID 是 `[15496, 995]`。这里不是说 `"Hello world"` 这句话的 ID 是 15496，而是 `"Hello"` 这个 Token 在它的词表里编号是 15496，`" world"` 编号是 995。所以如果输入 `"Hello world!"`，可能就会得到 `[15496, 995, 0]` 这种 Token ID 序列。到了我们实际的 Qwen 推理系统也是一样，Tokenizer 会把用户文本转成一串整数，比如 `[token_id_1, token_id_2, ...]`，然后模型真正接收的其实就是这串整数。进入模型以后，第一步通常就是通过 Embedding 表，例如 `embedding[token_id]`，把每个整数 ID 查成一个高维向量，后面的 Transformer 实际计算的就是这些向量。**所以 Token ID 的本质，就是一个 Token 在模型词表里的下标。**

### 2. 这个tokenizer是一个什么结构，这个属于模型训练自带的吗，在我的项目中直接调用autotokenizer吗，这个是什么，他怎么知道我用的什么模型

这个 `Tokenizer` 是**模型前面的文本编码器**，负责把人输入的字符串按照这套模型训练时使用的分词规则，转换成一串 Token ID。**它通常是跟模型一起配套发布的，因为模型训练的时候用的就是固定的一套词表、特殊 Token 和分词规则**，所以推理时必须继续用同一套，不能随便换。像我这个项目里，确实是直接用了 Hugging Face 的 `AutoTokenizer`，代码里是 `AutoTokenizer.from_pretrained(path)`。**这里的 ****`AutoTokenizer`**** 可以理解成一个自动选择 Tokenizer 实现的工厂类，我不需要手动写死说“我要用 QwenTokenizer”，而是把模型目录 ****`path`**** 传进去，比如 ****`~/huggingface/Qwen3-0.6B/`****，它会去这个目录里读取 ****`tokenizer_config.json`****、词表文件、特殊 Token 配置、Chat Template 等文件，根据这些配置判断该加载哪一种 Tokenizer，**并把对应规则初始化出来。所以不是 `AutoTokenizer` 自己凭空“猜”我是什么模型，而是**我通过模型路径告诉它模型文件在哪，它再读取这个目录里的配置来决定该实例化什么 Tokenizer**。比如在我的代码里先写 `path = "~/huggingface/Qwen3-0.6B/"`，然后 `AutoTokenizer.from_pretrained(path)`，那它加载的就是这个 Qwen3 模型目录配套的 Tokenizer；后面 `apply_chat_template()` 也是用这个模型目录里保存的聊天模板，把 user、assistant 这些角色信息组织成 Qwen 训练时熟悉的格式。最后真正调用 `encode()` 的时候，再按照这套词表和分词规则把字符串变成 Token ID。所以我会把它总结成一句话：**Tokenizer 是模型训练协议的一部分，模型权重和 Tokenizer 是配套的；我项目里没有自己实现分词器，而是通过 Hugging Face 的 ****`AutoTokenizer.from_pretrained(model_path)`**** 根据模型目录中的配置自动加载对应的 Tokenizer。**

### 3. 我将提示词转换成tokenid后，直接将tokenid传入sequence封装成一个sequence，那么这个sequence的所有信息都只来自于tokenid吗

不是，`Sequence` 里面的信息**不只是来自 Token ID**。Token ID 只是它最核心的一部分输入，表示“这条请求具体有哪些 token”。在我的项目里创建 `Sequence` 时，除了 `token_ids`，通常还会把 `sampling_params` 一起传进去，所以这个对象里的信息大致来自三部分。

第一部分是**输入本身**，也就是 `token_ids`，由它可以得到 prompt 长度、当前最后一个 token、已经生成了多少 token 这些信息；

第二部分是**生成配置**，来自 `sampling_params`，比如 temperature、最大生成长度、停止条件这些，这些不是 Token ID 能推出来的；

第三部分是**运行过程中动态维护的状态**，比如这个请求现在是 `WAITING`、`RUNNING` 还是 `FINISHED`，它**分配了哪些 KV Cache block、**当前已经真正写入了多少 KV、Qwen3\.5 的 GDN state slot 是多少，这些都是后面的 Scheduler、BlockManager、StateSlotManager 在执行过程中逐步写进去的。

所以更准确地说，`Sequence` 不是“Token ID 的包装器”，而是**一条推理请求的完整状态对象**。刚创建时它主要由 `token_ids + sampling_params` 初始化，之后随着调度、Prefill、Decode、KV 分配和 token 生成，它里面的状态会不断被更新。可以简单记成：**Token ID 决定这条请求“是什么内容”，sampling params 决定“怎么生成”，运行时状态决定“现在执行到哪一步、资源占了多少”。**

### 4. 那这个刚创建的sequence的运行过程中动态维护的状态是怎么样的，它其中的blocktable刚创建时就给他分配好了吗，用实际工程上的一个请求举例

不是，`Sequence` 刚创建出来的时候，**很多运行时状态其实只是初始化，并没有真正给它分配 GPU 资源，尤其是 ****`block_table`**** 刚创建时就是空的**。我用一个实际请求来讲，比如用户输入“介绍一下 Qwen3\.5 的模型结构”，经过 Chat Template 和 Tokenizer 以后，假设最终得到了 600 个 Token ID，那么执行 `Sequence(token_ids, sampling_params)` 时，这个 Sequence 会先拿到一个唯一的 `seq_id`，状态被设成 `WAITING`，`num_tokens=600`，`num_prompt_tokens=600`，最后一个 Token 会记录到 `last_token`，而**运行时相关的信息这时候基本都是初始值，比如 ****`num_cached_tokens=0`****，表示现在还没有可复用的前缀；****`num_scheduled_tokens=0`****，表示 Scheduler 还没有决定这一轮计算多少 Token；****`kv_num_tokens=0`****，表示 GPU 上目前还没有真正算出来的 KV；**`state_slot_id=-1`，表示 Qwen3\.5 的 GDN 状态槽还没有分配；最关键的 `block_table=[]`，也是空的。所以**Sequence 创建和 KV Block 分配是两个不同阶段**。**创建完以后只是通过 ****`Scheduler.add()`**** 放到 waiting 队列，等第一次 ****`Scheduler.schedule()`**** 真正选中这个请求做 Prefill 时，Scheduler 才会调用 ****`BlockManager.can_allocate()`**** 看显存还有没有足够的 Block，然后调用 ****`BlockManager.allocate()`**** 分配。**我的项目里 Block 大小比如设成 256 个 Token，那么 600 个 Token 理论上需要 `ceil(600/256)=3` 个 Block，BlockManager 可能从全局 KV Cache 池里拿到物理 Block 12、37、85，那么这个 Sequence 的 `block_table` 才会从 `[]` 变成 `[12, 37, 85]`。这里要注意，**block\_table 只是说“未来这条请求的 KV 应该放到哪些物理 Block”，并不代表里面的 KV 已经算好了**；真正进入 ModelRunner 做 Prefill 以后，模型算出 K、V 并按照 `slot_mapping` 写进去，`kv_num_tokens` 才会逐渐从 0 增长到实际已经生成 KV 的数量。如果开启 Prefix Cache，情况还会更有意思，比如**前 512 个 Token 正好和之前某个请求相同，那么前两个 Block 可能直接复用，**`num_cached_tokens` 会变成 512，只需要为剩下部分真正计算新的 KV。对于 Qwen3\.5 Hybrid 模型，**第一次被 Scheduler 调度时还会再通过 ****`StateSlotManager`**** 给它分一个 GDN 状态槽，比如 ****`state_slot_id=3`**。然后随着请求运行，Sequence 的这些字段会一直变化。比如 600 个 Prompt 全部 Prefill 完成以后，`kv_num_tokens` 大约对应已经实际写入 KV 的 Prompt 部分，模型同时采样出第一个回答 Token，这个 Token 会通过 `append_token()` 加到逻辑 `token_ids` 后面，所以这时候可能出现一个非常关键的状态：**`num_tokens=601`****，但是 ****`kv_num_tokens=600`**，因为第 601 个 Token 虽然已经“生成出来了”，但它还没有作为下一轮输入真正经过模型，所以还没有自己的 KV。下一轮 Decode 时 Scheduler 设置 `num_scheduled_tokens=1`，BlockManager 先检查当前 Block 还能不能装下这个 Token；如果当前最后一个 Block 还有空间，就继续用原来的 Block，如果刚好跨过 256 的边界，`may_append()` 才会再申请一个新的物理 Block。模型执行成功以后调用 `commit_kv_tokens(1)`，这时这个 Token 的 KV 才正式算进去，然后模型又采样出下一个 Token，再 `append_token()`，于是这个过程不断循环。所以我理解 **Sequence 本质上就是一条请求的动态状态账本**：刚创建时只有 Token、采样参数和一堆初始状态，`block_table` 并不会提前在构造函数里分配；**第一次被 Scheduler 真正调度时才分 KV Block 和 GDN 状态槽，后面 Prefill、Decode、抢占、Prefix Cache、KV 压缩都会不断修改这些字段，**最后遇到 EOS 或达到最大生成长度以后，状态变成 `FINISHED`，BlockManager 释放它的物理 Block，`block_table` 被清空，KV 状态归零，GDN 的 state slot 也被释放，这条 Sequence 的完整生命周期才结束。

## KV Cache 空间管理与 PagedAttention

### 6. 这个blocktable的值是怎么分配的，举个例子说明，从整个大的block的角度，如果我有空闲的block，我是按照编号从小到大给新请求分配？那如果请求释放了呢，给他怎么编号，先说原理再举个具体的实际工程上的例子

可以先从原理上理解：`block_table` 不是 BlockManager 给请求重新编的一套编号，而是记录“这条请求的第 0、1、2……个逻辑 KV Block，实际放在全局 KV Cache 的哪个物理 Block 里”**。** 在我的项目中，**模型启动时会先根据剩余显存创建一个全局 KV Cache 池，**假设一共能放 8 个物理 Block，那么它们从一开始就有固定编号 `0~7`，**同时 BlockManager 维护一个空闲 Block 队列 ****`free_block_ids=[0,1,2,3,4,5,6,7]`****。**新请求需要 Block 时，代码实际上取的是 `free_block_ids[0]`，所以**系统刚启动的时候看起来确实是按 0、1、2、3 从小到大分配的，但它的本质不是“每次找最小编号”，而是“取空闲队列最前面的 Block”**。比如我的项目默认一个 KV Block 可以保存 256 个 Token，现在有一个比较长的请求 A，经过 Tokenizer 后有 600 个 Token，那么它需要 `ceil(600/256)=3` 个物理 Block，第一次调度时就可能依次拿到 `0、1、2`，于是 A 的 `block_table=[0,1,2]`，意思是 A 的前 256 个 Token 的 KV 放物理 Block 0，接下来 256 个放 Block 1，剩余部分放 Block 2；此时空闲队列变成 `[3,4,5,6,7]`。然后又来一个请求 B，需要两个 Block，它就拿到 `3、4`，B 的 `block_table=[3,4]`，空闲队列只剩 `[5,6,7]`。这里如果请求 A 生成结束，它占用的 `0、1、2` 会被释放，但**这些 Block 不会重新编号，0 永远还是物理 Block 0，1 还是物理 Block 1**；BlockManager 只是把它们重新放回空闲队列。**我的代码在 ****`deallocate()`**** 里会倒着遍历 A 的 ****`block_table`****，也就是先释放 2、再 1、再 0，然后通过 ****`_deallocate_block()`**** 把它们追加到空闲队列末尾，所以这时候空闲队列实际会变成 ****`[5,6,7,2,1,0]`**。如果现在又来了请求 C，需要两个 Block，它拿到的是队首的 `5、6`，而**不是重新去找最小编号 0、1**。所以这一点面试时我会特别说明：我的项目里初始阶段看起来是从小到大分配，但运行一段时间以后是按照空闲队列的顺序复用，Block 的编号本身从创建到销毁都不会改变。请求自己的 `block_table` 也完全可以是 `[5,6]`、`[7,2,1]` 这种不连续的编号，因为逻辑上连续的 Token 并不要求它们的 KV 在显存物理地址上连续，这正是 Paged KV Cache 的核心思想之一。另外，如果开启了 Prefix Cache，还有一个特殊情况：BlockManager 会先根据这一块 Token 的哈希值看看以前有没有完全相同的前缀 Block，如果命中了，就可能直接复用原来的物理 Block，并增加它的引用计数，而不是从空闲队列重新拿一个；等某个请求结束时也不是看到这个 Block 就立即释放，而是引用计数减一，只有降到 0，说明已经没有任何请求使用它了，才真正回到空闲队列。所以总结起来就是：**全局 KV Cache 的物理 Block 在系统初始化时就有固定编号；****`block_table`**** 只是请求的“逻辑 Block → 物理 Block”映射；新分配取空闲队列队首，释放时保持原编号重新放回空闲队列，绝不是每次释放以后重新编号或者要求请求占用连续 Block。**

### 7. 在给每个请求分配kvcache的空间时，是怎么从众多空闲的block池拿block给特定的请求

可以简单理解成，系统启动时会先把整块 KV Cache 显存切成很多固定大小的物理 Block，然后由 BlockManager 维护一个**全局的空闲 Block 队列**。某个请求第一次做 Prefill，或者 Decode 时现有 Block 不够用了，Scheduler 会先算这条请求还需要几个 Block；如果空间够，**就从空闲队列前面依次拿出对应数量的 Block**，把这些物理 Block 编号写进这个请求自己的 `block_table`。

### 8. 在实际的vllm框架中每个请求的blocktable也是这么分配的吗

是的，**从最核心的原理上看，我这个 nano\-vLLM 和正式 vLLM 的思路是一致的：每个请求都维护自己的 Block Table，里面记录的是“这条请求逻辑上的第几个 KV Block，对应全局 KV Cache 池里的哪个物理 Block”，所以逻辑上连续的 Token 并不要求物理 Block 连续。** 不过正式版 vLLM V1 的管理会更复杂一些。它启动时会**预先建立一个全局的 KV Block 池，每个物理 Block 都有固定的 ****`block_id`**，这个编号本身不会因为请求结束而重新编号；真正分配时由 `KVCacheManager` 和 `BlockPool` 管理，**新的物理 Block是从 ****`free_block_queue`**** 的队头取，所以同样不是“每次寻找编号最小的 Block”**。

比如现在一个请求 A 逻辑上需要 3 个 Block，它可能拿到物理 Block `[5, 8, 2]`，那么它的 Block Table 就记录这三个编号；请求结束以后，这些 Block 的引用计数会减少，如果已经没有其他请求在使用，就重新进入空闲队列等待以后复用，编号 5 还是 5、8 还是 8，不会重新编号。当前 vLLM V1 在释放一条请求的 Block 时，还会**按照请求 Block 的反向顺序把可释放 Block 放回空闲队列尾部**，因此系统运行一段时间以后，空闲队列肯定不再是简单的 `0、1、2、3……` 顺序。

另外正式 vLLM 开启 Prefix Cache 后会先根据 Prompt Token 的哈希去找已经计算过的 Block，如果命中，**就直接复用这些物理 Block并增加引用计数**；只有缺少的部分才继续从空闲队列申请，所以一个请求的 Block Table 可能同时包含“复用来的 Block”和“刚申请的新 Block”。官方给出的例子里，一个请求的 Block Table 可以是 `[0, 3]`，而缓存里实际上还存在内容相同的另一个物理 Block，这也说明正式 vLLM 并不要求 Block Table 的物理编号连续。\([vLLM](https://docs.vllm.ai/en/stable/design/prefix_caching/)\) 所以如果面试官问我项目和正式 vLLM 是否一致，我会说：**Paged KV 的核心思想是一致的，都是固定的全局物理 Block 池加每个请求自己的逻辑到物理映射；但 nano\-vLLM 是为了学习把 BlockManager 做得比较简单，而正式 vLLM V1 又加入了 Prefix Cache、引用计数、缓存淘汰以及不同 KV Cache Group 等更完整的管理机制。** \([vLLM](https://docs.vllm.ai/en/stable/design/prefix_caching/)\)

### 9. 简单介绍下什么是block\_table（面试版）

“逻辑 KV Block 到物理 KV Block 的映射表”。因为在 vLLM ，一条请求的 KV Cache 不要求在显存中连续存放，而是被切成一个个固定大小的 Block。所以 `block_table` 的作用就是把请求看到的连续 Token 序列和显存中实际不连续的 KV Block连接起来。

### 10. 说一下什么是pagedattention思想（面试）

把一条请求连续增长的 KV Cache，切成固定大小的 Block，然后这些 Block 在显存里不连续存放，再用 `block_table` 去记录逻辑 Block 和物理 Block 的对应关系。

传统做法如果要求每条请求的 KV Cache 连续存储，请求长度又是动态变化的，就很容易造成显存碎片和浪费；PagedAttention 借鉴了操作系统分页的思想，需要空间时就从全局 KV Cache 池里拿几个空闲 Block，不要求物理地址连续，请求结束后再把这些 Block 回收。

这样做的好处是显存利用率更高，也更适合大模型推理里请求长度不一致、动态加入和退出的 Continuous Batching 场景。

### 11. 为什么传统做法如果要求每条请求的 KV Cache 连续存储，请求长度又是动态变化的，就很容易造成显存碎片和浪费

因为传统连续存储要求一条请求的 KV Cache 在显存里占一整块连续空间，但生成长度事先又不知道。比如一开始只给请求预留 1K Token 的空间，后面生成到 2K 时，原位置后面可能已经被别的请求占了，就很难直接扩展；如果一开始按最大长度比如 8K 去预留，大多数请求实际只生成 1K，又会浪费大量显存，这就是显存碎片。

## 调度器、ModelRunner 与执行上下文

### 12. 当一个请求被调度器调度之后，这个调度器会输出什么信息给谁

当多个请求被 Scheduler 调度完成以后，它不会直接把文本或者完整的模型输入张量传下去，而是先输出一批“这一轮真正要执行的 Sequence”以及这一轮的执行类型和相关调度信息，然后**交给 ****`ModelRunner`**** 去整理成 GPU 真正需要的数据。**在我的项目里，最核心的就是返回类似** ****`seqs`**** 和 ****`is_prefill`** 这样的信息：`seqs` 表示这一轮具体选中了哪些请求，**每个 Sequence 里面已经带着自己的 Token、****`block_table`****、当前长度、KV 已经计算到哪里、GDN 状态槽这些运行状态**；`is_prefill` 则告诉后面的 `ModelRunner` 这一轮走 Prefill 还是 Decode。然后 `LLMEngine.step()` 会调用 `model_runner.call("run", seqs, is_prefill)`，把这些调度结果交给 `ModelRunner`。**`ModelRunner`**** 再根据这些 Sequence 去准备真正的 ****`input_ids`****、****`positions`****、****`slot_mapping`****、****`block_tables`****、****`context_lens`****、****`cu_seqlens`**** 等 GPU 张量，最后送进模型 forward**。所以可以简单理解成：**Scheduler 决定“这一轮谁执行、执行多少、走 Prefill 还是 Decode、各请求的 KV 资源是什么”，ModelRunner 再把这些调度结果转换成模型真正能执行的张量。**

### 13. 被调度的sequence送进模型之前要先经过modelrunner做处理，最后处理得到了哪些参数，这些参数简要解释含义

在我的项目里，Scheduler 把这一轮选中的 `Sequence` 交给 `ModelRunner` 以后，`ModelRunner` 的作用就是把这种“请求状态对象”整理成 GPU 和模型真正能使用的张量。最核心的参数有这么几个：**第一是 ****`input_ids`**，也就是这一轮真正需要送进模型计算的 Token ID，Prefill 时可能是一段 Prompt Token，Decode 时通常每个请求只有最新的一个 Token；**第二是 ****`positions`**，表示这些 Token 在各自序列中的位置，后面做 RoPE 或 MRoPE 时需要；**第三是 ****`slot_mapping`**，它告诉 Attention 当前这些 Token 新算出来的 K、V 应该写到 KV Cache 的哪个具体物理位置；**第四是 ****`block_tables`**，记录每条请求逻辑 KV Block 到全局物理 KV Block 的映射，Decode 时 Attention 就通过它找到历史 KV；**第五是 ****`context_lens`**，主要在 Decode 时表示每条请求当前已经有多少历史 Token，也就是当前 Query 应该读取多长的历史 KV；**第六是 ****`cu_seqlens`**** 以及最大序列长度这类信息**，主要用于 Prefill，因为多个不同长度的请求会把 Token 拼在一起送进 Flash Attention，所以需要告诉算子每条请求在这块连续 Token 数据中的起止位置；另外对于我的 Qwen3\.5 Hybrid 模型，还会准备 **`state_indices`**，告诉 GDN 层这条请求应该读取和更新哪个 recurrent state 和 convolution state 槽。最后真正调用模型 `forward` 时，表面上传进去的主要是 `input_ids` 和 `positions`，而像 `slot_mapping`、`block_tables`、`context_lens`、`cu_seqlens`、`state_indices` 这些信息会放到这一轮执行的上下文里，Attention 和 GDN 层在计算时再读取。所以可以概括成：**ModelRunner 就是把 Sequence 里面偏调度层的信息，转换成“当前算哪些 Token、Token 在什么位置、KV 写哪里、历史 KV 去哪里找、每条请求有多长、GDN 状态在哪里”这些模型真正执行需要的数据。**

### 14. 这些信息会放到这一轮执行的上下文里，Attention 和 GDN 层在计算时再读取。执行的上下文是什么意思，这是个怎么样的存在，发挥什么作用

这里说的“执行上下文”可以理解成**这一轮模型 forward 的公共运行信息包**。在我的项目里它不是一个很抽象的概念，而是在 `nanovllm/utils/context.py` 里真的定义了一个 `Context` 数据结构，**里面保存这一轮执行需要共享的信息，**比如 `is_prefill` 表示这一轮是 Prefill 还是 Decode，`slot_mapping` 表示新算出来的 KV 要写到什么位置，`block_tables` 表示历史 KV 在哪些物理 Block，`context_lens` 表示每条请求当前有多长，`cu_seqlens` 表示 Prefill 时多个请求在拼接 Token 里的边界，Qwen3\.5 还会放 `state_indices`，告诉 GDN 层每条请求对应哪个状态槽。

具体流程是，`ModelRunner.prepare_prefill()` 或 `prepare_decode()` **把这些信息整理好以后，会调用 ****`set_context()`****，把它们暂时保存到当前这一轮的全局 ****`Context`**** 里**，然后才调用模型的 `forward()`。后面模型一层一层执行时，就不用把 `block_tables、slot_mapping、state_indices` 这些参数从 `Qwen3_5ForCausalLM.forward()` 一直层层传到每个 Attention 和 GDN 函数里，而是** Attention 到了需要这些信息的时候直接调用 ****`get_context()`**** 去读取**，比如 Attention 根据 `context.slot_mapping` 写 KV，根据 `context.block_tables` 找历史 KV；GDN 根据 `context.state_indices` 找对应请求的 recurrent state。

所以它本质上起到的是一个“这一轮 forward 的共享元数据容器”的作用，把调度层准备的信息和模型底层算子连接起来。等这一轮模型计算和采样结束以后，`ModelRunner.run()` 会调用 `reset_context()` 把它清掉，下一轮 Decode 再重新设置新的 Context。因此它不是 Sequence 的长期状态，也不是 KV Cache 本身，而是只在某一次模型执行期间临时有效的一组公共运行参数。
