## 一、适配 Qwen3.5 Hybrid 架构

### 1. 讲一下你这个项目适配qwen3\.5的这一部分的内容:

我这部分主要做的是**把 nano\-vLLM 原本面向普通 Transformer 的推理框架，适配成能够正确运行 Qwen3\.5 Hybrid 混合架构**。因为 Qwen3\.5 和原来的 Qwen3 最大的区别之一，就是它不是每一层都使用 Full Attention，而是同时包含 **Gated DeltaNet 层和 Full Attention 层**，所以我首先根据模型配置把两类层区分开，分别走不同的执行路径。Full Attention 层还是按照传统方式维护 KV Cache，而 Gated DeltaNet 层不保存完整的历史 KV，而是需要持续维护自己的两个状态分别是 recurrent state 和卷积 state，简单来说，recurrent state 可以理解成对前面历史 Token 信息不断累积、更新形成的一份“长期记忆”，每生成一个新 Token 都会基于旧状态继续更新；

而 卷积 state 可以理解成保存最近几个 Token 的局部信息，也就是一份“短期记忆”，主要供下一步的卷积计算使用。因此针对额外设计了一套 state slot 管理机制，和管理kcvavhe类似来管理新增的这两个状态。

### 2. qwen3\.5为什么要增加这个GDN层呢，有什么好处？：

Qwen3\.5 增加 GDN 层，最主要的目的就是**降低长上下文推理时的计算量和显存占用**。传统 Full Attention 在生成新 Token 时，需要访问前面所有 Token 的 KV，而且历史越长，KV Cache 也越大；GDN 不需要完整保存这些历史 KV，而是把历史信息持续压缩到 recurrent state 和卷积 state 里，所以序列很长时，它的计算和显存开销会更稳定。当然，GDN 相当于把历史信息压缩了，在精确访问很久以前某个 Token 的能力上不如 Full Attention，所以 Qwen3\.5 没有全部使用 GDN，而是采用 **GDN \+ Full Attention 的混合结构**：大部分层用 GDN 提高效率，部分层保留 Full Attention 做全局信息交互。简单来说，就是**用 GDN 降低长上下文成本，再用 Full Attention 保证模型能力，在效率和效果之间做平衡**。

### 3. 你刚才提到GDN层这两个状态的管理，具体是怎么管理的，占用多少空间？：

在我这个版本里，GDN 的两个状态不是跟 KV Cache 一样按 Token 分块管理的，而是我专门做了一套**状态槽**。这里要注意，**不是整个模型只有一份 recurrent state 和卷积 state，而是每个 GDN 层、每个正在运行的请求都有自己的一份状态**。以 Qwen3\.5\-27B 为例，它一共有 64 层，其中是 3 个 GDN 层配 1 个 Full Attention 层，所以总共有 **48 个 GDN 层和 16 个 Full Attention 层**。我会提前在 GPU 上申请一块状态池，一个位置就对应一个请求；请求第一次被调度时分配一个 slot，Prefill 时把状态初始化并不断更新，Decode 时一直在同一个 slot 上原地更新，请求结束以后就把这个 slot 回收；如果请求被抢占，把 slot 释放之后重新 Prefill 来恢复状态。

空间上，27B 的 recurrent state 每个 GDN 层大约是 **48×128×128 个 float32，约 3MB**；卷积 state 只需要保留最近 3 个位置，大约 **60KB**，48 个 GDN 层加起来，一个请求的两类状态大约是 **147MB**。如果用 4 卡张量并行，因为这些 head 会切到 4 张卡上，所以大概是**每张卡 36～37MB/请求**。而它的 Full Attention 一共有 16 层，4 个 KV head、每个 head 256 维，用 BF16 保存，那么 KV Cache 大约是**每个 Token 64KB**：4K 上下文约 256MB，8K 约 512MB，32K 就已经约 2GB。

所以两者最大的区别就是：**KV Cache 会随着上下文长度线性增长，而 GDN 的这两份状态基本是固定大小的，大约 147MB，不会因为从 4K 增长到 32K 就跟着变大**，这也是 GDN 在长上下文推理里非常重要的优势。

### 4. 你了解cuda graph吗，在你项目中怎么体现的：

简单来说，普通推理时 CPU 每一步都要不断向 GPU 发起算子，而 CUDA Graph 是**先把一整套固定的执行流程录下来，后面直接重复回放**，这样可以减少 CPU 发起 Kernel 的开销。它比较适合 Decode 阶段，因为 Decode 每次基本都是处理一个新 Token，执行流程很固定，而 Prefill 的输入长度变化比较大，所以我这个项目主要是在 Decode 阶段使用。具体实现上，我会针对不同 Batch 大小提前录制多张 Graph。真正 Decode 时，根据当前请求数量选择合适的 Graph，然后把新的 Token、位置、KV 索引这些数据写进提前分配好的固定缓冲区，再直接 `replay`。

Qwen3\.5 还多了 GDN 的状态，所以我额外维护了固定的 `state_indices` 缓冲区，每轮只更新请求对应的 state slot 编号，让 GDN 层能够找到自己的 recurrent state 和卷积 state。这样 **Full Attention 通过 KV 索引找缓存，GDN 通过 state slot 找状态**，两套状态都能兼容 CUDA Graph。

### 5. 介绍一下chuncked prefill，在你的项目中怎么体现的：

Chunked Prefill 简单来说就是长 Prompt 不一次性全部计算，而是拆成多个小块，分几轮完成 Prefill。比如 600 个 Token，一次最多处理 256 个，就可以拆成 `256 + 256 + 88`。这样可以避免单个长请求一次占用太多计算资源和显存，也更方便调度。在我这个 Qwen3\.5 版本里，主要由 Scheduler 根据每轮的 Token 预算决定当前处理多少 Prompt Token。每个 Chunk 计算完以后，Full Attention 层产生的 KV Cache 会保留下来，下一块直接接着前面的历史继续算，不需要重复 Prefill。Qwen3\.5 还多了 GDN 状态，所以 **recurrent state 和卷积 state 也必须跨 Chunk 保持连续**，不能每处理一块就重新清零。等所有 Prompt Chunk 都算完以后，请求才进入逐 Token 的 Decode 阶段。

### 6. 介绍一下continues banching，在你的项目中怎么体现的：

Continuous Batching 简单来说就是Batch 里的请求不是固定的，而是每轮推理都会动态调整。比如 A、B、C 一起 Decode，B 提前结束后，不需要等 A、C，也可以马上把新的请求 D 加进来，这样能减少 GPU 空闲，提高吞吐。在我这个项目里，Scheduler 维护 waiting 和 running 两个队列。每轮 Decode 后都会重新组织下一轮 Batch；请求结束后，会立即释放它占用的 **KV Cache Block**，Qwen3\.5 还会同时释放对应的 **GDN state slot**，然后新的请求就可以复用这些资源。这里适配 Qwen3\.5 的关键是：**状态必须跟请求绑定，而不能跟 Batch 里的位置绑定**。Full Attention 通过自己的 KV Block 找历史信息，GDN 通过 state slot 找 recurrent state 和卷积 state。

这样即使每轮 Batch 的成员和顺序发生变化，请求之间的状态也不会串。

### 7. 从端到端介绍一下你的项目qwen3\.5的一次forward流程：

如果从**一次完整的 Qwen3\.5 Forward** 来讲，我会从调度开始说。首先请求进来以后，Scheduler 会判断这一轮是 **Prefill 还是 Decode**，然后 ModelRunner 根据当前请求准备好 `input_ids`、位置、KV Cache 的写入位置，以及 Qwen3\.5 新增的 GDN `state slot` 等信息，再真正进入模型。进入模型以后，Token 先经过 **Embedding 变成 hidden states**，然后依次通过所有 Decoder Layer。这里是 Qwen3\.5 和 Qwen3 最大的区别：每一层会根据配置判断自己是 **Full Attention 还是 GDN**。如果是 Full Attention，就先生成当前 Token 的 Q、K、V，做位置编码，然后把新的 K、V 写进 KV Cache，再结合之前缓存的历史 KV 做注意力计算；

如果是 GDN 层，就不走 KV Cache，而是读取这个请求对应的 **卷积 state 和 recurrent state**，完成这一层计算以后再把两个状态更新回去。也就是说整个模型 Forward 过程中，是 **Full Attention 层不断更新 KV Cache，GDN 层不断更新自己的两个 state**，两条路径交替执行。每个 Decoder Layer 做完它自己的 Attention 或 GDN 计算以后，还会经过 MLP 和残差连接，然后传给下一层。所有层跑完以后，再经过最后的 RMSNorm 得到最终 hidden states，接着通过 **LM Head 映射到整个词表的 logits**，Sampler 根据这些分数采样出下一个 Token。最后这个 Token 会返回 Scheduler，加入当前请求，下一轮再继续 Decode，直到生成 EOS 或达到最大生成长度。

普通 Decode 如果开启了 CUDA Graph，主要是把 **Embedding 到最后 hidden states 这一段模型 Forward** 进行 Graph Replay，LM Head、采样和 Scheduler 仍然在 Graph 外。所以我会把整个流程概括成：**Scheduler 准备请求 → ModelRunner 准备 KV 和 GDN 状态索引 → Embedding → 多层 Full Attention/GDN 混合计算 → Final Norm → LM Head → 采样下一个 Token → 返回 Scheduler → 下一轮继续生成。**Qwen3\.5 适配里最核心的点，就是在整个 Forward 过程中同时保证 **Full Attention 的 KV Cache 和 GDN 的 recurrent/conv state 都跟着对应请求正确更新**。

## 二、多模态

### 1. 请介绍一下你在 Qwen3\.5 多模态部分做了哪些工作，简要说一下整体端到端流程：

主要做的是把原来 nano\-vLLM 只处理文本的推理链路扩展成能够同时处理文字和图片。整体流程我可以简单分成几步：首先用户输入的是 messages，里面既可以有文本，也可以带图片；在进入模型之前，先通过处理器把文本转换成 token，同时在文本序列里面为图片预留对应的图片占位位置。图片这一路会先做尺寸调整、归一化这些预处理，然后送进 Qwen3\.5 的视觉编码器，把原始图片转换成模型能够理解的一组视觉特征。接下来比较关键的一步，就是把这些视觉特征按照前面预留的图片位置，替换或者注入到文本 token 对应的隐藏向量里面，这样进入主模型之后，它看到的就不再是单纯的一串文字，而是一条已经把文字信息和图片信息融合到一起的序列。同时因为图片本身除了前后顺序，还有高和宽两个维度，所以我也适配了 Qwen3\.5 使用的位置编码方式，让文字和图片的位置都能够正确对应。

完成这些处理之后，后面的流程就和正常的大模型推理比较接近了：融合后的序列进入 Qwen3\.5 的主干模型做 Prefill，经过各层计算得到上下文状态，然后进入 Decode 阶段逐个生成 token，最后通过 tokenizer 把生成的 token 转回文字。所以我在多模态部分主要解决的其实就是三个问题：第一是怎么让 nano\-vLLM 接收文本加图片的输入；第二是怎么把视觉编码器产生的图片特征正确插入语言模型；第三是保证图片和文字混合以后的位置编码和整个推理流程仍然是正确的。

### 2. 具体说一下图片预处理和Vision Encoder特征注入这部分，这两部分发生在哪个环节：

具体来说，我把这部分分成两个阶段。第一部分是图片预处理，它发生在请求刚进入 `LLMEngine`、还没有真正进入模型计算的时候。原来的 nano\-vLLM 基本只接收文本，我这里扩展成可以接收 messages 加 image。当识别到图片以后，会先调用图片处理模块：首先把图片统一转成 RGB，然后根据视觉模型的 patch 大小把图片尺寸调整到合适的倍数，再转成张量并做归一化。之后按照 Qwen3\.5 视觉模型要求把图片切成一块一块的 patch，最终得到 `pixel_values`；同时还会记录图片切分以后时间、高度、宽度三个方向的网格大小，也就是 `image_grid_thw`。这里还有一个比较关键的工程问题，就是图片和文本必须对得上。所以我会根据图片最终产生多少个视觉 token，在文本序列里面提前插入相同数量的 `image_pad` 占位符，外面再加图片开始和结束标记。

比如视觉编码器最终会输出 196 个视觉特征，那文本序列里面就提前留 196 个图片位置。最后文本经过 tokenizer 得到 token ids，而 `pixel_values` 和 `image_grid_thw` 会一起挂在这个请求的 Sequence 上送进调度器。第二部分就是 Vision Encoder 和特征注入，它发生在这个请求第一次做 Prefill 的时候。`ModelRunner` 在准备 Prefill 输入时，会把当前 batch 里的图片数据收集起来，同时根据哪些 token 是 `image_pad` 构造一个 `image_token_mask`，相当于记录“语言序列里面哪些位置应该放图片特征”；这里还会根据 `image_grid_thw` 给图片计算三维的位置编码。如果是多卡推理，还要把这些图片张量从 rank 0 同步给其他卡。

真正进入模型以后，先把 `pixel_values` 送进 Vision Encoder。视觉编码器会先把图片 patch 映射成隐藏特征，再经过自己的位置编码和多层视觉模块，最后通过 patch merger 得到和语言模型隐藏维度一致的 `image_embeds`。然后语言模型这一边先正常执行文本的 embedding，得到整条序列的 `hidden_states`，接着做最关键的一步：根据刚才的 `image_token_mask`，把那些 `image_pad` 位置原本的普通 token embedding 直接替换成 Vision Encoder 输出的 `image_embeds`。也就是说最后形成的是类似“文字特征、文字特征、图片特征、图片特征、文字特征”这样的一条统一序列，然后再一起进入 Qwen3\.5 后面的 Hybrid Decoder 层进行计算。这个替换位置就是我理解的真正的视觉特征注入点。

所以如果一句话概括工程位置：**图片预处理是在请求进入引擎、创建 Sequence 之前完成；Vision Encoder 和图片特征注入是在 Prefill 的模型 forward 中完成，其中 Vision Encoder 先把图片变成特征，随后在 token embedding 之后、进入第一层 Decoder 之前，把图片占位位置替换成真正的视觉特征。后续 Decode 就不需要再跑图片和 Vision Encoder 了，而是直接利用 Prefill 已经建立好的上下文状态继续逐 token 生成。**

### 3. 具体说下Interleaved MRoPE的特点，它在forward的哪一个环节，现在的结构相比于原来的版本有哪些提升：

Interleaved MRoPE 我理解它本质上还是位置编码，只不过是为了让 Qwen3\.5 能同时处理文字和图片，对原来 Qwen3 的 RoPE 做了多维扩展。原来的 Qwen3 比较简单，每个 token 只有一个一维位置，比如第 0、1、2、3 个 token，然后在 Attention 里面给 Q 和 K 加上这种位置信息；但是图片不一样，一张图片被切成很多视觉 token 之后，只知道它是第几个 token 是不够的，还希望模型知道它在图片的第几行、第几列，视频的话还要知道它属于哪个时间位置。所以 Qwen3\.5 的 MRoPE 会给视觉 token 维护三组位置，可以简单理解成时间、高度和宽度三个维度。

这里的 Interleaved，也就是“交错”的意思，是说这三种位置信息不是简单各占一整块维度，而是按照一定规则交错放到旋转位置编码的不同维度里面，比如一部分频率表示时间、一部分表示高度、一部分表示宽度，让这三类空间信息共同进入 Q、K。我们这个实现里还用了部分旋转，也就是并不是整个 head\_dim 都做位置旋转，而是只对前面一部分维度做 MRoPE，剩下的维度保持不变。它在 forward 里的位置也比较明确。对于多模态请求，在 Prefill 之前，ModelRunner 会先根据图片切分后的 `image_grid_thw`，给图片 token 算出时间、高度、宽度这三维的位置；文本 token 则还是正常的一维顺序。进入模型以后，先做文本 embedding，并且把图片占位 token 替换成 Vision Encoder 得到的视觉特征。

之后进入每一层 Decoder，如果这一层是 Full Attention，就先把 hidden states 投影成 Q、K、V，然后对 Q 和 K 做归一化，**紧接着就在真正计算 Attention 之前执行 Interleaved MRoPE，把位置信息加到 Q 和 K 上，再拿处理后的 Q、K、V 去做 Attention**。所以它的位置可以记成：`QKV 投影 → Q/K 归一化 → Interleaved MRoPE → Attention`。另外这个项目里的 Gated DeltaNet 层不走这套 Full Attention，所以 MRoPE 主要是在 Full Attention 层里面使用。相比原来的 Qwen3，我觉得它最大的提升不是说计算速度更快，而是**位置表达能力更强，而且同时兼容纯文本和多模态**。

原来的 Qwen3 RoPE 只有一维位置，并且基本就是对整个 head\_dim 做普通旋转，它很适合纯文本，因为文字天然就是一条一维序列；Qwen3\.5 现在如果是纯文本，仍然可以传普通的一维位置，这时候效果基本就退化成普通 RoPE，不影响文本推理；如果遇到图片，就切换成三维位置，让模型不仅知道“这个视觉 token 排在第几个”，还知道“它在图片的什么位置”。所以从工程上看，我只需要维护一套 Interleaved MRoPE，就可以同时覆盖纯文本和图文混合两种场景；从模型能力上看，它给视觉 token 保留了更完整的二维空间关系，这也是 Qwen3\.5 能够把视觉信息比较自然地融合进语言模型的一部分基础。

## 三、MTP 投机解码原型

### 1. 讲一下你的MTP这部分内容，说一下整体流程：

我这部分做的是一个 MTP 投机解码原型，核心思路是**让一个更轻量的 MTP 分支先预测后面几个 token，再由主模型统一验证，如果预测正确，就一次接受多个 token，从而减少主模型逐 token 解码的次数。**具体流程是，一轮生成开始后，主模型先正常生成一个 token，同时保留当前最后位置的隐藏状态。然后把这个隐藏状态和刚生成 token 的 embedding 一起送进 MTP 模块，经过归一化和特征融合后，连续预测后面的几个候选 token，这一步就是 Draft。接下来进入 Verify。因为 MTP 只是负责“猜”，候选结果不能直接采用，所以还需要让完整的 Qwen3\.5 主模型重新计算这些位置，并从前往后逐个比较。如果候选和主模型结果一致，就连续 Accept；一旦出现第一个不一致的位置，就 Reject 后面所有候选，并采用主模型在这个位置得到的正确结果。这里比较关键的是状态一致性。

因为 Qwen3\.5 是 Hybrid 架构，Verify 过程中不仅 Full Attention 的 KV Cache 会发生变化，Gated DeltaNet 的 recurrent state 和 conv state 也会被更新。如果候选最后被拒绝，这些错误候选产生的状态不能保留下来。所以我在 Verify 前会保存状态快照，包括 Sequence 长度、Block 信息、KV Cache 以及 GDN state。如果候选全部通过，就直接保留验证后的状态；如果中途 Reject，就恢复到验证前的状态，然后只对已经确认的正确前缀重新计算，重新建立正确的 KV Cache 和 GDN state，再进入下一轮生成。

### 2. 为什么项目中是mtp而不是完整的投机解码，你的项目中如果要完整的做投机解码还需要做哪些工作：

严格来说，我这个项目不是说“做了 MTP，所以没有做投机解码”，而是**用 MTP 作为投机解码里面的 Draft 模块，目前把核心链路做成了一个原型，还没有做到完整的生产级投机解码引擎**。MTP 主要负责根据主模型的隐藏状态提前预测后面几个 token，我已经把 Draft、主模型 Verify、Accept/Reject，以及 Qwen3\.5 Hybrid 架构下 KV Cache 和 GDN state 的快照回滚这些核心逻辑跑通了。但是现在这套逻辑还有一些比较明显的原型限制，比如主要是单请求运行，部分 MTP 快路径还是 text\-only，而且 Verify 虽然可以一次处理多个候选 token，但底层还没有做到真正高效的并行验证，所以目前重点是验证正确性，还不能保证一定比普通 Decode 更快。如果要继续把它做成完整的投机解码，我觉得主要还要补几个方面。

第一，要把现在相对独立的 MTP 流程真正集成进 Engine 和 Scheduler 的正常 Decode 循环，而不是通过单独的测试流程控制。第二，要支持 Continuous Batching，也就是多个请求同时运行时，每个请求的 draft 长度、接受长度都可能不一样，调度器要能够动态组织这些请求。第三，要把 Verify 做得更高效，最好能够一次并行验证多个候选 token，而不是内部仍然接近逐 token 执行，否则虽然减少了调度次数，但主模型计算量并没有真正降下来。第四，要优化状态管理，现在 Reject 后需要快照恢复甚至重新计算正确前缀，生产级实现需要尽量减少 KV Cache 和 GDN state 的拷贝、恢复和重算开销。最后还要补齐不同采样策略、EOS、抢占、CUDA Graph、多卡以及多模态这些边界场景，并通过实际 Benchmark 证明接受率和额外开销最终能够带来 Decode 吞吐或者 TPOT 的真实提升。

所以我现在更愿意把它描述成\*\*“基于 MTP 打通了投机解码的核心正确性链路”，距离完整的高性能投机解码主要还差调度器集成、批量并发和验证路径的性能优化。\*\*

### 3. 你的项目中draft模型是什么结构，简要说一下如何验证draft模型的输出是否正确：

我这个项目里的 Draft 模型并不是再单独放一个完整的小语言模型，而是**挂在主模型旁边的一套轻量 MTP 模块**。它的输入有两部分：一部分是主模型或者上一轮 MTP 得到的 hidden state，代表前面的上下文；另一部分是当前已经生成 token 的 embedding。两路先分别做 RMSNorm，然后拼接成大约 `2H` 的特征，再通过一个线性层压回 `H` 维。后面只经过很少量的 Decoder 层，每层还是比较标准的 Full Attention 加 MLP 结构，最后再做一次归一化，并复用主模型的 LM Head 得到下一个 Draft token。所以相比完整主模型，它层数少很多，计算量更小，适合用来提前“猜”后面的 token。验证的时候，**Draft 的结果不能直接作为最终输出，真正的标准还是主模型**。

比如 MTP 连续预测了 A、B、C 三个 token，我会把这些候选交给主模型做 Verify，得到主模型认为对应位置应该生成的 token，然后从前往后比较。当前原型主要采用贪心解码，所以判断方式比较直接：Draft token 和主模型 token 相同就 Accept，继续比较下一个；一旦某个位置不同，就从这个位置开始 Reject 后面的候选，采用主模型的结果，并根据需要恢复 KV Cache 和 GDN state。也就是说，**MTP 负责低成本地提出候选，主模型负责最终判定正确性，因此即使 Draft 猜错，也不会改变最终主模型的生成结果。**

### 4. 你的draft模型是qwen3结构吗有几层，解释一下主模型验证draft模型输出是否正确是逐token验证还是一次性输入一轮的token进行验证：

我这里的 Draft 模型严格来说**不是一个完整的 Qwen3 小模型**，而是一个轻量的 MTP 模块。它的主体比较像 Qwen3 的标准 Decoder 层，使用的是 Full Attention 加 MLP，没有采用 Qwen3\.5 主模型里面 Gated DeltaNet 和 Full Attention 混合的结构。前面会先把主模型的 hidden state 和当前 token 的 embedding 分别归一化，然后拼接、线性映射回 hidden size，再进入 MTP Decoder。我的实现里层数由 `num_nextn_predict_layers` 控制，如果配置里没有指定就默认是 **1 层**，所以它相比几十层的主模型要轻很多，最后再复用主模型的 LM Head 来预测候选 token。主模型验证 Draft 输出时，我这个原型的默认实现实际上是**逐 token 验证**。

比如 MTP 猜出了 A、B、C 三个 token，外层会把这一轮候选一起交给 Verify 接口，但是 Verify 内部仍然按照正常 Decode 的方式：先输入当前真实 token，让主模型预测 A；再把 A 加进去预测 B；再预测 C。所以从接口上看是一轮验证多个 token，但底层实际上做了多次主模型 forward，然后拿主模型得到的 A、B、C 和 Draft 的结果从前往后比较，一旦第一个位置不一致，就 Reject 后面的候选。项目里我也做了一条 chunk verify 的实验路径，就是希望把这一轮多个候选一次性送进主模型，通过因果掩码一次 forward 得到多个位置的结果，这才是真正更有性能价值的并行验证。

但是因为 Qwen3\.5 还有 GDN 的 recurrent state 和 conv state，多个 token 一次计算时状态更新比普通 Transformer 更复杂，所以目前这条路径还是实验性质，还会和逐 token 的可信结果做一致性校验。所以面试时我会明确说：**Draft 是默认 1 层的轻量 Full Attention Decoder，不是完整 Qwen3；当前稳定的 Verify 是外层批量、内部逐 token 验证，同时实现了单次 forward 验证多个 token 的 chunk 原型，但 GDN 状态处理还需要继续完善。**

### 5. 讲一下如何状态快照回滚：

我这里做状态快照回滚，主要是因为主模型在 Verify 候选 token 时会真实修改内部状态，但候选最后可能被 Reject，所以必须能够恢复到 Verify 之前。Qwen3\.5 是 Hybrid 架构，所以需要保存两类状态。第一类是调度侧状态，比如当前 Sequence 的 token、长度、Block Table 和 BlockManager 的占用情况；第二类是 GPU 上的模型状态，包括 Full Attention 的 KV Cache，以及 Gated DeltaNet 每一层的 conv state 和 recurrent state。为了减少开销，KV Cache 不会整块复制，而是只保存当前请求 Verify 可能修改到的那些 KV slot。Verify 完成后，如果候选全部 Accept，就直接保留新的 KV 和 GDN state，把快照丢掉；

如果中途 Reject，就先恢复 Sequence 和 Block Table，再把保存的 KV Cache、conv state 和 recurrent state 写回原来的位置，让模型恢复到 Verify 之前的状态。恢复以后，还会用主模型重新计算真正接受的正确 token，把对应的 KV 和 GDN state 重新建立起来，再进入下一轮生成。

### 6. 你刚才提到隐藏状态和刚生成 token 的 embedding 一起送进 MTP 模块，经过归一化和特征融合，展开说一下：

这里展开讲一下。MTP 每预测一个候选 token，会同时用两类信息：一类是**主模型或上一轮 MTP 的隐藏状态**，表示前面上下文的信息；另一类是**当前已经生成 token 的 embedding**，告诉 MTP 当前具体生成到了哪个 token。第一步 Draft 时，主模型 forward 后先取最后一个位置的 hidden state，再通过 LM Head 得到下一个 token。这个 token 再经过主模型的 embedding 层得到向量。这样 MTP 就有两路输入：上下文 hidden state 和当前 token embedding。进入 MTP 后，两路特征会**分别做 RMSNorm，然后在最后一个维度拼接**。假设 hidden size 是 H，两路都是 H 维，拼接后就是 2H，再经过一个线性层投影回 H 维。

这个过程就是特征融合，可以理解成让模型自己学习怎么组合“前面的上下文”和“当前生成的 token”这两部分信息。融合后的特征再经过 MTP 自己的一层 Decoder 和最终归一化，得到新的 hidden state，然后复用 LM Head 预测下一个候选 token。如果继续 Draft，就把这个新的 hidden state 和刚预测 token 的 embedding 再走一遍相同流程。所以整体可以概括成：\*\*上下文 hidden state \+ 当前 token embedding → 分别归一化 → 拼接成 2H → 线性投影回 H → MTP Decoder → LM Head → 得到下一个候选 token。\*\*这样既保留上下文信息，也明确告诉 MTP 当前生成到了哪个位置。

## 四、融合 KV Cache 压缩机制

### 1. 请你简单讲一下你的 KV Cache 压缩机制：

我的 KV Cache 压缩只作用在 Qwen3\.5 Hybrid 架构的 Full Attention 层，因为 Gated DeltaNet 层维护的是 recurrent state 和 convolution state，并不使用标准的 KV Cache。整体上，我采用的是周期式、窗口化的在线压缩机制：Scheduler 会维护全局 Decode 调度步，每隔固定周期检查当前请求，从已经积累出足够大未压缩 KV 窗口的候选请求中，选取有限数量进行压缩。压缩时只处理一个固定大小的窗口；利用当前 token 在该 Attention 层产生的 Query，与窗口内的 Key 计算注意力相关性，再通过 SnapKV的思想保留重要的 K/V缓存。随后，我会把筛选出的 K/V 压紧到 KV Cache 中block的连续位置，并通知 Scheduler 和 BlockManager 回收不再使用的尾部物理 Blocks。

这样请求继续生成时，会重新积累新的未压缩窗口，达到下一次调度周期后再执行压缩，因此它主要适合长序列生成和高并发场景，可以降低 KV Cache 的长期增长速度；但由于属于有损压缩，也需要权衡压缩开销和长上下文精度。举个例子以默认配置来说，一个 Block 是 256 个 token，窗口是 4 个 Block，也就是 1024 个 KV，每次压缩从窗口的1024个kvcache中保留一半，那么在生成的token中就能节省一半的kvcache显存占用，但是这个压缩策略只是压缩decode阶段生成token的kvcache，不压缩prefill阶段的kvcache。

### 2. 你的kv cache压缩策略主要想解决什么问题呢，你有关注目前业界使用的kvcache压缩策略吗：

这个策略主要想解决的是在长文本生成和高并发场景下，KV Cache 会随着序列长度和请求数量不断增长，不仅会占用越来越多的显存，降低系统能同时处理的请求数，而且每生成一个新 token 都要读取更长的历史缓存，单步生成也可能越来越慢。 我有关注目前常见的 KV Cache 优化方法，大致可以分成三类：第一类是减少保留的历史 token，例如 StreamingLLM 固定保留开头少量位置和最近窗口，H2O 保留近期内容以及长期受到较多关注的位置，SnapKV 根据当前生成状态筛选重要历史位置，PyramidKV 则进一步为不同网络层分配不同的缓存量。\(arXiv\) 第二类是不删除 token，而是降低每份 KV 的存储精度，例如 vLLM 已支持 FP8 KV Cache，KIVI 则研究了更低位宽的量化。\(vLLM\) 第三类是缓存管理，例如前缀复用以及把暂时不用的缓存转移到 CPU，TensorRT\-LLM 就提供了这类能力。

### 3. 在你的项目中，kv cache保存发生在哪个环节，使用什么策略，在显存中是怎么保存的，展开来讲一下：

在我的项目里，KV Cache **不是等一层计算结束后统一保存，也不是在整个模型最后再保存，而是在每个全注意力层内部，算出当前 token 的 K、V 后立即写入显存**。具体来说，输入先经过投影得到 Q、K、V，Q 和 K 再完成归一化以及位置编码，然后在真正进行注意力计算之前，当前这批 token 的 K、V 会先被写入缓存；预填充阶段如果使用分块预填充，就一次保存本轮处理的那一段输入 token，生成阶段则每轮保存当前输入 token 的一份 K、V，再利用缓存中的历史 K、V 计算下一个 token。显存管理上，我采用的是分页式策略：程序启动时先根据可用显存申请一个大的 KV Cache 池，它的结构可以理解为“K 和 V 两份、全注意力层数、物理块数量、每块 256 个 token、本张卡负责的 KV 头数、每个头的维度”。调度器不会要求一个请求的缓存连续存放，而是给请求分配若干物理块，并用块表记录“第几个逻辑块对应哪个物理块”；

模型执行前，再根据 token 的逻辑位置计算实际写入地址，也就是“物理块编号乘以 256，再加块内偏移”。注意力层中有一个 Triton 写入算子，会按照这张地址表把 K、V 写到对应槽位；后面读取历史缓存时，再通过块表和当前有效长度找到所有物理块，因此请求增长时只需要追加新块，请求结束时按块回收，不需要搬动整段缓存。多卡推理时，每张卡只保存分配给自己的那部分 KV 头，而不是每张卡都保存完整缓存。另外，Qwen3\.5 是混合架构，只有 Full Attention 层使用这种 KV Cache，Gated DeltaNet 层保存的是另外一套卷积状态和循环状态。在我加入压缩机制后，生成阶段还会周期性地根据当前 Query 对一段历史 KV 进行重要性筛选，保留关键历史信息和最近窗口，把保留的 KV 向前紧凑存放，然后缩短物理 KV 长度并释放尾部不用的块；

这里逻辑 token 历史仍然完整，只是显存中真正保留的 KV 数量变少了，这也是我项目中同时维护逻辑长度和物理 KV 长度的原因。

### 4. 我看你的项目中写到你的筛选的策略是snapkv思路，展开讲一下这个筛选策略。这个思路是你自己想的吗还是有参考来源的参考，如果是参考的那是参考的哪里的思路，和人家原版有什么区别：

这个筛选思路不是我从零提出的，我主要参考了 2024 年的论文《SnapKV：模型在生成前就知道自己要找什么》以及它的公开代码。原版 SnapKV 的核心观察是：对于一段很长的输入，模型后续生成时真正反复关注的历史位置通常只占一小部分，而且这些重要位置可以通过输入末尾的一小段内容提前判断出来。它具体会把输入末尾保留为一个“观察窗口”，让这个窗口中的多组 Query 和前面较长的历史 Key 计算注意力分数，再把同一历史位置得到的分数累加；为了避免只保留某个孤立的词、破坏一整段信息，它还会对相邻位置的分数做池化，相当于让重要位置周围的内容也有更大机会保留下来。之后，每个注意力头分别选出得分最高的一部分历史 K/V，再和完整的观察窗口拼接，作为后续生成使用的压缩缓存。

\([arXiv](https://arxiv.org/html/2404.14469v2)\) 我的实现保留了它最核心的思想，也就是**用当前的注意力关系判断哪些历史 K/V 更重要，而不是简单地按新旧顺序删除**，但并不是对原版算法的直接复现。第一，原版主要在输入处理结束时对很长的提示词压缩一次，后续生成阶段基本不再更新；我的方案是在生成过程中周期性执行，每当积累出一个新的未压缩窗口，就可以再次筛选，所以更适合持续生成很长内容的场景。第二，原版用输入末尾多个 Query 共同投票，并且每个注意力头可以保留不同的位置；我的实现为了控制在线压缩开销，主要使用当前 token 的 Query 进行评分，再把各个头的结果汇总成每层统一的 token 重要性分数，同时做局部平均平滑，然后选出得分最高的位置。第三，我的窗口之外还会保护开头的固定位置、当前 token 和尚未进入压缩窗口的近期内容，避免把维持生成连续性的信息误删。

第四，也是我项目中更主要的工程工作，筛选结束后不是只得到一个下标列表，而是把选中的 K/V 在分页缓存中真正搬到连续位置，等所有全注意力层都完成后，再通知调度器回收不用的物理缓存块；同时，Qwen3\.5 中的 GDN 层不是标准 KV Cache，因此只压缩全注意力层。

## 五、性能评估

### 1. 这些指标都是什么意思，比如ttft，tpot，吞吐量等等：

在大模型推理里，我一般会把性能指标分成**用户体验、系统吞吐和资源占用**三类来看。首先，**TTFT，也就是首个 token 延迟**，指从用户提交请求开始，到模型返回第一个 token 需要多长时间，它主要受到排队、输入预处理和预填充计算影响，输入越长，通常 TTFT 越大；这个指标决定用户点击发送后要等多久才能看到模型开始回答。第二个是 **TPOT，也就是平均每生成一个 token 的耗时**，通常只统计生成阶段，例如 TPOT 是 20 毫秒，就表示模型平均每 20 毫秒生成一个 token；它越低，用户看到的输出速度越快。和它接近的还有 **ITL，也就是相邻两个输出 token 之间的时间间隔**，TPOT 更像整段生成过程的平均值，而 ITL 可以反映生成过程中是否出现卡顿。第三个是**端到端延迟**，也就是从请求进入到整段回答全部生成完成的总时间，它大致由排队时间、首个 token 延迟，以及后续所有 token 的生成时间组成。

吞吐量则表示系统单位时间能完成多少工作，但要区分具体口径：**token 吞吐量**通常是每秒处理或生成多少个 token，**请求吞吐量**是每秒完成多少个请求，也就是 QPS；我的项目里重点测试的 **Decode Throughput**，就是生成阶段每秒能够产出多少个 token。吞吐量高不一定代表单个用户体验好，例如通过增大批处理可以同时服务更多请求、提升总吞吐，但每个请求可能需要排队更久，TTFT 和 TPOT 反而上升，所以延迟和吞吐一般需要一起看。另外还有**并发量**，表示系统能同时处理多少个请求；**显存占用**，主要包括模型权重、KV Cache 和临时计算空间；**KV Cache 或 Block 占用**，表示历史缓存使用了多少物理块；以及我压缩功能重点关注的**压缩耗时、缓存峰值下降比例、最大并发提升比例和精度损失**。

所以评价一个推理系统不能只看单一指标：交互式聊天更关心 TTFT 和 TPOT，离线批量任务更关心整体吞吐，而我的 KV Cache 压缩方案需要综合证明它确实降低了显存、提升了并发，同时没有让 TPOT 和回答准确率出现过大的退化。

### 2. 讲一下你的性能测试这部分内容，你怎么设计的实验，这些指标都代表什么意思：

我这部分性能测试主要分成三组，整体环境固定在 **4 张 RTX 3090、TP=4**，核心思路是做控制变量，每组实验只回答一个问题。第一组是测我适配完 Qwen3\.5\-27B 之后的基础推理性能，我固定 **并发 8、每个请求 1K 输入、1K 输出**，关闭 KV Cache 压缩和 MTP，正式测试前先预热，并且把输入、输出长度和采样参数固定住，避免不同请求长度造成干扰，最后测到 **Decode 吞吐是 111\.8 token/s**。这里 Decode 吞吐指的是进入逐 token 生成阶段以后，整个系统所有请求加起来每秒能生成多少个 token，所以越高代表持续生成能力越强。另外我也会关注 **TTFT 和 TPOT**，TTFT 就是请求提交以后多久能看到第一个 token，它主要反映前面的 Prefill 和调度开销；

TPOT 是第一个 token 出来以后，后续平均生成一个 token 需要多长时间，它更能反映 Decode 阶段的延迟。第二组实验专门测试我做的 **KV Cache 压缩**，这里使用 **4K 输入、4K 输出**的长序列，因为 KV Cache 的压力主要是在长上下文和高并发下才明显。我会保证模型、Prompt、输出长度、显存配置这些都完全一样，只对比关闭压缩和开启压缩两种情况，然后逐渐提高并发。这里我没有简单用 `nvidia-smi` 的显存变化来证明压缩效果，因为底层 KV Cache 的大块显存是提前申请好的，我更关注实际正在使用的 **活跃 KV Block**。结果是开启压缩以后，峰值活跃 Block **降低了 47\.2%**。同时我还统计了请求抢占，因为当 KV 空间不够时，调度器可能需要把某个请求暂时抢占掉，后面再重新计算，这会产生额外开销。

所以我又统计了“**零抢占最大并发**”，也就是所有请求都正常完成而且一次抢占都没有时，最多能同时跑多少请求，这个指标从 **4 提升到了 7**。因为 KV 压力和抢占重算减少了，最终 **Decode 吞吐相比不开压缩提升了 11\.6%**。所以这部分的结论不只是“KV 少了 47\.2%”，而是说明压缩确实进一步转化成了更高的可用并发和实际吞吐收益。第三组实验是测试 **Qwen3\.6\-27B 的 MTP\-1**，这里主要看 Draft Token 的接受率。简单来说就是 MTP 先猜主模型下一个会生成什么 token，然后主模型真正计算一次，如果两个 token 相同就算接受，不同就拒绝，最后用“接受的 Draft Token 数除以总验证次数”得到接受率，我测出来是 **63\.72%**。也就是说大约每 100 次预测有 64 次能够直接猜中主模型结果。

不过我在简历里只写接受率，没有直接说它带来了多少加速，因为接受率不等于端到端加速比，实际速度还要考虑 Draft 本身的计算开销以及 Verify 的成本。整体来说，我这三组实验分别验证了三个问题：**基础 Qwen3\.5 推理速度怎么样、KV Cache 压缩能不能真正改善长序列高并发能力，以及 MTP 生成的 Draft Token 到底有多可靠。**

### 3. 测第一个实验时固定并发8万一达不到并发8是因为什么原因，解释一下实验2峰值活跃 Block 降低了 47\.2%，什么是峰值活跃 Block：

第一个实验里我说固定并发 8，实际含义是**一次向引擎提交 8 个请求，希望调度器同时维护这 8 个请求**，并不代表任何情况下 GPU 上都一定能同时跑满 8 个。如果最后实际运行过程中达不到并发 8，我首先会判断是不是**资源限制或者调度限制**。比如 `max_num_seqs` 如果小于 8，那是配置直接限制了并发；`max_num_batched_tokens` 太小的话，8 个请求的 Prefill 可能不能一起处理，而是被拆成多轮；更关键的是显存，如果模型权重加载之后，剩下的显存不足以同时保存 8 个请求需要的 KV Cache 和 Qwen3\.5 GDN 层的状态，那么调度器就只能先让一部分请求运行，其他请求等待，严重时还可能发生抢占。

所以我实验一专门固定 `max_num_seqs=8`，1K 输入、1K 输出时 `max_num_batched_tokens=8192`，并且给运行时和 GDN state 留一定显存余量，就是为了保证这个并发 8 本身是可运行的。实验二里我写的 **“峰值活跃 Block 降低 47\.2%”**，这里的 Block 指的是我项目里管理 KV Cache 的基本存储单位，一个 Block 可以理解成一页 KV Cache，我这里一个 Block 对应 **256 个 token**。 一个请求生成得越长，它历史上需要保存的 K、V 越多，占用的 Block 也就越多；并发请求越多，所有请求加起来占用的 Block 就更多。所谓“**活跃 Block**”，就是某一个时刻真正分配给当前这些活跃请求、里面保存着有效 KV 数据的 Block；“**峰值活跃 Block**”就是整个测试运行过程中，这个数量达到过的最大值。

比如不开压缩时，运行过程中最多同时占用了 1000 个有效 Block，而开启压缩后最高只占用了 528 个，那么下降比例就是 47\.2%。我的压缩机制会周期性把 Full Attention 层里重要性比较低的历史 KV 删除掉，只留下关键历史信息和最近窗口，所以旧 Block 可以被释放，重新放回空闲 Block 池，后面的请求或者新生成的 token 就能够继续使用这些 Block。这个指标我觉得比直接说“显存降低 47\.2%”要严谨，因为我的 KV Cache 底层显存池在初始化时就已经提前申请好了，所以你去看 `nvidia-smi`，可能不会看到显存真的下降 47\.2%。\*\*真正降低的是运行过程中有效 KV 数据占用的物理 Block 数量，也就是 KV Cache 的实际使用压力。

\*\*这也是为什么我后面还要继续看零抢占并发和 Decode 吞吐：按照我现在简历上的 **4K 输入、4K 输出**实验结果，峰值活跃 Block 降低 **47\.2%** 后，空闲 Block 更多了，所以更多请求可以同时驻留，零抢占并发从 **4 提升到了 7**；同时因为抢占和重新计算减少，Decode 吞吐最终提升了 **11\.6%**。也就是说，这三个指标实际上是一条完整的因果链：**KV 压缩 → 活跃 Block 占用下降 → KV 空间压力减小 → 能同时保留更多请求、减少抢占 → 最终提高并发能力和 Decode 吞吐。**

## 六、项目相关八股

### 1. 讲一下kvcache：

KV Cache 的作用是缓存模型在生成过程中已经计算过的 Key 和 Value，避免每生成一个新 Token 都重新计算前面所有 Token 的注意力结果。在 Prefill 阶段，模型会一次性处理输入序列，并在每个 Transformer 层保存各个 Token 对应的 K、V，然后将它存在显存当中；进入 Decode 阶段后，每次只需要计算新 Token 的 Query、Key 和 Value，然后让新的 Query 与缓存中的历史 K、V 做注意力计算即可。这样就把逐 Token 解码时大量重复计算转化成了缓存读取，显著降低计算量并提高生成速度，但代价是 KV Cache 会随着序列长度、并发请求数和模型层数增加而占用大量 GPU 显存，因此 KV Cache 的分配、复用和压缩是大模型推理系统中的核心优化点。

### 2. 讲一下kv cache的占用显存应该怎么计算？：

KV Cache 的显存占用，我一般先从单个请求的理论占用来算，公式是：\(2 \\times L \\times S \\times N\_\{kv\} \\times D\_\{head\} \\times Bytes\)。其中 2 表示 Key 和 Value 两份缓存，\(L\) 是 Transformer 层数，\(S\) 是当前缓存的 Token 数，\(N\_\{kv\}\) 是 KV Head 数，\(D\_\{head\}\) 是每个 Head 的维度，\(Bytes\) 是数据类型的字节数，比如 FP16 或 BF16 是 2 字节、FP8 是 1 字节；如果有多个并发请求，还要对每条请求的有效缓存长度求和，长度相同时可以直接乘并发数。这里要注意，GQA 或 MQA 模型应该使用 KV Head 数，而不是 Query Head 数，所以它们的缓存会明显更小。

如果使用张量并行，还要看 KV Head 是否按卡切分，均匀切分时单卡占用大约再除以 TP 数，但某些 KV Head 较少的情况可能发生复制，不能机械地除。工程上如果使用 Paged KV Cache，实际占用还不是严格按 Token 连续分配，而要把每条请求的长度向上取整到 Block 大小，例如需要的 Block 数是 \(\\lceil S/B\\rceil\)，再乘每个 Block 在所有层中的 K、V 大小；因此实际显存还会受到 Block 对齐、尾块未填满、Prefix Cache 共享和缓存池预分配方式的影响。最终我会区分两个指标：公式算出的是有效 KV 数据量，而推理框架真正可调度的占用要看已使用的物理 KV Block 数；模型权重、激活值和临时计算空间则不属于 KV Cache 本身。

### 3. 一般情况下，kv cache的一个block应该是多大？这个有讲究吗？你的项目用的是多大，解释一下：

一般没有绝对统一的最优值，例如当前 vLLM 默认是 16 个 token 一块。这个参数本质上是在显存利用率和管理开销之间做平衡：block 越小，分配和回收越精细，最后一个没装满的块浪费更少，前缀复用、请求抢占和缓存压缩也更灵活，但 block 数量会变多，块表、索引和调度开销更大；block 越大，块的数量更少，管理更简单，但短请求和最后一个块更容易产生显存碎片，释放和压缩的粒度也会比较粗。我的项目是在 nano\-vLLM 上做 Qwen3\.5 Hybrid 和 KV Cache 压缩适配的， 实际采用的是 **256 个 token 一个 block**，仓库里的 `Config.kvcache_block_size` 和 `Sequence.block_size` 默认都是 256，而且配置要求 block 大小必须是 256 的倍数。

这里选择 256，不是说它理论上一定最优，而是因为原 nano\-vLLM 的序列管理、块表映射、缓存分配等实现都是围绕这个粒度设计的，我在加入 Qwen3\.5 和压缩机制时优先保持原有执行链路稳定；同时压缩窗口也是按 block 配置的，例如默认 4 个 block，就对应 1024 个 token 的待压缩窗口。它的缺点是粒度比较粗，单个请求最后一个 block 最坏可能空出 255 个位置，因此更严谨的做法是后续对 16、32、64、128 和 256 等不同取值进行测试，综合比较显存碎片、吞吐、调度开销、压缩耗时和最大并发量，再确定具体硬件和模型下的最优值。

### 4. 讲一下page attention的思想，并且在你的项目当中是怎么体现的：

PagedAttention 的核心思想可以类比操作系统的分页管理：它**不改变注意力计算本身，而是改变 KV Cache 在显存里的存放和管理方式**。传统做法可能会为每个请求预留一整块连续显存，但不同请求的输入长度和生成长度都不确定，容易出现预留过多、显存碎片以及扩容困难的问题；PagedAttention 会把 KV Cache 划分成固定大小的物理块，一个请求在逻辑上仍然拥有连续的历史 KV，但这些数据在显存中可以分散存放，再通过一张块表记录“请求的第几个逻辑块对应显存中的哪个物理块”。这样请求变长时只需要再申请一个空闲块，请求结束或被抢占时也可以按块回收，不需要搬动整段缓存，因此能够提高显存利用率和并发请求数量。在我的项目里，这套机制主要体现在四个位置：首先，每个请求的 `Sequence` 中都有一张 `block_table`，记录逻辑块到物理块的映射，项目设置的是每个块存放 **256 个 token** 的 KV；

其次，`BlockManager` 负责物理块的申请、复用和释放，调度器根据请求当前的 KV 长度判断是否需要增加新块；然后，`ModelRunner` 会根据块表计算当前 token 应该写入的具体显存位置，也就是 `slot_mapping`；最后，注意力层在解码时把块表和当前有效 KV 长度交给注意力算子，使它能够从分散的物理块中读取完整历史 KV。因为我的项目适配的是 Qwen3\.5 混合架构，所以还要强调一点：只有全注意力层使用这种分页式 KV Cache，Gated DeltaNet 层保存的是固定大小的卷积状态和循环状态，由另一套状态槽管理。另外，我做 KV Cache 压缩时也依赖这套分页机制：先把筛选后保留的关键 KV 搬到前面的有效位置，再更新物理 KV 长度和块表，最后释放尾部不再需要的物理块。也就是说，PagedAttention 不仅解决了普通推理中的显存碎片问题，也为我的动态压缩、块回收和高并发调度提供了基础。

### 5. 一般大模型所说的上下文包含哪些内容：

一般说的大模型上下文，可以理解成**模型在生成当前回答时能够看到的全部信息**。它不只是用户这一轮输入，还包括系统提示词、之前多轮对话中的用户问题和模型回答、当前问题，以及通过工具检索出来的文档内容、搜索结果等。对于多模态模型，图片或视频经过视觉编码后得到的特征，也会按照特定位置插入到文本序列中，成为上下文的一部分；我的项目支持 `messages + image` 输入，就是先把对话内容整理成 token，再把图片特征注入到对应的图片占位位置中。 在生成阶段，模型已经生成出来的 token 也会不断加入上下文，例如生成第十个 token 时，前九个生成结果都属于它当前能够参考的历史。我们平时说的 32K、128K 上下文长度，通常指一次请求中**输入 token 和允许生成的输出 token 的总长度上限**。

需要区分的是，上下文是逻辑上的历史内容，而 KV Cache 是为了避免重复计算，把这些历史 token 在各层计算得到的 K、V 保存下来；模型权重、临时中间结果以及显存里预留但还没使用的空间，都不能算作上下文本身。

### 6. 简单讲一下你的项目中是怎么进行采样得到token的，使用的是什么方案：

我的项目采用的是一种比较简单的**温度随机采样方案**，目前没有实现 top\-k、top\-p 这类进一步筛选候选词的方法。具体过程是：模型完成一轮前向计算后，最后的输出层会为词表里的每个 token 计算一个分数；预填充阶段只取每个请求最后一个位置的结果，生成阶段则取当前 token 对应的结果。多卡运行时，每张卡先计算自己负责的那部分词表分数，再把它们汇总到主卡，组成完整词表的分数。接下来，采样器先用分数除以温度，再通过归一化得到每个 token 的概率：温度越低，概率越集中，回答越稳定；温度越高，候选 token 的概率越接近，输出会更随机。得到概率后，项目不是简单选择概率最大的 token，而是给每个候选项加入随机因素，再按照概率大小完成一次抽样，效果等价于根据整个词表的概率分布随机选出一个 token。

选中的 token 会追加到当前请求的序列中，作为下一轮生成的输入，然后继续逐个生成，直到采样到结束标记，或者达到用户设置的最大生成长度。项目默认温度是 1，并且当前实现不允许把温度设为 0，所以严格来说它只支持随机采样，还没有提供完全确定的贪心生成；这是一个实现比较轻量、容易批量并行的基础方案，后续可以继续加入 top\-k、top\-p 和重复惩罚等策略。

### 7. 简要说一下transformer的结构和现在常见大模型的decoder\-only结构有什么不同，为什么大模型使用的是decoder\-only，他们分别处理什么任务：

原始 Transformer 是一个 **Encoder \+ Decoder** 的结构。Encoder 主要负责“理解输入”，它可以同时看到整个输入序列，把输入编码成一组语义表示；Decoder 主要负责“根据已经生成的内容继续往后生成”，而且在原始 Transformer 里，Decoder 还会通过交叉注意力去读取 Encoder 的结果。所以这种结构最典型的任务就是机器翻译，比如 Encoder 先把英文整句话理解完，Decoder 再根据这个理解逐个生成中文。现在很多大语言模型，比如 Qwen、Llama，采用的是 **Decoder\-only**，也就是把 Encoder 和交叉注意力去掉，只保留 Decoder，然后统一做一件事情：**根据前面的 Token 预测下一个 Token**。比如输入“今天天气”，模型就根据前面的内容预测后面最可能出现什么，然后一个 Token 一个 Token 往后生成。

之所以大模型普遍喜欢 Decoder\-only，我觉得主要有三个原因：第一，结构更简单，训练和扩展到几十亿、几百亿参数比较方便；第二，训练目标非常统一，只需要大量文本做“预测下一个 Token”，不需要专门给每种任务设计训练形式；第三，它虽然本质上是生成模型，但通过把问题、上下文、指令都放到前面的 Token 里，也可以完成问答、分类、总结、代码这些原本偏“理解”的任务。所以简单概括就是：**原始 Transformer 是 Encoder 负责理解、Decoder 负责生成；Decoder\-only 则把理解和生成统一成一个自回归预测过程，这也是现在通用大模型最常见的结构。**
