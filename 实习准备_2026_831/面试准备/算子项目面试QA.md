# CUDA FP32 GEMM 项目面试问答

> 本文按当前仓库源码整理，回答口径面向真实技术面试。仓库目前只保留了最终的 Warp Tile 实现，没有保留 Naive、Shared Memory Tile 等中间版本，所以“优化路线”是根据最终代码结构还原的，而不是声称 Git 中还能逐版运行。
>
> 当前稳定性汇总记录的 5 次平均性能比为 `0.745648`，标准差为 `0.021764`。这个数字表示测试集合上的平均值，不代表每个形状都能达到 cuBLAS 的 75%。另外，现有常量数据测试不足以完整证明正确性，第 16 题会专门说明这个问题。

## 1. 请你整体介绍一下这个 CUDA GEMM 项目，你主要做了哪些优化？

这个项目主要是我从零实现并优化了一个 CUDA FP32 的 GEMM，也就是矩阵乘法算子。最开始我先写了一个最基础的版本，一个线程负责计算 C 矩阵中的一个元素，然后用 cuBLAS （NVIDIA 官方提供的一套高性能矩阵计算库）作为性能和正确性的对照。我主要做了三方面优化。第一是**计算层次和数据复用**，我把计算按照线程块、Warp 和单线程三级进行分块，让一个线程不再只算一个结果，而是在寄存器里计算一小块结果，同时把 A、B 的数据先搬到共享内存中重复使用，通过寄存器分块、外积累加和循环展开（我先通过 Shared Memory 分块减少对显存的重复访问，然后让每个线程在寄存器里同时维护一小块结果，通过外积的方式让一次取进来的 A、B 数据参与多个结果的计算（一次取一小组 A 和 B 到寄存器里，然后让它们交叉组合，一次更新很多个 C），提高数据复用；另外再配合循环展开减少循环开销，让 GPU 更连续地做计算。）来减少对显存的反复访问。第二是**访存和流水优化**，我使用 `cp.async`（异步数据搬运机制） 把数据异步搬到共享内存，并做了双缓冲，也就是当前这一块数据在计算的时候，提前加载下一块数据，让访存和计算尽量重叠；另外还使用了 16 字节搬运和 `float4` 写回来提高连续访存效率。第三是**不同矩阵尺寸的适配**，因为一套分块参数不可能适合所有矩阵，所以我设计了 Fast 和 Edge 两条执行路径，并准备了三组不同的 Tile 配置，根据矩阵尺寸选择不同 Kernel，边界不整齐的情况走单独的处理逻辑。最后我搭了一套和 cuBLAS 对比的测试框架，用 CUDA Event （CUDA 官方提供的 GPU 计时器）计时并统计 GFLOPS（GPU 每秒能够完成多少十亿次浮点运算）。**所以这个项目对我来说重点不只是实现 GEMM，而是完整走了一遍 GPU 算子从线程映射、数据复用、访存优化、计算流水到不同 Shape 调度和性能评测的优化过程。**

## 2. 最朴素的 CUDA GEMM 是怎么实现的，它的主要性能瓶颈是什么？

最朴素的 CUDA GEMM 实现其实很直接：假设要计算 (C=A\times B)，我会让一个线程负责 C 矩阵中的一个元素，比如线程先根据自己的 block 和 thread 索引确定它要计算的行和列，然后沿着 K 维做一个循环，每次从 A 里取这一行的一个元素，再从 B 里取这一列对应的一个元素，相乘以后一直累加，最后把结果写到 C 里面。这个方法的问题主要不在计算本身，而在**访存效率太低**。因为每个线程都是直接从显存里反复读取 A 和 B，同一份数据其实会被很多线程重复读取，但没有被共享起来，所以会产生大量显存访问；而显存访问相比 GPU 做乘加运算要慢很多，最后 GPU 很多时间是在等数据，而不是在真正计算。另外，一个线程只计算一个结果，寄存器和线程之间的数据复用也比较少，所以整体计算强度比较低。后续优化的核心就是解决这个问题：先把 A、B 按块搬到共享内存，让一个线程块里的线程共同复用，再让每个线程在寄存器里一次计算多个结果，把数据尽量多用几次，从而减少显存访问的开销。

## 3. 你的 GEMM 从 Naive 版本到最终版本，完整优化路线是什么？

我的优化路线是从**“减少显存访问、提高数据复用、隐藏访存等待、最后适配不同矩阵尺寸”**这条主线一步一步做的。最开始的 Naive 版本就是一个线程计算 C 矩阵的一个元素，沿着 K 维循环，每次直接从显存读取 A 和 B，这个版本最大的问题是同一份数据会被很多线程重复读取，GPU 很多时间都在等数据。第一步我做了 \**Shared Memory 分块\**，把 A、B 的一小块先从显存搬到共享内存，让一个线程块里的线程共同复用这些数据；第二步继续做 \**CTA、Warp、Thread 三级分块和寄存器分块\**，让一个线程不再只算一个结果，而是在寄存器里同时维护一小块 C，通过外积累加让一次取进来的 A、B 数据参与多个结果计算，再配合循环展开减少循环开销。第三步是优化访存，我把连续数据按照 \**16 字节进行搬运，并用 `float4` 写回结果\**，提高连续访存效率。第四步是做流水优化，我用了 `cp.async` 和共享内存双缓冲，简单来说就是**当前 K-Tile 在计算的时候，提前把下一个 K-Tile （每次沿 K 方向处理 8 个位置）搬进来，尽量让计算和访存同时进行**，减少等待数据的时间。最后，因为一套分块参数不可能适合所有矩阵，我又做了 **Fast 和 Edge 两条路径**，完整、对齐的块走快路径，边界或者不规则尺寸单独处理，同时准备了三组不同的 Tile 配置，根据矩阵大小和 Shape 选择不同 Kernel。整个过程中我一直用 cuBLAS 做基准，通过 CUDA Event 计时和 GFLOPS 对比性能，所以整体上就是从 **Naive → 共享内存复用 → Warp/Thread 分块和寄存器复用 → 向量化访存 → 异步双缓冲流水 → 多 Shape 调度** 这样逐步优化下来的。

## 4. 什么是 CTA Tile、Warp Tile、Thread Tile？为什么要做三级分层映射？

CTA Tile、Warp Tile、Thread Tile，本质上就是把一个大的矩阵乘法任务按照 GPU 的执行层级逐层切小。首先 **CTA Tile** 是一个线程块负责的 C 矩阵区域，比如一个线程块负责计算一块 (128\times256) 的 C；然后这个区域还比较大，所以再切成多个 **Warp Tile**，每个 Warp，也就是 32 个线程，负责其中更小的一块，比如 (64\times64)；最后一个 Warp 内部再继续划分，每个线程负责自己的 **Thread Tile**，比如一个线程最终在寄存器里计算一个 (8\times8) 的小块结果。之所以要做三级分层，主要是为了和 GPU 本身的硬件执行结构对应起来，同时逐层提高数据复用。CTA 这一层可以把 A、B 的数据搬到共享内存，让整个线程块重复使用；Warp 这一层把计算任务合理分给不同 Warp；Thread 这一层再利用寄存器，让一个线程读取一次 A、B 数据后同时更新多个 C 元素。所以它不是单纯为了把矩阵切得更细，而是为了让 **线程块级复用共享内存、Warp 级合理分工、线程级复用寄存器**，减少重复访存，让 GPU 的计算资源能够更充分地利用起来。

## 5. 以你项目中的一组 Tile 配置为例，一个 CTA、Warp、Thread 分别负责 C 矩阵多大的区域？

以我项目里默认的一组 Tile 配置为例，参数是 **BM=128、BN=256，WM=64、WN=64，TM=8、TN=4**。首先一个 CTA，也就是一个线程块，负责计算 C 矩阵中 **128×256** 的区域；这个 CTA 一共有 256 个线程，也就是 8 个 Warp，所以我把这块区域进一步划成 8 个 **64×64 的 Warp Tile**，正好一个 Warp 负责一块。再往下，一个 Warp 有 32 个线程，每个线程会在寄存器里保存自己负责的结果。因为我这里 `TM=8、TN=4`，同时 N 方向会重复计算 4 次，所以一个线程实际上会计算 **4 个 8×4 的小块，也就是总共 128 个 C 元素**，等效可以理解成每个线程负责 8×16 个结果，只不过这 16 列并不是完全连续放在一起的。这样从上到下就是 **一个 CTA 算 128×256 → 一个 Warp 算 64×64 → 一个线程算 128 个元素**。这样设计的目的就是让 CTA 层充分复用共享内存里的 A、B 数据，再让线程层通过寄存器一次维护多个结果，把同一份数据尽量重复利用起来。

## 6. Shared Memory Tiling 为什么能够提升 GEMM 性能？A、B 的数据是怎么复用的？

Shared Memory Tiling 能提升 GEMM 性能，核心原因就是**减少对显存的重复访问，让同一份 A、B 数据被更多线程重复利用**。因为最朴素的 GEMM 里，每个线程算一个 C 元素，沿 K 维循环时会一直从显存读取 A 和 B，但很多线程其实会反复读取相同的数据，比如同一行的 A 会被同一块里的多个线程使用，同一列的 B 也一样。我的做法是先把 A、B 按 Tile 分块，一次把当前要计算的一小块数据从显存搬到 Shared Memory。Shared Memory 在片上，访问速度比显存快很多，而且同一个线程块里的线程都能访问，所以数据搬进来一次以后可以被反复使用。具体来说，A 的一份数据会被同一个线程块里负责不同列的线程重复使用，B 的一份数据会被负责不同行的线程重复使用；然后每个线程再把自己需要的数据从 Shared Memory 取到寄存器里继续复用。这样就把原来大量的显存重复读取，变成了**显存只搬一次，在 Shared Memory 和寄存器里多次使用**。所以 Shared Memory Tiling 的本质不是减少计算量，而是提高数据复用率，让 GPU 把更多时间花在乘加计算上，而不是一直等待显存数据。

## 7. 什么是 Register Blocking？为什么每个线程要一次计算多个 C 元素？

Register Blocking，也就是**寄存器分块**，可以理解成让一个线程不再只负责 C 矩阵里的一个元素，而是负责一小块结果，并且把这些中间结果一直放在线程自己的寄存器里。比如最朴素的 GEMM 里，一个线程只算一个 `C[i][j]`，那它每次从 A、B 取到数据以后只做一次乘加，数据利用率比较低；而做了寄存器分块之后，一个线程可能同时维护几十个甚至上百个 C 元素。这样线程从 Shared Memory 里取一次 A 的几个值、B 的几个值，就可以通过外积的方式组合出很多次乘加，也就是说**同一份 A、B 数据能在寄存器里被重复利用很多次**。另外，C 的中间累加结果也不需要反复写到 Shared Memory 或显存，而是一直留在寄存器里，最后计算完成后再一次性写回。所以它的主要作用就是进一步提高数据复用、减少访存，让 GPU 做更多有效计算。当然也不能让一个线程算得无限多，因为用的寄存器太多会降低同时能运行的线程数量，所以 Thread Tile 的大小本身也是一个需要权衡的参数。

## 8. 你项目中的“外积累加”具体是什么意思，为什么采用这种计算方式？

我项目里的“外积累加”，可以理解成每个线程在处理某一个 K 位置时，不是只取一个 A 和一个 B 去更新一个 C，而是先从共享内存里取一小组 A 的值和一小组 B 的值到寄存器里，然后让这两组数据两两相乘，一次更新线程负责的一整小块 C。比如我取到 8 个 A 和 4 个 B，那么这一轮就可以产生 (8\times4=32) 次乘加，把结果累加到寄存器里的 32 个 C 元素上；接着继续处理下一个 K 位置，一直累加到整个 K-Tile 算完。之所以这样做，主要是为了提高数据复用，因为一个 A 的值读进寄存器以后可以和多个 B 相乘，一个 B 也可以和多个 A 相乘，相比一个线程只算一个 C 元素，同样一次从共享内存取进来的数据能做更多计算。另外这些 C 的中间结果一直保存在寄存器里，最后才统一写回显存，所以也减少了中间访存。简单来说，**外积累加就是“每次拿一小列 A 和一小行 B，交叉相乘，一次更新一整块 C”，核心目的是让数据多算几次、少搬几次。**

## 9. Tile Size，比如 BM、BN、BK、WM、WN、TM、TN，是怎么选择的？选大或选小分别有什么影响？

这几个 Tile 参数本质上是在做一个平衡：**块越大，数据复用通常越好，但占用的共享内存和寄存器也越多；块越小，资源压力更低、调度更灵活，但数据复用又会下降。**具体来说，BM、BN、BK 决定一个线程块一次处理多大的 A、B 和 C 区域，其中 BM、BN 变大以后，一次搬进共享内存的数据可以被更多计算重复利用，但同时共享内存占用会上升，一个 SM 能同时驻留的线程块可能变少；BK 变大可以一次沿 K 方向多算一些，减少分块和同步次数，但也会增加共享内存占用，而且流水不一定更好。WM、WN 是一个 Warp 负责的区域，它要和 CTA 的大小以及 Warp 数量匹配，太大可能让单个 Warp 承担太多计算，太小又会让数据复用不充分。TM、TN 是每个线程负责的小块，增大以后，一个线程从共享内存取一次 A、B 就能更新更多 C 元素，寄存器级复用会更高，但是线程需要保存更多中间结果，寄存器压力也会变大，严重时会降低 Occupancy，甚至发生寄存器溢出。所以这些参数不是越大越好，我项目里主要是结合 GPU 的线程数、共享内存和寄存器限制，再通过实际 Benchmark 去调，最后针对不同矩阵尺寸保留几组效果比较好的配置。简单来说就是：**大 Tile 换数据复用，小 Tile 换资源灵活性，最后要在复用率、并行度和硬件资源占用之间找平衡。**

## 10. cp.async 是什么？相比普通的 Global Memory → Register → Shared Memory 搬运有什么优势？

`cp.async` 是较新架构提供的异步拷贝指令，可以把数据从全局显存直接送到 Shared Memory。传统写法一般是线程先把数据读进寄存器，再执行一次 Shared Memory 写入；这既需要显式的中间寄存器，也把加载和写入拆成了更多指令。

项目里的 `cp_async16()` 每条搬 16B，也就是 4 个 float，并带有 `L2::128B` 提示。线程发出一组 A、B 拷贝后调用 `cp.async.commit_group`，后面通过 `cp.async.wait_group` 等待数据可用。

它的优势不只是“少一次寄存器中转”，更重要的是异步性。加载下一块数据时，当前块还可以继续计算，从而用计算时间遮住一部分显存延迟。这样做还可能减少用于搬运的寄存器和指令压力。项目编译目标是 `sm_89`，硬件支持这条路径。

不过 `cp.async` 本身不会自动带来重叠，必须配合多缓冲、正确的 commit/wait 和线程块同步；如果刚发出就立刻等待，收益会很有限。

## 11. 你项目中的 Shared Memory 双缓冲是怎么工作的？请完整讲一下一个 K-Tile 的加载和计算流水。

`cp.async` 可以理解成 CUDA 里一种**异步的数据搬运方式**，主要用来把数据从全局显存搬到共享内存。普通做法一般是先从 Global Memory 把数据读到线程的寄存器，再从寄存器写到 Shared Memory，中间线程要参与这两步，而且通常要等数据准备好之后才能继续后面的计算。`cp.async` 的优势是可以让数据**直接从 Global Memory 异步搬到 Shared Memory**，减少中间经过寄存器的搬运开销，而且发出搬运指令以后，线程不需要马上等它完成，可以继续做别的计算。我的项目里就利用这一点配合双缓冲：当前这一块 K-Tile 正在计算的时候，同时用 `cp.async` 把下一块 K-Tile 提前搬到另一块共享内存里，等当前计算结束以后，下一块数据基本已经准备好了，就可以直接继续计算。这样主要解决的是**显存访问延迟比较高的问题**，通过让“算当前数据”和“搬下一批数据”尽量重叠，减少 GPU 因为等数据而空闲的时间。简单来说，普通方式更像“先搬完再算”，而 `cp.async` 配合流水以后更接近“**边算边提前搬下一批**”。

## 12. 为什么使用 16B 搬运和 float4 写回？它们具体优化了什么？

我这里使用 16B 搬运和 `float4` 写回，主要优化的是**显存访问效率**，不是提高数据复用率。因为一个 `float` 是 4 字节，`float4` 正好是 16 字节，所以在地址满足对齐条件的时候，可以一次连续读写 4 个 `float`，相比一个一个标量去读写，能减少访存指令数量，也更容易形成连续、合并的显存访问。具体到我的项目里，A、B 从显存搬到共享内存时，我尽量按照 16B 一次搬一组数据；最后 C 计算完成以后，也用 `float4` 一次写回 4 个结果。这样做不会减少 GEMM 本身需要的数据量，但是可以让每次访存更“宽”，降低很多零碎小访问带来的开销，更充分利用显存带宽。当然它有一个前提，就是地址和矩阵边界要满足对齐要求，所以不规则边界不能直接这么处理，需要走单独的 Edge 路径。简单来说，**Shared Memory 和寄存器分块解决的是“同一份数据多用几次”，而 16B 和 `float4` 解决的是“每次搬数据尽量搬得更高效”。**

## 13. 什么是 Global Memory Coalescing？你项目中 A、B、C 的访存是怎样实现合并访问的？

Global Memory Coalescing，也就是**合并访存**，可以简单理解成：一个 Warp 里的 32 个线程访问显存时，尽量让相邻线程访问相邻的地址，这样 GPU 就可以把很多零散的访问合并成更少的显存事务，一次把一大片连续数据取回来，而不是每个线程单独访问显存。在我的项目里，B 的数据在内存中 N 方向是连续的，所以加载 B 时，我让线程按照 N 方向读取，每个线程一次搬 16 字节，也就是连续 4 个 `float`，相邻线程继续读取后面的连续数据，这样比较容易形成合并访问；C 在最后写回时也是类似的，因为 C 的 N 方向连续，我用 `float4` 一次写回连续 4 个结果，让相邻线程尽量写相邻区域。A 稍微特殊一点，因为 A 是按行存储的，它连续的方向其实是 K，所以正确的优化思路也是让线程优先沿 K 方向读取连续数据，再根据计算需要放到共享内存对应的位置。整体来说，**合并访存解决的就是“同样要搬这些数据，尽量连续地一起搬，而不是零零散散地搬”**，从而减少显存访问事务，提高有效带宽。

## 14. 为什么要设计 Fast Path 和 Edge Path？它们分别处理什么情况？

我设计 Fast Path 和 Edge Path，主要是因为**规则矩阵和边界矩阵的最优处理方式不一样**。Fast Path 专门处理尺寸比较规整、能够完整落在 Tile 里的区域，比如 M、N、K 满足分块和向量化访问的对齐要求，这种情况下就可以尽量去掉边界判断，直接使用 `cp.async`、16B 搬运和 `float4` 写回，把访存和计算流水做得更紧凑，追求最高性能。Edge Path 则负责处理矩阵最后剩下的不完整区域，比如 M、N 不是 Tile 大小的整数倍，或者 K 最后一段不足一个 BK，这时候如果还按照完整 Tile 去读写就可能越界，所以需要增加边界判断，必要时对无效位置补零，再完成最后的计算和写回。之所以不把所有情况都放到一个 Kernel 里处理，是因为如果每次计算都做边界判断，会给最常见的规则区域也带来额外分支和访存开销。所以我的思路就是：**大部分规则区域走 Fast Path，把性能做到最好；只有真正碰到边界时才走 Edge Path，用少量额外开销换正确性和通用性。**

## 15. 为什么需要三组不同的 Tile 配置以及 Shape-aware Dispatch？不能所有矩阵都使用同一个 Kernel 吗？

需要三组 Tile 配置和 Shape-aware Dispatch，主要是因为**不同尺寸、不同长宽比例的矩阵，对 GPU 资源的最优使用方式不一样，一套 Kernel 很难在所有 Shape 上都跑得好**。比如大矩阵通常更适合用比较大的 CTA Tile，这样 A、B 搬进共享内存以后可以被更多计算重复利用，计算效率更高；但如果矩阵本身比较小，还强行用很大的 Tile，就会出现很多线程或者计算区域是空的，反而造成资源浪费。另外，不规则或者长宽差异比较大的矩阵，如果仍然使用同一套 BM、BN、Warp Tile 和 Thread Tile，也可能导致线程分配不均、边界处理变多，性能明显下降。所以我项目里准备了三组不同的 Tile 参数，然后在启动 Kernel 之前根据矩阵的 M、N、K 和边界情况选择更合适的一组，这就是 Shape-aware Dispatch。它本质上和 cuBLAS 这类库的思路是一样的：**不是寻找一个“万能 Kernel”，而是准备多个实现，根据输入 Shape 选择更合适的那个。**当然我项目目前只是比较简单的规则选择，如果继续优化，我会考虑对更多真实矩阵 Shape 做 Benchmark，甚至用自动调参的方式找到更合适的 Tile 配置。

## 16. 你是怎么验证 GEMM 正确性的？

我验证 GEMM 正确性的思路主要是**把 cuBLAS 的计算结果作为参考答案，然后和我自己的 Kernel 输出逐元素比较**。具体来说，同一组 A、B、C 输入分别跑我的 GEMM 和 cuBLAS，再统计两边结果的绝对误差和相对误差，只要误差控制在 FP32 合理范围内，就认为结果正确。另外我会专门覆盖几类情况，包括正常对齐的矩阵、M/N/K 不能被 Tile 整除的边界矩阵，以及 `alpha`、`beta` 不同取值，确保 Fast Path 和 Edge Path 都没有问题。测试数据最好使用随机数，而不能只用全 1、全 2，因为这种规则数据即使索引写错，也可能碰巧得到正确结果。**所以我的验证原则就是：用 cuBLAS 做基准，用随机输入覆盖不同 Shape 和边界情况，再通过数值误差判断正确性，最后性能测试只在正确性通过之后进行。**

## 17. 你是怎么做性能 Benchmark 的？为什么使用 CUDA Event、Warmup、重复测试和 cuBLAS 对照？

我做性能 Benchmark 的流程比较固定。首先我会准备一组不同尺寸的矩阵，用同样的输入分别测试我自己的 GEMM 和 cuBLAS，然后用 **CUDA Event** 来计 GPU 上真正的执行时间，因为 Kernel 是异步执行的，普通 CPU 计时容易把启动开销和等待时间混在一起。正式计时前我会先做几轮 **Warmup**，主要是让 CUDA 上下文、缓存和 GPU 运行状态先稳定下来，避免第一次执行特别慢把结果带偏。之后每个 Shape 会重复跑多次，再取平均值，同时看波动情况，这样可以减小偶然调度、频率变化带来的影响。拿到执行时间以后，我再根据 GEMM 的计算量大约是 (2MNK) 次浮点运算，换算成 GFLOPS。最后我会和 **cuBLAS** 做对照，因为它是 NVIDIA 官方已经高度优化的实现，单看我自己的 GFLOPS 没什么参照意义，和 cuBLAS 比以后就能比较直观地看出我的 Kernel 达到了成熟实现的大概多少性能。整体来说就是 **先 Warmup，CUDA Event 准确计时，多次重复取稳定结果，再用 cuBLAS 做基准比较**。

## 18. 你的 Kernel 平均只有 cuBLAS 大约 75% 的性能，你认为主要差距可能来自哪里？

我觉得主要有几方面原因。第一，**cuBLAS 本身是 NVIDIA 长期针对不同 GPU 架构优化出来的成熟库**，它不是只有一个 GEMM Kernel，而是针对不同矩阵尺寸准备了很多实现，并且会自动选择比较合适的方案；而我的项目目前只有几组 Tile 配置，调度策略也比较简单，所以不可能对所有 Shape 都做到最优。第二，我虽然已经做了共享内存分块、寄存器分块、`cp.async` 双缓冲和向量化访存，但是在**寄存器使用量、共享内存布局、Warp 调度以及计算和访存重叠程度**这些细节上，和 cuBLAS 还有差距，比如 Tile 参数不一定是最优的，寄存器用多了还可能影响同时运行的线程数量。第三，我的实现主要还是 FP32 的普通 CUDA Core 计算，没有继续做到更底层、更细粒度的指令调度和针对具体架构的深度优化。另外一些小矩阵或者不规则尺寸会走 Edge Path，边界判断带来的额外开销也会拉低平均值。所以我觉得这个 75% 的结果更多说明我已经把 GEMM 的主要优化路径跑通了，但是距离成熟工业库还有不少细节优化空间。如果继续做，我会先用 Nsight Compute 定位到底是访存、寄存器压力还是计算流水限制了性能，再有针对性地优化，而不是单纯继续调 Tile 参数。

## 19. 如果用 Nsight Compute 分析你的 Kernel，你最关注哪些指标？怎么判断是计算瓶颈、访存瓶颈还是寄存器/Occupancy 问题？

如果我用 Nsight Compute 分析这个 Kernel，我主要会看三类指标。第一类是**计算单元有没有吃满**，比如 SM 的计算吞吐、浮点计算单元利用率，如果这些已经很高，同时显存带宽还没到上限，那说明更可能是计算瓶颈；第二类是**访存情况**，我会看 DRAM 带宽利用率、L1/L2 命中情况以及访存效率，如果显存带宽已经接近上限，但是计算单元利用率不高，而且很多 Warp 都在等内存数据，那基本可以判断是访存瓶颈。第三类是**线程并发和资源占用**，我会重点看 Occupancy、每个线程使用多少寄存器、每个 Block 使用多少 Shared Memory，以及一个 SM 实际能同时驻留多少个 Warp。如果寄存器用得太多，比如我的 Thread Tile 设得太大，就可能导致一个 SM 同时跑的 Warp 变少，这时候 Occupancy 会下降；如果同时还能看到很多流水线因为没有可执行 Warp 而停顿，就说明资源压力已经影响到隐藏延迟的能力。另外我还会看 Warp Stall 的原因，比如是在等显存、等 Shared Memory、等同步还是等计算依赖。我的判断思路一般不是看单个指标，而是把它们结合起来：**计算单元满而带宽没满，更像计算瓶颈；带宽满而计算单元不满，更像访存瓶颈；两边都没吃满，同时 Occupancy 很低、寄存器占用很高，就优先怀疑资源占用或者并行度不够。**然后再针对真正的瓶颈去改 Tile、寄存器分块或者访存流水，而不是盲目继续调参数。

## 20. 如果让你继续优化这个项目，你下一步会怎么做？

如果让我继续优化，我会分三个优先级来做。第一步我不会马上继续堆技巧，而是先用 Nsight Compute 把现在的瓶颈定位清楚，比如到底是显存带宽没利用好、寄存器用得太多，还是计算流水没有跑满，然后针对性调整 Tile 大小、共享内存布局和双缓冲流水。第二步我会重点往 **Tensor Core** 方向做，因为我现在这个版本主要还是 FP32 的普通 CUDA Core 计算，如果扩展到 FP16 或 BF16，再使用 MMA 这类矩阵乘指令，可以一次完成一小块矩阵乘加，更接近现在工业 GEMM 的优化方式，这应该是性能提升空间最大的一步。第三步是把项目做得更工程化，我现在只有几组手工选择的 Tile 配置，后面可以增加更多 Kernel 配置，针对不同 M、N、K 自动测试并选择最优方案，同时补充大模型里更常见的长方形矩阵，而不只是方阵测试。另外我也会继续优化边界路径，比如减少不规则 Shape 下的判断和无效计算。**所以我的思路不是单纯继续把某一个 Kernel 调快，而是先通过性能分析定位瓶颈，再引入 Tensor Core 提高计算上限，最后通过更多 Shape 和自动调度把它做成一个更完整的 GEMM 实现。**

## 21. 平均吞吐达到cuBLAS的76.32%，跨次标准差2.06个百分点，你的这个性能测试怎么定义的

我这里的 **76.32%** 不是说某一个矩阵尺寸能达到 cuBLAS 的 76.32%，而是一个**跨多组 Shape 的平均相对性能**。具体做法是：我准备一组不同大小、包含对齐和非对齐情况的矩阵，对每一个 Shape 都分别测试自己的 GEMM 和 cuBLAS。正式计时前先 Warmup，然后用 CUDA Event 测 GPU 上实际执行时间，换算成 GFLOPS。对于每一个 Shape，我会计算一次 **自己的 GFLOPS 除以 cuBLAS 的 GFLOPS**，比如我的算力是 15 TFLOPS、cuBLAS 是 20 TFLOPS，那么这一组就是 75%。然后把所有测试 Shape 的这个比例取平均，得到一次完整 Benchmark 的平均相对吞吐；我又把整套测试独立重复多次，最终这些测试的平均值是 **76.32%**。这里的**跨次标准差 2.06 个百分点**，表示多次完整 Benchmark 得到的平均比例之间波动大约是 2.06 个百分点，比如结果基本在 76% 附近小幅变化，它主要用来说明测试结果的稳定性。所以这两个数字分别回答两个问题：**76.32% 表示相对于 cuBLAS 整体能跑到什么水平，2.06 个百分点表示这个结果重复测试时稳不稳定。**
